# Рабочие материалы ИИ-агентов

Локальные материалы задач проекта **Realize — AI Platform**. Порядок размещения,
использования и очистки задаёт
[правило операционного слоя](../.ai/rules/scope-control/RULE-TASK-WORKSPACE-ARTIFACTS.md).

Основная задача создаётся в Task Manager. `task:workspace create` сначала
обращается к серверу; при успехе локальные TASK и manifest не создаются.
Управляемое досье ниже — резерв при отсутствии настройки платформы или
доказанной недоступности соединения. Ошибка доступа или неизвестный исход
серверного запроса не разрешают создание второй задачи.

## Структура задачи

```text
.ai-workspace/
├── README.md
├── .gitignore
├── tasks/
│   └── <localKey>/
│       ├── TASK.md
│       ├── artifact-manifest.json
│       ├── references/
│       ├── screenshots/
│       ├── snapshots/
│       ├── logs/
│       │   └── results/
│       ├── drafts/
│       └── tmp/
└── history/
    └── <localKey>/
        ├── TASK.md
        ├── artifact-manifest.json
        └── …
```

| Элемент                  | Содержание                                                  |
| ------------------------ | ----------------------------------------------------------- |
| `TASK.md`                | Frontmatter состояния/ревизии и краткое описание задачи     |
| `artifact-manifest.json` | Зарегистрированные артефакты, revisions, hashes и retention |
| `references/`            | Исходные изображения, образцы, HTML и другие референсы      |
| `screenshots/`           | Скриншоты проверок и сравнений                              |
| `snapshots/`             | Снимки DOM, дерева доступности и состояния интерфейса       |
| `logs/`                  | Вывод команд, тестов и диагностики                          |
| `logs/results/`          | Durable result manifests и evidence результата              |
| `drafts/`                | Черновики отчётов и промежуточные выводы                    |
| `tmp/`                   | Зарегистрированные temporary материалы отдельных producers  |
| `history/<localKey>/`    | Закрытое quiescent досье с сохранёнными результатами        |

Дерево показывает локальное резервное досье. Подкаталоги создаются по
необходимости; `TASK.md` нужен для продолжительных задач и возобновления работы.
Материалы открываются адресно по задаче.

## Короткая операция

Перед созданием досье выбери [рабочий контекст](../.ai/rules/scope-control/RULE-TASK-WORKSPACE-ARTIFACTS.md#выбор-рабочего-контекста).
Обычный самостоятельный add/commit/push использует только необходимые файлы
инструмента, без TASK, manifest и команд task-workspace. Каталог
`tasks/<taskId>/` может содержать операционный контекст и журнал, не становясь
управляемым досье. Продолжение задачи использует её существующее досье;
завершённые материалы не дописываются ради доставки.

Git-контекст и его ограниченная очистка принадлежат
[Git-обработчику](../.ai/tools/git-delivery/README.md#короткая-операция-и-рабочий-контекст).
Его журнал сохраняется независимо от временного контекста. Наличие файлов
операции не разрешает общий cleanup или архивирование каталога.

Общий verification runner хранит IDE receipts в
`tasks/<taskId>/logs/git-verification`, а platform execution/preview receipts —
в `runtime/verification` исходного host repository. Второй каталог назначает
сервер; он находится вне изменяемых candidate worktrees и не создаёт локальную
задачу. Формат и границы — [verification runtime](../packages/verification-runtime/README.md).

## Вход в lifecycle

Создание, явное принятие legacy TASK, состояния, результаты, регистрация/settle,
план очистки, очистка, archive/reopen и recover проходят через
`npm run task:workspace -- <command>`. Начало работы —
[шаблон TASK](../.ai/templates/task-workspace/TEMPLATE-TASK.md);
команды и JSON contracts — [CLI owner](../.ai/tools/task-workspace/README.md).
Перед записью читай `inspect`; мутации versioned досье требуют
`--expected-revision`. Разовые JSON-входы передавай через `--input -`, имеющиеся
файлы — через `--input <JSON-file>`; отдельный каталог входов не требуется.
`--compact` сокращает ответ, сохраняя ссылки результата и восстановления.

Незавершённая мутация возвращает ссылку восстановления. При pending продолжи
`recover --task <localKey> --operation <operationId>`; новая revision и другой
план не заменяют исходную операцию. Журналы находятся у инструмента, не в досье;
[протокол восстановления](../.ai/tools/task-workspace/README.md#план-очистки-и-восстановление)
определяет диагностику, старые журналы и неизвестный исход.
Квитанция подключённой фикстуры регистрируется до ресурсов. При pending владелец
может записать диагностику в своё открытое дерево после проверки его writers,
сохраняя retained/pinned/unsettled; metadata ожидают recovery. Потерянный handle
не воссоздаётся из JSON: после восстановления завершаются проверенные artifact IDs.

У несвязанного резерва `TASK.md` остаётся источником локального состояния.
`sync --task <localKey>` явно передаёт существующее managed досье в Task Manager;
уже выбранный резерв повторяет доставку перед следующей локальной мутацией,
когда подключение настроено и контекст выбран. URL и JWT задают подключение,
`--project` и `--list` — выбор для конкретной задачи; прежние env Project/List
игнорируются. Новый `create` с настроенным подключением требует проект,
единственный список может
быть выбран автоматически. Резерв без выбора остаётся редактируемым локально;
передача требует явного `sync` с недостающими selectors.
Неизвестный исход сохраняет исходный UUID для
точного повтора, без второго TASK. Настройка и границы —
[Task Manager и локальный резерв](../.ai/tools/task-workspace/README.md#task-manager-и-локальный-резерв).
Активное исполнение и producers откладывают автоматическую передачу, чтобы
локальная работа могла штатно завершиться; явный `sync` до этого отклоняется.

После подтверждённой связи сервер владеет предметной задачей. `inspect`
показывает сохранённые серверные идентификаторы и прежний локальный снимок
без обращения к сети; локальные
мутации блокируются. TASK и артефакты сохраняются, автоматического переноса
файлов, синхронизации lifecycle и очистки нет. Старые TASK не преобразуются
автоматически: `adopt` сохраняет body и требует явно заданного состояния,
а передача в Task Manager требует отдельного `sync`.
Локальные `done/closed` не означают серверную приёмку; сервер пока использует
`backlog/in_progress/review`. Archive не означает приёмку, закрытие не
перемещает папку, reopen не возобновляет старый runtime.

Cleanup ограничен зарегистрированными disposable материалами в `tmp/` текущей
задачи и применяет точный reviewed plan. Результаты, удержания, работающие
producers и execution блокируют purge. Правила и исключения принадлежат
[операционному слою](../.ai/rules/scope-control/RULE-TASK-WORKSPACE-ARTIFACTS.md).

В Git сохраняются только этот README и `.gitignore`. Постоянные планы, решения
и значимые результаты принадлежат [документации проекта](../documentation/INDEX.md).
