## Архитектура: проект для согласования

Следующие разделы содержат предложения по разделению ответственности,
вложенности и переносимости модулей. Они дополняют обсуждение и пока не
заменяют действующие архитектурные инструкции. Имена в примерах следуют
правилу выше; набор файлов и каталогов не является обязательным каркасом.

### Основные положения

- Один файл имеет одну ответственность и одну основную единицу реализации.
  Компонент или функциональный модуль может состоять из группы файлов.
- Один компонент представления, класс, самостоятельная операция или хук
  определяется в отдельном файле. Локальные обработчики и закрытые вспомогательные
  функции одной операции могут оставаться рядом. Отдельный контракт, причина
  изменения или переиспользование требуют выделения самостоятельного владельца.
- Собственные именованные типы и интерфейсы размещаются в `.types.ts`.
  Связанные типы одного контракта могут находиться вместе; общий склад типов
  всего проекта не создаётся. Подходящие типы Payload переиспользуются.
- Количество строк не определяет роль файла; сокращение кода не должно
  скрывать назначение.

### Компоненты, типы и хуки

Роль `.model` не используется для ручной копии документа Payload. Файл
`.types.ts` не содержит исполняемой логики: значения `as const` и runtime enum
относятся к `.constants.ts`, классы ошибок — к `.error.ts`.

При достаточности `.component.tsx` отдельный `.container.tsx` не создаётся.
При разделении поведения и представления основной компонент связывает hook
и view. В view остаются JSX, отображение props, условия отображения и вызов
переданных обработчиков.

Hook-файл определяет один хук и не содержит JSX. Обычная функция форматирования
не получает `.hook.ts`, если не является React- или Payload-хуком.

React-хуки объявляются на уровне модуля; фабрики динамических React-хуков
не используются. Если Payload-хуку нужна конфигурация, допустима фабрика
одного хука, например `createResolveSearchProfileField.hook.ts`. Она не
возвращает набор независимых хуков и не объединяется с React-хуками.

### Каталоги и вложенность

`primitives` содержит базовые элементы без бизнес-правил конкретной
функциональности; `components` — составные элементы интерфейса. `utils`
содержит чистые функции без запросов, секретов, состояния и побочных эффектов.
Сборники несвязанных `helpers.ts`, `utils.ts`, `common.ts` не создаются.

Сначала код группируется по функциональности, затем — по необходимым
обязанностям. Разделение `client`/`server` применяется на границе исполнения.
Маленький компонент хранит свои файлы рядом; каталоги `hooks`/`types` внутри
каждого компонента не создаются автоматически.

Пример компонента с разделённым поведением и представлением:

```text
connection-form/
├── ConnectionForm.component.tsx
├── ConnectionForm.view.tsx
├── ConnectionForm.types.ts
├── useConnectionForm.hook.ts
├── formatConnectionStatus.util.ts
├── ConnectionForm.module.css
└── ConnectionForm.index.ts
```

Пример более крупной функциональности внутри существующего пакета:

```text
git-connections/
├── client/
│   ├── components/
│   │   └── connection-form/
│   └── gitConnections.client.index.ts
└── server/
    ├── controllers/saveGitHubConnection.controller.ts
    ├── services/resolveGitHubConnection.service.ts
    ├── repositories/GitHubConnection.repository.ts
    ├── validators/validateGitHubConnection.validator.ts
    ├── mappers/mapGitHubConnection.mapper.ts
    ├── types/GitHubConnection.types.ts
    └── gitConnections.server.index.ts
```

Оба дерева — примеры размещения, а не готовые пути проекта или обязательный
каркас. Создаются только нужные файлы и каталоги. Каждый уровень вложенности
должен обозначать владельца или границу; повторение вроде
`modules/git-connections/module/components/components` недопустимо.

Поведение, нужное нескольким частям одной функциональности, принадлежит этой
функциональности. Между независимыми функциональностями оно выносится в
существующий общий модуль или пакет с явным контрактом. Новый `shared` не
создаётся только ради переноса файла.

### Приведение к правилам при рефакторинге

Рефакторинг включает приведение затронутого кода к действующим правилам
именования, структуры, комментариев и разделения ответственности. Обнаруженные
нарушения внутри рефакторимого компонента или модуля исправляются в рамках
этой же задачи. Давность кода и отсутствие отдельного запроса на каждое
нарушение не являются основанием оставить его без исправления.

Проверяется компонент или модуль целиком в согласованных границах, а не только
изменённые строки. В рефакторинг входят:

- Именование — по действующему правилу, указанному выше.
- Структура: размещение файлов у правильного владельца, понятная вложенность,
  устранение дублирования реализации и логики.
- Ответственность: разделение независимых операций, логики и представления;
  выделение хуков и собственных типов по правилам выше. Перенос смешанной
  логики целиком из контроллера в другой большой файл не устраняет нарушение.
- Комментарии — по действующему правилу, указанному выше.

Непосредственно зависимые файлы обновляются настолько, насколько этого требует
корректность рефакторинга. Обнаружение нарушения не запускает обход всего
репозитория. Долг в независимом модуле фиксируется отдельно. Явные ограничения
пользователя на файлы и действия сохраняются; если они мешают устранить
нарушение в рефакторимом модуле, в результате указываются конкретный остаток
и ограничение, без заявления о полном соответствии.

Рефакторинг считается завершённым, когда в его границах устранены обнаруженные
нарушения, согласованы зависимости и комментарии, а результат проверен по
фактическим изменениям. Внешнее поведение и публичные контракты сохраняются,
если их изменение не входит в задачу. Отдельный отчёт для каждого файла и
полный набор тестов только из-за переименования или правки комментариев
не требуются.

### Переносимость и внедрение

Пакет обращается к другим пакетам через их публичные exports. Внутренние
импорты используют поддерживаемые package/runtime paths; зависимость от
`@/` или `src/**` конкретного host-проекта не вводится в переносимый модуль.
Серверные настройки, credentials и зависимости передаются через явные
контракты. Именование не заменяет границы доступа и ответственности.

Для каждой новой основной единицы до реализации определяются владелец, роль,
имя файла, основной символ и допустимые зависимости. Во время review
проверяется соответствие имени фактическому содержимому. Это часть обычной
проверки изменения, без отдельного отчёта для каждого файла.

После согласования архитектурной части её требования закрепляются у владельцев в `.ai/rules/`, а
связанные checks, templates и skills синхронизируются с ними. Проверки и
шаблоны не должны ослаблять обязательные требования правил. Этот проект
документа затем заменяется навигацией на принятые правила, чтобы не сохранять
две конкурирующие нормативные версии. До этого он не отменяет существующие
правила и не подтверждает готовность автоматической проверки.

Архитектурное внедрение выполняется небольшими областями. Для переименований
применяется [действующее правило](../../.ai/rules/development/RULE-CODE-NAMING.md).

Первое применение предлагается выполнить на модуле Git-подключения после
согласования правил ответственности. Массовое переименование репозитория в
этот документ не входит.
