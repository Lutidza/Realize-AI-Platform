# Интеграция GPT — Codex

Codex настраивается в `/admin/integrations/codex`. Подключение `codex:primary`
используют чат CMS, исполнитель изменений и независимый проверяющий.
Git-воркер операционного слоя сохраняет собственную настройку запуска.

## Чат и инструменты Admin

Страница содержит вкладки «Подключение», «Агент», «Чат», «Инструменты». Настройки чата
хранятся в `configuration.chat` той же интеграции и сохраняются независимо от
авторизации. Выбор вкладки сохраняется в адресе (`#agent`, `#chat`, `#tools`).

- `displayMode`: `panel` — правая панель рядом с текущей страницей,
  `page` — контентная область `/admin/ai`, `window` — отдельное окно браузера
  с представлением `/admin/ai/window`. Пути учитывают настройку маршрутов plugin.
- `showHistory` задаёт исходную видимость истории; `showActivity` — сведения
  о текущей задаче; `sendOnEnter` управляет отправкой по Enter. Shift+Enter
  сохраняет перенос строки, ввод через IME не отправляет сообщение преждевременно.
- `tools.codeChanges` и `tools.dataOperations` ограничивают существующие
  операции над кодом и данными CMS. Сервер проверяет их при новых действиях
  и подтверждениях дополнительно к доступу и capability guards. Чтение, отказ,
  отмена и откат сохраняются. Уже запущенные задания не отменяются.

Исходные значения: правая панель, история и отправка по Enter включены,
сведения о задаче выключены, оба инструмента включены. Сохранение настроек до
входа создаёт выключенное подключение без credential и не запускает Codex.
Выход из аккаунта удаляет авторизацию и сведения аккаунта, сохраняя настройки
агента и чата в выключенной записи с новой ревизией. Переключатель агента
на вкладке «Агент» сохраняет авторизацию.

`GET /api/realize-ai/chat/settings` возвращает только `CodexChatSettingsDto`
после проверки `canUseChat`. `PUT /api/realize-ai/integrations/codex/chat-settings`
принимает полный `settings`, `expectedRevision` и `Idempotency-Key` под
`canManageIntegrations`; запись защищена общей блокировкой, CAS и audit.
Настройки не ослабляют sandbox и approvals. MCP остаётся запрещён; встроенный
веб-поиск Codex включается явно для отдельного сообщения чата.

Внутренний UI чата принадлежит `admin/chat`, размещение и переходы —
`admin/chat-presentation` внутри plugin. Один контроллер сохраняет выбранный
диалог при навигации Admin. Отдельное окно использует тот же authenticated API;
передача выбранного диалога и черновика ограничена принадлежащими чату окнами
того же origin. Блокировка popup показывается пользователю, тексты диалогов
не записываются в URL или browser storage.

Правая панель занимает всю высоту viewport без скруглений. Левый край меняет
ширину перетаскиванием или стрелками клавиатуры; Home/End выбирают границы,
двойной щелчок возвращает исходную ширину. На desktop ширина ограничена
360–960 px с сохранением минимум 360 px для основной области. Выбор сохраняется
при закрытии и повторном открытии в текущей вкладке до перезагрузки. На экранах
до 900 px панель занимает весь viewport, изменение ширины скрыто.

### Управление агентом

Вкладка «Агент» (`#agent`) управляет единственным `connection.enabled`.
`configuration.agent` хранит основную `model`, отдельную `reviewModel` и
разрешения `execution`, `preview`, `release`, `sourcePromotion`.
Пустая основная модель использует выбор провайдера; пустая модель проверяющего
использует основную. Начатые chat runs сохраняют свой снимок модели.
В дополнительных параметрах задаются сроки в секундах: capability — 3 600
(минимум 60), результаты выполнения — 86 400 (минимум 3 600), preview —
21 600 (минимум 900), release — 86 400 (минимум 3 600). Максимум — 604 800.
Legacy записи без `agent` получают эти значения и выключенные разрешения этапов.

`PUT /api/realize-ai/integrations/codex/agent-settings` принимает
`{expectedRevision, enabled, settings}` и обязательный `Idempotency-Key`.
Проверяется `canManageIntegrations`; сохранение использует общую блокировку,
CAS и аудит. Ответ — безопасный `CodexIntegrationConnectionDTO`. Авторизация,
аккаунт и `configuration.chat` сохраняются. Неопределённый результат запроса
повторяется с тем же ключом и телом; конфликт ревизии сохраняет черновик формы.

Payload читает интеграцию заново для каждого действия, worker — перед чтением
очередей. Выключение запрещает новые действия, сохраняя историю, события уже
принятых запусков, отмену и откат. `GET /api/realize-ai/status` требует включённое,
настроенное подключение и доступный control plane; исправный процесс сам по
себе не означает готовность агента. UI обновляет доступность после сохранения
и возвращения фокуса. Роли, инструкции и рабочие процессы остаются в
`/admin/ai/settings`; разрешения инструментов — на вкладке «Инструменты».

Переменные окружения больше не выбирают модели и не включают этапы.
`runtime.isolated` — отдельное инфраструктурное ограничение проверок и preview,
в которых запуск запрещён независимо от скопированной конфигурации Admin.

### Диагностика агента

В начале вкладки «Агент» показаны состояние чата с причиной недоступности,
подключение, сохранённые модели, разрешения выполнения кода, preview, выпуска
и Pull Request. Пустая основная модель означает выбор провайдера; пустая модель
проверяющего наследует основную. Эти настройки не выдаются за подтверждённое
название модели последнего ответа.

`GET /api/realize-ai/integrations/codex/diagnostics` доступен только
`canManageIntegrations` и возвращает `CodexAgentDiagnosticsDTO`. Один снимок
Codex содержит безопасную сводку подключения, `models`, `accessTest`,
`runtime`, `operations`, `worker` и `checkedAt`. Проверка runtime
использует тот же `resolveRuntimeStatus`, что и `/status`: локальную
конфигурацию и авторизованный маршрут control plane. В диагностике учитывается
также право текущего пользователя работать с чатом. Для центрального режима
без адреса показывается отдельная причина: «Адрес сервиса выполнения агента
не настроен». Локальный режим сохраняет loopback-сервис по умолчанию.

Состояния операций: `allowed` — разрешено общими настройками и правами,
есть свежий исполнитель, принимающий задания этого этапа;
`disabled` — этап выключен; `blocked` — имеется конкретная препятствующая
причина. Учитываются разрешение изменений кода, подпись execution, зависимость
preview от execution и проверенное подключение GitHub для публикации.
Подготовка выпуска блокируется, если сохранённое GitHub-подключение выключено
или некорректно; отсутствие такой записи само по себе не блокирует внешний
release orchestrator.
`worker` соответствует `WorkerAvailabilityDTO`: `state`
(`available`, `busy`, `unavailable`), `reason`, `lastSeenAt`, `activeCount`,
`busyCount` и `currentJob | null` с `kind` и `changeRequestID`.
Состояние читается из скрытой служебной коллекции `realize-ai-worker-presence`,
куда каждый экземпляр worker записывает heartbeat каждые 5 секунд.
Свежесть ограничена 20 секундами и определяется по времени PostgreSQL.
Процесс передаёт фактически обслуживаемые этапы, включая необходимые ему
инфраструктурные команды; занятый исполнитель может принимать очередь после
текущего задания. Остановка различается с потерей связи через текст причины.
Heartbeat не подтверждает авторизацию модели или успех конкретного задания.
Согласование изменения, scope, hashes и сроки проверяются при выполнении.

Heartbeat работает независимо от долгого задания. Перед новым получением
задачи обязательна успешная запись состояния; при ошибке БД новые задания
не принимаются. `SIGTERM` переводит процесс в `draining`: он продолжает
посылать сигналы и завершает текущую задачу, не получая следующую.
Автоматического повтора после аварийного завершения нет. Операционные записи
старше суток очищаются, кроме последнего экземпляра для диагностики.

Чтение execution в чате добавляет `worker` к `ChangeExecutionDTO`. Для
полученного задания проверяется именно назначенный экземпляр, поэтому другой
работающий worker не скрывает потерю его исполнителя. `currentJob` ограничен
доступным пользователю Change Request; чужие идентификаторы не выдаются.
Менеджер интеграций видит общую сводку. PID, ключ экземпляра и серверные пути
не входят в публичный DTO.

Кнопка «Проверить доступ» вызывает существующий `POST /integrations/codex/test`.
Она проверяет авторизацию без генерации и обновляет существующие
`lastTestStatus/lastTestedAt`. UI отдельно показывает время обновления текущего
снимка и последнюю сохранённую проверку доступа. При `never` прежняя дата не
отображается. Проверка доступа не подтверждает баланс или доступность выбранной
модели. GET диагностики не меняет результат этой проверки.

Снимок обновляется каждые 5 секунд на активной вкладке, после изменения
подключения, проверки и возвращения фокуса. Устаревшие ответы отбрасываются, несохранённый черновик
не заменяется. Проверка доступа блокируется при несохранённых изменениях,
неподтверждённом сохранении и выполнении другой операции подключения.

### Совместный локальный запуск

В `local-development` команда `npm run dev` запускает Next, control plane и
worker через общий supervisor в `scripts/runtime`. Окружение всех процессов
загружается штатным `@next/env`; параметры и порты проверяются до запуска.
PostgreSQL session lock защищает от второго совместного запуска того же
checkout. Worker запускается после health-ответов приложения и control plane.
При остановке supervisor дожидается текущего задания worker. В central и
isolated режимах запускается только Next; отдельная команда `dev:web`
используется также браузерными тестами. Настройки и разрешения остаются в Admin.
Этот способ относится к trusted local runtime; `npm start` и production
Compose не запускают локальный worker. Порядок настройки — в
[локальном runbook](../delivery/01-local-admin-ai.md#4-процессы-разработки).

### Вложения и контекст сообщения

Блок ввода принимает приватные изображения JPEG/PNG/WebP и текстовые файлы
UTF-8, включая исходники. Доступны выбор файлов, перетаскивание и вставка
изображения из буфера. Предпросмотр и удаление относятся к черновику; ошибка
отправки сохраняет его содержимое. PDF и Office-документы не поддерживаются:
обработчик извлечения их содержимого не установлен.

Ограничения возвращает `GET /api/realize-ai/chat/capabilities`: до пяти вложений,
до 8 МиБ на изображение, 256 КиБ на текстовый файл, 20 МиБ суммарно и до десяти
выбранных файлов проекта. Сервер проверяет фактический формат и размер, а не
доверяет расширению или MIME браузера. Обычные текстовые расширения учитываются
вместе с проверкой UTF-8; `.ts` не отклоняется из-за системного MIME `video/mp2t`.

Файлы проекта выбираются через `GET /api/realize-ai/chat/project-files?q=…`.
Каталог использует тот же безопасный фильтр, что и Context Pack, и возвращает
относительные пути, размеры и SHA-256. Отправка повторно проверяет выбранную
версию; произвольные абсолютные пути, выход за корень и секреты не принимаются.

Запрос сообщения содержит `content`, `attachmentIDs`, `projectFiles`
(`path`/`sha256`), `webSearch` и выбор `agentConfiguration`, когда выпуск активен.
Пустой текст допустим с вложением или файлом
проекта. Идемпотентность учитывает весь запрос. Сообщение сохраняет снимок
контекста; старые записи без дополнительных полей продолжают отображаться.

`POST /api/realize-ai/chat/attachments` принимает файл через multipart.
Скачивание и удаление чернового вложения используют собственные защищённые
маршруты. Payload проверяет `canUseChat` и владельца; публичная коллекция Media
не участвует. Бинарные данные передаются в control plane отдельно от JSON
сообщения через авторизованный серверный канал. В браузер не выдаются серверные
пути или доступ к файловому хранилищу. Текстовые вложения скачиваются как файлы,
а HTML и SVG не исполняются в интерфейсе.

Приватный каталог задаётся `REALIZE_AI_CHAT_ASSET_ROOT` вне checkout, с правами
`0700`. Для постоянной истории нужен сохраняемый том control plane и его
резервное копирование вместе с БД. Неиспользованные загрузки истекают через
24 часа и удаляются при следующей загрузке или ежечасной очистке. Файлы
отправленных сообщений неизменяемы и сохраняются с историей.

Изображения материализуются сервером внутри контекста запуска и передаются
штатным `localImage`; текстовые вложения и выбранные исходники включаются в
контекст. Профиль `realize_chat_snapshot` разрешает чтение подготовленного
снимка и минимальных системных файлов. Приватное хранилище вложений, `CODEX_HOME`
и файлы WIF недоступны инструментам чата. Веб-поиск разрешён только при
`analysis-readonly` и явном
`webSearch: true`; обычный чат по умолчанию, исполнитель кода и reviewer
сохраняют отключённый поиск. Источники берутся из данных провайдера, проходят
проверку HTTP(S) URL и сохраняются вместе с ответом. Непрозрачные идентификаторы
цитат не превращаются в выдуманные ссылки. Контракт провайдера описан в
[Codex App Server](https://learn.chatgpt.com/docs/app-server).

### Оформление плана из ответа

Кнопка «Оформить план изменения» доступна по серверному
`MessageDTO.changePlan.status: ready`. Готовность вычисляется из сохранённого
текста той же проверкой, которую использует создание Change Request; browser
не извлекает пути самостоятельно. Обычная редакция текста без файлового scope
не предлагается как готовый план изменения кода.

Для неполного ответа действие «Уточнить изменение» добавляет запрос в поле
ввода и сохраняет уже набранный черновик. Пользователь проверяет и отправляет
его отдельно. Уточнение различает работу с данными CMS и кодом: для кода нужны
точные файлы и проверки, для данных — поддерживаемая операция. Отсутствующую
возможность требуется объяснить, не выдумывая пути или доступный executor.

Data Lane, workflow и существующие карточки изменений сохраняют свои действия.
После загрузки истории или завершения SSE готовность приходит через обычную
проекцию detail. Она не заменяет отдельные approvals, права и ограничения
исполнения. Разбор scope учитывает `./`, файлы корня и Next route segments,
сохраняя отказ для абсолютных путей и выхода из проекта. Контракт статусов — в
[API specification](../specifications/realize-ai-commerce/v1.0/03-runtime-delivery-and-security/22-api-and-streaming-contracts.md#готовность-ответа-к-оформлению-плана-кода).

### Управляемое создание страницы

`analysis-readonly` запрещает самой модели менять файлы и БД. Для запросов
создания обычной CMS-страницы подключён `pages.createDraft.v1`: ассистент
предлагает один `realize-data-operation` блок с заголовком, `slug`, текстовыми
секциями и необязательным SEO-описанием. Ответ не должен отказывать из-за
read-only, выдавать предполагаемую проверку БД за выполненную или отправлять
этот запрос в очередь изменения кода.

Payload Data Lane проверяет права и свободный адрес, сохраняет точный preview,
а после действий «Подтвердить создание» и «Создать черновик» вызывает Local API
со штатными access/hooks. Host mapper преобразует обычный текст в существующие
`Pages.hero`, `Content` и SEO-поля. Статус всегда `draft`; результат содержит
ссылку на редактор Admin. Исполнитель кода, Git worktree и публикация в этом
действии не участвуют.

Откат с отдельным подтверждением может удалить только неизменённый созданный
черновик без истории публикации. Транзакционный advisory lock используется
и в Data Lane, и в `Pages.beforeOperation` до чтения при записи/autosave;
проверка версии не отделена от удаления конкурентным изменением.
Подробные ограничения intent и hash-привязки — в
[Data/Config Pipeline](../specifications/realize-ai-commerce/v1.0/02-change-engine-and-pipelines/14-data-config-pipeline.md#145-создание-черновика-cms-страницы).

### Конфигурация агента для чата

В `/admin/ai/settings` администратор сохраняет и проверяет черновик, создаёт
immutable release, просматривает его состав и отдельно активирует выпуск.
Rollback переключает active pointer на более ранний совместимый выпуск.
Сохранение и проверка черновика не меняют настройки новых или текущих runs.

Чат получает через `GET /api/realize-ai/config/runtime` только сводку активного
выпуска и включённые профили, без текстов инструкций. В блоке ввода показаны
профиль и выпуск следующего ответа; список поддерживает поиск и страницы
по 25 записей. При первом чтении единственный профиль выбирается автоматически,
при нескольких выбор делает пользователь. Точный выбор сохраняется при переносе
диалога между панелью, страницей и окном. Если каталог обновился, устаревший
выбор автоматически не заменяется: отправка требует нового выбора, текст
сообщения остаётся в форме. Без active pointer используется системная конфигурация.

Browser передаёт только `{releaseID, manifestHash, profileKey}`. Payload сверяет
его с active pointer, компилирует exact immutable release и сохраняет закрытый
`AIChatConfigurationSnapshot` в `runs.turnContext.agentConfiguration`.
Control plane повторно проверяет форму и hashes. Публичный `RunDTO` содержит
только сводку выпуска, профиля и хешей; история показывает конфигурацию
сохранённого запуска. Повтор того же подтверждённого запроса возвращает исходный
run, даже если active pointer уже переключён.

Renderer включает описание и locale профиля, прямые роли, правила по убыванию
priority, выбранные навыки как условные процедуры и прямые шаблоны
`slot: agent_instructions`. Поддержаны `request`, `context`, `profile_key`,
`profile_title`, `locale`; подстановка выполняется один раз как JSON-quoted
данные. Default `context` содержит ключ, название и locale профиля. Неизвестная
переменная активного шаблона вызывает ошибку. Slots `planner`, `reviewer`,
`workflow_step` и шаблоны, выбранные только workflow, в инструкции обычного
сообщения не входят.
Для явно выбранного процесса control plane выполняет только один bounded
read-only `agent_turn` с exact шаблоном шага; orchestration и checkpoints
принадлежат Payload/Change Engine. В обычном чате workflows не запускаются.
Capability/check metadata не предоставляет полномочий и не подтверждает checks.
Контракт сегментов и продолжения описан в [workflow runtime](../specifications/realize-ai-commerce/v1.0/01-architecture/10-ai-codex-layer-integration.md#108-исполнение-workflow-сегментами).

Снимок ограничен 2 000 000 сериализованных символов и 8 МиБ UTF-8, renderer —
128 КиБ, итоговый JSON с `developerInstructions` и `prompt` — 256 КиБ UTF-8.
Переполнение отклоняется без усечения инструкций. Server policy, sandbox
и ограничения провайдера действуют независимо от installation profile.

`runtimeContextHash` связывает compiled config hash с моделью, текущими server
developer instructions, включая web-search policy, и версией политики контекста.
Последний завершённый provider thread переиспользуется только при совпадении
этого fingerprint. Иначе создаётся новый thread, получающий до 32 КиБ UTF-8
сохранённых реплик пользователя и ассистента как недоверенные данные;
старые developer instructions не переносятся. При ограничении истории
приоритет имеют последние реплики. Уже созданные runs сохраняют свой snapshot.

## Авторизация

- **Вход через браузер:** администратор открывает ссылку OpenAI и подтверждает
  доступ аккаунта ChatGPT. Разрешение входа по коду устройства не требуется.
- **Код устройства:** администратор получает одноразовый код и вводит его на
  странице OpenAI. В настройках безопасности ChatGPT должен быть разрешён вход
  Codex по коду устройства; для рабочего пространства действуют его разрешения.
- **API key:** ключ вводится в поле с маскировкой и передаётся только серверу.
  API оплачивается отдельно от подписки. Пустое поле сохраняет существующий
  ключ только при неизменном способе авторизации.
- **Codex access token:** токен с доступом к Codex для рабочего пространства
  ChatGPT Business или Enterprise. Администратор разрешает его создание;
  источник доступа — соответствующая учётная запись рабочего пространства.
- **Workload identity:** сервер получает краткоживущий доступ через OIDC или
  SPIFFE. Требуются управляемое рабочее пространство, правило доверия и
  включение beta-возможности со стороны OpenAI.

Способ доступа сохраняется явно, автоматического переключения оплаты нет.
Google, Apple, Microsoft и SSO используются на странице входа ChatGPT;
отдельные режимы интеграции для них не создаются. Используется официальный
Codex App Server, внутренний экспериментальный импорт OAuth-токенов не применяется.
Источники:
[авторизация](https://developers.openai.com/codex/auth),
[протокол](https://developers.openai.com/codex/app-server),
[access tokens](https://learn.chatgpt.com/docs/enterprise/access-tokens),
[workload identity](https://learn.chatgpt.com/docs/enterprise/workload-identity).
Совместимость проверена с CLI `0.153.4`.

Проверка читает лимиты аккаунта либо каталог моделей API. Запрос к модели не
выполняется; наличие средств и доступ ко всем моделям не подтверждаются.
Для API-проверки требуется разрешение чтения моделей.

## Хранение и выполнение

Существующая коллекция интеграций хранит настройки, ревизию и результат проверки.
Для ChatGPT и API key сохраняется зашифрованный штатный `auth.json`; для Codex
access token — отдельная зашифрованная запись с типом `codexAccessToken`.
Общий AES-256-GCM vault привязывает секрет к провайдеру и подключению. Workload
identity не сохраняет credential в БД; при переходе к нему предыдущий секрет
удаляется. Схема БД не меняется. DTO содержит режим, способ входа ChatGPT,
разрешённые сведения об аккаунте и признак наличия сохранённого credential.

`packages/codex-adapter` владеет RPC и профилем. Модуль
`packages/payload-ai-plugin/src/integrations/codex/` управляет входом,
сохранением и проверкой; его `runtime/` предоставляет авторизацию исполнителям.
SQL остаётся в `IntegrationRuntimeRepository`.

Запись, проверка и запуск используют общую блокировку PostgreSQL. При занятом
подключении действие отклоняется с предложением повторить его. Обновлённый
credential сохраняется с проверкой исходной ревизии и envelope. Отсутствующее,
отключённое или повреждённое подключение блокирует новый запуск агента; личный профиль
и переменные с API key не служат заменой. Сам RPC-адаптер требует явно переданное
окружение с абсолютным `CODEX_HOME` до запуска subprocess; пути не берутся из
личного профиля автоматически. Прямой HTTP-запрос к каталогу моделей применяется
только при проверке введённого API key и не генерирует ответы.

## Серверное окружение

Next/Payload, control plane и worker используют одну БД и постоянный
`REALIZE_CODEX_STATE_ROOT`. Для способов с сохраняемым credential у всех
процессов должен быть одинаковый `REALIZE_INTEGRATIONS_ENCRYPTION_KEY`;
workload identity не требует vault.
Путь абсолютный, по умолчанию `~/.local/share/realize-ai-cms/codex`. Нескольким
контейнерам нужен общий том и согласованный системный пользователь. Независимые
установки CMS должны иметь разные каталоги. Codex CLI берётся из `PATH` либо
из `REALIZE_CODEX_BINARY`.

В подкаталоге `runtime/` сохраняется история для `thread/resume`. На время
запуска ChatGPT/API credential записывается с правами `0600` в каталог `0700`,
после синхронизации удаляется. Codex access token передаётся в окружении только
запускаемого процесса через `CODEX_ACCESS_TOKEN`, без записи `auth.json`.
Личный `~/.codex` не читается и не изменяется. Унаследованные переменные другого
способа авторизации исключаются при создании окружения.

### Серверная идентификация

Оператор задаёт `REALIZE_CODEX_FEDERATION_RULE_ID` и
`REALIZE_CODEX_IDENTITY_TOKEN_FILE` всем процессам CMS, использующим Codex.
Адаптер передаёт их как штатные `OPENAI_FEDERATION_RULE_ID` и
`OPENAI_IDENTITY_TOKEN_FILE` только при сохранённом режиме `workloadIdentity`.

Файл токена находится вне checkout, имеет абсолютный путь, принадлежит
системному пользователю процессов CMS и использует права `0400` или `0600`;
каталог — `0700`. Символические и дополнительные жёсткие ссылки не допускаются.
Инфраструктура обновляет файл до истечения токена. В форме доступны состояние
готовности сервера и повторная проверка, без чтения токена или ввода пути.
Готовность конфигурации не подтверждает принятие токена OpenAI: для этого после
сохранения используется отдельная проверка доступа.

Для запусков с workload identity адаптер выбирает профили разрешений Codex,
запрещающие инструментам чтение каталога токена. Профили сохраняют требуемый
режим работы исполнителя или проверяющего.

### Браузерный вход на удалённом сервере

Штатный Codex принимает возврат OpenAI на `http://localhost:1455/auth/callback`.
На одном компьютере вход завершается автоматически. Для удалённого размещения
можно использовать перенаправление порта SSH либо раскрыть в форме блок
завершения входа и передать полный адрес, на который OpenAI перенаправил браузер.

Передача адреса через форму — адаптация CMS поверх локального callback Codex.
Защищённый POST привязан к владельцу и действующей попытке входа; сервер
проверяет исходный адрес возврата, OAuth state и однократность передачи.
Принимается только фиксированный callback текущего процесса, перенаправления
не выполняются. Адрес с одноразовым кодом не сохраняется в аудите и не
возвращается через DTO. На обслуживающем сервере одновременно допускается
один браузерный вход из-за общего порта Codex. Отдельная блокировка PostgreSQL
согласует вход между процессами одной установки и освобождается после закрытия
процесса авторизации. Порт `1455` должен быть доступен этому процессу; вход по
коду устройства его не использует.

Старые native threads из личного профиля автоматически не переносятся. Для
диалога, начатого до перехода на интеграцию, создайте новый чат; сообщения
предыдущего диалога в CMS сохраняются.

Вход использует временный профиль, принадлежит начавшему его администратору и
ограничен десятью минутами. Отмена, ошибка и истечение срока закрывают процесс.
Новая попытка заменяет предыдущую попытку этого администратора. Допускается
восемь активных входов на процесс. Результат сохраняется однократно при опросе
формы, с повторной проверкой прав и ревизии.

Незавершённые входы хранятся в памяти сервера: нескольким репликам требуется
закрепление запросов за репликой на время входа. После перезапуска вход
повторяется. Сбой БД при обновлении токенов приводит к ошибке синхронизации и
может потребовать повторного входа. Пароль ChatGPT, OAuth-токены и сохранённый
API key и Codex access token не возвращаются через Admin/API.

Завершение входа ожидает два штатных события: успешное `account/login/completed`
и последующее `account/updated` для ChatGPT. Только после обновления аккаунта
читаются профиль и credential. Ошибки различают отказ OpenAI, получение аккаунта
и чтение серверного credential. Журнал содержит только этап, способ входа и
фиксированный код причины; текст внешней ошибки, коды и URL в него не попадают.
