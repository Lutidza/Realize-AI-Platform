# Одно чтение файла в рамках попытки

**Статус.** Контракт реализован для назначения в режиме `static-read-only`. В рамках одной попытки первый запрос получает вызов `repo_read_file`, второй передаёт результат вызова и получает итоговое сообщение. Разрешённые пути и версии файлов задаёт привязка выбранного назначения. Обмен проверяется на локальном транспорте в памяти. [Допуск API-запроса](openai-chat-completions.md) · [Контракт подтверждения прав V1](adapter-access-evidence-v1.md)

## Что принадлежит попытке

Оркестратор хранит `attemptId`, `assignmentId`, `revision`, `contextId`, `lockSha256`, исполнителя, модель и ревизию политики. Для каждого запроса адаптер выделяет свой `requestId` и получает допуск V1. Транспорт связывает ответ с тем запросом, который его получил. На один запрос ожидается один ответ.

Для одного ожидающего вызова ключ `AuditCallKey` содержит `attemptId`, исходный `requestId`, `toolCallId` и `argumentsSha256` — хеш имени функции и исходной строки аргументов. Запись операции хранит этот ключ, имя функции, разобранные аргументы, ожидаемый SHA-256 из привязки и исход чтения. При успехе квитанция содержит путь, SHA-256 всего файла, границы фактически выданных строк и признак усечения. При отказе операция хранит код `FORBIDDEN`, а квитанция отсутствует. Текст прочитанных строк передаётся в сообщении `tool`. Проверочные чтения при допуске учитываются отдельно. [Типы ключа и операции](../../../.ai/tools/worker-assignment/src/exchange/SingleRead.types.ts) · [Чтение и формирование квитанции](../../../.ai/tools/worker-assignment/src/exchange/performSingleRead.service.ts)

## Порядок обмена

1. После допуска первого запроса ожидается сообщение `assistant` с одним элементом в `tool_calls`. Оркестратор сверяет полученные от транспорта `attemptId` и `requestId` с отправленным запросом. Для `repo_read_file` он проверяет аргументы по схеме, вызывает обработчик с правами назначения и сверяет путь и SHA-256 результата с привязкой.
2. Обмен переходит в `pending`. Продолжение содержит исходное сообщение `user`, принятое сообщение `assistant` и сформированное Realize сообщение `tool`. Поле `tool_call_id` в точности равно `assistant.tool_calls[0].id`. В случае отказа содержимое сообщения `tool` включает только код `FORBIDDEN`.
3. Для отправки продолжения оркестратор передаёт в `finish` ключ операции. При несовпадении ключа он получает `blocked` с кодом `tool_call_mismatch`. При совпадении заново открывается тот же контекст и проверяются пакет, привязка и ревизия политики. Новый запрос той же попытки получает отдельный `requestId` и допуск V1 на окончательные сообщения, инструменты и права. Перед выдачей текста обработчик подтверждает закреплённую версию файла. В транспорт поступают проверенные байты.
4. Повторный или одновременный вызов `finish` с тем же ключом в этом обмене получает общий результат одной отправки. Если транспорт прервал отправку без подтверждения, попытка возвращает `delivery_unknown`. Автоматической повторной отправки нет.

## Завершение

| Событие | Решение |
| --- | --- |
| Разрешённый диапазон передан | Чтение завершено. Оркестратор ожидает следующий ответ в этой попытке. |
| Запрошен путь вне назначения или операция записи | Обработчик возвращает `FORBIDDEN`. Продолжение передаёт только код отказа и может получить итоговое сообщение. |
| Потеряна привязка, изменился файл или подменён вызов | `blocked`. Подготовленный результат чтения отбрасывается. |
| Связь оборвалась после начала отправки | `delivery_unknown`. Какая из передач осталась без подтверждения, видно по `requestId`. |
| Ответ относится к другому запросу или попытке | `blocked` с кодом `request_mismatch`. |
| Получено итоговое сообщение своего запроса | Для `received` ожидается `finish_reason: "stop"` и непустой текст `assistant` без нового вызова. Несоответствие формату даёт `blocked` с кодом `result_missing`. |

Статус `received` подтверждает получение отчёта как после разрешённого чтения, так и после ответа `FORBIDDEN`. При оценке покрытия ревьюер использует квитанции успешных чтений в области назначения. Для нескольких последовательных чтений и восстановления после перезапуска действует контракт контрольных точек.
