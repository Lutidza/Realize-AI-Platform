# Одно чтение в попытке аудита статьи

**Статус.** Контракт согласован для аудита формы «Создать статью». Первый срез воспроизводит один вызов функции и итоговый ответ через локальный транспорт в памяти. [Допуск API-запроса](openai-chat-completions.md) · [Назначение и приёмка](../../../.ai/templates/worker-assignment/TEMPLATE-WORKER-ASSIGNMENT-MANIFEST.md#приёмка-аудита-формы)

## Что принадлежит попытке

Оркестратор хранит `attemptId`, `assignmentId`, `revision`, `contextId`, `lockSha256`, исполнителя, модель и ревизию политики. Для каждого запроса адаптер выделяет свой `requestId` и получает допуск V1. Транспорт связывает ответ с тем запросом, который его получил. На один запрос ожидается один ответ.

Оркестратор регистрирует один ожидающий вызов по паре `(attemptId, tool_call_id)`. Запись связывает его с исходным `requestId`, именем функции, аргументами, ожидаемым SHA-256 из локальной привязки и состоянием операции. После чтения в доказательства попадают путь, SHA-256 всего файла, фактически выданные строки и признак усечения. При отказе сохраняется код. Байты для передачи живут только в текущем обмене. Пробы допуска учитываются отдельно от чтения аудитора.

## Порядок обмена

1. После допуска первого запроса транспорт возвращает сообщение `assistant` с одним `tool_calls[]`. Оркестратор проверяет принадлежность ответа запросу и попытке. Аргументы читает по схеме `repo_read_file` и вызывает закреплённый обработчик.
2. Результат привязан к точному `assistant.tool_calls[0].id`. Продолжение содержит исходное сообщение `user`, принятое сообщение `assistant` и сообщение `tool` с тем же `tool_call_id`. Его содержимое формирует Realize. Для отказа в доступе полезная нагрузка содержит только код `FORBIDDEN`.
3. Перед передачей оркестратор сверяет ожидающий вызов, заново открывает тот же контекст, проверяет ревизии привязки и политики. Валидатор V1 проверяет окончательные сообщения, инструменты, права и новый идентификатор запроса в той же попытке. Перед выдачей текста обработчик подтверждает закреплённую версию прочитанного файла. В транспорт поступают проверенные байты.
4. Повтор обработки того же события использует уже начатую операцию или её результат. Подмена идентификатора, исходного запроса или аргументов ожидающего вызова останавливает передачу. При обрыве после начала отправки исход доставки неизвестен. Автоматического повтора нет.

## Завершение

| Событие | Решение |
| --- | --- |
| Разрешённый диапазон передан | Чтение завершено. Оркестратор ожидает следующий ответ в этой попытке. |
| Запрошен соседний файл или запись | Обработчик отклоняет операцию. Ответ с кодом отказа позволяет продолжить аудит в разрешённой области. |
| Потеряна привязка, изменился файл или подменён вызов | `blocked`. Подготовленный результат чтения отбрасывается. |
| Связь оборвалась после начала отправки | `delivery_unknown`. Какая из передач осталась без подтверждения, видно по `requestId`. |
| Получено непустое финальное сообщение своего запроса, открытых вызовов нет | `received`. Оркестратор получил отчёт и доказательства чтения. На этом имитатор завершает обмен. |

В этом срезе ожидается финальное сообщение после одного вызова. Статус `received` подтверждает получение отчёта. Оценку покрытия 12 файлов выполняет ревьюер. Для двух последовательных чтений отдельный имитатор использует PostgreSQL, восстанавливает историю после перезапуска и проверяет пакет для ревью.
