# Аудит процесса commit/push

- Дата: 7 сентября 2026 года.
- Задача: полный commit/push накопленных изменений с наблюдением за работой
  операционного слоя ИИ-агентов.
- Область: Git-навык, процесс, правило, две проверки и два навигационных индекса.
- Режим: доставка разрешена; Git-инструкции в этом шаге не изменяются.

Последующее целевое решение об обязательном Git-воркере, программном обработчике
и подключениях HTTPS/SSH сохранено в
[ADR-0016](../architecture/decisions/ADR-0016-development-git-delivery-handler.md).
Наблюдения и предложения ниже описывают состояние на момент аудита.

## Наблюдения этого прохода

1. Пользовательский запрос сразу разрешил полный проверенный состав изменений
   и push. Повторное согласование, отдельная сессия runtime и назначение
   исполнителя для Git не потребовались. Независимый агент анализировал только
   инструкции; команды доставки выполнял ведущий агент.
2. Проверки рабочего изменения уже выполнены: ссылки, YAML, навыки, правила
   исключения файлов, ESLint и формат конфигурации. Изменение
   `eslint.config.mjs` осталось прежним. Повторный запуск сборки, браузера,
   миграций и полного набора тестов ради коммита не нужен. Новый отчёт требует
   только проверки его содержания, ссылок и итогового diff.
3. Просмотр состава изменений обнаружил новый корневой
   `169-ru-homepage.png`: снимок страницы CAPTCHA, без ссылок из отслеживаемого
   текста. Он сохранён локально в рабочей области с неопределённым статусом.
   Это подтверждает пользу проверки состава перед полным `git add -A`;
   происхождение файла и применение правил создавшим его агентом неизвестны.
4. Семь прежних материалов перенесены в игнорируемую рабочую область.
   Git показывает удаление старых путей, но локальные файлы сохранены и
   совпадают с исходниками по SHA-256. Печать полного удаления двух снимков
   страниц добавила бы 1 159 строк сырого содержимого. Для их проверки
   достаточно списка путей, размеров и контрольных сумм.
5. В рабочем окружении не заданы `user.name` и `user.email`, активные Git hooks
   отсутствуют. Для коммита доступны ранее подтверждённые авторские данные.
   Диагностика этой настройки — расход окружения, а не требование Git-процесса.
6. Даже после исключения сырых удалений общий staged diff дал 611 строк и был
   обрезан лимитом вывода инструмента. Повторная печать всего diff была бы лишней:
   исходные правки уже рассмотрены, совпадение staged-файлов с рабочими файлами
   проверено побайтово. В процедуре нужно различать проверку состава индекса
   и повторное чтение уже проверенного содержания; новые изменения читать адресно.

## Что требует оптимизации

| Находка | Подтверждение | Предлагаемое исправление |
| --- | --- | --- |
| Проверка коммита поставлена до staging | Процесс: строки 30–32; проверка коммита: 17–20 уже требует staged diff | Завершать проверку итогового состава после `add` |
| Проверка push поставлена до SSH preflight | Процесс: строка 33; проверка push: 20 требует выполненную SSH-проверку | Сначала SSH preflight, затем оценка готовности и push |
| Commit-only может подключать лишние требования | Навык: строка 10 предлагает связанные checks; правило: 27–28 объединяет их с требованием к `origin` | Подключать remote/SSH и проверку push только при запросе push |
| Выбор проверок отсылает к неточному источнику | Навык: 15–19; правило: 24–26 ссылаются на глобальное правило, где нет матрицы проверок | Назвать действующего владельца выбора проверок и использовать уже полученные результаты |
| Один порядок повторяется в нескольких местах | Навык: 13–34; процесс: 29–34; правило: 22–33; оба checks | Оставить порядок в процессе, условия в правиле, критерии в checks, команды в навыке |
| Повторяется служебная отчётность | Авторизация, отсутствие обязательного runtime, запрет полного набора тестов и итоговые поля повторяются почти во всех документах | Оставить один источник каждого требования и короткие адресные ссылки |
| Лишний объём вывода инструментов | Сырые удаления снимков страниц занимают 1 159 строк | Сначала обзор состава; содержимое печатать только для осмысленного изменения |
| Повторный вывод уже проверенных правок | Отфильтрованный staged diff: 611 строк и обрезанный ответ инструмента | Подтверждать соответствие staged-содержимого проверенной версии; полностью читать новые или изменившиеся участки |

Дубли текста не доказывают повторное выполнение команд. Просмотр рабочего diff
и итогового staged diff имеет разное назначение: второй подтверждает именно
содержимое будущего коммита. Повторять неизменившиеся тесты между ними не нужно.

SSH preflight создаёт отдельный сетевой запрос. Он предусмотрен действующим
правилом и сохраняется в этом проходе. Удаление этой проверки потребует
отдельного решения; успешный `ls-remote` подтверждает чтение удалённого
репозитория, но сам по себе не доказывает право записи.

## Первый небольшой пакет доработки

Изменить три документа: процесс доставки, Git-навык и правило Git.

1. Установить порядок: область и исходный diff → достаточные проверки изменения
   → staging → проверка staged diff → commit → при разрешённом push SSH preflight
   → проверка готовности → push.
2. В навыке оставить команды и особенности Git, исключив второй пересказ
   процесса. Выбирать checks по запрошенному действию.
3. В правиле отделить требования push от локального commit и уточнить источник
   выбора проверок.

Сохранить авторизацию, защиту секретов и чужих изменений, проверку staged diff,
проверенную ветку, SSH-only, ограничение force push и достаточные проверки
изменения. Постоянный отчёт на каждую доставку не вводить: этот документ создан
для явно запрошенного анализа процесса.

Результат самого commit/push сообщается после выполнения команд. Наблюдения
выше не являются утверждением об уже выполненной доставке.
