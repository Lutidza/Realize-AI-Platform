# Задание агенту: создать внутренний MCP-сервер Realize

Ты работаешь внутри актуального репозитория Realize. Реализуй и проверь первый рабочий MCP-сервер проекта. Realize пока запускается локально на компьютере владельца. В дальнейшем сервер будет использоваться для подключения Realize к ChatGPT и другим MCP-клиентам.

Нужен работающий код в текущем проекте, команды запуска и проверенное подключение MCP-клиента. Изучи репозиторий, кратко обозначь выбранное решение и приступай к реализации. Обычные технические решения принимай самостоятельно, опираясь на устройство проекта.

## 1. Изучи текущую реализацию

Прочитай `AGENTS.md`, инструкции разработки, манифесты зависимостей, команды запуска и архитектурную документацию. Проверь, нет ли уже заготовок MCP. Определи, как устроены серверная часть, авторизация, бизнес-сервисы и доступ к данным.

Сохрани существующие незавершённые изменения. Используй принятые в репозитории язык, менеджер пакетов, структуру модулей и инструменты проверки. Не меняй стек ради MCP.

Продуктовый бриф и функциональный каталог Realize описывают целевой продукт. Их наличие не подтверждает реализацию всех перечисленных модулей. Для состава инструментов опирайся на действующий код. Если этих документов нет в репозитории, продолжай по коду и доступной документации.

## 2. Реализуй сервер и локальный запуск

Используй официальный MCP SDK для текущего серверного стека. Основной транспорт — **Streamable HTTP**, endpoint — `/mcp`. Для TypeScript используй `@modelcontextprotocol/sdk` и совместимую библиотеку проверки схем. Выбери совместимую с проектом версию SDK по актуальной документации и зафиксируй зависимости. Ориентир: [официальное руководство OpenAI по MCP-серверу](https://developers.openai.com/plugins/build/mcp-server).

Размести сервер внутри существующей архитектуры: отдельным процессом или серверным модулем, в зависимости от возможностей проекта. Обработчики инструментов должны быть отделены от транспорта и использовать общие сервисы Realize. `stdio` добавляй только при необходимости для уже используемого локального агента, с теми же обработчиками.

По умолчанию слушай `127.0.0.1`; порт и корень репозитория задаются конфигурацией. Обеспечь понятную ошибку при неверной конфигурации или занятом порте, корректную остановку и повторный запуск. Не открывай внешний сетевой интерфейс автоматически.

Реализуй штатный цикл MCP через SDK: инициализацию, согласование версии, получение списка инструментов, вызовы и ошибки. Если транспорт использует сессии, изолируй их между клиентами и освобождай ресурсы при завершении. Идентификатор сессии не заменяет проверку доступа.

## 3. Обязательные инструменты доступа к проекту

Реализуй следующий небольшой набор. Названия можно согласовать с существующими соглашениями проекта, сохранив назначение.

| Инструмент | Что должен возвращать |
| --- | --- |
| `realize_get_context` | Название и версия проекта, сведения о доступном контексте пользователя, фактически подключённые модули и возможности MCP. Для кода — ветка, `HEAD` и признак локальных изменений. |
| `repo_list_files` | Список разрешённых файлов по относительному пути, с ограничением глубины и размера страницы. |
| `repo_read_file` | Текст разрешённого файла или диапазона строк, относительный путь и сведения, позволяющие определить прочитанную версию содержимого. |
| `repo_search` | Поиск текста в разрешённых исходниках и документации: путь, номер строки, короткий фрагмент и сведения об ограничении выдачи. |
| `repo_git_status` | Состояние рабочей копии: ветка, `HEAD`, разрешённые изменённые файлы и их статусы. Учти detached HEAD и новый репозиторий без коммитов. |
| `repo_git_diff` | Ограниченный diff разрешённых файлов: отдельно индекс или изменения рабочей копии. Произвольные команды и аргументы Git не принимаются. |

Чтение и поиск должны учитывать текущие локальные изменения. Не выдавай содержимое рабочей копии за содержимое `HEAD`. При обрезанной выдаче явно возвращай `truncated` и способ продолжить чтение: курсор, диапазон строк или более узкий запрос.

## 4. Подключи существующие функции Realize

Если в проекте уже есть рабочие сервисы задач, документов, проектов или других объектов, добавь хотя бы один полезный сценарий чтения: найти или перечислить объекты и получить выбранный объект по ID. Выбери наиболее готовый модуль. Используй его существующие сервисы, проверки прав и форматы данных.

Для первого действия, изменяющего данные, выбери создание задачи или черновика документа, **только если соответствующий бизнес-сервис уже реализован**. Инструмент должен возвращать реальный ID и сохранённое состояние объекта. Повтор одного запроса не должен создавать дубликат: используй ключ идемпотентности и сохраняемый результат в рамках пользователя и рабочей среды. Защита должна работать при параллельных вызовах и после перезапуска; создание объекта и фиксацию результата свяжи транзакцией или существующим надёжным механизмом сервиса. Один ключ с другим содержимым запроса должен приводить к конфликту.

Если сервисов приложения пока нет, заверши работающий MCP с инструментами репозитория и явно укажи в контексте и отчёте, что доступ к данным Realize ещё не подключён. Если доступны только операции чтения, подключи их и зафиксируй отсутствие готового сервиса записи. Не создавай отдельный CRUD, новую предметную модель или фиктивные ответы ради списка инструментов.

Операция через MCP должна иметь тот же смысл, что и соответствующая операция в интерфейсе Realize. Сохрани штатные проверки, события и автоматизации. Например, создание задачи не должно дополнительно вызывать второй запуск агента поверх запуска, уже созданного штатной автоматизацией. Если действие создаёт связанные процессы, возвращай их идентификаторы, когда они доступны.

На этом этапе не добавляй инструменты удаления данных, произвольного выполнения команд, изменения исходников, отправки сообщений или публикации. Расширение этих возможностей — отдельные задачи после проверки базового сервера.

## 5. Проверь доступ на стороне сервера

Используй существующую авторизацию Realize, если она подходит для MCP-клиента. Иначе для локальной разработки добавь отдельный случайный bearer-токен из окружения. Проверяй авторизацию каждого HTTP-запроса к MCP; при отсутствии обязательной настройки сервер должен завершать запуск с понятной ошибкой. Учитывай допустимые `Host` и `Origin`; отсутствие `Origin` у обычного MCP-клиента допустимо.

Доступ к исходникам разрешай явно настроенному владельцу или разработчику. Обычное участие в рабочей среде Realize само по себе не должно открывать репозиторий.

Для инструментов приложения получай пользователя или сервисную учётную запись из проверенных сервером учётных данных. Переданные моделью `userId`, `role` или `workspaceId` не дают дополнительных прав. Выбор рабочей среды допустим только после проверки доступа к ней. Локальный токен не должен автоматически превращаться в администратора всех сред.

Корень репозитория задаётся сервером. Проверяй фактические пути и границы корня; закрывай выход через `..`, абсолютные пути и симлинки. Единая политика разрешённых файлов должна применяться к списку, чтению, поиску, статусу и diff. Исключи реальные файлы окружения, ключи и учётные данные, внутренности `.git`, зависимости, сборки и неподходящие бинарные файлы. Шаблоны конфигурации без значений секретов можно разрешить явно.

Git вызывай через библиотеку или фиксированные команды с массивом аргументов, без shell-интерполяции пользовательского ввода. Отключи внешние diff-обработчики и textconv при получении diff. Введи ограничения времени, объёма файлов и результата. Используй действующие правила проекта для защиты секретов; не помещай токены, строки подключения и содержимое чувствительных файлов в ответы или логи.

## 6. Сделай понятный контракт инструментов

Для каждого инструмента укажи назначение, строгую входную схему, схему структурированного результата и корректные MCP-аннотации. Для чтения установи `readOnlyHint: true`; для записи — `false`. Остальные аннотации должны соответствовать реальному действию. Они не заменяют серверную авторизацию.

Возвращай данные через `structuredContent` и понятное текстовое описание через `content`. Различай ошибку доступа, отсутствие объекта, неверный ввод, конфликт и недоступность зависимого сервиса. Ожидаемые ошибки выполнения инструмента возвращай как `CallToolResult` с `isError: true`; ошибки протокольного запроса обрабатывай штатным механизмом SDK. Ошибку HTTP-авторизации обрабатывай до вызова инструмента. Не возвращай фиктивный успех или внутренние трассировки с секретами. Формат инструментов и результатов описан в [руководстве OpenAI](https://developers.openai.com/plugins/build/mcp-server).

Держи ответы компактными: списки с пагинацией, файлы по диапазонам, поиск с лимитом совпадений. Статическая карточка возможностей должна соответствовать действующим обработчикам. Если модуль подключён, но его сервис временно недоступен, возвращай эту ошибку явно.

## 7. Проверь сервер реальным MCP-клиентом

Запусти сервер и подключи совместимый SDK-клиент или MCP Inspector. Одного HTTP-ответа от `/mcp` недостаточно для проверки протокола.

Проверь и зафиксируй результаты:

1. Клиент выполняет инициализацию, получает инструменты и вызывает их с авторизацией.
2. Через MCP можно прочитать реальный разрешённый файл проекта, найти известную строку и увидеть актуальные сведения Git.
3. Неверный токен, выход за корень, симлинк наружу и доступ к исключённым файлам через чтение, поиск или diff отклоняются. Ограничения объёма выдачи работают.
4. Если подключены данные Realize, инструменты возвращают реальные данные в разрешённой рабочей среде. Если в проекте есть несколько пользователей или сред, проверь запрет доступа к чужим объектам.
5. Если реализована запись, созданный в тестовом контексте объект читается через обычный сервис приложения; повторы с тем же ключом, в том числе параллельные и после перезапуска, не создают дубликат. Не проверяй это на ценных пользовательских данных.
6. Ошибки инструментов не завершают сервер; остановка освобождает порт, повторный запуск работает.

Добавь воспроизводимые интеграционные проверки для протокола и существенных границ доступа. Тестовые данные и временные репозитории допустимы; рабочие инструменты должны обращаться к реальным источникам. Запусти применимые проверки типов, линтер и тесты проекта. Отдельно обозначь ранее существовавшие ошибки и проверки, которые не удалось выполнить.

## 8. Подготовь результат для владельца

Добавь код сервера, команды запуска и проверки, пример конфигурации без секретов и документацию в принятом месте репозитория, например `docs/mcp.md`. В документации объясни настройку локальных учётных данных, корня репозитория и подключение MCP-клиента.

В итоговом ответе верни:

1. Что реализовано и какие части существующей архитектуры использованы.
2. Изменённые файлы и добавленные зависимости.
3. Точную команду запуска и локальный URL `/mcp`.
4. Названия переменных окружения и способ задать их, без значений секретов.
5. Конфигурацию подключения для используемого локального MCP-клиента.
6. Список реально работающих инструментов: чтение репозитория, чтение данных приложения, запись — если реализована.
7. Выполненные проверки и их результаты.
8. Что потребуется для следующего шага — подключения сервера к ChatGPT.

## 9. Граница текущего этапа

Текущий результат — работающий и проверенный локальный MCP. Публикация сервера, настройка внешнего доступа и создание интерфейса плагина в этот этап не входят.

Для последующего подключения ChatGPT потребуется доступный ему транспорт: HTTPS endpoint или поддерживаемый механизм подключения к частному серверу. Локальный bearer-токен сам по себе не подтверждает готовность пользовательской авторизации ChatGPT; совместимую схему нужно выбрать и проверить на этапе подключения. Ориентиры: [подключение MCP к ChatGPT](https://developers.openai.com/plugins/deploy/connect-chatgpt), [авторизация](https://developers.openai.com/plugins/build/auth), [Secure MCP Tunnels](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels).

Не объявляй интеграцию с ChatGPT готовой до фактического подключения и проверки вызовов из ChatGPT. Сейчас доведи локальный сервер до воспроизводимого запуска и успешного вызова его инструментов.
