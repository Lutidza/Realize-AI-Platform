# ТЗ: программное создание и развитие агентов

Версия: 0.1. Дата: 2026-11-09. Статус: согласовано пользователем, реализация начата.
Задача Task Manager: `330143e8-f1cd-4098-a18f-5121a725b1e5`.
До явного согласования этого ТЗ разрешены анализ и документация; реализация,
активация ролей и исправление существующего agent.toml в эту стадию не входят.

Пользователь согласовал ТЗ командой «приступай» после передачи версии 0.1.
Последующие разделы описывают целевой результат; не все этапы реализованы.

### Фактический первый срез

Добавлены `renderCodexAgent`, `validateCodexAgent` и kind `codex.agent` в
существующий project binding. Поддержан ограниченный canonical TOML с тремя
полями: name, description, developer_instructions. Произвольный TOML, настройка
skills/tools и активация агента этим профилем не реализованы. Прямой consumer
может готовить bytes и использовать прежние prepareContent/plan/preview/apply.
Проверена публикация на изолированной FS через native runtime и replay apply.

Важное ограничение актуальной документации Codex: sandbox_mode в custom agent
не переопределяет конфигурацию родителя. Read-only обязан обеспечить host;
native validator не утверждает проверку permissions, runtime или поведения.
Реальная загрузка frontend guardrail, behavioural corpus и host admission
остаются незавершённой частью первого этапа.

## 1. Цель и границы

Создать проектный процесс и программные инструменты полного цикла:
описание → создание → валидация → оценка → улучшение → сравнение → активация.
Первый runtime — Codex. Цель превзойти LangChain должна подтверждаться
результатами на общем корпусе; до измерений превосходство не заявляется.

Область аудита и проектирования включает агентов, skills, prompts, workflows,
rules/checks, registries, шаблоны, утилиты и другие source-файлы агентского слоя.
Поддержка каждого формата вводится явно, неизвестные форматы отклоняются.
Anthropic и LangChain используются как источники сравнительных практик;
реализация их adapters, универсального оркестратора и Admin UI вне первого среза.

## 3. Владельцы и отсутствие дублирования

- Общие операции записи остаются в engineering-runtime, project placement и
  native profiles — в `.ai/tools/engineering`.
- Порядок работы принадлежит `.ai/workflows`, требования — `.ai/rules`,
  критерии — `.ai/checks`; `.codex` содержит только Codex-specific adapters.
- Общие eval DTO остаются в ai-contracts, оценка и сравнение — в change-engine,
  запуск — у существующего runtime/evaluation owner.
- Авторинг связывает эти владельцы и не вводит второй filesystem writer,
  ledger, task lifecycle или независимый каталог проектных правил.
- Новые точки входа и kind IDs сначала фиксируются в контракте соответствующего
  владельца. Точные CLI/tool names определяются первым срезом; здесь они не
  выдаются за существующие команды.

## 4. Контракт описания агента

Вход содержит schemaVersion, стабильные id/version, назначение и описание
маршрутизации, ownerRef, целевой runtime и проверенную версию совместимости,
базовые инструкции, ссылки на workflow/rules/checks, skills и требуемые tools,
политику доступа, формат результата и evalSuiteRef.

Конкретное задание передаётся при запуске отдельно от постоянной роли.
Runtime и перечень tools выбирает trusted host. Описание агента не может
самостоятельно выдавать grants, подключать произвольные команды или secrets.
Для каждого skill/tool фиксируются доступность и способ подключения в целевом
runtime; ссылка в prompt не считается подключением.

Один источник авторских инструкций и воспроизводимая сборка native файла:
для Codex формируется поддерживаемый developer_instructions с текстом.
Текстовые ссылки на workflow требуют реального чтения агентом.
Путь к Markdown не подставляется вместо текста инструкций.
Неизвестные поля, несовместимая версия, неоднозначный owner и недоступные
обязательные зависимости дают отказ до записи.

## 5. Создание файлов и утилит

Процесс: определить kind/owner → разрешить зависимости → подготовить content
и change plan → показать preview → выполнить разрешённый apply → проверить.
Для source использовать действующие naming/header validators и профильные
проверки; для AI-файлов — native metadata, IDs, граф и потребителей.

Rules/checks/workflows/skills добавляются отдельными профилями, со своими
валидаторами и relationship sync. Нельзя записывать их как ai.template,
обходя active registry checks. Generated outputs обновляются через recipe
владельца; authored/generated статус и recovery проверяются до apply.

Запись ограничена разрешёнными путями. Конфликт версии, symlink, выход из
owner boundary или неполный dependency scan блокирует эффект. Применяются
существующие гарантии runtime; неподдержанная операция возвращает unsupported.

## 6. Оценка, улучшение и сравнение

Каждая версия проходит формальные проверки, загрузку в целевом runtime и
поведенческие сценарии в изолированной среде. Сохраняются версии инструкций,
skills/tools, модели, runtime, corpus, fixture и evaluator, hashes и результаты
неудач. Секреты и рабочие пользовательские данные в corpus запрещены.

До изменения фиксируется baseline. Первый corpus включает корректную генерацию,
неизвестное поле, отсутствующий skill/tool, запрет записи для read-only роли,
отказ при изменении входов, полезность findings и cleanup после сбоя.
Реальные ошибки должны обнаруживаться без ложного заявления о проверке.

Разделяются набор для улучшения и контрольный набор. Предлагается три повтора
каждого поведенческого сценария для baseline и candidate; первый прогон времени
учитывается отдельно. Это ограниченный эксперимент, не доказательство
статистического превосходства. До модельного запуска утверждается budget;
потолки токенов/времени/стоимости применяются существующим ledger/runtime.

Метрики: успешность обязательных сценариев, нарушения полномочий, полнота и
точность findings на размеченных fixtures, время, токены и фактическая стоимость.
Неизвестная стоимость остаётся null, а не нулём. Сравнение разрешено только
при совпадении фиксированных условий и явном перечне изменённых осей.
Смена evaluator/corpus требует нового baseline. Смена authoring harness
оценивается отдельным версионированным протоколом, не ослаблением старого gate.

Улучшение: разобрать ошибки → изменить ограниченную часть → повторить проверки
и контрольные сценарии → сравнить → принять или отклонить candidate.
Автоматическое саморедактирование активных правил и бесконечные платные retry
не допускаются. Candidate не активируется при нарушении прав, неполном прогоне
или непроверенной регрессии. Смысловой review включает человека до активации
первого среза. Сравнение с LangChain — отдельный этап на общем corpus с
зафиксированными версиями и сопоставимым доступом к tools.

## 7. Этапы и результаты

1. Согласование этого ТЗ пользователем; до него только docs/read-only работа.
2. Первый вертикальный срез: контракт Codex agent, renderer, validator,
   разрешённый вход через существующий engineering runtime, frontend guardrail,
   фактическая загрузка и ограниченный поведенческий corpus.
3. Skills и AI-инструкции: native profiles, references/registry sync, создание
   и обновление через общий процесс; существующие source profiles сохраняются.
4. Расширение eval contracts, review и сравнения; контрольный набор и отчёт
   baseline/candidate. Совместимость старого шестисценарного gate сохраняется.
5. Сравнительный эксперимент с LangChain и решение о дальнейших adapters.

Каждый срез включает документацию фактических возможностей, проверки и cleanup;
широкий целевой каталог не считается реализованным после одного среза.

## 8. Критерии приёмки

- Идентичные входы дают идентичный content; версии и источники прослеживаются.
- Агент загружается установленным Codex без malformed/unknown-field warnings.
- Skills/tools доступны фактически; read-only запрет проверен попыткой записи.
- Негативные входы не создают частичную конфигурацию и не повышают полномочия.
- Preview/apply, stale input и recovery проверены через существующего FS owner.
- Отчёт оценки содержит все сценарии/повторы либо явный incomplete; неудачи
  не скрываются, расходы учитываются, собственные процессы/fixtures очищены.
- Сравнение отвергает несопоставимые условия; улучшение подтверждено на
  контрольном наборе без ухудшения обязательных ограничений.
- Нет дубликатов writer/eval engine/правил, ссылки и metadata согласованы.
- Выбранные tests/typecheck/lint и installed runtime evidence соответствуют
  срезу; структурная проверка не заменяет интеграционную приёмку.

## 9. Решения, требующие согласования

Согласовать scope и этапность этого ТЗ, первый пилот frontend guardrail,
три повтора для модельных сценариев и человеческое решение об активации.
Денежный бюджет задаётся отдельно перед реальными платными прогонами;
согласование документа не разрешает неограниченные расходы, commit/push/deploy.
