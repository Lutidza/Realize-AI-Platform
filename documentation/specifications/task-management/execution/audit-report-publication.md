# Публикация отчёта аудитора и карты покрытия в досье задачи

**Статус.** Первую реализацию проверили 2026-11-25 на изолированной PostgreSQL с имитатором. Проверка охватывала публикацию в досье и получение материалов из отдельной очереди ревью.

Для публикации нужны задача Foundation, сохранённая ревизия плана и подтверждённая попытка аудитора. Task Manager сохраняет отчёт и карту покрытия как два версионируемых артефакта одного результата задачи. По событию публикации независимый ревьюер получает именно эти версии в рамках уже выданного ему назначения. [Попытки и досье](attempts-and-dossier.md) · [Подготовка пакета по подтверждённым чтениям](checkpoints-and-reads.md#последовательные-чтения-в-одной-попытке)

## Публикация в досье

1. Источником служит подтверждённое состояние `received` и квитанции той же попытки. Карта покрытия содержит по одной записи на каждый файл ревью, включая непрочитанные. Полный набор источников также включает обязательные материалы назначения. Сервер выбирает сохранённый план по проекту, задаче, исполнению, этапу и ревизии назначения. Перед записью он проверяет попытку и требует точного совпадения путей и SHA-256 источников с `sourcePins`, а покрытия — с `scopePins` этого плана.
2. Досье сохраняет точные байты отчёта и карты покрытия. У каждого артефакта есть собственная ссылка с полями `artifactId`, `revision` и `sha256`. Файлу без квитанций соответствует статус `unread`. Для прочитанного файла сервер сверяет указанные диапазоны с объединением строк из квитанций. Досье хранит закреплённые версии исходников и обязательных материалов даже после очистки рабочего каталога аудитора. Достаточность покрытия оценивает ревьюер. [Типы публикации и ссылок](../../../../packages/payload-task-manager/src/server/audit-review/AuditPublication.types.ts) · [Проверка байтов и диапазонов](../../../../packages/payload-task-manager/src/server/audit-review/prepareAuditMaterials.mapper.ts)
3. В одной транзакции становятся видимыми версии материалов, `TaskResult` и событие публикации для доставки. До подтверждённого commit пакет остаётся ожидающим публикации. Сбой до commit позволяет повторить операцию, после commit событие доступно диспетчеру. Для каждой пары `(origin, attempt_id)` досье хранит один результат. При точном повторе издатель возвращает сохранённый `resultId` и те же версии артефактов. Повтор с изменённым отчётом или картой покрытия отклоняется с ошибкой `audit_publication_conflict`. В обоих случаях дополнительное событие доставки не создаётся.

Для подготовки пакета рабочий слой открывает попытку по `attemptId`, повторно проверяет привязку и закреплённые источники. Он передаёт отчёт, карту с квитанциями и байты источников. Закрытый серверный адаптер Task Manager пересчитывает SHA-256 полученных байтов. Сверка с планом и запись результата в досье выполняются в одной транзакции. После commit список результатов открывается по задаче, отчёт, карта и каждый источник — по идентификатору результата с проверкой прав. ## Кто получает работу

Получателя определяет сервер по двум этапам сохранённого плана. У ревьюера собственные назначение, область доступа и попытка. При отсутствии действующего назначения, права чтения или независимости от аудитора и автора реализации выдача останавливается с причиной. Опубликованный результат остаётся в досье. Текст отчёта не участвует в выборе исполнителя.

Событие публикации сохраняет намерение передать определённую версию результата. Логический ключ работы задают исполнение, этап ревью, назначение с ревизией и итерация ревью в области проекта. Ключ отделён от хеша содержимого. Под ним закрепляются версия результата и ссылки на обе версии артефактов. Подмена входа даёт конфликт. Для ревью исправленного результата требуется явно запланированная следующая итерация.

Диспетчер проверяет очередь по ключу и подтверждает событие только для совпавшей работы. При потере ответа после приёма он восстанавливает квитанцию по тому же ключу. При недоступном или неизвестном исходе событие остаётся ожидающим сверки. Полный текст отчёта, копия назначения, права аудитора и его переписка в очередь не передаются.

Runtime проверяет текущее назначение, точные ссылки на опубликованные материалы, независимость и действующие права ревьюера в момент получения работы. Конкурирующие получатели могут создать одну попытку ревью. Чтение досье, материалов и закреплённых исходников заново проверяет доступ, в том числе после выдачи работы. Получение задания подтверждает доставку. Техническое заключение и приёмка задачи имеют отдельный жизненный цикл. [Очередь и её владелец](../../task-management-execution.md#61-readiness-и-одна-передача-исполнения) · [Версии результатов](../../task-management-execution.md#152-ревизии-результаты-и-evidence)

Сохранённый план и разрешения принадлежат Task Manager. Для чтения нужны явное разрешение на отчёт, карту и все версии источников данной ревизии, а также действующее членство в проекте Foundation или права его владельца. Изменение состава проекта учитывается и после выдачи работы. Оркестратор доставляет событие, очередь runtime фиксирует job и попытку. Проверка полномочий и запись попытки выполняются одной транзакцией. [План и права](../../../../packages/payload-task-manager/src/server/audit-review/auditReviewPlan.repository.ts) · [Диспетчер событий](../../../../.ai/tools/worker-assignment/src/review-queue/dispatchPendingReviews.service.ts) · [Выдача работы](../../../../.ai/tools/worker-assignment/src/review-queue/PostgresReview.repository.ts)

После `claim` сервер читает отчёт и карту из досье с действующими правами ревьюера и сверяет SHA-256 каждого буфера со ссылкой из задания. При совпадении он возвращает оба материала получателю. При расхождении возвращает `review_material_mismatch`. Если чтение прервалось, тот же участник с тем же `consumerId` может продолжить по сохранённой квитанции. ## Приёмка среза

- Сохранить задачу и план до аудита. После публикации и очистки контрольных точек и рабочего каталога открыть досье по задаче. Отчёт, карта по `scopePins` с квитанциями и все источники по `sourcePins` доступны с исходными SHA-256.
- Прервать публикацию до commit. Результат, материалы и событие не становятся видимыми частично. При сбое после commit и до отправки новый процесс обнаруживает неподтверждённое событие. Точный повтор и конкурирующие публикации одного пакета дают один результат, версию каждого из двух артефактов и одно событие. Изменённый пакет той же попытки отклоняется.
- Потерять ответ после приёма в очередь. Повтор находит ту же работу, связывает с ней событие и сохраняет исходное назначение. Конфликт версий под одним ключом блокирует выдачу.
- Дать двум процессам возможность получить одну работу. В очереди остаётся один job, у существующего назначения появляется одна попытка ревью.
- Проверить отзыв права до выдачи и после неё, замену или отсутствие назначения, попытку саморевью и чужую задачу. Доказательства сохраняются в досье, закрытые данные недоступны отозванному участнику. Недоступность одного получателя не задерживает события остальных задач.
- При смене плана поздний отчёт сохраняется у исходной попытки. Аудитор с действующими правами может открыть его в досье задачи. Новому ревьюеру работа прежнего назначения не выдаётся.
