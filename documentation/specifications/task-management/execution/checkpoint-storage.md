# Хранилище контрольных точек попытки на PostgreSQL

**Статус.** Первую реализацию проверили 2026-11-25 на отдельной PostgreSQL 18.6 с имитатором транспорта. Хранилище Assignment сохраняет состояние одной попытки между процессами. Связи с задачей и правила подтверждения чтений описаны в спецификации Task Manager. [Попытки и досье](attempts-and-dossier.md) · [Контрольные точки и чтения](checkpoints-and-reads.md)

## Хранение одной попытки

При создании попытки Assignment повторно открывает контекст выбранного назначения. В начальную ревизию входят идентификаторы задачи, исполнения и этапа, ревизии плана и назначения, хеши привязки и входа, параметры исполнителя и политики. Поле `scopePins` закрепляет пути и SHA-256 файлов в области ревью. Перед каждой отправкой адаптер заново проверяет привязку и полномочия. [Начальное состояние](../../../../.ai/tools/worker-assignment/src/checkpoints/createAuditCheckpointState.service.ts) · [Допуск запроса](../../../architecture/assignment-adapter/openai-chat-completions.md)

Адаптер хранит данные в закрытой схеме `audit_checkpoint`. Проверки контрольных точек, очереди и досье используют выделенную тестовую БД `realize_assignment_test`. Каждая транзакция сверяет `current_database()` с этим именем до чтения или записи. При несовпадении хранилище контрольных точек возвращает `checkpoint_database_mismatch`, а очередь и досье — `audit_database_mismatch`. [Имя тестовой БД](../../../../packages/payload-task-manager/src/server/audit-review/assignmentTestDatabase.config.ts) · [Адаптер PostgreSQL](../../../../.ai/tools/worker-assignment/src/checkpoints/PostgresCheckpoint.repository.ts) · [Схема хранения](../../../../.ai/tools/worker-assignment/src/checkpoints/checkpointSchema.sql)

| Таблица | Что в ней сохраняется |
| --- | --- |
| `attempts` | ID попытки, текущая ревизия, владелец, срок lease по времени БД и монотонный fencing token. Только действующий владелец может продвинуть ожидаемую ревизию. |
| `revisions` | Неизменяемые версии состояния с SHA-256. Снимок закрепляет задачу, исполнение, этап, ревизию назначения, контекст и политику. Состояние сохраняет ожидающий вызов или намерение отправить точный запрос, историю подтверждений, а в `received` — текст отчёта и его SHA-256. |
| `receipts` | Неизменяемая квитанция привязана к попытке, вызову, запросу продолжения и следующей ревизии. Успех содержит путь, SHA-256, фактически переданные строки и признак усечения. При отказе сохраняется код. Квитанция и следующая ревизия фиксируются одной транзакцией. |

Попытка начинается с ревизии 0. Повтор создания с тем же `attemptId` и теми же байтами начального состояния возвращает текущую ревизию. Другие начальные данные дают `checkpoint_conflict`. При чтении снимка адаптер проверяет его SHA-256. Чтобы продвинуть попытку, процесс предъявляет ожидаемую ревизию и действующий lease с идентификатором владельца и токеном `fence`.

При восстановлении адаптер открывает ту же привязку, воспроизводит прочитанный текст из закреплённых версий файлов и сверяет хеши с историей. До обращения к транспорту он записывает состояние `sending` и намерение отправки с `requestId`. Подтверждённый ответ связывает квитанцию чтения со следующим состоянием. Если после перезапуска осталось неподтверждённое намерение, адаптер фиксирует `delivery_unknown` и признак `recovery_required` для задачи. Повторной отправки в этом состоянии нет. [Подготовка запроса](../../../../.ai/tools/worker-assignment/src/checkpoints/prepareCheckpointRequest.service.ts) · [Возобновление попытки](../../../../.ai/tools/worker-assignment/src/checkpoints/advanceAuditCheckpoint.service.ts)

Из `received` Assignment готовит пакет для независимого ревью. Он сверяет SHA-256 отчёта и соответствие `scopePins` повторно открытой привязке. Успешные чтения сверяются с путями и хешами из `readPins`. Карта содержит каждый файл из `scopePins`, фактически подтверждённые диапазоны и ссылки на квитанции этой попытки. При отсутствии таких чтений файл получает статус `unread`. Пакет публикуется в досье отдельной операцией. [Подготовка пакета](../../../../.ai/tools/worker-assignment/src/checkpoints/prepareAuditHandoff.service.ts) · [Публикация отчёта и карты](audit-report-publication.md)

## Порядок приёмки

1. **Два чтения и перезапуск.** Имитатор возвращает первый вызов, затем в ответ на результат — второй. После фиксации первой квитанции остановить процесс. В новом процессе открыть ту же попытку, повторно проверить допуск и выполнить второе чтение. Ожидаются один `attemptId`, три разных `requestId` за весь обмен, две подтверждённые квитанции и один отчёт в `received`. В журнале имитатора каждая отправка встречается один раз.
2. **Состав пакета.** Восстановить отчёт по хешу. Сопоставить пути и SHA-256 карты с `scopePins` выбранного назначения, а диапазоны с квитанциями текущей попытки. Файлы без чтений отмечены явно, пробные обращения при проверке допуска исключены. Повтор подготовки по тому же снимку и квитанциям возвращает тот же пакет.
3. **Проверить прерывание отправки.** Прервать обмен после фиксации намерения отправить второе чтение и до записи подтверждения. Новый процесс возвращает `delivery_unknown` и соответствующую причину для `recovery_required` в задаче. Подтверждённым остаётся первое чтение, счётчик повторных отправок равен нулю.
4. **Проверить целостность.** Повторить подтверждение, подменить `tool_call_id`, запросить соседний путь, изменить закреплённый файл и отозвать право чтения перед продолжением. Повтор подтверждения сохраняет одну квитанцию, соседний путь даёт `FORBIDDEN` без текста, остальные подмены или утрата допуска блокируют передачу. Ни один из этих случаев не расширяет покрытие.
5. **Проверить смену владельца.** Дать двум процессам одну ожидаемую ревизию. Ровно один может продвинуть её и получить право на отправку. После перевыдачи lease прежний владелец не может подтвердить результат. Повторное открытие после `received` возвращает сохранённый отчёт без запроса к транспорту.

## Результаты проверки

При проверке первой реализации все пять сценариев прошли на имитаторе. Сверка снимков и квитанций с журналом транспорта подтвердила продолжение той же попытки в новом процессе, воспроизводимость отчёта и карты, остановку без повторной отправки после `SIGKILL`, отказ при подмене и защиту от записи прежним владельцем. При повторном открытии `received` адаптер вернул сохранённый отчёт без обращения к транспорту.

Для воспроизведения используется временный кластер с включёнными `fsync` и `synchronous_commit`.
