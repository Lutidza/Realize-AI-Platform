# Доработка и повторная приёмка аудита статьи

**Проверено 2026-11-25 на отдельной PostgreSQL 18.6 с имитаторами аудитора и ревьюера.**

Входом служит решение по конкретной версии заключения. Оркестратор зафиксировал получателя, исходное назначение, пункты доработки и критерии их проверки. Выходом служит решение по следующей итерации в том же исполнении задачи. [Заключение и первое решение](article-audit-conclusion.md)

## Получение поручения

Участник видит свои открытые поручения во входящих. Claim закрепляет идентификатор попытки обработки поручения. До передачи следующей итерации повтор после потери ответа возвращает прежнюю попытку. Сервер определяет адресата по сохранённому решению. Он проверяет членство в проекте, разрешение на материалы, действующий план, назначение и основание. В контекст доработки передаются проверяемые пункты, прежний отчёт, заключение и ссылки на доказательства. При подготовке каждого обмена runtime повторно сверяет доступ, хеш входа и закреплённые исходники.

## Что меняется в каждой итерации

| Решение | Результат адресата | Следующая проверка |
| --- | --- | --- |
| Вернуть аудит | Аудитор проходит новую попытку, сохраняет исправленный отчёт, его карту собственных чтений и ответ с точной цитатой на каждый пункт. Версия отчёта увеличивается. | По тому же назначению независимого ревьюера создаётся следующая итерация с точными ссылками на исправленную публикацию и исходное замечание. |
| Уточнить заключение | Ревьюер получает исходный отчёт и карту тех же версий, конкретный вопрос и критерий ответа. | Ревьюер подтверждает новые чтения, уточняет обоснование и публикует следующую версию заключения. |
| Принять аудит | Решение фиксирует завершение проверки аудита. | Новое поручение не создаётся. Завершение родительской задачи определяется её политикой. |

Для каждого возвращённого пункта ревьюер сохраняет результат повторной проверки, его обоснование и связь с исходным критерием. Предметное доказательство включает цитату отчёта и квитанции этой попытки. Неподтверждённый пункт можно вернуть повторно. Оркестратор принимает аудит по действующим критериям и политике.

## Сбои, версии и права

Опубликованные отчёты, заключения и решения неизменяемы. У новой публикации есть ссылка на конкретный предшествующий результат и поручение. Одна попытка и один результат на поручение позволяют безопасно повторить обращение после обрыва. Уточнение пропускает этап публикации нового отчёта. Очередь различает итерации даже при совпадении исходных материалов. При смене основания зависимый переход требует актуального решения владельца. Повторная выдача проверяет права участника.

## Владельцы данных

| Запись | Где найти |
| --- | --- |
| Поручение, адресат и критерий проверки | `audit_acceptance.work` ссылается на решение. Во входящих исполнителя видны актуальные открытые поручения. |
| Получение и завершение работы по поручению | `audit_rework.claims` связывает поручение с попыткой. `audit_rework.completed` закрывает выдачу. Для уточнения это передача работы на новый этап ревью. |
| Исправленный отчёт и карта | Досье сохраняет новые версии артефактов под прежними идентификаторами. В `audit_dossier.revision_links` остаются ссылка на предыдущий результат, исходное решение и ответы по каждому критерию. |
| Вход очередной попытки ревью | `audit_rework.review_routes` закрепляет версии материалов и основания. Очередь выдаёт работу по ключу назначения и итерации. Квитанция сохраняется в `audit_rework.review_acknowledgements`. |
| Заключение и его предшественник | В `audit_conclusions.successors` связаны поручение и обе версии заключения. За решение по новой версии отвечает оркестратор. |

## Как проверить

Из корня проекта запустите `npm run ai:assignment:rework-pilot`. Нужны версии Node/npm из проекта, PostgreSQL с `pg_config` и право открыть приватный Unix-сокет в `/tmp`. Команда создаёт временную БД и удаляет её после прогона. [Инструкция по проверке](../../../../.ai/tools/worker-assignment/README.md#доработка-и-повторная-приёмка)

Для проверки всего пути, начиная с первой контрольной точки, выполните `npm run ai:assignment:audit-cycle`. В выводе каждый из четырёх наборов показывает число пройденных тестов. Строка `Отчёт v1 → v2; заключение v1 → v2 → v3; итог accept_audit` относится к маршруту с возвратом аудитору и последующим уточнением ревьюера. В сценарии открытого замечания отчёт доходит до v3. Идентификаторы в выводе принадлежат временной задаче прогона. [Сквозные сценарии](../../../../.ai/tools/worker-assignment/test/rework/articleRework.test.ts)

В полном прогоне прошли все четыре набора. В наборе доработки прошли 11 из 11 сценариев, включая восстановление после потери ответа очереди, конфликт двух издателей, отзыв прав перед отправкой, подмену доказательств и обновление исторического досье V1 с сохранением его материалов.
