# Просмотр тестового аудита в досье задачи

Отчёт аудитора, заключение независимого ревьюера и решение оркестратора можно посмотреть в карточке настоящей тестовой задачи. Стенд использует имитаторы исполнителей и отдельный постоянный кластер PostgreSQL. [Контракт аудита](article-audit-conclusion.md) · [Цикл доработки](article-audit-rework.md)

## Приёмка TASK-1

**26 ноября 2026 года пользователь проверил досье в браузере и принял результат. Этап закрыт.** Контрольным примером служит задача «Проверить форму создания статьи» из проекта «Пилот документации». В досье сохранены отчёт аудитора v1, заключение независимого ревьюера v1 с подтверждением четырёх критериев и решение оркестратора «Аудит принят» (`accept_audit`). [Открыть принятое досье TASK-1 на стенде :3210](http://127.0.0.1:3210/system/task-manager/3d36a148-a7c8-427a-90ae-f9e8305f5989/dossier/8a90819a-95fc-41a9-b1ec-0a45008b2a71)

Приняты сохранение трёх материалов, проверка прав доступа и просмотр из карточки задачи. На момент приёмки статус самой задачи Foundation — «На проверке» (`review`). Развитие интерфейса Task Manager и запуск аудита с реальными исполнителями относятся к следующим этапам.

## Как открывается досье

Маршрут `/system/task-manager/<taskId>/dossier/<decisionId>` закрепляет задачу и конкретное решение. На тестовом стенде откройте Task Manager, выберите проект «Пилот документации» и список «Аудит», затем нажмите название задачи «Проверить форму создания статьи». В карточке раздел «Досье аудита» ведёт к сохранённому решению. Три ссылки внутри раздела открывают отчёт аудитора, заключение ревьюера и решение оркестратора по отдельности. После входа сервер получает идентичность оркестратора из сессии Payload и проверяет право чтения решения. В одном снимке БД он сверяет задачу, заключение, версию отчёта и хеши материалов. Недоступному читателю содержимое не выдаётся.

Отчёт открывается в исходном виде. В заключении видны оценки критериев с цитатами, а в решении — исход, причина, дата и версия принятого заключения. Маршрут читает сохранённые записи при открытии страницы. Временная БД автоматических тестов продолжает обслуживать отдельные проверочные прогоны.

## Где хранится результат

PostgreSQL сохраняет задачи и материалы в `.data/audit-dossier-preview/pgdata/`. Файл `.data/audit-dossier-preview/manifest.json` указывает на последний прогон. В `runs/<taskId>.json` остаются идентификаторы ранее сохранённых прогонов. Текст материалов читается из PostgreSQL. Учётные данные тестового оркестратора находятся в локальном файле `preview-login-<orchestratorId>.json` рядом с манифестом.

Для просмотра сохраняются постоянная БД и действующая веб-служба. При штатной остановке служба удаляет временную копию исходников и каталог своей сборки. Команда с аргументом `audit` предназначена для отдельного нового прогона и создаёт новую задачу.

## Повторная проверка принятого досье

1. На существующем стенде используйте постоянную БД и манифест из `.data/audit-dossier-preview/`. Из корня проекта выполните `node .ai/tools/worker-assignment/test/dossier-preview/runDossierPreview.mjs verify`. Команда сверяет сохранённые материалы и права чтения. Поскольку `verify` проверяет последний прогон, сопоставьте выведенные `taskId` и `decisionId` с идентификаторами в ссылке на принятое досье выше.
2. Откройте ссылку на принятое досье и войдите под тестовым оркестратором. Убедитесь, что видны отчёт v1, четыре оценки ревьюера и решение «Аудит принят». Та же страница открывается через «Пилот документации» → «Аудит» → `TASK-1` → «Досье аудита».
3. Для автоматической проверки браузером на работающем стенде выполните `node scripts/runtime/audit-dossier-preview/verifyAuditDossierBrowser.controller.mjs`. Проверка охватывает вход, переход из карточки, мобильный экран, повторное открытие и отказ при чужом идентификаторе решения.

Если существующий кластер остановлен, его открывает `node .ai/tools/worker-assignment/test/dossier-preview/runDossierPreview.mjs start`. Для перезапуска веб-службы стенда используется `systemctl --user restart realize-audit-dossier-preview-web.service`.
