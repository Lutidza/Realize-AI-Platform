## От задачи до фактического запуска

Одна задача может исполняться несколько раз. Один `TaskExecution` закрепляет ревизию задачи и плана, состав участников и входные материалы. Каждый этап этого исполнения адресуется отдельно. Попытка связывает **один этап одного исполнения с одной ревизией назначения**. Повторные чтения того же аудитора принадлежат этой попытке. [Снимок исполнения](../../task-management-execution.md#32-snapshot)

| Сущность | Единица учёта и связи |
| --- | --- |
| `Task` | Задача в проекте и основном списке. По `taskId` доступны её назначения, исполнения, история и опубликованные материалы в пределах прав пользователя. |
| `TaskAssignment` | Назначение участнику конкретной задачи. Имеет стабильный ID, ревизию, роль, область работы и критерии. Для агента фиксируется отдельная ссылка на манифест поручения и его ревизию. |
| `TaskExecution` и этап | Исполнение ссылается на задачу и зафиксированный план. Этап принадлежит исполнению и связывается с назначениями из снимка плана. |
| `Attempt` | Хранит `attemptId`, ссылки на исполнение, этап, назначение и его ревизию. После передачи работы с ним связываются владелец runtime и реальные идентификаторы run/job. У одного этапа возможны разные назначения и несколько попыток. |
| Контрольная точка и квитанция чтения | Записи runtime адресуются через попытку. Одна попытка имеет несколько ревизий контрольной точки и несколько квитанций. Владельцем внутренних переходов workflow остаётся его движок. |
| `TaskEvent` | Предметное событие задачи. Для события исполнения сохраняются ссылки на этап, попытку и исходное событие владельца. |
| `TaskResult`, `TaskArtifact` и ревизии | Результат связывает попытку с конкретными версиями материалов и доказательств. Каталог хранит метаданные, версии, хеши и права. Байты файла доступны через закрытый адаптер хранения. |

В Foundation задачи хранятся в `realize_tasks`, события — в `realize_task_events`, квитанции команд — в `realize_task_operations`. Для целевой модели назначение, исполнение, этап, попытка, контрольная точка, квитанция чтения, результат и версия артефакта имеют отдельно адресуемые записи. Досье собирается по связям задачи. Эти данные могут размещаться в одной базе PostgreSQL. Внутри модуля допустимы внешние ключи. Через границу Task Manager и заменяемого runtime передаются стабильные идентификаторы и команды адаптера. [Миграция Foundation](../../../../src/migrations/20261011_162630_task_manager_foundation.ts) · [Граница модулей](../../task-management-execution.md#2-границы-модулей-и-переносимость)

При создании попытки оркестратор сверяет, что этап принадлежит указанному исполнению, а ревизия назначения входит в снимок этой же задачи и разрешена для этапа. Квитанция другого назначения или попытки не может подтвердить чтение аудитора. Если runtime выдаёт собственный ID, адаптер сохраняет соответствие с `attemptId` из claim на весь срок восстановления.

До передачи task orchestration хранит намерение исполнения и готовность этапа. При выдаче работы фиксируется попытка, а повтор команды связывается с уже выданной работой по ключу идемпотентности. После передачи job, его очередь и восстановление принадлежат исходному runtime. На стороне задачи хранятся ссылки и восстанавливаемая сводка. Безопасное продолжение сохраняет `attemptId`. Явный retry после сверки исхода создаёт новую попытку со ссылкой на предшествующую. [Очередь и передача исполнения](../../task-management-execution.md#61-readiness-и-одна-передача-исполнения)

## Что видит пользователь

| Место | Содержание на примере аудита формы |
| --- | --- |
| Приватный checkpoint | На каком вызове остановился аудитор, к какому запросу относится результат, какая доставка подтверждена и какое продолжение безопасно. Доступ проверяет runtime. |
| История задачи | Назначен аудитор, начата попытка, потребовалось восстановление, опубликован результат, назначен ревьюер, получено заключение. Запись указывает время, участника, ревизию, исполнение, этап, попытку и причинную связь. Сводка может показать последний подтверждённый диапазон с учётом прав на источник. |
| Досье | Входные и выходные материалы, версия отчёта аудитора, карта покрытия с квитанциями и отдельная версия заключения ревьюера. Пользователь видит автора, версию, назначение материала и этап. Каждая ссылка проверяется по действующим правам владельца. |

Task Manager принимает долговечные события runtime с дедупликацией, присваивает им последовательность истории задачи и обновляет сводку. Приватная переписка, полные инструкции и данные учётной записи закрыты от выдачи через историю и досье. Ревизии материалов, необходимые активной попытке, восстановлению или ревью, удерживаются согласно политике досье. ## Аудит и независимое ревью

В плане задачи «Проверить форму создания статьи» два последовательных этапа. Назначение аудитору ссылается на манифест `audit-create-article-001`, ревизия `1`. Этот ID описывает поручение рабочего слоя. Экземпляр `TaskAssignment` определяет, кому и в рамках какой задачи его выдали. Для запуска из Task Manager необходима явная связь. [Манифест аудита](../../../../.ai/templates/worker-assignment/TEMPLATE-WORKER-ASSIGNMENT-MANIFEST.md#сообщение-исполнителю)

1. Получив финальное сообщение своей попытки без открытых вызовов, оркестратор фиксирует `received`. Для публикации связывает исходный отчёт и его SHA-256 с назначением и попыткой, прикладывает карту всех 12 файлов области, квитанции, причины пропусков и ограничения. Замечание содержит правило, путь, строки и влияние. Если цитируемые строки выходят за подтверждённое покрытие, расхождение видно ревьюеру.
2. Пока обязательные материалы публикуются, действует `publishing_result`. Когда версии доступны и manifest результата долговечно зафиксирован, этап может завершиться как `succeeded`. Вход следующего этапа указывает на эту версию `TaskResult`. Повтор события публикации использует уже созданный результат и назначение.
3. Независимый frontend-ревьюер получает собственное назначение, попытку, допуск на чтение, критерии, отчёт и те же закреплённые версии исходников. Его чтения учитываются в его попытке. Заключение указывает точную версию отчёта, расхождения либо подтверждение. Оркестратор связывает заключение с результатом и принимает аудит либо возвращает конкретный пункт на доработку. Приёмка родительской задачи следует её политике. Доработка отчёта образует новую версию для ревью.

В изолированном срезе проверена цепочка от `received` до создания отдельной попытки ревью. Далее независимый ревьюер публикует версию заключения, а уполномоченный оркестратор принимает аудит или адресует доработку. [Контракт заключения и решения](article-audit-conclusion.md).
