## От задачи до фактического запуска

Одна задача может исполняться несколько раз. Один `TaskExecution` закрепляет ревизии задачи и плана, состав участников и версии входных материалов. Каждый этап этого исполнения адресуется отдельно. Попытка связывает **один этап одного исполнения с одной ревизией назначения**. Последовательные действия исполнителя в рамках этой попытки сохраняют её `attemptId`. [Снимок исполнения](../../task-management-execution.md#32-snapshot)

| Сущность | Единица учёта и связи |
| --- | --- |
| `Task` | Задача в проекте и основном списке. По `taskId` доступны её назначения, исполнения, история и опубликованные материалы в пределах прав пользователя. |
| `TaskAssignment` | Назначение участнику конкретной задачи. Имеет стабильный ID, ревизию, роль, область работы и критерии. Для агента фиксируется отдельная ссылка на манифест поручения и его ревизию. |
| `TaskExecution` и этап | Исполнение ссылается на задачу и зафиксированный план. Этап принадлежит исполнению и связывается с назначениями из снимка плана. |
| `Attempt` | Хранит `attemptId`, ссылки на исполнение, этап, назначение и его ревизию. После передачи работы с ним связываются владелец runtime и реальные идентификаторы run/job. У одного этапа возможны разные назначения и несколько попыток. |
| Контрольная точка и квитанция чтения | Записи runtime адресуются через попытку. Одна попытка имеет несколько ревизий контрольной точки и несколько квитанций. Владельцем внутренних переходов workflow остаётся его движок. |
| `TaskEvent` | Предметное событие задачи. Для события исполнения сохраняются ссылки на этап, попытку и исходное событие владельца. |
| `TaskResult`, `TaskArtifact` и ревизии | Результат связывает попытку с конкретными версиями материалов и доказательств. Каталог хранит метаданные, версии, хеши и права. Байты файла доступны через закрытый адаптер хранения. |

В Foundation задачи хранятся в `realize_tasks`, события — в `realize_task_events`, квитанции команд — в `realize_task_operations`. Для целевой модели назначение, исполнение, этап, попытка, контрольная точка, квитанция чтения, результат и версия артефакта имеют отдельно адресуемые записи. Досье собирается по связям задачи. Эти данные могут размещаться в одной базе PostgreSQL. Внутри модуля допустимы внешние ключи. Через границу Task Manager и заменяемого runtime передаются стабильные идентификаторы и команды адаптера. [Миграция Foundation](../../../../src/migrations/20261011_162630_task_manager_foundation.ts) · [Граница модулей](../../task-management-execution.md#2-границы-модулей-и-переносимость)

При создании попытки оркестратор сверяет, что этап принадлежит указанному исполнению, а ревизия назначения входит в снимок этой же задачи и разрешена для этапа. Квитанция другого назначения или попытки не может подтвердить чтение аудитора. Если runtime выдаёт собственный ID, адаптер сохраняет соответствие с `attemptId` из claim на весь срок восстановления.

До передачи task orchestration хранит намерение исполнения и готовность этапа. При выдаче работы фиксируется попытка, а повтор команды связывается с уже выданной работой по ключу идемпотентности. После передачи job, его очередь и восстановление принадлежат исходному runtime. На стороне задачи хранятся ссылки и восстанавливаемая сводка. Безопасное продолжение сохраняет `attemptId`. Явный retry после сверки исхода создаёт новую попытку со ссылкой на предшествующую. [Очередь и передача исполнения](../../task-management-execution.md#61-readiness-и-одна-передача-исполнения)

## Что видит пользователь

| Место | Какие сведения доступны и кому |
| --- | --- |
| Приватная контрольная точка | Среда исполнения хранит состояние для возобновления попытки. По нему можно определить, на каком вызове остановился исполнитель, к какому запросу относится ответ и подтверждена ли его доставка. Доступ проверяет владелец runtime. |
| История задачи | Пользователь с правом просмотра видит события назначения, начала попытки, восстановления, публикации результата и принятого решения. Запись указывает время, участника, ревизию, исполнение, этап, попытку и причинную связь с исходным событием, когда они применимы. Сводка может показать последний подтверждённый диапазон с учётом прав на источник. |
| Досье | По задаче доступны версии входных и выходных материалов, их авторы, назначение и связь с этапом и результатом. Для независимого ревью это отчёт, карта покрытия с квитанциями, заключение и решение со ссылкой на версию заключения. Владелец материала проверяет текущие права при каждом обращении. |

Task Manager принимает долговечные события runtime с дедупликацией, присваивает им последовательность истории задачи и обновляет сводку. Приватная переписка, полные инструкции и данные учётной записи закрыты от выдачи через историю и досье. Ревизии материалов, необходимые активной попытке, восстановлению или ревью, удерживаются согласно политике досье. [События адаптера](../../task-management-execution.md#4-контракт-команд-и-событий-адаптера) · [История и досье](../../task-management.md#11-история-и-досье)

## Аудит и независимое ревью

В реализованном процессе план содержит отдельные назначения для аудитора и независимого ревьюера. Каждое закреплено за участником и этапом в конкретной ревизии плана. Для агентного запуска Task Manager передаёт `executionId`, `stageId`, `taskAssignmentId` и `assignmentRevision` вместе с идентификаторами проекта, задачи и ревизиями задачи и плана. Контрольная точка связывает эти данные с отдельной парой `id` и `revision` манифеста рабочего слоя. [Схема плана](../../../../packages/payload-task-manager/src/server/audit-review/planSchema.sql) · [Связь назначения с контрольной точкой](../../../../.ai/tools/worker-assignment/src/checkpoints/createAuditCheckpointState.service.ts) · [Формат манифеста](../../../../.ai/templates/worker-assignment/TEMPLATE-WORKER-ASSIGNMENT-MANIFEST.md#сообщение-исполнителю)

1. **Получение отчёта.** Когда пришло финальное сообщение попытки и нет открытых вызовов, runtime фиксирует `received`. Для публикации Assignment связывает отчёт и его SHA-256 с попыткой и назначением. Карта включает каждый путь и SHA-256 из `scopePins` выбранного назначения. Подтверждённые диапазоны выводятся из квитанций этой попытки, файлы без чтений отмечаются `unread`. В отчёте аудитор объясняет пропуски и ограничения, а для замечаний по коду приводит правило, путь, строки и последствия. Ревьюер может сопоставить каждую ссылку с покрытием. [Контрольные точки и чтения](checkpoints-and-reads.md)
2. **Публикация результата.** В целевой модели этап находится в `publishing_result`, пока обязательные материалы публикуются. Он может перейти в `succeeded`, когда доступны их версии и сохранён манифест результата с хешами. Вход следующего этапа ссылается на эту версию `TaskResult`. В реализованном процессе точный повтор публикации возвращает прежний результат по `(origin, attempt_id)`. Доставка использует назначение ревьюера из плана. [Публикация отчёта и карты](audit-report-publication.md) · [Ревизии и результаты этапа](../../task-management-execution.md#152-ревизии-результаты-и-evidence)
3. **Независимое ревью и решение.** Ревьюер с действующим доступом получает работу по своему назначению, открывает закреплённые версии отчёта, карты и исходников. Его чтения подтверждаются квитанциями собственной попытки. Заключение связывает оценки по критериям с проверенной версией отчёта. Оркестратор принимает отчёт, возвращает конкретные пункты аудитору или запрашивает уточнение у ревьюера. В решении он указывает точную версию заключения. Возврат аудитору ведёт к новой версии отчёта, уточнение ревьюера использует прежнюю версию. Завершение родительской задачи определяется её политикой. [Критерии заключения и решение](review-conclusion.md) · [Доработка и повторная приёмка](review-rework.md)

На изолированной PostgreSQL ранее проверили путь от `received` до выдачи уже назначенному ревьюеру отдельной попытки. При потере ответа тот же участник с тем же `consumerId` получает сохранённый `reviewAttemptId`. [Выдача и повторное получение работы](../../../../.ai/tools/worker-assignment/src/review-queue/PostgresReview.repository.ts)
