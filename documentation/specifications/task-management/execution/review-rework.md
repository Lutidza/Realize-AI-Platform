# Доработка отчёта аудитора и повторная приёмка

**Статус.** Первую реализацию проверили 2026-11-25 на отдельной PostgreSQL 18.6 с имитаторами аудитора и ревьюера.

Входом служит решение по конкретной версии заключения. Оркестратор зафиксировал получателя, исходное назначение, пункты доработки и критерии их проверки. Выходом служит решение по следующей итерации в том же исполнении задачи. [Заключение и первое решение](review-conclusion.md)

## Получение поручения

Участник видит свои открытые поручения во входящих. При получении поручения (`claim`) сервер определяет адресата по сохранённому решению и связывает `workId` с одной попыткой. Пока основание действительно, повтор после потери ответа возвращает тот же `attemptId`. Сервер проверяет членство в проекте, доступ к материалам, план и назначение. В контекст доработки входят возвращённые пункты, прежний отчёт, заключение и ссылки на доказательства. При подготовке каждого обмена runtime повторно сверяет доступ, хеш входа и закреплённые исходники. [Выдача поручения](../../../../packages/payload-task-manager/src/server/audit-review/rework/reworkClaim.repository.ts)

## Что меняется в каждой итерации

| Решение | Результат адресата | Следующая проверка |
| --- | --- | --- |
| Вернуть отчёт аудитору (`return_audit`) | Аудитор в новой попытке публикует исправленный отчёт, карту собственных чтений тех же версий исходников и ответ на каждый возвращённый пункт. Ответ содержит точную цитату исправленного отчёта. Версия отчёта увеличивается. | По тому же назначению независимого ревьюера начинается следующая итерация. Она ссылается на исправленную публикацию и заключение, послужившее основанием для возврата. |
| Уточнить заключение (`clarify_reviewer`) | Ревьюер получает вопрос и критерий ответа. Для уточнения используются прежние версии отчёта и карты. | Ревьюер получает квитанции чтений своей новой попытки, уточняет обоснование и публикует следующую версию заключения. |
| Принять отчёт (`accept_audit`) | Решение завершает проверку отчёта. | Нового поручения по этому решению нет. Завершение родительской задачи определяется её политикой. |

В повторном заключении `resolutions` содержит по одному ответу на каждый пункт поручения. Идентификатор критерия и `acceptanceTest` должны совпадать с решением. Ревьюер указывает исход `resolved` или `still_open` и обосновывает его. Оценка по тому же критерию содержит цитату проверяемого отчёта и квитанции текущей попытки. Исход `still_open` соответствует оценке `discrepancy` и позволяет оркестратору вернуть пункт ещё раз. Для уточнения ревьюер дополняет обоснование оценки или объяснение ответа. Оркестратор принимает отчёт по действующим критериям и политике. [Проверка ответов аудитора](../../../../packages/payload-task-manager/src/server/audit-review/rework/auditRevisionResponses.validator.ts) · [Проверка повторного заключения](../../../../packages/payload-task-manager/src/server/audit-review/conclusions/validateReviewResolutions.validator.ts)

## Сбои, версии и права

Опубликованные отчёты, заключения и решения неизменяемы. Новая публикация ссылается на предшествующую версию и поручение. Точный повтор публикации исправленного отчёта возвращает сохранённый результат при действующем доступе. Если для того же поручения изменились материалы или ответы, сервер возвращает конфликт. Смена основания останавливает зависимый переход до подтверждения актуального основания. [Публикация исправленной версии](../../../../packages/payload-task-manager/src/server/audit-review/rework/auditRevision.repository.ts)

Очередь различает итерации одного назначения даже при совпадении материалов. После потери ответа диспетчер сначала запрашивает квитанцию по ключу выдачи. Если очередь подтверждает отсутствие работы, диспетчер отправляет её. Если результат запроса неизвестен, выдача ожидает повтора. Для сохранённой квитанции диспетчер сверяет материалы и подтверждает доставку. Повторная выдача проверяет текущие права участника. [Восстановление доставки](../../../../.ai/tools/worker-assignment/src/review-queue/reconcileReviewDelivery.service.ts)

## Владельцы данных

| Запись | Где найти |
| --- | --- |
| Поручение, адресат и критерий проверки | `audit_acceptance.work` ссылается на решение. Во входящих исполнителя видны актуальные открытые поручения. |
| Получение и завершение работы по поручению | `audit_rework.claims` связывает поручение с попыткой. `audit_rework.completed` закрывает выдачу. Для уточнения это передача работы на новый этап ревью. |
| Исправленный отчёт и карта | Досье сохраняет новые версии артефактов под прежними идентификаторами. В `audit_dossier.revision_links` остаются ссылка на предыдущий результат, исходное решение и ответы по каждому критерию. |
| Вход очередной попытки ревью | `audit_rework.review_routes` закрепляет версии материалов и основания. Очередь выдаёт работу по ключу назначения и итерации. Квитанция сохраняется в `audit_rework.review_acknowledgements`. |
| Заключение и его предшественник | В `audit_conclusions.successors` связаны поручение и обе версии заключения. За решение по новой версии отвечает оркестратор. |

## Как проверить

Из корня проекта запустите `npm run check:assignment:postgres -- rework`. Нужны версии Node/npm из проекта, PostgreSQL с `pg_config` и право открыть приватный Unix-сокет в `/tmp`. Команда создаёт временную БД и удаляет её после прогона. [Инструкция по проверке](../../../../.ai/tools/worker-assignment/README.md#доработка-и-повторная-приёмка)

Для проверки всего пути от первой контрольной точки до решения оркестратора выполните `npm run ai:assignment:audit-cycle`. Сквозные сценарии охватывают возврат аудитору, уточнение у ревьюера, повторный возврат открытого замечания и окончательную приёмку. Проверки сбоев охватывают потерю ответа очереди, конкурирующие публикации, отзыв прав перед отправкой, подмену доказательств и сохранность материалов прежней версии досье. [Проверки цикла доработки](../../../../.ai/tools/worker-assignment/test/rework/)
