## Хранение одной попытки

Рабочий слой связывает поручение с 18 закреплёнными путями и проверяет полномочия перед каждой отправкой. Имитатор подставляет ответы транспорта и ведёт журнал запросов. Приватная схема `audit_checkpoint` создаётся только в базе `realize_checkpoint_pilot`. [Допуск запросов](../../../architecture/assignment-adapter/openai-chat-completions.md) · [Схема хранения](../../../../.ai/tools/worker-assignment/src/checkpoints/checkpointSchema.sql)

| Таблица | Что в ней сохраняется |
| --- | --- |
| `attempts` | ID попытки, текущая ревизия, владелец, срок lease по времени БД и монотонный fencing token. Только действующий владелец может продвинуть ожидаемую ревизию. |
| `revisions` | Неизменяемые версии состояния с SHA-256. Снимок закрепляет задачу, исполнение, этап, ревизию назначения, контекст и политику. Состояние сохраняет ожидающий вызов или намерение отправить точный запрос, историю подтверждений, а в `received` — текст отчёта и его SHA-256. |
| `receipts` | Неизменяемая квитанция привязана к попытке, вызову, запросу продолжения и следующей ревизии. Успех содержит путь, SHA-256, фактически переданные строки и признак усечения. При отказе сохраняется код. Квитанция и следующая ревизия фиксируются одной транзакцией. |

Прочитанный текст восстанавливается из закрытой копии исходников через закреплённый reader. При возобновлении адаптер сверяет файл и хеш результата, заново проверяет права и всю историю сообщений. Для подготовки пакета ревьюера запись истории связывает квитанцию с ID запроса подтверждения и SHA-256 операции чтения. Пакет включает отчёт, его хеш, карту покрытия и ссылки на квитанции. [Подготовка запроса](../../../../.ai/tools/worker-assignment/src/checkpoints/prepareCheckpointRequest.service.ts) · [Подготовка пакета для ревью](../../../../.ai/tools/worker-assignment/src/checkpoints/prepareAuditHandoff.service.ts)

В проверке хранилища идентификаторы Task Manager задаёт сценарий. Срез заканчивается подготовкой пакета для ревью. Следующий изолированный срез сохраняет реальную задачу Foundation, публикует этот пакет в досье и проверяет выдачу работы ревьюеру. [Публикация и передача результата](article-audit-publication.md)

## Порядок приёмки

1. **Два чтения и перезапуск.** Имитатор возвращает первый вызов, затем в ответ на результат — второй. После фиксации первой квитанции остановить процесс. В новом процессе открыть ту же попытку, повторно проверить допуск и выполнить второе чтение. Ожидаются один `attemptId`, три разных `requestId` за весь обмен, две подтверждённые квитанции и один отчёт в `received`. В журнале имитатора каждая отправка встречается один раз.
2. **Проверить состав передачи.** Восстановить из хранилища исходный отчёт по хешу и карту всех двенадцати файлов. У показанных диапазонов есть ссылки на квитанции именно этой попытки. Файлы без чтения отмечены явно, пробные обращения допуска исключены. Повтор подготовки возвращает те же версии, пригодные для будущей передачи независимому ревьюеру.
3. **Проверить прерывание отправки.** Прервать обмен после фиксации намерения отправить второе чтение и до записи подтверждения. Новый процесс возвращает `delivery_unknown` и соответствующую причину для `recovery_required` в задаче. Подтверждённым остаётся первое чтение, счётчик повторных отправок равен нулю.
4. **Проверить целостность.** Повторить подтверждение, подменить `tool_call_id`, запросить соседний путь, изменить закреплённый файл и отозвать право чтения перед продолжением. Повтор подтверждения сохраняет одну квитанцию, соседний путь даёт `FORBIDDEN` без текста, остальные подмены или утрата допуска блокируют передачу. Ни один из этих случаев не расширяет покрытие.
5. **Проверить смену владельца.** Дать двум процессам одну ожидаемую ревизию. Ровно один может продвинуть её и получить право на отправку. После перевыдачи lease прежний владелец не может подтвердить результат. Повторное открытие после `received` возвращает сохранённый отчёт без запроса к транспорту.

## Результаты проверки

| Сценарий | Наблюдаемый результат на PostgreSQL 18.6 |
| --- | --- |
| Продолжение из нового процесса | Одна попытка, три разных `requestId`, две подтверждённые квитанции и один отчёт в `received`. Каждая отправка встречается в журнале один раз. |
| Материалы ревью | Из БД восстановлен отчёт с тем же SHA-256. Из 12 файлов у формы подтверждены строки 20–39 и 60–79 одного файла. У остальных 11 стоит `unread`. |
| Прерывание отправки | После `SIGKILL` состояние указывает `delivery_unknown` и причину для `recovery_required`. Первая квитанция сохранилась. Повторных отправок при восстановлении — 0. |
| Целостность | Точное повторное подтверждение сохранило одну квитанцию. Соседний путь получил `FORBIDDEN` без текста. Подмена вызова, изменение файла и отзыв права остановили передачу. |
| Смена владельца | Два процесса конкурировали за одну ревизию. Право получил один, прежний token после перевыдачи lease получил отказ при подтверждении. Повторное открытие `received` вернуло исходный отчёт без отправки. |

Приёмка сравнивает записи БД с журналом локального транспорта. Временный кластер работает с включёнными `fsync` и `synchronous_commit`.
