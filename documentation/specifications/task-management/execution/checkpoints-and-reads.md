# Контрольные точки и подтверждённые чтения

**Статус.** Согласованный целевой контракт Task Manager от 2026-11-25. Состояние попытки сохраняет среда исполнения Realize через свой адаптер хранения. Стороне задачи принадлежат ссылки, предметные события и опубликованные материалы. Обмен одного чтения реализован в памяти. Два последовательных чтения и восстановление из другого процесса проверены на отдельной PostgreSQL. ## Что нужно для продолжения попытки

Контрольная точка отвечает на вопрос «какое действие можно выполнить после остановки процесса?». Ревизии образуют упорядоченную цепочку внутри одного `attemptId`. Подтверждённые квитанции сохраняются с собственными идентификаторами. Накопленное покрытие можно заново построить из них.

Существующий checkpoint сегмента `AIRun` сохраняет в Payload текущий шаг workflow и данные для перехода к следующему сегменту. Этим переходом управляет движок workflow. Контрольная точка попытки аудитора фиксирует обмен внутри этапа, включая ожидающий вызов и подтверждение конкретного чтения. При исполнении через `AIRun` попытка ссылается на него. Завершение чтения само по себе не выдаёт следующий этап задачи. [Исполнение workflow сегментами](../../realize-ai-commerce/v1.0/01-architecture/10-ai-codex-layer-integration.md#108-исполнение-workflow-сегментами)

| Часть записи | Что сохраняет runtime |
| --- | --- |
| Принадлежность | Версию формата, `attemptId`, ссылки на проект, задачу, `TaskExecution`, этап и ревизию `TaskAssignment`, идентификаторы исполняющего адаптера и run при наличии. |
| Основание допуска | Ссылку на зафиксированный снимок исполнения, ревизию манифеста поручения, `contextId`, `lockSha256`, исполнителя, модель и ревизию политики. Полномочия на очередную отправку проверяются заново. |
| Порядок изменений | Ревизию контрольной точки, предшествующую ревизию, состояние обмена и время фиксации. Запись проверяет ожидаемую ревизию и действующий fencing token владельца попытки. |
| Ожидающий вызов | ID исходного запроса, точный `tool_call_id`, имя инструмента, проверенные аргументы и их хеш, ожидаемый SHA-256 файла, состояние операции и ссылку на подготовленный результат или код отказа. |
| Доставка и завершение | ID запроса продолжения, намерение отправки, корреляцию подтверждения транспорта, ссылки на квитанции. При завершении — неизменяемую ссылку на полученный отчёт, его хеш и состояние публикации. |

Для восстановления точной последовательности сообщений runtime удерживает закрытые версии необходимых данных и их хеши. Если содержимое разрешено восстановить из закреплённого источника, владелец проверяет полученные байты по хешу перед отправкой. При утрате исходных данных или допуска продолжение блокируется с причиной. Секреты доступа в checkpoint не сохраняются. Доступ к записям и сроки удержания проверяются у владельца. ## Последовательные чтения в одной попытке

1. Оркестратор принимает ответ только для ожидаемого запроса своей попытки. В каждый момент допускается один открытый вызов `repo_read_file`. Для пары `(attemptId, tool_call_id)` фиксируются исходный запрос и аргументы. Повтор того же события использует прежнюю запись. Совпадение ID при других аргументах или источнике блокирует обмен.
2. Обработчик сверяет путь и SHA-256 с привязкой. Для успешного чтения сохраняет фактически выданные начальную и конечную строки включительно и признак усечения. Допуск охватывает шесть источников назначения и двенадцать файлов аудита. Отчёт о покрытии относится к этим двенадцати файлам. Проверочные пробы адаптера и чтения ревьюера учитываются отдельно.
3. Для продолжения выделяется новый `requestId`. Оркестратор проверяет права, закреплённую версию файла, политику, соответствие сообщения `tool` открытому вызову и допуск `AdapterAccessEvidenceV1` к окончательному запросу. До обращения к транспорту runtime долговечно фиксирует намерение отправить именно этот запрос. Сетевой обмен проходит вне транзакции хранения.
4. Когда транспорт возвращает соответствующий ответ на продолжение, runtime одной транзакцией подтверждает доставку предыдущего результата, закрывает его вызов и сохраняет следующий вызов либо финальный отчёт. Квитанция успешного чтения входит в покрытие только после такого подтверждения. Для `FORBIDDEN` сохраняется исход без диапазона строк. Ошибка привязки или подмена ID блокирует передачу.

**Как считать покрытие.** Группировка идёт по паре «путь и SHA-256 всего файла». Пересекающиеся и соседние диапазоны объединяются для показа, исходные квитанции сохраняются. Например, строки 20–39, 35–48 и 60–64 одной версии дают **20–48 и 60–64**. Строки 49–59 остаются пробелом. Другая версия того же пути имеет отдельное покрытие. Квитанция подтверждает доставку строк, а достаточность прочитанного для выводов оценивает независимый ревьюер.

## Восстановление

| Где произошла остановка | Что разрешено после рестарта |
| --- | --- |
| Вызов сохранён, намерения отправки ещё нет | Открыть ту же попытку, получить право записи, сверить снимок и текущие права. Продолжить от последней ревизии. |
| Намерение отправки сохранено, подтверждения нет | Установить `delivery_unknown`, сверить исход по идентификатору запроса у владельца транспорта. Пока нет достоверного исхода, задача показывает `recovery_required`, повторная отправка заблокирована. Ранее подтверждённое покрытие сохраняется. |
| Ответ с очередным вызовом уже зафиксирован | Восстановить именно этот открытый вызов. Повтор подтверждения оставляет одну квитанцию. Устаревшая ревизия или прежний владелец после перевыдачи lease не могут продвинуть попытку. |
| Финальный отчёт принят, публикация прервалась | Из `received` продолжить идемпотентную публикацию сохранённого отчёта и доказательств. Этап ревью получает ссылку на долговечную версию результата. |

При безопасном возобновлении сохраняется `attemptId`. Явный повтор с новым `attemptId` разрешается после сверки исхода предыдущей попытки. Квитанции сохраняют принадлежность исходной попытке.
