## 1. Назначение и результат

Task manager — рабочая среда Payload Admin для постановки, планирования,
исполнения и контроля задач людьми и ИИ-агентами. Пользователь управляет
не только списком работ, но и тем, кто, по какому процессу, с каким контекстом
и в каком порядке выполняет задачу, где результат и кто его проверил.

Подтверждённые требования пользователя:

- Интерфейс и функциональность максимально приближены к ClickUp.
- В задаче есть постановщик, исполнитель, тестировщик и наблюдатель.
- На любую роль можно назначить человека, агента или нескольких агентов.
- Задача связывается с workflow, ролями ИИ, профилями, режимами и связанными настройками.
- Нужна глубокая интеграция с админским ИИ-ассистентом и существующим AI-функционалом.
- Во время выполнения ведутся история и материалы задачи по структуре приложенного скриншота.
- Управление работой ИИ, очередями и результатами — основная функция продукта.
- Создаются отдельные проекты со своими задачами, участниками и настройками.
- Задачи связываются с диалогами, в которых их обсуждали и решали.
- Поддерживаются связанные задачи и направленные зависимости между задачами.
- Работа передаётся между исполнителями и делегируется соисполнителям с сохранением контекста и истории.
- Сохраняется требование переносимой установки в совместимый Payload-проект.
- Порядок: **ТЗ → референсы → реализация → внедрение**.
- Task Manager становится постоянным местом ведения задач людьми и ИИ;
  локальные досье в корне проекта выводятся из рабочего процесса после
  проверенного переноса и переключения инструментов.
- Задачи разработки тесно связаны с коммитами, PR, проверками, документацией
  и выпусками платформы; ручная ссылка не подтверждает действие в Git.

В сообщении «постановщик» указан дважды. До уточнения это одна роль.
Отдельная роль ревьюера/приёмщика вынесена на обсуждение; сам этап проверки
и принятия результата необходим независимо от названия роли.

Редакция 0.2 заменяет прежнее предложение обычного task manager с необязательным
AI. Один исполнитель, один уровень подзадач, только List/Kanban и отсутствие
workflow/очередей больше не являются границами целевого продукта.

## 2. Измеримый результат и границы поставки

Пользователь из диалога или интерфейса создаёт задачу, назначает людей/агентов
на разные роли, выбирает процесс и материалы. Система проверяет готовность,
выстраивает очередь, выполняет допустимые шаги, запрашивает недостающее решение,
передаёт результат тестировщику и сохраняет доказательства. После закрытия
браузера работа продолжается; после сбоя её состояние восстанавливается.

Успешный ответ модели не равен завершённой задаче. Принятие связывается с
конкретной версией результата, критериями и проверками. Публикация и release
имеют свои условия; task manager показывает и вызывает их через владельца.

Форма поставки предлагается прежняя: npm-пакет с Payload-плагином плюс
версионированный адаптер AI runtime. В Realize интеграция с существующим
ассистентом обязательна для приёмки. Установка без AI-адаптера допустима только
как явно ограниченный режим; её нельзя назвать полной поставкой этого продукта.
Архитектура и матрица совместимости — в технической части ТЗ.

## 4. Термины и уровни ответственности

| Термин                    | Значение                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------ |
| Workspace / Folder / List | Рабочая среда, необязательные папки и контейнер задач                                            |
| Project                   | Самостоятельный проект со своими задачами, участниками, настройками, доступом и жизненным циклом |
| Представление             | Способ показать одни данные: List, Board, Calendar и другие                                      |
| Task                      | Цель, контекст, участники, зависимости, критерии и принятый результат                            |
| Роль задачи               | Ответственность: постановщик, исполнитель, тестировщик, наблюдатель                              |
| Соисполнитель             | Участник исполнения с отдельным назначением, частью работы и собственным результатом             |
| Участник                  | Адресуемый человек, агент или команда                                                            |
| Агент                     | Устойчивая идентичность AI-участника с настройками и доступными возможностями                    |
| Профиль                   | Версионированная конфигурация поведения; профиль не является агентом или процессом               |
| Роль ИИ                   | Инструкции и bindings из AI-layer; не роль доступа и не роль в задаче                            |
| Режим исполнения          | Политика запуска, автономности, лимитов и контрольных точек                                      |
| Workflow                  | Версионированное определение шагов и переходов                                                   |
| TaskExecution             | Одно исполнение конкретной версии задачи и плана                                                 |
| Attempt                   | Попытка этапа, связанная с реальным run/job исходного runtime                                    |
| Артефакт                  | Версия материала/результата с авторством, происхождением и hash                                  |
| Приёмка                   | Решение о конкретной версии результата, подтверждённое критериями и evidence                     |

Проект — отдельная сущность со стабильным ID. Предлагаемая иерархия:
Workspace → Project → необязательные Folder/Subfolder →
List → Task → Subtask. Проект является явным дополнением к ориентиру ClickUp,
с собственным жизненным циклом. Промежуточного уровня Space («Область») нет.
Workspace/Project не означают автоматически отдельного SaaS-tenant:
границы host/tenant описываются явно.

Workspace — рабочая среда организации или команды; Project — самостоятельная
цель с участниками и собственными списками. «Список задач» (List) — контейнер с собственным ID, а «Список» в панели
представлений — способ отображения задач выбранного контейнера.
Чеклисты находятся внутри задачи или подзадачи и не являются уровнем контейнеров.

Основа проверена по официальной документации ClickUp 2026-09-18:
[иерархия](https://help.clickup.com/hc/en-us/articles/13856392825367-Intro-to-the-Hierarchy),
[организация проектов](https://help.clickup.com/hc/en-us/articles/9703037723159-Organize-your-Hierarchy-for-project-management),
[подзадачи](https://help.clickup.com/hc/en-us/articles/29665922829335-Work-with-subtasks-from-tasks),
[чеклисты](https://help.clickup.com/hc/en-us/articles/6309942197783-Use-task-checklists).
ClickUp организует проекты папками и списками; отдельный уровень Project —
сознательное дополнение Realize, сохраняющее ранее заданные требования проекта.

### 4.1. Проекты и принадлежность задач

В разделе «Проекты» доступны создание, поиск, фильтрация, обзор, настройки,
архивирование и восстановление. У проекта есть название, описание, ключ/ID,
руководитель, участники/команды/агенты, состояние и сроки, timezone, статусы,
поля, bindings и правила исполнения по умолчанию. Состояние проекта отличается
от статуса его отдельных задач и не меняет их массово без явной операции.

У каждой задачи ровно один основной `projectId`; её основной List, папка и
родительская задача принадлежат тому же проекту. При создании проекта предлагается
создавать List «Задачи», чтобы пользователь мог сразу работать. «Мои задачи»
и общие views показывают доступные задачи разных проектов с обозначением проекта.

В интерактивном срезе 0.7 у задачи обязателен `listId`; List принадлежит её Project.
Подзадача наследует основной List родителя. Перенос родителя с потомками в другой
List отклоняется до появления отдельной атомарной операции переноса ветки.
Workspace/Folder вычисляются по связям контейнеров, не копируются в Task.

Доступ проекта ограничивает дочерние списки, задачи и материалы. Членство
в одном проекте не открывает другой; общие ограничения host/Workspace сохраняются.
Проект не получает отдельную копию каталога профилей или новое provider-подключение
автоматически: настройки ссылаются на существующие доступные ресурсы.

Перенос задачи в другой проект — отдельная операция с проверкой участников,
доступа, статусов, полей, bindings, подзадач, диалогов и зависимостей. Сохраняются
устойчивый ID и история. Активное исполнение сначала завершается либо подтверждённо
останавливается; его snapshot и авторство не переписываются. Межпроектная связь
не переносит задачу и не создаёт её копию. Архив проекта с активными работами
требует того же согласованного завершения/остановки; восстановление не запускает очередь.

## 6. Участники, роли и полномочия

| Роль задачи                 | Ответственность                                                                                       | Люди/агенты                                 |
| --------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| Постановщик                 | Цель, контекст, scope, критерии и ответы на уточнения; назначение приёмки                             | Один или несколько, включая агентов         |
| Исполнитель / соисполнитель | План, своя часть работы, артефакты, отчёт и передача результата; ведущий координирует общий результат | Один или несколько, включая команды агентов |
| Тестировщик                 | Проверки, evidence, дефекты, повторная проверка и заключение                                          | Один или несколько людей/агентов            |
| Наблюдатель                 | Получение событий, просмотр разрешённых результатов; для агента — анализ/сигналы по заданной политике | Один или несколько людей/агентов            |
| Ревьюер/приёмщик            | Если роль согласована — отдельная ответственность за review/принятие                                  | Дополнительная роль на обсуждении           |

`createdBy` — неизменяемый автор создания. Он не меняется при переназначении
постановщика. `initiatedBy`, действующий `actor` и `delegatedBy` различаются
в истории: действие агента не записывается как будто его вручную сделал человек.

Любая роль принимает массив участников. Команда может быть человеческой,
агентной или смешанной; при запуске состав раскрывается в зафиксированные
назначения. Изменение команды не меняет уже выполняемую попытку.

Для нескольких участников задаются стратегия исполнения и правило результата:
последовательно, независимо параллельно, распределение по подзадачам; завершение
всех обязательных работ, решение ведущего или согласованный quorum.
Предлагаемый default — отдельные задания, завершение всех обязательных;
неявная гонка «кто первым ответил» недопустима.

Агент-наблюдатель не получает write-доступ только из назначения. Его подписка
имеет ограниченный перечень событий, частоту/объём анализа и права на сигналы;
собственное сообщение не запускает бесконечный цикл наблюдения.

Права модуля отделяются от ролей задачи: администратор, руководитель проекта,
участник, читатель/гость. Scope назначения не расширяет доступ к чужим проектам,
секретам, файлам, репозиториям и deploy. Гость/внешний клиент допускается только
в явно расшаренную область; multi-tenant SaaS требует отдельного host-контракта.
Окончательная ACL-матрица формируется до референсов.

Приёмку может выполнять назначенный агент, если это разрешено политикой
задачи и операции. Это не заменяет обязательное человеческое подтверждение
Data/Code/release, если действующий host-контракт требует именно его.
Независимый reviewer проверяет другую попытку/результат; собственный отчёт
исполнителя не является независимой проверкой.

Принятие — отдельное полномочие выбранного участника или группы, а не обязательно
пятая роль. Если ревьюер не вводится, предлагается явно выбирать принимающего
из постановщиков с нужными правами. План до запуска содержит принимающего и
правило решения; отсутствие обязательного назначения даёт объяснимый блокер.
При последующей недоступности принимающего результат сохраняется и ожидает
разрешённого переназначения, но автоматически принятым не становится.

### 6.1. Передача, соисполнение и делегирование

| Действие                                | Что меняется                                                                       | Что сохраняется                                                                                  |
| --------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Передать задачу/назначение              | Исполнитель всей работы либо выбранного задания заменяется после handoff           | ID задачи, цель, история, результаты и связь со старым назначением                               |
| Добавить соисполнителя                  | Создаётся отдельное назначение с миссией, scope, сроком и результатом              | Действующие назначения; завершение соисполнителя не закрывает всю задачу                         |
| Делегировать часть работы               | Исполнитель передаёт ограниченный участок человеку/агенту/команде                  | Ответственность делегирующего за объединение результатов, если явно не оформлена полная передача |
| Делегировать в подзадачу                | Создаётся отдельная задача со своими назначениями и критериями                     | Parent/child, происхождение и условия возврата результата                                        |
| Вернуть результат / запросить доработку | Принимается конкретная версия результата либо создаётся связанный цикл исправлений | Предыдущие attempts, evidence и авторство                                                        |

Соисполнение — разновидность назначения исполнителя, а не скрытая административная
роль. Для нескольких исполнителей явно выбирается ведущий/агрегатор и правило
готовности общего результата. Доступны человек → человек, человек → агент,
агент → человек и агент → агент в границах разрешённой делегации.

Передача содержит отправителя/получателя, причину, остаток работы, актуальные
материалы и их версии, выполненные проверки, блокеры, критерии и следующий шаг.
Получатель подтверждает приём задания либо отклоняет его с причиной. Для агента
приём может быть автоматическим после проверки назначения/готовности по политике;
назначение не означает, что он уже начал работу. До завершения передачи прежнее
назначение не исчезает; отказ не оставляет задачу без ответственного.

У работающего агента нельзя просто заменить имя исполнителя: сначала выясняется
состояние старой попытки, фиксируется результат/безопасная остановка и передаются
ресурсы. История показывает, кто кому что передал, что принято и что осталось.
Дальнейшая передача ограничивается явной политикой, scope и общим budget;
делегирование работы само по себе не выдаёт новые полномочия.

## 7. Данные и правила целостности

| Сущность                       | Обязательные сведения и связи                                                                                                                                     |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace/Folder/List          | Идентификатор, parent, ACL, настройки, timezone, архив; наследование без циклов                                                                                   |
| Project                        | Устойчивый ID, Workspace, название/ключ, руководитель, членство, состояние, настройки и архив                                                                     |
| Task                           | ID/revision, обязательный projectId и основной List, parent, title/type/description, status, priority, даты, tags/fields, участники, критерии, зависимости, архив |
| Participant/Agent/Team         | Тип, устойчивый ID, отображение, доступность; для агента — ссылки на provider/profile и полномочия делегации                                                      |
| TaskAssignment                 | task, role, participant, ведущий/соисполнитель, миссия/scope, порядок/группа, профиль/режим, revision и автор назначения                                          |
| TaskHandoff                    | Предыдущее/новое назначения, вид передачи, инициатор/получатель, состояние приёма, причина и manifest контекста/результатов                                       |
| TaskConversationLink           | Task/Conversation, назначение связи, связанные message/run IDs, автор/время, доступная проекция и история привязки                                                |
| TaskRelation                   | Тип связи, обе задачи, направление/условие для зависимости, версия графа и происхождение                                                                          |
| TaskBinding                    | Версии workflow/profile/AI role/skill/check/capability и execution policy                                                                                         |
| TaskExecution/Stage/Attempt    | Снимок задачи, назначения, зависимости, ресурсы, фактические run/job, состояния и результаты                                                                      |
| TaskArtifact/Revision          | Категория, имя, MIME, размер, hash, storage reference, автор, execution/stage/attempt, retention                                                                  |
| TaskEvent/Comment/Notification | Авторство, последовательность, причинность, ACL, ссылки на результат/запуск                                                                                       |
| Acceptance                     | task/result revisions, критерии/check receipts, verdict, принимающий и время                                                                                      |

Имена — логический контракт; slugs и DTO определяются на этапе реализации.
Все пользовательские пути записи, включая штатный REST/GraphQL и публичные
сервисы, обеспечивают одни инварианты. Обходящий их путь закрывается.

Предлагаемые правила:

- У задачи один основной List. Связь с дополнительными Lists — представление
  одной задачи, а не копии; статусы и ACL разрешаются по основной принадлежности
  и projectId. Размещение в view другого проекта не меняет владение или доступ.
- Подзадачи имеют собственные назначения, execution и результат. Глубина
  ограничена явно проверяемым параметром; для первой инженерной поставки — до 7 уровней.
  Смена parent не создаёт цикл и не переносит данные в недоступную область.
- Срок может быть датой либо датой со временем. Date-only использует timezone
  области, timestamp хранится в UTC. Пересчёт зависимых дат — отдельная настройка
  с предпросмотром; он не запускает агентов сам по себе.
- Стабильный ID статуса отделён от названия. Удаление используемого статуса
  требует замены; перенос между Lists показывает mapping статусов и полей.
- Для изменения используется expectedRevision. Конфликт сохраняет ввод и
  объясняет различия; массовые операции сообщают результат по каждому объекту.
- Архив доступен для чтения по тем же правам, скрыт из активного backlog.
  Архивирование активной задачи сначала требует завершить/остановить исполнение.
  Восстановление не запускает работу автоматически.
- Закрытие родителя учитывает обязательные дочерние результаты. Исключение
  фиксируется отдельным решением, не маскируется как успешное выполнение.
- Зависимость на принятую версию результата сохраняет её ID/hash. Изменение
  результата делает зависимые планы требующими проверки, а не тихо актуальными.

### 7.1. Связанные задачи и зависимости

| Отношение            | Поведение                                                                              |
| -------------------- | -------------------------------------------------------------------------------------- |
| Связана с            | Симметричная смысловая связь без влияния на очередь или статус; допускает циклы связей |
| Зависит от           | Направленная зависимость: запуск этапа/задачи ждёт указанное условие по другой задаче  |
| Блокирует            | Обратное отображение той же зависимости; не вторая независимая запись                  |
| Родитель / подзадача | Структура декомпозиции; влияние на приёмку родителя задаётся правилами плана           |

Связи создаются/удаляются из карточки и ассистента с записью автора и причины.
Допустимы связи внутри проекта и между проектами при наличии прав на обе стороны.
Карточка показывает «Связанные», «Зависит от» и «Блокирует» отдельно, с быстрым
переходом к доступной задаче и объяснением условия ожидания.

Для зависимости выбирается проверяемое условие: принят результат нужной версии,
завершён конкретный обязательный этап или готов артефакт. Для обычной зависимости
в первой инженерной поставке выбран default «результат принят»; успешный turn модели или просто статус
Closed с исключением не достаточны. Удалённый/отменённый predecessor не считается
успешным. Самозависимости и циклы, включая межпроектные, запрещены.

Готовность пересчитывается при изменении результата, критериев или связи.
Изменение dependency активного исполнения сначала оценивает затронутые шаги
и side effects; текущий attempt не переписывается. Снятие блокировки запускает
работу только при разрешённом режиме и после повторного readiness, без дубля.
Недоступный blocker показывается безопасной причиной ожидания без чужого
названия/содержимого. Связь не расширяет ACL и не добавляет контекст агенту сама по себе.

## 8. Workflow, роли ИИ, профили и режимы

В задаче доступна вкладка «Исполнение»: процесс, этапы, участники, bindings,
входные материалы, ожидаемый результат, проверки, ресурсы и лимиты.
Назначение workflow не запускает его автоматически без заданного триггера.

Bindings выбираются из каталога существующего AI-layer. Редактор task manager
ссылается на владельца настройки и не создаёт собственные несовместимые копии
ролей, skills, profiles и workflow. Task-role может отображаться на одну или
несколько ролей ИИ, но эти понятия не сливаются.

Предлагаемое наследование: Workspace → Project → Folder → List → Task → Stage.
Перед запуском сервер показывает итоговую конфигурацию и источник каждого
значения. Ограничения доступа и server policy могут только сужаться.
Для каждого исполнения фиксируются task/assignment revisions, состав команды,
workflow/profile/release hashes, разрешённый режим, модель и входные артефакты.

| Режим продукта, предлагаемое название | Поведение                                                                         |
| ------------------------------------- | --------------------------------------------------------------------------------- |
| Ручной                                | Люди управляют задачей; агент отвечает/выполняет шаг по явному запуску            |
| По этапам                             | Следующий этап выполняется после указанной проверки или решения                   |
| Автоматический в разрешённых границах | Готовые этапы запускаются в очереди без открытого UI; обязательные gates остаются |

Режим не равен способу размещения чата, модели или sandbox profile.
Их фактические настройки показывает отдельная сводка. Нельзя выбрать
«автоматический» и тем самым расширить разрешения tools.

Процесс допускает несколько workflows по разным этапам/ролям. Пример:
постановка → анализ → референс → реализация → тестирование → review → приёмка.
Для конкретной задачи оставляются нужные этапы. Исполнения разных агентов
могут идти параллельно при отсутствии конфликтов; переход к тестам ждёт
согласованный набор результатов. Точные правила — в технической части ТЗ.

| AI-11 | «Покажи, где решалась задача»             | Разрешённые диалоги, конкретные сообщения, этапы и результаты в хронологии задачи                                     |

AI-команда не даёт модели произвольный CRUD или SQL. Требуется расширение
существующей границы typed capabilities и серверная авторизация task-команд.
Разрешённые внутренние действия могут выполняться по действующей делегации;
каждый комментарий не должен требовать нового ручного approval. Изменение
кода, публикация и внешние эффекты подчиняются действующим правилам своей операции.

Связи имеют направление и основание:
task → assignment → execution/stage/attempt → conversation/message →
workflow root/segment → DataOperation/ChangeRequest/job → preview/release.
Не все узлы обязательны для каждой задачи. Диалог может касаться нескольких
задач; привязка отдельного сообщения не открывает всем участникам личный диалог.

### 9.1. Диалоги, в которых решалась задача

Одна задача связывается с несколькими диалогами, один диалог — с несколькими
задачами. Это самостоятельная связь many-to-many, существующая и до первого run.
У связи есть назначение: «Постановка», «Работа», «Проверка», «Передача» или
«Решение»; при необходимости отмечаются конкретные сообщения/диапазоны и runs.

При создании задачи из чата автоматически сохраняется исходный conversation/message.
Работа из карточки с явным task context связывает новый рабочий диалог и
относящиеся к задаче сообщения. Можно явно привязать существующий разрешённый
диалог, продолжить его или открыть новый. Тематическое сходство текста само
по себе не создаёт связь; обсуждение нескольких задач не приписывается целиком одной.

В карточке вкладка «Диалоги» показывает доступные обсуждения, их назначение,
участников, даты, связанные этапы и переход к конкретному сообщению/результату.
В чате видны связанные доступные задачи и действия перехода/создания/привязки.
Передача другому исполнителю добавляет его рабочий диалог, сохраняя предыдущие.

Link не выдаёт доступ к личной переписке. Читаются только разрешённые сообщения
или явно опубликованная в задачу сводка. Названия, фрагменты, вложения, участники
и счётчики закрытых обсуждений не раскрываются через task API. Материалы,
ставшие входом/результатом, фиксируются отдельными разрешёнными revisions.

Отвязка прекращает актуальную связь, но не стирает audit и происхождение уже
полученных результатов; эти записи также подчиняются ACL/retention. Архивирование
или удаление диалога не удаляет задачу. Если источник более недоступен,
сохраняется разрешённая запись происхождения без восстановления закрытого текста.

## 10. Очередь, контроль и приёмка результата

В интерфейсе есть очередь по рабочей среде/проекту/агенту/ресурсу, активные работы, ожидающие
ввода, проверки, приёмки и recovery. Видны приоритет, dependencies, readiness,
время ожидания, последний heartbeat, лимиты и допустимые действия.
Неподготовленный executor показывается как блокер настройки, а не как
бесконечная очередь.

Ручное изменение приоритета влияет на ещё не выданную работу. Система учитывает
справедливость между задачами, вместимость provider connection и конфликтующие
write scopes. Число карточек агентов не определяет число параллельных Codex turns.

Статус задачи, состояние task execution, workflow segment и worker показываются
раздельно. Пример: «На тестировании» / «Ждёт свободного тестировщика» /
«Реализация завершена». Сбой одного необязательного анализа не закрывает
автоматически всю задачу; обязательность шага определена в плане.

Результат включает артефакты, выполненные проверки, известные ограничения и
заключение тестировщика. Решение о приёмке относится к этим версиям. Изменение
результата требует повторной проверки затронутых критериев. Если задача требует
внедрения, успешный preview ещё не означает выполнения этого критерия.

Базовые операции и права инженерной поставки зафиксированы в
[контракте исполнения §15](task-management-execution.md#15-целевой-контракт-задач-eng-04):
`review` остаётся active, `done` требует долговечного результата, `closed` —
выполненных closure gates; приёмка и доставка отображаются отдельно. Принимающий
по умолчанию — владелец проекта либо назначенный им участник, без обязательного
введения новой роли или дополнительного LLM. Текущий Foundation этим не меняется.

## 11. История и досье

История — упорядоченная лента с фильтрами «обсуждение / изменения /
исполнение / проверки / решения / материалы». Событие содержит ID, время,
actor/delegator, revision, task/execution/attempt, correlation/causation
и ссылки на разрешённые данные.

Записываются создание и изменение проекта/задания, назначения и bindings,
привязка/отвязка диалогов, связанные задачи и зависимости, передача и её приём,
постановка в очередь, этапы и попытки, вопросы/ответы, handoff, файлы/версии,
проверки, решения и внешние эффекты. Удаление комментария не уничтожает факт
его существования; содержимое и retention регулируются политикой доступа.

Полезный журнал включает краткое объяснение решения, наблюдаемые действия и
доказательства. Скрытые рассуждения модели, секреты, полный prompt и credential
не являются обязательным или публичным содержимым истории. Технические logs
и текстовые дельты диалога хранятся отдельно от предметных событий.

Досье имеет просмотр списка и дерева, поиск, версии, авторство, назначение
«вход/выход» и привязку к этапу. `TASK.md` экспортируется из зафиксированной
ревизии задания; он не конкурирует с БД за текущий статус.
Принятые файлы неизменяемы по версии; новая версия не подменяет старый результат.
Retention временных файлов отличается от сроков хранения решений и evidence.
История связывает события исполнения с этапами, назначениями и попытками.
Досье показывает опубликованные версии материалов и решения по ним с учётом прав
пользователя. Состояние для возобновления попытки хранит среда исполнения.
[История задачи и содержимое досье](task-management/execution/attempts-and-dossier.md#что-видит-пользователь) ·
[Владельцы и хранение материалов](task-management-execution.md#8-артефакты-taskmd-и-источники-истины)

Добавляются органичные панели «Агенты», «Исполнение», «Очередь» и «Материалы».

Перед созданием референсов фиксируются конкретные экраны/версия ClickUp и
сознательные отличия: брендинг Realize, размещение внутри Payload, AI-функции.

Матрица сравнения для каждого экрана:
источник → композиция/плотность/типографика/состояния/поведение →
наш вариант → отличие/обоснование → evidence. Приложенный filesystem-скрин
покрывает только структуру досье; визуальная близость к ClickUp ещё не проверялась.

Референсы будут отдельным интерактивным демонстрационным интерфейсом с
фиктивными данными. Их действия не создают реальные runs и не меняют рабочие
задачи. Принятие референса не является приёмкой исполнения.

### 12.1. Интерактивный прототип — первый срез

По запросу пользователя от 2026-09-17 разрешён первый frontend-прототип.
Точки просмотра первого среза: `/reference/task-manager` с публичными фиктивными
данными и прежний `/admin/task-manager/reference` под авторизацией Admin.
Во втором срезе защищённая точка заменяется `/system/task-manager/reference`
по разделу 12.2; первый адрес Admin не сохраняется как параллельный UI.
Один клиентский workbench в `src/components/admin/task-manager/reference/`
обслуживает обе оболочки; shared primitives принадлежат `@realize/ui-kit`.

Первый срез включает создание/выбор проектов и задач, List/Board, поиск,
карточку с четырьмя ролями, несколькими участниками и соисполнителями,
workflow/profile/mode, диалоги с обратными ссылками, related/dependencies,
передачу с принятием/отказом, досье, комментарии/историю и демонстрационную
очередь. Все изменения ограничены памятью открытой вкладки; сброс/перезагрузка
возвращают fixtures. Демонстрационное завершение run не принимает задачу.
Зависимости объясняют блокировку; циклы отклоняются. Передача меняет исполнителя
после принятия; делегирование сохраняет ведущего исполнителя. В этом срезе
принять передачу/делегирование можно после завершения или отмены активной
попытки: независимые задания соисполнителей внутри уже запущенного процесса
пока не моделируются. Новые задачи создаются в «Бэклог» или «К выполнению»;
дальнейшие статусы выбираются в карточке/на доске с проверкой критериев.

Визуальные источники (проверены 2026-09-17):
[карточка задачи](https://help.clickup.com/hc/en-us/articles/10552031987735-Intro-to-tasks),
[List view](https://help.clickup.com/hc/en-us/articles/6310260883351-Intro-to-List-view),
[Board view](https://help.clickup.com/hc/en-us/articles/6310080798615-Create-and-share-a-Board-view).
Сохраняются плотные строки, группировка, постоянная навигация и разделение полей
с activity. Сознательные отличия: Realize UI-kit, русский интерфейс, явная
demo-пометка, самостоятельный Project и отдельная очередь AI. Пользовательский
скриншот задаёт категории досье, не полную композицию UI.

Это прототип поведения для согласования; API, реальные агентные запуски,
фоновые workers, сохранение в Payload, ACL проекта, установка/публикация пакета,
Calendar/Gantt, отчёты и остальные расширенные функции ТЗ относятся к
последующим этапам. Они не считаются реализованными этим срезом.

### 12.2. Второй срез: полноценное управление задачей

Уточнения пользователя от 2026-09-17 заменяют ограниченный сценарий создания
из первого среза. Присланные 13 скриншотов — текущий визуальный источник:
узкая глобальная панель, независимая иерархия проектов, компактные List/Table,
Board с группами, карточка с Activity, тип задачи, подзадачи и несколько checklist.
Цвета/типографика/радиусы принадлежат Realize UI-kit. Баннеры аккаунта ClickUp
и недоступные продукту разделы не копируются как неработающие элементы.

**Полное создание и редактирование.** Один редактор позволяет до первого
сохранения заполнить название, описание, проект, тип (задача/дефект/веха),
начальный статус, приоритет, начало/срок, оценку времени, метки, четыре роли
с людьми/агентами, соисполнителей, workflow/profile/mode, родителя, критерии,
чеклисты, зависимости/related, диалоги и Git-ссылки. Обязательны название и
проект; ограничения остальных полей проверяются только при их заполнении.
Создание атомарно: ошибка не оставляет частичную задачу, не закрывает форму и
не теряет ввод. Создание из группы/подзадачи предзаполняет контекст. После
успеха форма закрывается, общий state немедленно обновляет все представления.
Описание сохраняется текстом; форматированный редактор остаётся в parity scope.

**Чеклисты и критерии.** Критерии приёмки отделяются от рабочих списков.
Пользователь создаёт несколько именованных чеклистов, меняет их названия,
добавляет/редактирует/удаляет и переставляет пункты. Пункт имеет исполнителя
(человек или агент), срок, отметку выполнения и обязательность для принятия.
Прогресс пересчитывается из пунктов. Незавершённый обязательный пункт или
критерий блокирует «Готово»; необязательный — нет. Изменения принятого результата
требуют переоткрыть задачу. Назначение пункта не повышает права участника.

**Управление.** Подзадача является обычной задачей с parentId в том же проекте;
циклы дерева запрещены. Родитель показывает прогресс и переходы к children,
незавершённые активные подзадачи блокируют принятие. Доступны дублирование,
архивирование/восстановление, копирование ID/ссылки. Дубликат получает новый ID,
не наследует результаты запусков/приёмку и незавершённые передачи. Архивирование
недопустимо при активном исполнении; архив исключён из очереди и обычного списка.
Table, List и Board работают с одной моделью; ключевые поля редактируются
без повторного открытия, selection/bulk операции проходят те же guards.

**Git и доставка.** Задача содержит типизированные связи с репозиторием,
веткой, коммитом (SHA), push receipt, pull request, проверкой CI и релизом.
Связь хранит тип, название, безопасный URL/ref/SHA, источник и состояние.
Ручная ссылка не доказывает push/merge или успешную проверку. В прототипе
доступны создание/редактирование/удаление ссылок и явно помеченные примеры;
Git-команды, push и внешние записи не выполняются. Целевой adapter связывает
подтверждённые provider events с попыткой/автором без подмены истории.

**Реактивность.** Единая командная модель возвращает явный результат операции
и ошибки полей. Формы используют controlled draft; создание/сохранение — одна
транзакция; немедленные inline-команды не расходятся с карточкой/историей.
Текст не создаёт событие на каждый символ. Вкладки редактора сохраняют draft;
закрытие изменённой формы предлагает сохранить или отбросить изменения.
Данные этого этапа остаются демонстрационными в памяти вкладки, сброс при
перезагрузке остаётся явным. Durable backend/SSE — отдельный следующий этап.

**Системный шаблон.** Task manager — первый потребитель
[SystemAdminShell](../architecture/system-admin-shell.md). Общая оболочка
принадлежит самостоятельному `@realize/template-realize`; рабочие модули
подключаются через единый SDK и neutral host. Отдельный `/system/task-manager/reference` использует
серверную авторизацию Payload без его CSS/DefaultTemplate. Публичный
`/reference/task-manager` показывает те же fixtures в том же шаблоне.
Остальные экраны переносятся постепенно отдельными заданиями. UI независим
от разметки Payload; auth/API adapter проверяется при обновлениях Payload.

**Визуальная приёмка.** Ни одна текстовая кнопка/вкладка не имеет нулевого
горизонтального отступа в hover/focus; позиции текста и геометрия стабильны.
Полная форма ограничена рабочей шириной около 1040px, имеет внутренний scroll
и закреплённые действия; mobile занимает доступный экран. Portal наследует
тему и typography через общий owner, а не случайный CSS страницы.
Проверяются 1440/768/390 px, обе темы, клавиатура, error/empty/long-content,
композиция по скриншотам и computed CSS нормального/hover/focus состояний.

Приёмка среза: создать полностью заполненную задачу одним submit; исправить
ошибку без потери draft; выполнить checklist/subtask/Git сценарии; увидеть
синхронные List/Board/Table/историю; проверить архив/дубликат и ограничения
очереди; сравнить screenshot и padding состояния. Первый упрощённый срез
сам по себе не подтверждает выполнение этих критериев.

### 12.3. Реализованный демонстрационный срез 0.4

На 2026-09-17 реализованы общий полный редактор создания/изменения, четыре
роли с несколькими людьми/агентами, соисполнители, отдельные критерии и
именованные чеклисты, подзадачи, зависимости, диалоги и ручные Git-ссылки.
Доступны List/Board/Table/Overview, inline-поля, настройка колонок, массовые
изменения, дублирование и архив/восстановление. Список по умолчанию показывает
исполнителей, срок и приоритет; прогресс чеклистов и AI-исполнение включаются
через настройку колонок. Доска поддерживает перенос карточки и доступную
смену статуса через select. Фильтры, очередь и история используют один store. После создания рабочая область
переходит в выбранный проект и открывает созданную карточку; закрытие карточки
оставляет новую задачу видимой в списке без прежних фильтров.

Код остаётся frontend-прототипом: данные живут в памяти конкретного экземпляра
рабочей среды до перезагрузки. Git-ссылки не запускают commit/push;
ручные записи помечаются как непроверенные. AI-очередь и сообщения диалогов
демонстрационные; серверная интеграция с ассистентом, реальные runs, постоянное
хранение, ACL задач/проектов, установка npm-пакета и доставка не реализованы.
Досье показывает материалы-примеры; добавление файлов и произвольные custom
fields остаются следующими этапами целевого ТЗ. Предпросмотр не является
production-релизом и не подтверждает полную функциональную паритетность с ClickUp.

Оболочка вынесена в `@realize/ui-kit`. Публичный `/reference/task-manager` и
защищённый `/system/task-manager/reference` используют один Workbench. В новом
системном route нет Payload UI/CSS; авторизация по-прежнему принадлежит
серверному Payload-адаптеру. Старое custom view удалено, ссылка Admin ведёт
на системный маршрут. Остальные экраны Admin не переносились.

Проверки модели, доступа и интерфейса фиксируются в рабочем материале
`.ai-workspace/tasks/2026-09-17-task-manager-refactor-e62f/TASK.md`;
скриншоты не заменяют интеграционные критерии целевого продукта из раздела 13.

### 12.4. Иерархия и навигация в референсе 0.7

В актуальном референсе переключаемые Workspace содержат самостоятельные Project.
Space («Область») исключён из модели и интерфейса. Workspace создаётся пустым,
Project атомарно получает основной List «Задачи»; необязательная Folder может
группировать List и вложенные Folder. Задачи и подзадачи остаются в рабочем
представлении, чеклисты — в карточках, без дублирования в глобальной навигации.

Панель показывает один уровень контейнеров: проекты выбранного Workspace либо
непосредственное содержимое проекта/папки. При переходе глубже отступы не растут,
имена остаются в одну строку с ellipsis и полным title. Есть возврат к родителю,
явное открытие всех задач текущего контейнера и создание в его контексте.
Переключение контейнера сбрасывает фильтры и выделение; чужая карточка закрывается.
Заголовки групп, разделители и строки быстрых переходов принадлежат общему UI-kit.

List/Table показывают раскрываемые подзадачи. При группировке по статусу группа
определяется корнем дерева, у ребёнка сохраняется собственный статус. Есть
плоский режим. Поиск подзадачи сохраняет видимую цепочку родителей как контекст;
такие родители не попадают в групповые команды автоматически. В карточке
доступны переход к родителю, создание подзадачи, именованные чеклисты, назначение
людей/агентов на пункты, сроки, обязательность и счётчики выполнения.

Источник состояния остаётся локальным store reference: изменения до перезагрузки,
два демонстрационных Workspace, никаких реальных запусков или API. Серверные
ACL, сохранение контейнеров на сервере, перенос/архив проектов, папок и списков,
вложенность пунктов чеклиста, преобразование пункта в Task и Tasks in Multiple Lists остаются
следующими этапами. Рабочие пункты чеклиста и критерии приёмки различаются.

### 12.5. Управление рабочими средами в референсе 0.8

Первый вертикальный срез: каталог доступных сред, создание, переключение, общие
настройки, участники/доступ, архивирование и восстановление. Каталог открывается
из навигации «Задачи» и переключателя; имеет поиск, сортировку и вкладки активных
и архивных сред. Карточка строки показывает владельца, участников, проекты,
активные задачи и состояния запусков. Настройки — отдельный экран общего shell
с вкладками «Общие», «Участники и доступ», «Управление».

Общие поля: название, описание, значок/цвет, часовой пояс, рабочие дни. Владелец
задаётся при создании. Участники — существующие вымышленные люди и агенты; роли
администратор, участник, гость. Владелец управляет средой; администратор управляет
настройками/участниками; участник работает с проектами/задачами; гость читает.
Private допускает только владельца/участников, internal даёт остальным известным
пользователям демо чтение. Изменение членства не подменяет роли конкретных задач.
Настройки проверяются общей моделью, без отдельного пути обхода через UI.

Архив сохраняет все связи, проекты, задачи и историю; контейнеры архивной среды
доступны для чтения. Queued/blocked/running/paused запуски требуют разрешения
состояния до архивации; команда не останавливает их молча. Восстановление не
запускает очередь. Несохранённые поля защищены при внутренних переходах; отказ
и конфликт revision сохраняют введённые значения.

Срез остаётся в памяти браузерного reference, не отправляет приглашения и не
обеспечивает серверную защиту. ACL хоста, команды, распространение прав на
материалы/диалоги и серверные записи внедряются отдельно. Наследование настроек
проектов, настройки ИИ, ресурсы/интеграции и автоматизации — следующий срез.

### 12.6. Действия над контейнерами в референсе 0.9

Названия проекта/папки/списка в навигации открывают их задачи. Отдельная стрелка
у проекта и папки открывает следующий уровень навигации. Постоянная строка
контекста не меняет положение поиска при возврате и входе внутрь. Заголовки
«Проекты»/«Разделы» и один плюс оставляют место названиям.

Меню контейнера открывает настройки, скрывает/возвращает строку и предлагает
удаление. Настройки редактируют название, описание, аватарку и персональную видимость.
Проект, папка и список имеют optional avatar. В reference локальный PNG/JPEG/WebP
до2MB нормализуется в128×128 и сохраняется в demo store до перезагрузки; можно
удалить картинку и вернуть стандартную иконку. Сохранение соблюдает прежний ACL
и dirty guard, отсутствие поля в старой команде сохраняет текущую картинку.
Аватарка/иконка отображается в боковой навигации и контекстных крошках.
Крошки заменяют отдельный заголовок контейнера: текущий уровень — h1, у каждого
уровня меню с поиском и записями того же типа под тем же родителем. Выбор родителей,
соседей и настроек использует существующую навигацию и проверки доступа.
Скрытие сохраняется в браузерных preferences навигации; «Показать скрытые»
в меню плюса позволяет вернуть любой скрытый контейнер, включая проект.
Скрытие родителя не удаляет его содержимое и не ограничивает доступ.

Удаление подтверждается компактной карточкой UiConfirmation в стиле
уведомления: название объекта, ненулевые количества вложенных папок, списков
и задач, краткое указание необратимости и кнопки отмены/удаления. Карточка
не закрывается по таймеру; на мобильном экране сохраняет компактную форму.
При запрете удаления показана одна причина и кнопка «Понятно».
Команда атомарно удаляет выбранную ветку, включая архивные задачи.
Активные состояния queued/blocked/running/paused, незавершённая передача и
входящие связи из задач за пределами ветки запрещают удаление. Права среды
проверяются при прямом dispatch. Родитель и перечень удалённых контейнеров
возвращаются для безопасной навигации и очистки избранного/видимости.
Связанные диалоги сохраняются. Серверное хранение и реальный execution runtime
этот срез не подключает; изменения данных reference сохраняются до перезагрузки.

### 12.7. Единое создание из шапки (2026-09-19)

Кнопка «Создать» открывает полное окно со сменой типа: задача, проект, папка,
список или рабочая среда. Используются те же редакторы и атомарные команды,
что в навигации; renderCreation slot задаёт общие вкладки. Вкладка задачи
показывает основной ввод; «Все поля задачи» раскрывает существующий полный
редактор с участниками, сроками, чеклистами и связями без сброса draft. Пустой draft можно
сменить сразу, заполненный требует явного решения сохранить текущий ввод или
отбросить его. Проект/папка/список имеют выбор расположения до записи; доступны
только рабочие среды с canWrite и корректные дочерние цепочки. Приватные,
архивные и недоступные записи не попадают в этот selector. Reducer повторно
проверяет права и принадлежность при сохранении. Внешние интеграции и новые
типы вроде документов/досок этим этапом не имитируются.

### 12.8. Постоянный Foundation (2026-10-11)

Отдельный маршрут `/system/task-manager` использует серверный модуль
`@realize/payload-task-manager@0.1.0`. Данные хранятся в PostgreSQL: проект,
его исходный список «Задачи», задача, журнал событий и записи повторов команд.
Идентичность автора берётся из сессии Payload; host допускает admin, затем
модуль проверяет членство в проекте. Чтение и создание/редактирование задач
доступны через строгие DTO и API, а общий CRUD скрытых коллекций закрыт.

Задача получает UUID, ключ `TASK-<id>`, ревизию, исполнителя, приоритет и
один из статусов `backlog`, `in_progress`, `review`. Обновление требует
ожидаемую ревизию; конфликт сохраняет пользовательский draft. Изменение,
событие и idempotency receipt записываются одной транзакцией. Git-привязка
содержит repository ID, назначение и полный SHA, с явными
`source: manual`, `verification: unverified`. Отдельная живая проекция коммита
и связанных PR описана в §12.9, долговечный polling — в §12.10. Полный
provider event sync, релизы и исполнение AI остаются следующими поставками
по разделу 15.

Интерфейс использует общий System Admin shell, навигацию и UI-kit, а
`/system/task-manager/reference` сохраняет демонстрационный сценарий.
Foundation не переносит и не удаляет `.ai-workspace/tasks/**` и не разрешает
закрытие задачи без будущего процесса приёмки. Миграция создаётся из
`scripts/migrations/task-manager.mjs`; откат populated-хранилища блокируется.
Точные команды, ограничения и критерии проверки находятся в
[контракте исполнения, §12](task-management-execution.md#12-первая-постоянная-поставка-foundation).

### 12.9. Ограниченное чтение Git-фактов (2026-10-12)

Рабочая карточка получает текущие сведения о репозитории, точном коммите и
связанных с ним PR по явному обновлению. Доступ проверяется до обращения к
provider и перед выдачей ответа; смена ревизии задачи во время чтения требует
загрузить актуальные данные. Проекция содержит время чтения и относится к
конкретной задаче, ревизии и сохранённым ручным привязкам.

Для чтения Git-фактов Task Manager использует настроенное GitHub-подключение платформы.
Привязка должна иметь назначение `platform-core`, идентификатор репозитория должен
совпадать со slug в подключении, а SHA коммита — состоять из 40 символов `0–9` и `a–f`.
Чтение клиентских репозиториев ждёт registry и отдельных разрешений. PR —
факты, возвращённые GitHub API associated pull requests для коммита; ответ
не объявляется полным перечнем всех PR репозитория. За одно обновление
обрабатываются первые восемь ручных привязок из допустимых 50; для каждого
коммита — первая страница до 20 PR. Неполное покрытие привязок и следующая
страница PR обозначаются отдельно. Ограничения и ошибки наблюдения
показываются отдельно от состояния задачи; provider `404` не считается
доказательством отсутствия коммита.

Это read-only расширение Foundation. Сохранённая привязка остаётся
`manual/unverified`; чтение не создаёт durable history и не запускает Git-команды.
Текущий live ответ также показывает Check Runs и commit statuses точного SHA;
пустые, неполные или успешные сведения не означают прохождение обязательных
проверок workflow, приёмку, Done, release или deployment. Полная поставка
Git observation из §15.2 остаётся открытой. Владельцы, endpoint и критерии —
[контракт исполнения, §13](task-management-execution.md#13-ограниченное-чтение-git-фактов-2026-10-12).

### 12.10. Долговечная синхронизация Git по запросу (2026-10-12)

Отдельная команда сохраняет текущее наблюдение repository/commit/PR/CI для
сохранённых привязок ожидаемой ревизии задачи. Результат получает устойчивый
ID, actor и время записи; история сохраняется после закрытия карточки,
reload и restart. Сведения старой ревизии видны как исторические, а новая
неудачная попытка не уничтожает ранее полученный успешный результат.

Потерянный ответ восстанавливается повтором той же команды с прежним
Idempotency-Key. Replay после новой проверки прав возвращает первоначальный
receipt и не перечитывает provider; новый polling требует нового ключа.
Открытая карточка удерживает неподтверждённую команду и ключ при смене ревизии.
После закрытия или reload восстанавливается история; browser key не хранится
между открытиями и новый POST автоматически не запускается.
Provider reads проходят вне DB-транзакции, а запись и receipt атомарны.
Изменение задачи или отзыв доступа во время polling не создаёт ложной записи
для новой ревизии. CI сохраняет точный SHA; success другого PR head или
результата squash/rebase не присваивается исходному коммиту.

Polling запускается явно. Webhooks, автономный background worker и reconciler
пока отсутствуют. Срез не меняет task status/revision/audit events или ручной
`manual/unverified`, не проводит приёмку и не подтверждает release/deploy.
Полная поставка §15.2 и cutover локальных задач остаются открытыми. API,
неизменяемая история и критерии —
[контракт исполнения, §14](task-management-execution.md#14-долговечная-синхронизация-git-по-запросу-2026-10-12).

## 13. Сквозные сценарии и критерии приёмки

Обязательный сценарий: человек создаёт задачу из диалога; постановщиком может
стать агент; два агента-исполнителя получают отдельные задания; агент-тестировщик
проверяет результат; человек и агент наблюдают за событиями. При ограничении
provider capacity задания честно ждут слот. После закрытия вкладки выполнение
продолжается; по завершении видны история, материалы и решение о приёмке.
Другой сценарий полностью человеческой задачи использует ту же модель данных.
Смешанный сценарий: агент подготовил материал → человек принял задание и
исправил его → агент-тестировщик проверил новую версию → выбранный принимающий
принял результат. Ручной этап не требует provider slot или worker heartbeat.

| ID    | Проверяемое условие                                                                                                                                                |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AC-01 | Каждая из четырёх ролей принимает человека, агента и несколько агентов; ID/авторство не подменяются профилями                                                      |
| AC-02 | Иерархия, поля, статусы, назначения и view сохраняются; одни данные показаны в разных представлениях                                                               |
| AC-03 | Ассистент создаёт/читает/обновляет задачи разрешёнными командами; повтор запроса не создаёт дубли                                                                  |
| AC-04 | В задаче и «Запусках процессов» видны ссылки на один реальный workflow; произвольный Code job не выдаётся за workflow                                              |
| AC-05 | Каждый attempt имеет точный снимок задания, назначений, конфигурации и входов; изменение профиля не переписывает историю                                           |
| AC-06 | Несколько агентов получают отдельные миссии и результаты; fan-in проверяет обязательные результаты; write-конфликт исключён                                        |

| AC-11 | Досье воспроизводит категории скриншота, версии и происхождение; чужие файлы/диалоги недоступны                                                                    |

| AC-13 | Все изменения и фактические действия имеют автора/причину; повторы событий не дублируют историю и уведомления                                                      |
| AC-14 | Browser evidence подтверждает утверждённые референсы, темы, клавиатуру, responsive и ошибочные состояния                                                           |
| AC-15 | Независимый Payload-host проходит установку архива пакета, upgrade и восстановление; AI проходит отдельную матрицу adapter                                         |
| AC-16 | Согласованные функции поздних фаз имеют собственные проверки; принятие A–B не объявляется полной ClickUp parity                                                    |
| AC-17 | Созданы два проекта с разными участниками и задачами; projectId устойчив, чужие задачи не видны; перенос/архив проверяют активные runs, ACL и связи                |
| AC-18 | Одна задача решается в нескольких диалогах, один диалог связан с несколькими задачами; работают обратные ссылки и message anchors без раскрытия закрытой переписки |

| AC-20 | Человек/агент передаёт работу и делегирует соисполнителю; контекст и история сохранены, приём/отказ явны; активный старый attempt не конкурирует за тот же эффект  |

| Docs                   | Создать вложенный документ, обсудить версию, изменить и восстановить            | Сохранены версии и авторы; конфликт редактирования обнаружен; restore создаёт новую ревизию; ACL действует на поиск и ссылки                                    |

| Шаблон задачи/процесса | Создать задачу по шаблону с ролями, bindings и критериями                       | Получена новая идентичность; version шаблона известна; секреты и старые approvals не копируются; назначения перепроверены                                       |
| Повторения             | Плановый запуск в timezone проекта, рестарт на границе периода                  | Одна задача на occurrence key; правила пропущенных периодов явны; повтор не дублирует автоматически запущенные работы                                           |
| Автоматизации          | Событие → условие → task action/AI stage                                        | Есть causal history; повтор события идемпотентен; цикл/лимит останавливается с объяснением; действия ограничены делегацией и budget                             |
| Учёт времени           | Человек запускает/останавливает таймер или добавляет запись                     | Интервалы и изменения авторизованы; повтор stop не дублирует запись; duration/usage агентов показаны отдельно от человеческих часов                             |
| Спринты                | Планирование backlog, старт/завершение итерации, перенос незавершённых задач    | Сохраняются история scope и принятые результаты; оставшиеся задачи не становятся завершёнными из-за окончания спринта                                           |
| Цели/вехи              | Связать критерий с принятыми результатами нескольких задач                      | Прогресс вычисляется по заданной формуле; переоткрытие/отзыв приёмки пересчитывает его; ручная поправка имеет автора/причину                                    |
| Dashboard/отчёты       | Посмотреть сроки, очередь, принятие, нагрузку и затраты по фильтрам             | Итоги сверяются с исходными событиями; нет недоступных данных; неизвестная стоимость не выдаётся за ноль                                                        |
| Inbox/уведомления      | Назначение, mention, блокер, сдача результата и отзыв доступа                   | Правильные адресаты, read/unread, отсутствие дублей; старое уведомление не открывает отозванный доступ; внешний канал включается только при настроенном adapter |
| Импорт/экспорт         | Импортировать совместимый набор и повторить; экспортировать со связями          | Preview ошибок/сопоставлений до записи; повтор не плодит задачи; версии, участники и связи сохраняются, credentials не экспортируются                           |

Для каждого экрана перед его реализацией нужны утверждённый референс и перечень
операций/DTO. Добавление типов представлений или интеграций вне этой матрицы
проходит явное уточнение scope, а не скрытую замену уже согласованных функций.

## 14. Последовательность поставки и открытые решения

Сначала утверждаются это ТЗ и технический контракт, затем создаются референсы.
После принятия референсов реализация делится на проверяемые части:

| Фаза                            | Результат                                                                                                                                             |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Предметная основа            | Проекты и иерархия, задача, участники/роли, диалоги/связи, handoff, карточка, базовые views, ACL, история, досье; execution references заложены сразу |
| B. Сквозное AI-исполнение       | Агентные идентичности, bindings, durable orchestration, очередь/capacity, ассистент, проверки/приёмка, восстановление без UI                          |
| C. Планирование                 | Calendar/Gantt/Timeline/Workload, Docs, поля, шаблоны, повторения, автоматизации и отчёты                                                             |
| D. Полная согласованная матрица | Остальные утверждённые сценарии ClickUp, интеграции, масштабирование и совместимость                                                                  |

A без B не удовлетворяет основной цели пользователя. A–B могут быть первым
пилотом, но не объявляются завершением полного объёма. После каждого среза —
адресные проверки, демонстрация и актуализация статуса; внедрение включает
миграции, backup/recovery, мониторинг и принятие пользователем. Сроки/стоимость
оцениваются после закрытия существенных решений, отдельно по фазам.

| Решение                | Предложение для согласования                                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Повтор «постановщик»   | Четыре указанные роли; отдельный приёмщик/ревьюер только после уточнения                                                          |
| Командное завершение   | Все обязательные задания + назначенный принимающий; quorum/first-success доступны как явные стратегии                             |
| Автономность           | По этапам по умолчанию; автоматический режим в уже разрешённых границах                                                           |
| Агентные подключения   | Сначала существующий провайдер с фактической capacity; несколько провайдеров/учётных записей — через adapter matrix               |
| Scope ClickUp          | Матрица TM-01–19 и отдельные Projects как целевые требования; дополнительные поверхности перечислены в разделе 5 и требуют выбора |
| Пользователи и tenancy | Рабочие команды внутри host; гости с ограниченным доступом; SaaS multi-tenant отдельно                                            |
| Установка              | Переносимый task package + AI adapter; текущий Realize AI требует PostgreSQL; installer не обязательная зависимость               |
| Данные                 | Закрытое artifact storage, контролируемый экспорт/restore, согласованный retention и лимиты                                       |
| Численные параметры    | Глубина, нагрузка, queue deadlines, budgets и объём контекста проверяются до выпуска                                              |

Базовые решения ENG-04 выше относятся к первой инженерной поставке и не означают
согласования всех расширений этой таблицы. Остальные предложения не считаются
принятыми по умолчанию. При согласовании фиксируются
решения и версия ТЗ; история текущей реализации обновляется только после
фактического внедрения.

## 15. Разработка платформы, Git и переход к постоянным задачам

Подтверждённое направление пользователя от 2026-10-11: Task Manager владеет
постановкой, назначениями, материалами, предметным статусом и приёмкой.
Git владеет историей исходников; provider — фактическими PR/CI событиями;
release owner — опубликованным manifest и артефактом; installation owner —
наблюдаемой установленной версией. Карточка задачи показывает связанные факты.

Уточнение от 2026-10-19: новые задачи создаются прежде всего в Task Manager.
Локальный TASK служит резервом при ненастроенной платформе или доказанной
недоступности до создания. Успешное серверное создание не дублируется
локальным досье; ограниченный intake описан в §15.4. Это не завершение
будущего переноса файлов и всего lifecycle.

### 15.1. Прослеживаемость разработки

Задача разработки связывает постоянные IDs требований из функционального
каталога, спецификацию/ADR по точному Git revision, материалы и revision
Мастерской, исполнения и результаты. Коммит определяется repository ID и
полным SHA. Один Task имеет несколько коммитов/PR; один коммит/PR может
относиться к нескольким задачам. ID задачи сохраняется при переносе.
ID требований `TM-*` и IDs этапов поставки не переопределяют друг друга.

Commit message содержит task key; сервер проверяет и сохраняет связь, её
происхождение и автора. Исполнение фиксирует base commit и commits результата.
Ручной SHA остаётся `unverified` до ответа Git owner. При squash/rebase
исходная история сохраняется, итоговый SHA фиксируется отдельно. Совпадение
названия ветки или наличие task key само по себе не является проверкой результата.
В ограниченных срезах §12.9–12.10 ответ owner показывается отдельно, а durable
receipt сохраняет наблюдение точной ревизии; флаг ручной привязки не переписывается.

Проверки/приёмка относятся к конкретным task/result revisions и commit SHA.
Изменение результата требует новых применимых checks и приёмки. Task status,
acceptance, merged, released и deployed отображаются раздельно; обязательность
release/deploy определяется критериями workflow. Планируемая версия не
подменяет фактический выпуск. Репозиторий ядра и клиентского проекта сохраняют
раздельные Git bindings и полномочия по [delivery](../delivery/04-platform-versioning.md).

Документация требований/архитектуры остаётся в Git и меняется вместе с кодом.
Task dossier хранит материалы работы и безопасные ссылки на точную версию
документа. Номер revision задачи не является SemVer платформы.

### 15.2. Порядок первых постоянных поставок

Это отдельные поставки внутри существующих требований, а не новые значения
`TM-01/TM-02` из функциональной матрицы.

| Поставка              | Проверяемый результат                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Foundation            | Постоянные Project/List/Task, server actor/ACL, revisions, atomic audit, idempotent команды; существующая системная оболочка и рабочий CRUD |
| Git observation       | Подтверждённые commits/PR/CI, durable события, дедупликация и сверка после сбоя; ручные привязки явно непроверенные                         |
| Release traceability  | Task → изменения → manifest/version/digest; отдельные planned/released/deployed состояния                                                   |
| Agent/artifact access | Admin/IDE/MCP работают с теми же задачами и материалами по API с проверкой прав и ревизий                                                   |
| Import/cutover        | Preview и перенос локальных досье, проверка восстановления и смена рабочего слоя; затем разрешённая очистка                                 |

Foundation не объявляет выполненными фазы A–D, AI orchestration или
предметную приёмку. Первое ограниченное исполнение на PostgreSQL описано в
[техническом контракте §12](task-management-execution.md#12-первая-постоянная-поставка-foundation).
Живое чтение и durable polling из §12.9–12.10 покрывают часть следующего этапа:
есть наблюдения PR/CI и replay receipt, но server-owned provider events,
автономная сверка и полное покрытие истории ещё не поставлены.

### 15.3. Условия переключения рабочего слоя

До cutover проверены постоянное хранение/восстановление задач и файлов,
server ACL, доступ агентов, audit, обработка конфликтов и повторов, а также
Git/release связи для workflow разработки. Импорт имеет manifest/hashes,
mapping участников и прежних IDs; повтор не создаёт копии, исторические runs
не запускаются заново. Недоступные материалы обозначаются явно.

Удаление выполняется после проверки полноты, backup/restore и замены
зависимых ссылок. Полная работа с материалами через Task API потребует
синхронизации `.ai` workflow/rule и `.codex` процедур у существующих владельцев.
Первичное создание уже выбирает Task Manager по §15.4; несвязанные резервы
сохраняют локальный lifecycle, а связанные снимки остаются без автоочистки.
После полного перехода временная материализация возможна вне корня
проекта; markdown-экспорт остаётся проекцией и не управляет статусом задачи.

### 15.4. Основное создание в Task Manager и локальный резерв

Рабочий `task:workspace create` сначала обращается к Task Manager. При успехе
задача остаётся только на сервере: локальные `TASK.md` и manifest не создаются.
CLI сохраняет служебную identity запроса для повтора. Подключение использует
адрес установки и credentials из browser login/keyring либо явного env override.
[Центр доступов](../architecture/platform-access.md) выдаёт отдельные personal/API
токены и CLI sessions с ограниченными scopes; прежний user JWT также поддерживается.
В текущем коде новый `create` с настроенным подключением получает проект
через `--project`, список — через `--list` либо однозначный единственный список
проекта. Прежние env Project/List игнорируются; неверный или незаданный выбор
в доступной платформе не разрешает локальный обход.

Если подключения нет либо read-only проверка до создания подтверждает offline,
допускается локальное досье. Ошибки доступа и конфигурации не обходятся локальным
созданием. Неизвестный исход отправленного POST требует повтора того же
`clientTaskId`; новая локальная или серверная задача не создаётся.

`sync` явно передаёт managed локальную задачу в сервер; уже выбранный резерв
также повторяет доставку при последующей CLI mutation, когда подключение
настроено и контекст выбран. Резерв, созданный без настройки подключения и выбора,
остаётся редактируемым;
для передачи недостающий project/list задают явно через `sync`. Закреплённые
проект, список и установка не заменяются при повторе.
Повтор исходной постановки возвращает текущую серверную запись,
не создавая копии. После подтверждения Task Manager становится предметным
владельцем, локальные мутации блокируются, прежний TASK и материалы сохраняются.
Чтение старого снимка не подтверждает текущий статус сервера.

Это первичный intake без импорта файлов, history, результата или приёмки.
Существующие legacy TASK не принимаются и не импортируются автоматически.
Локальные `done/closed` не являются серверной приёмкой: Foundation по-прежнему
использует `backlog/in_progress/review`. Условия переноса и удаления материалов
из §15.3 сохраняются. Точные API, replay и границы fallback —
[контракт исполнения §8.3](task-management-execution.md#83-создание-через-task-manager-и-локальный-резерв-2026-10-19)
и [§12.4](task-management-execution.md#124-первичный-intake-из-рабочего-слоя-2026-10-19).

Просмотр, создание и изменение проектов/списков через CLI описаны в
[§12.5](task-management-execution.md#125-явный-выбор-projectlist-и-управление-через-cli-2026-10-19).
Project metadata/members меняет owner, списки создают и переименовывают участники.
Этот новый код ещё не активирован в локальной web-сборке из §12.4; удаление
и архивирование не входят в поставку. CLI credential helper реализован отдельно
по контракту центра доступов и требует его серверной схемы/сборки.
