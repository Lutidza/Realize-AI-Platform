# RealizeAI Control Panel — первый релиз и переход с Realize

Версия документа: **0.34**, 2026-11-24. Статус: **Target specification**.
Источник: TASK-23 / ONE-04 в составе TASK-9. Это состав будущей поставки;
первый исходный срез нового пакета реализован для preview; полная поставка и переход не активированы.

## 1. Результат первого релиза

**RealizeAI Control Panel** — первый стандартный шаблон платформы с качественной
оболочкой, общими элементами, собственными auth/status композициями и интерфейсом
управления оформлением. Визуальная основа — референс Task Manager; его demo store
и бизнес-логика не входят в шаблон.

Одно назначение действует на всю область Admin, независимо от роли и набора
подключённых модулей; отдельное назначение действует на сайт. Новые разрешённые
collection/global/custom/module screens получают оформление через общий host,
без изменения пакета ради каждого URL. Состав навигации настраивают администраторы либо агенты в рамках разрешённых
задач; доступные модули, маршруты и права ограничивают возможные пункты. Матрица экранов — проверка покрытия, не allowlist шаблона.

Принятые границы заданы [ADR-0018](../architecture/decisions/ADR-0018-self-contained-template-packages.md)
и [§11 Мастерской](design-workshop.md#11-темы-компоненты-и-качество).
Этот документ определяет состав первого RealizeAI Control Panel и порядок перехода.
Решение от 2026-11-11 о новом package owner уточняет прежний план развития
`template-realize`: этот пакет остаётся legacy/reference. Остальные границы
ADR применяются в относящейся части; будущие ядро и установка требуют отдельной
проработки, без создания параллельных систем в первом срезе.

Основания по фактическому состоянию:
[ONE-01 — карта покрытия](../reports/2026-10-19-template-coverage-audit.md),
[ONE-02 — работа переключателя](../reports/2026-10-19-template-switching-browser-audit.md),
[ONE-03 — разбор референса](../reports/2026-10-19-realize-one-reference-breakdown.md).

## 2. Имя и версии

С 9 ноября 2026 года название семейства шаблона — **RealizeAI Control Panel**.
В дальнейшем у него могут появиться варианты, например **RealizeAI Control Panel Lite**,
**RealizeAI Control Panel Standard** и **RealizeAI Control Panel Enterprise**.
Это предварительные названия: состав возможностей, различия, лицензирование и способ
поставки вариантов ещё не определены. Они не объявляются отдельными установленными
пакетами, палитрами, тарифами или версиями. Первый каркас разрабатывается под общим
названием без назначения ему варианта.

Коды `ONE-01…ONE-32` сохраняются как исторические идентификаторы задач.
Старые identity, версии и история назначений не переписываются под новый продукт.

| Поле                     | Legacy/reference                          | Новый RealizeAI Control Panel                                              |
| ------------------------ | ----------------------------------------- | -------------------------------------------------------------------------- |
| Display name             | `Realize`                                 | `RealizeAI Control Panel`                                                  |
| Template ID              | `realize`                                 | `realizeai-control-panel`                                                  |
| Package                  | `@realize/template-realize`               | `@realize/template-realizeai-control-panel`                                |
| Package/template version | `0.1.0`                                   | Собственная `0.1.0` нового ID; не `realize@0.2.0`                          |
| Source owner             | `packages/template-realize`               | `packages/template-realizeai-control-panel`                                |
| Targets                  | Реализован только `admin`                 | Первый срез — `admin`; frontend остаётся отдельной последующей реализацией |
| Назначение               | Прежний функционал и визуальный reference | Новый развиваемый продукт                                                  |

Новый пакет не импортирует приватные реализации legacy-пакета и не меняет его
код, manifest, defaults или reference preset. Полезное общее поведение выделяется
к общему владельцу только в отдельном проверяемом изменении; полный перенос
старого shell вместе с demo-поведением не является первым срезом.

Версии manifest protocol, SDK/UI contract, settings schema и palette независимы
от package version. Их изменения определяются по фактическому контрактному diff.
`1.0.0` не используется как обещание стабильности до приёмки. Подключение нового
пакета для preview не устанавливает новое активное назначение и не переписывает
существующие palette/settings/manifestHash/receipts.

**Legacy baseline сохраняется.** `realize@0.1.0` и его reference продолжают
разрешаться в прежний код и assets. Изменение его identity/кода требует отдельного
baseline gate; создание нового независимого preview не требует предварительно
строить универсальный installer или переносить все legacy-потребители.
Перед последующей активацией нужно подтвердить точные версии обоих пакетов,
изоляцию стилей, доступность reference и восстановление прежнего назначения.
Сохранённый старый ID не может указывать на новый renderer Control Panel.

Общие элементы topbar подключаются через capability-driven contracts; их
владельцы и форма поставки согласуются отдельно, они не закрепляются как
неразделимые части шаблона. Первый
релиз не требует создания отсутствующих backend-поиска, inbox или финансового
сервиса ради заполнения панели: host передаёт реальные возможности, а недоступные
действия не имитируются. Наличие search trigger или demo notification в reference
не подтверждает платформенную интеграцию.

Применение RealizeAI Control Panel к сложному бизнес-экрану включает его общий chrome, используемые
primitives, tokens и overlays. Таблицы, редакторы и формы сохраняют предметную
композицию и возможности; их полный продуктовый редизайн не является условием.
Экран со старой независимой темой внутри новой рамки не считается подключённым.
Внешние payment widgets используют поддерживаемый provider appearance API;
ограничения внешнего UI фиксируются в проверке, без изменения платёжной логики.

### 3.1. Согласованный фокус и границы первого каркаса

Решения обсуждения от 2026-11-09 с уточнениями 2026-11-10/11 определяют целевую
архитектуру нового пакета; они не переносятся в legacy `realize@0.1.0`. Сначала создаются качественный чистый каркас
Control Panel и его подключение к host, затем — простая документация в новом
шаблоне. Полный состав релиза из таблицы выше сохраняется, но не должен целиком
переноситься в первую итерацию каркаса. Работа идёт небольшими проверяемыми
шагами: перед шагом сообщаются действия, после — результат и следующий шаг;
промежуточные продуктовые и визуальные решения согласуются.

**Первый проверенный MVP-срез (§3.9):** manifest и compiled definition нового пакета,
пустой стандартный макет `default`, отдельный preview route приложения и
браузерная проверка геометрии. Рабочие assignments не переключаются, БД и её
схема не меняются. Срез `without-topbar` описан в §3.10; текущее исправление
его preview UI — в §3.11.
Этот срез не требует реализации всего ядра, универсального установщика,
редактора или новой системы коллекций. Он не объявляется полным первым релизом.

Первый каркас охватывает архитектуру, layout, сетку, базовую палитру, параметры
и адаптивное поведение. Наполнение областей, реализация меню и элементов topbar
выполняются последующими шагами. Demo store, уведомления, профиль и task-specific
композиция референса не становятся обязательным наполнением каркаса.

Навигация нужна Admin и frontend, имеет гибкие настройки и синхронизацию с
роутингом. Состав и структуру формируют администраторы либо агенты с проверкой
полномочий. Показ дерева конкретного раздела определяется настройкой его пункта.
Выбор между компонентом, пакетом и плагином навигации, а также поставка topbar
и его элементов остаются отдельными решениями. Они не встраиваются в шаблон
как неотделимые функциональные подсистемы. Определение «ядра Realize» и границы
независимой поставки также остаются предметом дальнейшей проработки.

### 3.2. Макет внутри шаблона и система компоновки

Шаблон объединяет оформление, настройки, представления и один либо несколько
макетов. **Layout — «Макет»** в русскоязычной документации и интерфейсе. Макет
определяет композицию областей интерфейса внутри template package;
Next.js `layout.tsx` подключает host, но не является публичной моделью layout
редактора. У Control Panel согласованы два макета: `default` и
`without-topbar` по §3.8. Первый срез содержал пустой `default`; второй макет
описан в §3.10, исправление реактивного preview — в §3.11.

Используется полноценная система компоновки по проверенным подходам популярных
UI-библиотек. Все три уровня сохраняются; отказ от сетки содержимого ради
упрощения первого каркаса не является принятым решением.

| Уровень            | Контракт и реализация                                                                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Каркас панели      | CSS Grid с именованными областями, заданными размерами служебных панелей и растягиваемым содержимым `minmax(0, 1fr)`                                                                             |
| Содержимое экрана  | Адаптивная 12-колоночная сетка, span, вложенность, горизонтальные/вертикальные gutters; контейнеры fluid, ограниченный и узкий для чтения; автоматические сетки карточек при подходящем сценарии |
| Внутри компонентов | Flex для одномерных рядов/стеков и локальный Grid для двумерного размещения; компонент выбирает механизм по задаче                                                                               |

Это уровни одной дизайн-системы с общими токенами и правилами, а не три
независимых grid engine. Не каждый компонент обязан занимать 12 колонок:
полноширинные таблицы, формы и редакторы используют подходящую композицию.
Колонки и gutters относятся к содержимому, фиксированные панели — к каркасу.

Общие правила: шкала интервалов на базе 4px (4/8/12/16/24/32…), семантические
токены размеров и скруглений с сохранением принятой геометрии референса, mobile-first, `box-sizing: border-box`, логические
CSS-свойства, `min-inline-size: 0`/`min-block-size: 0` у сжимаемых областей и
явные владельцы прокрутки. Viewport управляет каркасом; независимые блоки могут
использовать container queries по доступной ширине. Breakpoints и их значения
не дублируются несогласованно в CSS и React. Тема, плотность, SSR/hydration и
portals получают согласованные значения через существующую границу host.

Основания: [Bootstrap Grid](https://getbootstrap.com/docs/5.3/layout/grid/)
(12 колонок, контейнеры, gutters), [Ant Design Layout](https://ant.design/components/layout/),
[Grid](https://ant.design/components/grid/) и [Flex](https://ant.design/components/flex/)
(каркас, сетка и локальная компоновка), [Tailwind responsive design](https://tailwindcss.com/docs/responsive-design)
и [Grid](https://tailwindcss.com/docs/grid-template-columns).
Применяются архитектурные подходы, установка самих библиотек не обязательна;
зависимости добавляются только при обоснованной необходимости в рамках общего
выбора стека, без параллельной UI-библиотеки ради сетки.

### 3.3. Области, пустые состояния и адаптивность

| Стабильный ID области | Назначение                                  |
| --------------------- | ------------------------------------------- |
| `rail`                | Область основной навигации                  |
| `topbar`              | Верхняя панель                              |
| `sidebar`             | Боковая панель                              |
| `panel-content`       | Основное содержимое экрана                  |
| `footer`              | Нижняя область справа от sidebar на desktop |

Название `workspace` не используется для новой публичной области содержимого,
чтобы не смешивать её с рабочими средами платформы. Существующий runtime API
с `screen: "workspace"` и прежние внутренние имена не переименовываются этим
документом; миграция потребителей требует отдельного изменения контракта.
Общий контейнер `panel-content` и `footer` — внутренняя деталь layout.

**Пустые области выводятся и сохраняют геометрию**. Отсутствие наполнения не
скрывает область и не перераспределяет её место. Наличие области, её содержимое
и адаптивная видимость различаются. При ширине viewport **≤1024px** применяется
мобильная композиция: desktop rail/sidebar убираются, навигация доступна через
мобильный drawer. При ширине **>1024px** действует desktop-композиция. Правило
охватывает дробные CSS-ширины; нельзя оставлять разрыв между 1024 и 1025px.

Topbar и footer остаются на месте при прокрутке `panel-content`; sidebar и rail
имеют собственные scroll области. Контекст страницы находится внутри
прокручиваемого содержимого. Широкие таблицы прокручиваются локально, не расширяя
document. Мобильный drawer сохраняет сетку под собой, управляет фокусом и
закрывается по Escape с возвратом фокуса. Минимальная высота footer утверждена: **36px на desktop и mobile**, включая
пустое состояние. Используется `min-block-size: 36px` с `box-sizing: border-box`: минимум
включает padding и border. Высота увеличивается по содержимому при переносе
текста и масштабировании, фиксированной высотой не ограничивается. Это целевой
контракт; runtime-код этим решением не изменён.

### 3.4. Принятая геометрия референса и условия корректировки

Проверка исходников и браузера 2026-11-09 охватила 10 размеров от 320 до 1440px,
включая границы 900/901px и desktop высотой 600px. Измерения относятся к preset
`comfortable`, sidebar 280px, светлой теме. Подтверждены отсутствие глобального
переполнения, фиксированное положение header/footer при прокрутке main и
мобильный drawer 390×844 с Escape/focus return. Тёмная тема в этой сверке не
проверена. Это evidence текущей геометрии, а не подтверждение реализации нового
breakpoint 1024px. Локальные материалы: `.ai-workspace/tasks/2026-11-09-control-panel-grid-reference/`
(`logs/grid-matrix.json`, `logs/behavior-checks.json`, `screenshots/`).

**Сетка референса принята как визуальная основа.** Пересмотр размеров только
ради кратности 4/8px не требуется. Предложения 74→72px, 58→56px, 52→56px и
изменения скруглений сняты. Общая шкала интервалов используется совместно с
семантическими layout-токенами, сохраняющими текущую геометрию.

| Параметр                          | Принятая основа (`comfortable`)                                                                                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Область rail                      | 74px                                                                                                                                              |
| Видимая панель rail               | 58px                                                                                                                                              |
| Topbar                            | 52px                                                                                                                                              |
| Sidebar                           | 280px                                                                                                                                             |
| Внешние отступы desktop           | 8px                                                                                                                                               |
| Промежутки панелей                | 16px                                                                                                                                              |
| Отступы mobile                    | 16px                                                                                                                                              |
| Скругление панелей                | 14px                                                                                                                                              |
| Внешнее скругление body           | 22px                                                                                                                                              |
| Footer с текущим demo наполнением | Измерено 35px desktop / 53px mobile; утверждённый минимум нового каркаса — 36px на desktop/mobile, включая пустое состояние; далее по содержимому |

Связи существующих размеров: `rail = 58 + 8 × 2`, внешнее скругление `14 + 8`.
Палитра Control Panel задаёт `--ui-surface-radius` через `--ui-radius-md`.
В обоих макетах все четыре угла sidebar, прокручиваемой области `panel-content`
и карточек внутри неё используют этот радиус (14px). В форме статьи видимая
рамка каждого раздела использует тот же токен. Правило действует в светлой и
тёмной темах, включая мобильный режим со скрытым sidebar.
[Замеры углов списка, формы и чтения](../../.ai-workspace/tasks/2026-11-11-control-panel-first-slice/logs/documents-corners-20261124/candidate-7ef4b5641b19a60f-result.json).

По проведённой сверке противоречий, требующих изменения геометрии, не обнаружено.
Улучшения структуры и поддержки направлены на единые источники размеров,
устранение дублирования и согласованную адаптивность. Изменение геометрии
допустимо только при выявленной конкретной проблеме (например, переполнение,
несогласованность отступов или конфликт адаптивных правил), с объяснением пользы,
минимальным влиянием на внешний вид и промежуточным согласованием.

Отдельное принятое изменение — mobile boundary **≤1024px** вместо прежних 900px.
Контрольные ширины новой композиции: 320/390/768/1024/1025/1280/1440px,
дополнительно дробная ширина у границы и малая высота; проверяются пустое,
длинное и динамическое наполнение. Отдельный визуальный вариант с округлёнными
размерами не нужен; браузерная приёмка проверяет сохранность референса и новый
breakpoint.

### 3.5. Компоненты и представления

Модуль владеет публичным контрактом данных, действий и обязательного поведения;
базовое представление использует общие primitives/tokens/slots. Шаблон может
заменить примитивы либо всё представление через объявленный совместимый контракт,
сохраняя функции, доступность и host ACL. Реестр различает идентичность и версию
контракта, доступные представления и описание возможностей редактирования.
Не каждый внутренний React-компонент или примитив обязан быть блоком редактора.

Представления не обязаны все физически храниться в каждом шаблоне: разрешается
явно объявленное совместимое базовое представление или наследование. Порядок
разрешения прозрачен: override активного шаблона → объявленное наследование/base →
ошибка совместимости. Отсутствие обязательного представления блокирует активацию;
автоматического возврата к штатному Payload UI нет. Точная schema реестра и
приоритетов требует контрактной проработки до реализации.

Администратор либо агент может создать собственный компонент по образцу
существующего: со своим ID, версией и доработанными параметрами/поведением.
Создание, проверка/поставка нового кода и активация — отдельные операции;
редактирование композиции само по себе не разрешает выполнение нового кода.
В области размещаются только совместимые компоненты: учитываются тип/контракт,
версия, target и ограничения области. Скрытие элемента меню не заменяет ACL.

#### 3.5.1. Описания для реестра и ИИ-агентов

Уточнение от 2026-11-16: публичные компоненты, примитивы, пакеты, плагины и
другие самостоятельные элементы Realize должны поставлять проверяемые сведения
для реестра и ИИ-агентов. UI-каталог Control Panel развивает общий подход из
[Declarative-first, §7.5–7.7](realize-ai-commerce/v1.0/01-architecture/07-declarative-first.md#75-проверяемое-описание-и-инструкция-у-владельца).
Доступность элемента в редакторе — отдельная характеристика; описание для
агента требуется и публичным элементам, которые не размещаются редактором.

Согласованные 16 ноября 2026 года правила идентичности, единственного владельца
контракта и независимых версий заданы в
[§7.5.1 Declarative-first](realize-ai-commerce/v1.0/01-architecture/07-declarative-first.md#751-идентичность-владелец-и-версии).
Control Panel использует эту общую модель: `namespace + id` сохраняется при
переносе реализации, выпуск пакета и digest отличаются от версии определения.
Это целевой контракт; действующие template ID, manifest protocol, версии и
receipts сохраняются. Формы identity, owner reference и versioned reference и
правила разрешения заданы в
[§7.5.2 Declarative-first](realize-ai-commerce/v1.0/01-architecture/07-declarative-first.md#752-формы-ссылок-и-проверка-разрешения).
Глобальная identity отличается от локального palette/layout ID; owner reference
не повторяет kind владельца. Черновик и опубликованная версия различаются,
неизменяемость начинается с принятой публикации. Проверка пяти реальных
элементов и границы текущего кода —
[в отчёте от 16 ноября](../reports/2026-11-16-element-identity-model-check.md).

Сохраняются три согласованные части: typed manifest рядом с владельцем
реализации, руководство по использованию и развитию, производный каталог из
фактических регистраций. Общая часть описывает устойчивую идентичность, вид,
владельца и происхождение, версии контракта и реализации, назначение и
ограничения, ссылки на публичные контракты, зависимости, руководства и
применимые проверки/операции. Сведения о жизненном цикле, замене и миграции
добавляются по применимости. Типовые расширения описывают особенности элемента:
параметры и slots компонента, совместимость представления, условия размещения
в области, редакторские поля либо состав и зависимости пакета. Единый подход
не требует одинакового набора UI-полей у всех видов элементов.

Схемы, defaults и сигнатуры не переписываются вручную для агента: manifest
ссылается на действующие источники. Реестр, Admin, редактор и агент получают
согласованные проекции этих сведений. Агенту выдаются выбранные описания и
нужные фрагменты руководств с точными версиями и hashes, в пределах задачи и
доступа. Полный каталог не включается в каждый prompt. Внутренний helper может
использовать руководство владельца; отдельный AI-файл на каждую функцию не
требуется. Контракт не зависит от поставщика модели или конкретного агента.

Описание поддержанной операции не регистрирует executor и не предоставляет
полномочий. Руководство установленного элемента не становится автоматически
действующей системной инструкцией. Применимость инструкций, текущие права,
доступность реализации и результаты проверок различаются и проверяются
соответствующими владельцами; векторный индекс остаётся производным средством
поиска, а не источником контрактов или разрешений.

**Фактическое состояние:** подход частично реализован в manifests
Pages/Content/FormBlock и их производном каталоге —
[§14.9 Data Lane](realize-ai-commerce/v1.0/02-change-engine-and-pipelines/14-data-config-pipeline.md#149-каталог-и-структура-pages-первый-реализованный-срез).
Это предметный пилот, не общий реестр всех компонентов. Первый общий срез
owner registrations и его нейтральный владелец согласованы в §3.5.2; полная
schema descriptors и подключение всех UI-элементов остаются следующими шагами. Настоящее уточнение не добавляет произвольное поле `ai`
в действующие manifests и не меняет существующие API или инструкции агентов.

#### 3.5.2. Регистрация владельца Control Panel в первом общем срезе

**Согласовано 2026-11-17.** Общий контракт owner registrations и resolver задан
в [§7.5.3 Declarative-first](realize-ai-commerce/v1.0/01-architecture/07-declarative-first.md#753-первые-регистрации-владельцев-и-нейтральный-resolver).
Control Panel использует его как потребитель; отдельная UI/AI модель владения
не создаётся.

Host явно регистрирует P: namespace `realize`, id
`project.realize-ai-platform`, kind `project`, title «Realize — AI Platform».
P — доверенный terminal anchor без owner. Пакет предоставляет T: namespace
`realize`, id `package.template-realizeai-control-panel`, kind `package`,
title «RealizeAI Control Panel», owner `{ identity: P }`. Kind и version
в OwnerRef не дублируются. Package identity T отличается от native template ID
`realizeai-control-panel` и npm packageName.

Owner registration не является опубликованным descriptor. Если descriptor
публикуется позднее, он использует ту же identity, а не создаёт второго
владельца. Начальная конфигурация не получает фиктивную SemVer; её точное
содержимое фиксирует детерминированный snapshot hash. Package binding отдельно
указывает `@realize/template-realizeai-control-panel@0.1.0` и required exports
`./manifest`, `./admin`, `./settings`, `./registry`. Host exact dependency задаёт
ожидаемую package version; фактические name/version/exports проверяются по
доверенному import package metadata через новый export `./package.json`.
Package version не выводится из template.version как общее правило.
Source bindings и наличие npm metadata не подтверждают runtime installation,
readiness или полномочия actor.

Ограниченная реализация находится в нейтральном `@realize/element-registry@0.1.0`;
template package предоставляет server-safe `/registry` с декларацией T. Host конфигурация
`src/registry/realizeOwnerRegistry.config.ts` собирает P/T и один package binding,
а `src/registry/realizeElementOwnerBindings.config.ts` — пять явных mappings:
Pages → P, template/palette/default layout/without-topbar layout → T. Metadata
передаются resolver через вход; зависимости на Payload, React, ИИ и чтение
файловой системы ему не требуются. Первый исходный срез поддерживает package owner
с цепочкой к явному root project, без заявления готовой поддержки всех kinds.

На первом owner-срезе Pages сохранял native `1.1`, template и palette —
`0.1.0`, макеты ещё не имели собственной definition version. Последующий
layout-срез §3.8.1 вводит первые самостоятельные draft definitions `0.1.0`,
без ретроактивной публикации и изменения исторического отчёта. Выпуск пакета не подставляется
в version макета; прежние manifests, selections, settings/protocol и receipts
не переписываются. Snapshot копируется и глубоко замораживается; lookup не
выбирает неизвестному owner проект автоматически. Его hash покрывает только
owner registrations и resolved package binding с export targets — не пять
source mappings, код, артефакт установки или ACL. Browser-safe entry общего
пакета экспортирует schemas/types; создание snapshot и lookup доступны из
`/server` с Node crypto, без файловых операций.

Ввод этих registrations не изменяет session/ACL, preview-only admission,
рабочие назначения, БД или порядок установки. Публикация полных descriptors,
installer, Context Pack compiler и новая выдача инструкций агентам остаются
отдельными шагами. Текущий host entry — read-only композиция при собственном
импорте; он не подключён к Payload/Extension Manager startup, HTTP/UI API или
runtime admission. Обычный запуск приложения ещё не гарантирует его импорт.
Общий published descriptor/versioned resolver и module-owner profile не
реализованы.

Проверены 4 Vitest suites / 79 tests (30 общих и 49 host/catalog/SDK), полный
typecheck и адресный ESLint. Отдельный Node import разрешил 2 owners, один
package binding и пять mappings без React/CSS загрузки. Реальные source owners:
[пакет](../../packages/element-registry/README.md),
[декларация T](../../packages/template-realizeai-control-panel/src/controlPanelOwnerRegistration.config.ts),
[host registry](../../src/registry/realizeOwnerRegistry.config.ts),
[mappings](../../src/registry/realizeElementOwnerBindings.config.ts).
Подробный [отчёт от 17 ноября](../reports/2026-11-17-element-owner-registry-first-slice.md)
описывает именно этот ограниченный implemented срез. Отчёт от 16 ноября
сохраняет статус исторического read-only исследования и не переписывается.

### 3.6. Будущий редактор Realize

Основной ориентир — собственный редактор, адаптированный под Realize. Puck
рассматривается как референс и возможный источник механизмов; окончательное
решение об использовании его кода или иной библиотеки не принято. Архитектура
не связывается с внутренними типами Puck, его `Config` или `DropZone`.
Собственный редактор может использовать проверенные библиотеки для отдельных
механизмов, не требуя разработки drag-and-drop и всех UI-средств с нуля.

Целевые границы:

- **Документ композиции:** сериализуемая структура с версией схемы, ссылками на
  template/layout и контракты компонентов, устойчивыми instance ID, параметрами,
  именованными slots, bindings данных и revision. HTML/DOM и React callbacks не
  являются источником истины документа.
- **Контракты и реестр:** проверяемые параметры/defaults, slots, совместимость,
  допустимая вложенность и действия; UI metadata редактора отделены от схемы
  валидации. JSON Schema — ориентир переносимого описания, конкретный формат и
  владельцы согласуются до добавления нового API.
- **Runtime:** host разрешает ID действий и источников данных в авторизованные
  callbacks/DTO. Ссылки на сущности различаются со снимками данных. Preview и
  рабочий интерфейс используют общий механизм представлений и разрешения темы.
- **Операции:** UI редактора и агенты используют общие проверяемые изменения
  (добавить/переместить/удалить компонент, изменить параметры, привязать данные).
  Сохранение проверяет структуру, права и expected revision на сервере;
  поддерживаются история и отмена в определённой области. Конкретный command API
  и persistence пока не реализованы и требуют отдельной спецификации.
- **Публикация:** черновик, предпросмотр, проверка и активация разделены;
  автосохранение не активирует интерфейс. Контракты и сохранённые документы
  версионируются; изменения параметров требуют миграции или совместимости.
- **Уровни настройки:** оформление, наполнение областей и структура layout
  различаются. **Изменение самой структуры — отдельная возможность редактора**
  с отдельными полномочиями; первый каркас сохраняет согласованную геометрию.
- **Среда:** клиентский редактор отделён от SSR/runtime и серверных resolver;
  preview получает тему, assets и providers в своей среде, включая iframe при
  его выборе. Изменения композиции не теряют доменные drafts/pending commands.
- **Доступность:** drag-and-drop дополнен клавиатурой и действиями указателя
  без перетаскивания (выбрать область, добавить, переместить выше/ниже).

Существующий `TemplatePresentationProps` с ReactNode/callbacks остаётся runtime
контрактом, а не форматом persistence редактора. Развитие использует существующие
`template-contracts`, template package, host, Мастерскую и Extension Manager;
отдельный универсальный engine/installer или параллельный storage не создаются
автоматически из этого решения. Точные границы новых owners определяются при
проектировании редактора. Полный редактор не входит в первую итерацию каркаса;
его будущая совместимость учитывается сейчас. CRDT/collaboration, произвольный
редактор исходников и свободный CSS не объявляются частью первого этапа.

### 3.7. Согласованный контракт настроек и приоритеты

Решение согласовано 2026-11-09. Таблица описывает целевой контракт; новые поля,
пользовательские предпочтения и их применение не считаются реализованными
только вследствие обновления документа.

| Уровень           | Содержание                                              | Владелец хранения/определения                                  |
| ----------------- | ------------------------------------------------------- | -------------------------------------------------------------- |
| Оформление        | Палитра, светлый/тёмный режим, плотность                | Назначение шаблона и разрешённые пользовательские предпочтения |
| Макет (layout)    | Области, размеры, интервалы, адаптивность и ограничения | Версионируемое определение макета с ограниченными настройками  |
| Композиция        | Компоненты областей, порядок, параметры и bindings      | Отдельный документ композиции в рамках будущего редактора      |
| Runtime-состояние | Открытый drawer, выбранный элемент, прокрутка           | Состояние интерфейса, отдельно от настроек шаблона             |

Первоначальный публичный набор:

| Поле                | Контракт                                                                                                               |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `paletteId`         | Совместимая палитра из manifest; существующее поле назначения, не дублируется внутри `settings`                        |
| `mode`              | Светлый/тёмный режим через существующий механизм оформления; не дублируется внутри `settings`                          |
| `density`           | `comfortable` / `compact`; конкретные изменения описаны токенами                                                       |
| `panelWidth`        | Существующее имя настройки, допустимый диапазон 220–400px, default 280px                                               |
| `settings.layoutId` | Необязательный явный выбор макета из каталога установленной версии; отсутствие означает наследование `defaultLayoutId` |

Выбор макета хранится в `settings.layoutId`, без добавления поля в `selection`.
Каталог и `defaultLayoutId` принадлежат определению версии шаблона по §3.8.
Изменение schema и обратная совместимость реализуются в TASK-25; новое поле не
передаётся в текущий strict validator до обновления владельца схемы.

Геометрия по умолчанию остаётся референсной: rail 74px, topbar 52px, sidebar
280px; footer имеет утверждённый минимум 36px. Mobile boundary — ≤1024px.
Ширина rail, высота topbar, скругления, интервалы и breakpoint представлены
именованными токенами layout; они не становятся отдельными полями обычной
формы настроек. Будущий редактор структуры получает доступ только к явно
объявленным возможностям. Плотность не должна неявно менять внешнюю геометрию:
изменение размеров каркаса требует отдельного описания токенов и проверки.

Экран внутри `panel-content` выбирает контейнер: полноширинный (`fluid`),
ограниченный (`contained`) или узкий для чтения (`reading`). Ограничения ширины
задаются токенами. Это контракт композиции экрана, а не глобальный параметр,
принуждающий все экраны к одной ширине. Экран использует общую 12-колоночную
сетку, gutters и вложенные Grid/Flex по §3.2.

Для каждого набора параметров один источник схемы обеспечивает серверную
валидацию, типы и описание полей редактора; layout формы и группировка полей
отделены от правил допустимости значений. Неизвестные параметры отклоняются.
Несовместимые сохранённые значения требуют миграции либо явного решения, без
тихого сброса на defaults. Наследуемые defaults и значения, явно выбранные
администратором, различаются при разрешении настроек.

Приоритет effective settings: **defaults версии шаблона → настройки назначения →
разрешённые пользовательские предпочтения**. Последний применимый уровень имеет
приоритет только для разрешённых ему полей. Пользователь может менять mode и
density в пределах политики администратора; эти preferences не меняют структуру
layout. Persisted preferences проверяются на совместимость с выбранной версией,
SSR/client/portals получают один разрешённый снимок. Существующий mode/cookie
механизм учитывается при реализации без молчаливого изменения его поведения;
пользовательская density этим документом ещё не внедрена.

### 3.8. Каталог макетов, default и явный выбор

Решение согласовано 2026-11-09. Пользовательское название поля — **«Макет»**.
Технические идентификаторы `layoutId` и `defaultLayoutId` сохраняются.

| Часть контракта     | Владелец                                | Смысл                                                                     |
| ------------------- | --------------------------------------- | ------------------------------------------------------------------------- |
| Каталог макетов     | Определение версии шаблона              | Стабильные ID, названия, поддерживаемые области и совместимость           |
| `defaultLayoutId`   | Определение версии шаблона              | Макет, применяемый при наследовании выбора; для первого выпуска `default` |
| `settings.layoutId` | Настройки назначения Admin или frontend | Необязательный явный выбор администратора из совместимых макетов          |

`selection` выбирает шаблон и его выпуск, а макет является настройкой выбранного
шаблона. Каталог и default проверяются вместе с установленной версией; renderer
разрешает только объявленные совместимые макеты. Конкретная сериализуемая schema
каталога и связь с compiled exports требуют изменения существующих контрактов,
а не второго registry или исполнения кода из JSON.

Первые два макета Control Panel для Admin:

| ID               | Название           | Поведение                                                                                     |
| ---------------- | ------------------ | --------------------------------------------------------------------------------------------- |
| `default`        | Стандартный        | Принятая геометрия референса со всеми согласованными областями                                |
| `without-topbar` | Без верхней панели | Topbar отсутствует по определению макета; освободившуюся высоту занимает нижняя часть каркаса |

В `default` пустой topbar продолжает занимать 52px. В `without-topbar` его
отсутствие — свойство структуры другого макета, а не автоматическое скрытие
пустой области. Остальные области сохраняют принятые размеры и поведение;
footer — минимум 36px. Правила §3.3 применяются к областям, предусмотренным
выбранным макетом. Два действительных макета нужны для проверки сменности;
это не два шаблона и не две палитры. Набор frontend-макетов определяется отдельно,
Admin-only макет не становится совместимым с frontend автоматически.

Разрешение выбора:

1. Явный `settings.layoutId` выбирает соответствующий совместимый макет.
2. Отсутствие поля означает наследование `defaultLayoutId` установленной версии.
3. Неизвестный либо несовместимый ID — ошибка совместимости, без тихой подмены.

Поле «Макет» показывает «По умолчанию», «Стандартный», «Без верхней панели».
«По умолчанию» — режим наследования, не отдельный сохранённый ID и не строковое
значение `layoutId`. Валидация runtime может вычислить effective ID, но persistence
должен сохранять различие между наследованием и явным выбором, не материализуя
default незаметно. Текущие сохранённые назначения без поля требуют проверки
совместимости при переходе; прежний baseline `0.1.0` не переписывается.

При обновлении версии изменение её default видно в preview. Явно выбранный
макет не заменяется молча: удаление/несовместимость требует миграции или решения
администратора. Выбор установленного макета и редактирование самой структуры —
разные возможности; последнее остаётся отдельной функцией редактора.

Управление оформлением, выбор макета и recovery доступны на отдельном экране
настроек и при `without-topbar`; доступность не зависит исключительно от кнопок
верхней панели. Смена макета сохраняет host ACL, доменные drafts/pending commands
и проходит проверки desktop/mobile, пустых областей и переполнения. Общий
каталог, сохранение назначения и пользовательские ревизии остаются target
contract; текущая реализация переключения ограничена preview по §3.10.

#### 3.8.2. Точная фиксация макета в назначении: сначала readers

**Согласовано 2026-11-18; первый reader-only этап реализован и проверен в source.
Второй source-срез описан ниже; durable запись binding выключена.** Самостоятельные definitions и release pins из
§3.8.1 подключаются к назначениям поэтапно. Общий контракт и порядок доставки —
[§7.5.5 Declarative-first](realize-ai-commerce/v1.0/01-architecture/07-declarative-first.md#755-exact-layout-binding-назначения-и-reader-before-writer).
Первый этап ограничен строгим чтением optional binding; durable сохранение таких
назначений и активация сейчас не разрешаются.

```ts
layout?: {
  schemaVersion: "1.0";
  localId: string;
  reference: LayoutVersionedRef;
  catalogHash: string;
};
```

Это server-derived поле `ExtensionAssignment`, не новая пользовательская
настройка и не новая коллекция. `localId` выбирается из каталога точного
template release; `reference` фиксирует global identity и definition version;
`catalogHash` относится к layout-каталогу этого выпуска. Owner snapshot hash и
существующий appearance catalog hash имеют другое назначение. Общая строгая
schema binding принадлежит Template SDK, а не частному пакету Control Panel.

`settings.layoutId` сохраняет intent: явный `default`/`without-topbar` остаётся
явным; отсутствие key (`undefined` при чтении отсутствующего свойства) означает
наследование; `null` невалиден. При наличии
binding явный alias обязан совпадать с `layout.localId`. При наследовании pure
resolver второго среза фиксирует effective alias/reference в binding, не материализуя default
в settings. Назначения без binding читаются как legacy в прежней форме:
их настройки не переосмысливаются, defaults и отсутствующий `layout` не
добавляются по текущему каталогу.
Явный `layoutId: undefined` нарушает bounded JSON контракт settings. Отсутствующий
binding опускается; собственные поля `layout: undefined` и `layout: null`
отклоняются reader.

В первом этапе расширены только общие типы, строгие DTO/schema и codec
state/plans/receipts. Чтение проверяет форму, неизвестные ключи, формат точной
версии/hash и согласованность явного alias; оно не проверяет происхождение hash,
доступность pin, установку кода, совместимость renderer, readiness и права.
На первом этапе resolver/prepare сохранял прежнюю форму без binding.
Appearance catalog hash, hashes legacy записей и успешные receipts этим этапом
не менялись; пересчёт истории, SQL migration и автодоставка reader не выполнялись.
Assign/recover/apply commands не принимают поле `layout` извне.

экрана настроек и не обязательная часть шаблона.

- legacy reference, основные маршруты и рабочие назначения сохраняются;
- фактические browser evidence и результаты проверок добавляются после

### 3.11. Исправление preview UI и реактивное переключение

Текущий корректирующий шаг заменяет ошибочный нативный preview UI из §3.10:
`details`/`summary`, raw select и GET reload. Выбор макета и режима применяется
сразу, без кнопки отправки, перезагрузки document, `location.assign` или записи
в cookie. Рабочие assignments, БД и общий installed catalog не меняются.

Панель проверки использует общий `UiButton` как trigger, `UiPopover` на
существующем Floating UI и управляемые `UiSelectMenu` на уже установленном
Radix Select. Компоненты принадлежат UI-киту; preview содержит только данные
полей и controller, без локальной параллельной реализации меню/порталов.
Нативный `UiSelect` и API его существующих потребителей сохраняются.

Публичные границы новых primitives ограничены текущим сценарием:

- `UiPopover`: controlled open/onOpenChange и renderTrigger;
- `UiSelectMenu`: controlled value, options, onValueChange и mode;
- общий nested portal container context в UI-ките;
- обратно совместимое optional расширение mode в `UiTemplateProvider`;
- optional `TemplateButtonProps.appearance?: "default" | "toolbar"` для
  явного подключения toolbar-представления кнопки.

Кроме перечисленных optional полей, primitive API и template protocol не расширяются. UI-kit добавляет
Radix Select как peer dependency по существующему root constraint `^2.3.3`;
версии внешних dependencies не обновляются. Общий контракт —
[Popover и управляемый список выбора](../architecture/ui-kit.md#popover-и-управляемый-список-выбора).

Client controller хранит layout/mode выше `Renderer` и controlled provider.
Обновление значения сразу меняет представление и адрес через History API
`pushState`; `popstate` восстанавливает состояние при back/forward. Начальный
SSR-снимок и гидратация согласованы с проверенными URL-параметрами; явный reload
страницы по-прежнему восстанавливает выбор из URL. Отсутствие `layout` означает
наследование и не превращается в явно сохранённый `default`. Смена режима
распространяется также на открытые portals через общий theme/provider, не
сбрасывая controller или пользовательские черновики renderer.

Геометрия макетов и независимое фиксированное размещение панели остаются по
§3.10. Размер trigger/панели не прыгает от длины выбранного названия или темы.
Popover закрывается наружным кликом и Escape с возвратом фокуса. Когда открыт
вложенный Select, первый Escape закрывает только его список; родительская
панель остаётся открытой. Светлая и тёмная темы используют semantic CSS и
`UiTheme`, включая portal вложенного списка.

Уточнение по screenshot и измерениям Task Manager от 2026-11-12:
обычный UI-button 42px с текстом 14px не является корректным действием внутри
topbar 52px. Новый package-owned `ControlPanelButton` отвечает за toolbar
presentation через активный UI adapter. `UiButtonPrimitive` потребляет
`appearance` и выводит `data-ui-appearance`; прежние consumers без поля
сохраняют поведение, legacy template не меняется.

Preview trigger использует `UiButton appearance="toolbar" variant="ghost"`
с иконкой 17px. Измеренная desktop-основа текстового действия: min-height 34px,
фактическая высота 36px (line-height 20px + вертикальные padding 7px × 2 +
border 2px), font 12px/600, radius 9px, gap 7px, padding 7px 10px. Touch target
остаётся не менее 44px. Нормальный ghost прозрачен и использует muted text;
hover/open — semantic surface-raised и основной text без изменения размеров.
Эта геометрия принадлежит шаблонному adapter, а не локальному CSS preview.

Стабильная обёртка `data-preview-canvas` находится вне сменяемого renderer и
сохраняется при переключениях и History API. Dismiss должен распознавать клик
по ней после смены макета, режима и back/forward; ссылка на прежний renderer
не может исключать наружный клик. Контракты вложенного Select и Escape
сохраняются. Подробности —
[toolbar appearance](../architecture/ui-kit.md#кнопки-верхней-панели-и-toolbar-appearance).

Уточнение dropdown к Task Manager reference от 2026-11-12 не расширяет props
`UiPopover` и `UiSelectMenu`. В `ControlPanelPalette` добавлены template-owned
семантические переменные, передаваемые также через `UiTheme` portals:

- `--ui-popover-width: 280px`, `--ui-popover-body-padding: 12px`;
- `--ui-menu-radius: var(--ui-radius-md)` (14px), `--ui-menu-padding: 5px`;
- `--ui-menu-font-size: 13px`, `--ui-menu-font-weight: 500`,
  `--ui-menu-line-height: 18px`;
- `--ui-menu-item-radius: var(--ui-radius-sm)` (10px),
  `--ui-menu-item-padding-inline: 9px`;
- `--ui-menu-selected-background: color-mix(in srgb, var(--ui-color-primary) 9%, var(--ui-color-surface))`.

Общие primitives имеют fallback, поэтому другим шаблонам не навязывается
presentation Control Panel. Точная таблица fallback —
[геометрия dropdown](../architecture/ui-kit.md#геометрия-dropdown-и-presentation-токены-шаблона).
Пункты меню имеют minimum height 36px и 44px на coarse pointer; selected
использует primary text и primary9% background, highlighted — surface-raised.
Legacy template и нативный `UiSelect` не меняются.

Общая `UI_FLOATING_GEOMETRY` задаёт указатель Popover 20×12px, arrow padding
20px, gap 6px и collision padding 8px. Popover width 280px и body padding 12px
не принадлежат локальным стилям preview. Отдельный scroll body ограничивается

Критерии приёмки исправления:

- макет и mode меняются немедленно без document reload, GET submit, assign
  и cookie writes; URL и controller сохраняют один выбор;
- reload/back/forward восстанавливают выбор, наследование отличается от явного

### 3.12. Внутренняя сетка содержимого

Текущий срез реализует согласованный второй уровень компоновки из §3.2 через
общие `UiContainer`, `UiGrid` и `UiGridItem` в UI-ките. Архитектурные основания —
контейнеры/колонки/gutters Bootstrap и Grid/Flex/container queries Tailwind,
ссылки приведены в §3.2. Сами Bootstrap/Ant Design не устанавливаются.

`UiContainer` предоставляет `fluid`, `contained`, `reading`; все варианты имеют
inline-size 100%, min-inline-size 0 и margin-inline auto, без дополнительного
padding поверх shell. `fluid` занимает доступную ширину. **Defaults данного
среза** — contained максимум 80rem и reading максимум 72ch, задаваемые токенами
`--ui-container-contained-max` и `--ui-container-reading-max` в палитре Control
Panel и fallback общего primitive. 72ch зависит от метрик шрифта; 80rem не
является фиксированной шириной каждого экрана.

`UiGrid` задаёт 12 колонок `repeat(12, minmax(0, 1fr))`. Горизонтальный и
вертикальный gutters независимы: `--ui-grid-column-gap` и `--ui-grid-row-gap`,
оба по умолчанию `var(--ui-space-4)` (16px). `UiGrid.style` принимает
экспортируемый `UiGridStyle`: `CSSProperties` с optional строковыми
`--ui-grid-column-gap` / `--ui-grid-row-gap`. Экран независимо задаёт запрошенные
gutters этими variables через общие spacing-токены или CSS-длины. Прямой inline
`columnGap` не используется, поскольку обходит защиту общего CSS. Новые поля
настроек шаблона или дублирующие gap-props для этого не создаются.

Column gutter вычисляется как `min(requestedGap, calc(100% / 12))`, где
requestedGap — `--ui-grid-column-gap` либо fallback `--ui-space-4`. При достаточной
ширине запрошенные 16px/24px сохраняются; в узком слоте верхний предел оставляет
неотрицательную доступную ширину для всех 12 треков. Row gutter сохраняет своё
независимое значение. Browser-проверка до исправления выявила overflow при
viewport 320px: вложенная сетка 228px имела 11 gutters по 24px (264px).
Новый предел в таком слоте — 19px; исправление внесено в общий primitive,
а demo использует variables, чтобы не обходить его inline `columnGap`.

`UiGridItem.span` принимает число 1…12 или объект `{ base?, md?, lg? }` с такими
же значениями. Default — все 12 колонок. Пропущенный base означает 12, md
наследует base, lg — md. Например, `{ base: 12, md: 6, lg: 4 }` даёт три
возможных раскладки карточек по доступной ширине. Внутренние CSS variables
base/md/lg задаются заново на каждом item; вложенный item без span не наследует
ширину внешнего элемента.

**CSS-only thresholds данного среза:** md от 48rem и lg от 64rem по ширине
ближайшего именованного inline-size container `UiGrid`. Это не viewport
breakpoints: вложенная сетка измеряет собственную ширину. Значения определены
только в CSS, без React hooks/JS-копии и hydration-перекомпоновки. Порог
перестроения самого shell **≤1024px остаётся прежним** и не связывается с

### 3.13. Подключение к штатным настройкам без активации

Исходный срез от 2026-11-12/13 подключает Control Panel к существующим
штатным настройкам оформления. Это интеграция исследуемого appearance-механизма,
а не принятие его прототипа lifecycle как общей доктрины платформы. Пакет
предоставляет server-safe export `/settings`; host добавляет его manifest,
settings schema и compiled validator в серверный каталог с
`readiness: "preview-only"`.

Readiness — optional host-owned policy `"ready" | "preview-only"`, отсутствие
которой сохраняет прежнее ready-поведение legacy. Она не является возможностью,
которую шаблон может сам себе выдать через manifest. Readiness влияет на
`catalogHash`, не меняя `manifestHash` прежнего manifest. Readonly plan DTO
показывает readiness кандидата; plans, assignments, history и receipts не
получают нового persisted поля.

Разрешены редактор настроек, prepare и защищённый actor-bound preview после
проверок actor, TTL, catalog/revision и settings. Новое применение preview-only
назначения (включая recover), использование его как current/bootstrap/fallback
и активация пакетной оболочки запрещены серверной проверкой
`TEMPLATE_PREVIEW_ONLY`. Повтор ранее успешно выполненной операции возвращает
прежний receipt по существующим replay-гарантиям, без повторной активации.

Inventory отключает select с причиной `preview_only`, сохраняя отдельную
доступность settings и остальные ACL/runtime/storage gates. UI выключает Apply
и не отправляет его из command hook; серверный gate обязателен независимо от
клиентского состояния. Ready legacy-шаблоны продолжают штатные сценарии.
Статус карточки доступного пакета — «Для предпросмотра», даже если runtime
пока unverified; причина недоступности действия показывается отдельно.

Protected preview использует generic readiness, не special-case по ID нового
шаблона: для preview-only renderer передаётся пустая функциональная модель без
рабочей навигации, capabilities и page actions. Содержимое и controls явно
проверочные. Обычный runtime не использует этот режим для рабочих экранов.

Для optional enum общий settings editor показывает «По умолчанию»: выбор
удаляет поле settings, сохраняя наследование, а не записывает пустую строку.
Для `layoutId` явные `default` и `without-topbar` остаются отдельными значениями.
Required enum не получает фиктивного наследования; defaults/schema валидации
остаются у владельца параметров.

Срез не требует миграции или изменения schema БД, не применяет назначения
автоматически, не редактирует legacy-навигацию и не создаёт новый installer.
Prepare использует существующее хранилище планов/replay; чтение и preview
не меняют рабочее назначение. Доступность source
каталога не объявляется подтверждённой runtime-установкой. Публичный
`/reference/control-panel` сохраняется отдельным UI preview; защищённый preview
работает через штатную проверку сессии/ACL и actor-bound плана.

Критерии приёмки:

- новый пакет виден в штатном catalog/settings без React/CSS импорта серверным
  `/settings` entry и без изменения старого manifest/hash;
- отсутствие readiness совместимо с legacy; её изменение меняет catalog hash,
  candidate DTO не расширяет persisted ledger/history;
- разрешённый actor может подготовить и открыть preview обоих макетов с
  разрешёнными settings, optional layout inheritance сохраняется;
- UI и server исключают применение/current/bootstrap/shell activation
  preview-only, прямой API не обходит запрет;
- готовый legacy candidate и точный replay прежнего успешного результата
  сохраняют поведение, readiness не превращается в новый authority пользователя;
- рабочие назначения и БД не меняются от чтения, настройки draft или preview;
  invalid settings/actor/TTL/catalog/revision сохраняют явные отказы.

Общий контракт —

#### 3.14.1. Административные документы и защищённое чтение

**Первый срез реализован и проверен в изолированной среде 2026-11-22.**
Добавлена самостоятельная Payload collection
`documents` («Документы»). Все CRUD операции доступны только администратору
через существующую `adminOnly` policy. Это сущность документа, а не настройка
шаблона; общий редактор, workflow, status, drafts и публикация в срез не входят.

| Поле | Хранение и ограничения |
| --- | --- |
| `id` | Native Payload identity документа |
| `slug` | Обязательный unique/indexed text до 128 символов, строгий ASCII lowercase-kebab; адрес документа |
| `title` | Обязательный text, до 160 символов |
| `description` | Необязательный textarea, до 1000 символов |
| `sections` | Упорядоченный array, минимум один раздел |
| `sections[].anchor` | Обязательный явный ASCII lowercase-kebab, до 128 символов; уникален внутри документа |
| `sections[].title` | Обязательный text, до 160 символов |
| `sections[].paragraphs` | Упорядоченный array, минимум один объект `{ text }` с обязательным textarea; текст не состоит только из whitespace |
| `updatedAt` | Native Payload timestamp, не ручное поле формы |

Native IDs строк массивов не заменяют `anchor`. Изменение заголовка не
пересчитывает slug/anchors; повторные anchors и невалидные
идентификаторы отклоняются, без автоматической генерации суффиксов или тихого
переименования. Абзацы остаются обычным текстом, не HTML/rich text или схемой
блоков будущего редактора.

Защищённый маршрут — `/system/documents/[slug]`. Он сначала применяет
существующий `requireSystemAdmin`, затем читает точный slug через Local API
от имени текущего actor (`user/req`), с `overrideAccess: false`, `depth: 0`,
`limit: 1`. Server guard не заменяет collection ACL. Невалидный slug либо
отсутствующий документ завершается 404, без fallback к fixture или чужому документу.

Server mapper выдаёт только `DocumentReadingScreenProps`: `title`, optional
`description`, ISO `updatedAt` и readonly `sections[{ id: anchor, title,
paragraphs: string[] }]`. Raw Payload document и native array row IDs не
передаются экрану/client boundary. Существующие mode/layout query и каркас
панели переиспользуются без изменения рабочего назначения или сохранения
preview preferences в БД.

Публичный `/reference/control-panel/document` продолжает получать только
локальную fixture: реальные документы через него не выдаются. Его прежняя
browser-приёмка не подтверждает protected route, ACL или persistence нового
среза. Новые коллекция/mapper/route и миграция проверяются отдельно.

Schema source принадлежит коллекции; миграции создаются штатным Payload/Drizzle
генератором. SQL/TS/snapshot/index и generated types не правятся вручную.
Upgrade и сохранность прежних данных проверяются на изолированной БД.
Применение миграции к рабочей установке и deployment в этот срез не входят.

На отдельном PostgreSQL прошли 35 миграций, включая цикл `down` и `up`
пустой коллекции `documents` с сохранением трёх существующих тестовых
пользователей. Администратор создал документ через Payload API, открыл его и
увидел обновлённое содержимое при повторном открытии. Повторные slug и anchors
дали HTTP 400, неизвестный и невалидный slug — 404.

Гость и пользователь с ролью `customer` получили перенаправление с защищённого
экрана, а API отклонил их операции чтения, создания, изменения и удаления с
HTTP 403. Chrome подтвердил чтение обновлённого текста в `default` и

| `/system/documents/[slug]` | `fromPage` | Страница для ссылки «Все документы» над статьёй. Без параметра ссылка ведёт на первую страницу. |

`page` и `fromPage` принимают одно положительное целое десятичное значение
в поддерживаемом диапазоне. Некорректные или повторяющиеся значения дают 404.
Канонические ссылки опускают значение `1`. После проверки доступа запрос
страницы за концом списка перенаправляется на последнюю доступную страницу
или на первую при пустой коллекции. Ссылки пагинации, перехода к чтению и
возврата сохраняют текущие `mode` и `layout` в `href`, включая изменения через
панель предпросмотра. Отсутствие `layout` означает наследование макета по
умолчанию. Возврат использует фиксированный маршрут списка и проверенный
номер страницы. При смене страницы списка прокручиваемая область содержимого
открывается сверху.

`DocumentListScreen` зарегистрирован как компонент проекта
`realize/document-list-screen@0.1.0`. Server binding связывает его с существующим
project owner и renderer. Agent metadata имеет режим `descriptive-only`, editor
metadata — `metadata-only`.

#### 3.14.3. Создание статьи внутренней документации

Действие «Создать статью» рядом с заголовком списка открывает защищённый
маршрут `/system/documents/actions/create` в `panel-content` обоих макетов.
`fromPage` задаёт исходную страницу списка. При прямом входе используется
первая страница. Вложенный путь сохраняет доступ к статьям с любым уже
допустимым одноуровневым `slug`, включая `create` и `actions`.

| Поле | Контракт формы |
| --- | --- |
| Заголовок статьи | Обязательный, до 160 символов. |
| Адрес статьи (`slug`) | Обязательный, до 128 символов. Уникален в `documents`. |
| Краткое описание | Необязательное, до 1000 символов. |
| Разделы | Минимум один. В каждом обязательны заголовок, `anchor` и хотя бы один непустой текстовый абзац. |

Форма начинается с одного пустого раздела и абзаца. Администратор может
добавить разделы и абзацы и изменить их порядок. Форма предлагает `slug` и
`anchor` по заголовкам: транслитерирует кириллицу, приводит латиницу к нижнему
регистру и разделяет слова одиночными дефисами. `anchor` использует тот же
формат, до 128 символов, и уникален внутри статьи. Пример ссылки —
`/system/documents/kak-nastroit-maket#pervyi-zapusk`.
До ручной правки адрес следует за заголовком. После ручной правки сохраняется
выбранное значение. Сервер сохраняет подтверждённые адреса как стабильные
идентификаторы, в том числе при последующем переименовании заголовка.

Серверное сохранение проверяет административную cookie-сессию и применяет
ACL коллекции `documents` через Payload с `overrideAccess: false`. Уникальность
`slug` защищена индексом БД, включая параллельные сохранения. Пока запрос идёт,
форма блокирует повторное сохранение. При успехе открывается созданная статья
с текущими `mode`, `layout` и `fromPage`. «Отмена» возвращает к списку с теми же
настройками, а при изменённой форме сначала запрашивает подтверждение выхода.

Форма проверяет поля до отправки, сервер повторяет проверку перед записью.
Ошибки валидации и занятых адресов появляются у соответствующих полей, фокус
переходит на первое ошибочное поле. Ввод и порядок разделов и абзацев
сохраняются при исправлении ошибок и переключении макета. Если результат
записи неизвестен, форма запрашивает статью по одному `slug` и сверяет её
с отправленным черновиком. При совпадении открывается экран чтения.
Если запись отсутствует, можно исправить черновик или повторить сохранение.
Если по этому адресу сохранено другое содержимое, форма предлагает изменить
адрес статьи.

24 ноября 2026 года сценарий прошёл в Chromium на отдельном PostgreSQL
в макетах `default` и `without-topbar` при 1440 × 900 и 390 × 844.
В каждом сочетании проверены сохранение и чтение через Payload, порядок
разделов и абзацев, отмена с подтверждением, ошибки обязательных полей,
повторяющегося адреса раздела и занятого `slug`. При возврате открылась
исходная страница 2. Защищённый маршрут проверен для гостя и для `customer`.
На десктопе отдельно проверены обрыв до отправки и потеря ответа после записи.

## 4. Auth и полномочия

Template оформляет разрешённый host-сценарий, а не создаёт новую модель доступа.
В инициализированной установке обычная регистрация создаёт `customer`; доступ
в Admin требует роли `admin`. Назначение ролей сохраняет серверную проверку.
При пустой Users применяется существующий bootstrap первого пользователя.

Оформляются действующие процессы `/login`, `/create-account`, восстановления
пароля и Payload login/create-first-user/unauthorized в пределах владельца target.
Маршруты и redirects уточняет TASK-25/39/40; не требуется выдумывать общий
`/admin/register`. После bootstrap обычная публичная регистрация не выдаёт
права администратора; существующее исключение первой Users-записи сохраняется.
Приглашения, заявки на доступ и новые правила выдачи ролей не входят в этот релиз.

При выборе native Admin его доступность и возврат определяет host policy;
RealizeAI Control Panel не создаёт копию Payload и не назначает ему фиктивный manifest.
Выключение native auth допустимо только после проверки самостоятельных auth/status
процессов и восстановления. Payload backend, session и ACL сохраняются.

Источники: [Users](../../src/collections/Users/index.ts),
[bootstrap hook](../../src/collections/Users/hooks/ensureFirstUserIsAdmin.ts),
[CreateAccountForm](../../src/components/forms/CreateAccountForm/index.tsx),

## 7. Переход установки и данных

1. **До смены build** сохранить действующие assignments/settings, history,
   reference baseline и точные версии. Подтвердить исход незавершённых команд;
   неизвестный outcome не теряет UUID при обновлении UI.
2. **Переходная сборка** содержит legacy `realize@0.1.0` и отдельный
   `realizeai-control-panel` с его собственной точной версией в согласованных
   server/client registries. До явного применения назначения
   старый вариант остаётся рабочим; default/fallback не переключаются автоматически.
   Выполнение этого пункта ещё не является полным installer нового кода.
3. **Reference** продолжает использовать прежний exact выпуск и preset.
   Проверяются прямые `/ui` imports, общие tokens/CSS и зависимости; одного
   сохранённого `templateVersion` недостаточно. Пересмотр самого образца — отдельная работа.
4. **Новое Admin назначение** выбирает ID `realizeai-control-panel` и точную
   версию после проектирования и проверки механизма применения.
   Совместимые `density/panelWidth/mode` сохраняются после валидации; несовместимые
   настройки требуют явного решения в preview, без тихой подстановки defaults.
   Применение должно проверять revision и сохранять прежнее назначение для возврата.
5. **Frontend candidate** готовится и принимается отдельно. Исходное `null`
   не превращается в активный RealizeAI Control Panel вследствие Admin apply. До первого frontend
   назначения проверяется возврат к исходной storefront-конфигурации; нынешний
   recover требует non-null previous и этот сценарий пока не обеспечивает.
   Нужный initial-assignment recovery contract входит в TASK-27/42/48/49.
6. **История остаётся неизменной.** Не переписываются старые manifestHash,
   assignments и receipts массовым SQL. Новая сборка/catalog может сделать
   неприменённый старый plan неактуальным: после установленного исхода прежней
   операции готовится новый план, ledger сохраняется.
7. **Проверить возврат до активации для эксплуатации.** Recover Admin должен
   разрешать прежние exact version/settings/hash; переходная сборка остаётся
   доступной. Перед откатом на старый build назначение возвращается к поддерживаемой
   им версии. Ошибка renderer не должна закрывать доступ к recovery.
8. **После приёмки** отдельно обновить defaults новых установок. Старый артефакт
   нельзя удалить, пока он нужен reference, действующим назначениям или обещанному
   recovery. Недоступная версия показывается unavailable, а не как новый код под старым ID.

Установка и activation — отдельные действия; сам документ не разрешает commit,
push, миграцию или deployment. Их порядок принадлежит существующей доставке.
Существующие исследуемые реализации lifecycle: [Extension Manager](extension-management.md),
[точный recover](../../packages/payload-extension-manager/src/appearance/prepareExtensionAppearance.service.ts),
[registry](../../src/components/admin/system-shell/systemAdminTemplates.registry.ts).
