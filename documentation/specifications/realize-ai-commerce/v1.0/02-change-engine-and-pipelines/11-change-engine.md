# 11. Change Engine

- **Статус:** target specification

## 11.1. Назначение

Change Engine — единственный owner управляемого изменения. Он преобразует
намерение в versioned plan, разрешает state transitions, связывает approvals с
exact hashes и передаёт работу только server-owned executors.

## 11.2. CapabilityDescriptor

Каждая возможность регистрируется сервером и содержит:

- стабильные `id` и `version`;
- класс: content, data, schema, design, frontend, code, module, plugin,
  configuration или release;
- применимый project profile;
- разрешённые actions и versioned input schema reference;
- стабильные server-side selector/resolver и executor references;
- read/write scope и protected-resource policy;
- risk signals, limits, required checks и approvals;
- preview, idempotency и rollback support.

Installation overlay может выбрать разрешённый descriptor или дополнительно
сузить его, но не создать новый executable или расширить scope.

Registry отклоняет malformed descriptor и повтор exact пары `id@version`.
Change Request и run всегда ссылаются на точную версию; неявный выбор
«последней» версии во время исполнения запрещён. Строковые references на
schema/resolver/executor/check являются идентификаторами server-owned
реализаций, а не командами для shell или кодом из installation config.

## 11.3. ChangeRequest

Нормативный Change Request фиксирует:

- actor и installation identity;
- system release и `AIConfigSnapshot` hash;
- исходное intent и выбранные capability versions;
- normalized operations и exact scope;
- risk assessment и estimated usage/cost;
- checks, preview и rollback strategy;
- input/current-state hashes и optimistic-lock values;
- approvals, artifacts, events и audit references.

## 11.4. State machine

```text
draft → planned → awaiting_approval → approved
→ executing → evidence_ready → awaiting_acceptance
→ accepted → release_ready → production_authorized → completed
```

Допустимы отдельные `rejected`, `cancelled`, `failed`, `blocked`,
`superseded` и `rolled_back`. Переходы выполняются командами с expected version;
повтор не должен создавать второй side effect.

## 11.5. Инварианты

Модель не вызывает executor напрямую. Raw SQL, unrestricted Payload CRUD,
произвольный shell и credentials не являются capabilities. Отсутствующий
descriptor означает отказ или operator escalation, а не импровизированный
обход.

## 11.6. Выбор способа исполнения

**Статус разделов 11.6–11.8: проект архитектуры, 13 сентября 2026 года.**
Browser-write и разработка/подключение сервиса встроенным агентом по этому
протоколу ещё не реализованы. Текущие typed DataOperation и Code Lane
остаются основой; добавление раздела не меняет разрешения runtime.

Действие описывается по смыслу: например, переместить существующий блок
в выбранной странице. Сервис и браузер — способы выполнить это действие.
Разработка отсутствующего способа — связанная engineering-задача со своим
результатом и проверками.

| Ситуация | Выбор |
| --- | --- |
| Есть подходящий разрешённый сервис | Обычно использовать его: строгий вход, проверяемый результат и устойчивость к изменению UI |
| Нужна работа с интерфейсом или нет специализированного сервиса | Использовать зарегистрированный browser adapter, если он поддерживает действие и требуемые гарантии |
| Нет подходящего исполнения, пользователь поручил его разработать | Подготовить engineering-задачу; вернуться к исходной операции после проверки и подключения реализации |
| Действие запрещено, отозваны права или нет обязательного подтверждения | Сообщить причину; другой способ не снимает ограничение |

Capability отвечает за вход, разрешённое действие и effect scope, а versioned
executor binding — за реализацию. Текущий descriptor имеет одну ссылку executor;
поддержка нескольких способов требует совместимого расширения контракта,
registry и server dispatch. Перечень в инструкции не регистрирует executor.

Выбор сначала проверяет полномочия, затем поддержку способа и доступность.
Отсутствие реализации допускает альтернативный разрешённый способ. Ошибка
validation, конфликт ревизии, `forbidden`, отзыв доступа и отсутствие approval
не допускают fallback. После timeout или потерянного ответа сначала выясняется
фактический результат; запуск другого исполнителя не должен повторить запись.

План связывает целевой результат, допустимые способы, их версии и доказательства.
Если эквивалентные способы заранее включены в подтверждённый план, их выбор
не требует повторного подтверждения каждого клика. Смена scope, результата,
семантики восстановления или непросмотренного side effect требует обновления
плана. Пользователь подтверждает бизнес-действие и его последствия.

Все способы используют прежний DataOperation/Change Request lifecycle и audit.
Нужное расширение typed intents, snapshots и transitions вводится явно.
Универсальный инструмент произвольной записи Payload не предоставляется модели.

## 11.7. Работа через браузер

Браузер является полноценным адаптером интерфейса: он может читать состояние,
настраивать поддержанные элементы и выполнять заранее разрешённую запись.
Кнопки и DOM — способ взаимодействия; источником подтверждения результата
остаются состояние предметного объекта, ревизия и audit, дополненные визуальными
доказательствами.

### Подготовка и autosave

Payload Pages использует autosave: изменение живой формы может записать draft
до нажатия «Сохранить». Поэтому подготовка через обычный редактор выполняется
в отдельной candidate-сессии, где autosave сохраняет изолированный candidate.
Это тот же интерфейс редактора с другим разрешённым источником данных;
поддержка candidate routing/хранения ещё должна быть реализована.

Из результата строится точный предметный diff. После подтверждения его можно
применить сервисом или browser adapter с серверным контролем записи. Даже при
отсутствии специализированного сервиса необходим общий проверяемый контракт
эффекта операции; произвольное сохранение всей формы не становится разрешением
на произвольные изменения документа.

Прямая работа браузера с рабочей страницей возможна после предварительного
подтверждения, если сервер контролирует каждую запись, включая autosave и
допустимые промежуточные состояния. Длительная DB transaction между кликами
не удерживается. Частично выполненный сценарий отражается явно; UI replay
не получает обещание общей атомарности нескольких HTTP-запросов.

### Делегированная сессия

Executor получает короткоживущую сессию, связанную с пользователем, run,
операцией, конкретными целями, ожидаемыми версиями и разрешёнными действиями.
Использование полной cookie открытой админской вкладки вместо этого контракта
не допускается. Секрет сессии не попадает в prompt, URL или журнал.

Origin/routes ограничены, а серверный guard проверяет side effects независимо
от состояния UI. Скрытая кнопка и allowlist URL не заменяют проверку запроса.
У модели нет права подтверждать собственный план, изменять свои разрешения
или подключения. Публикация требует собственного разрешённого действия.
Отзыв доступа и отмена задачи останавливают новые записи; уже завершённые
записи остаются отражены в audit.

Browser adapter связывается с поддержанной версией интерфейса, семантическими
контролами и устойчивыми идентификаторами объектов. Неоднозначный target или
изменившаяся форма приводят к повторному чтению/уточнению, а не случайным кликам.
Содержимое страницы, подсказки и сообщения UI рассматриваются как данные,
которые не могут выдать дополнительное полномочие.

### Проверка и восстановление

До записи сервер проверяет before/candidate hashes, версию schema/adapter,
текущие права и утверждённый эффект; после — фактический результат и сохранность
нетронутых данных. Pages advisory lock переиспользуется, но сам по себе не
доказывает, что произвольный browser-save соответствует плану.

Журнал фиксирует logical operation, выбранный способ, step IDs, ожидаемые
ревизии и наблюдаемые результаты. Для неопределённого исхода предусмотрена
сверка: применено, не применено, конфликт или требуется разбор. Нельзя слепо
повторять добавление/удаление блока, публикацию или компенсирующее действие.
Повтор разрешается только после доказанного отсутствия эффекта либо с
серверной идемпотентностью.

DOM, screenshots и traces дополняют проверки содержимого, но не заменяют их.
Доказательства ограничены необходимым scope и не содержат credentials или
лишних данных. Если внешний редактор не даёт нужной авторизации и проверки
версии, его адаптер ограничивается инспекцией/подготовкой либо требует явного
финального действия пользователя; эквивалентность Data Lane не заявляется.
Подготовка в таком случае означает локальный или изолированный candidate,
сохраняющий рабочие данные без изменений, включая скрытый autosave.

### Что доступно сейчас

Текущий встроенный чат работает в read-only policy; Codex RPC запускается с
`mcp_servers={}`. Adapter допускает только зарегистрированные сервером
`pages_search`, `pages_read`, `pages_structure` в обычном аналитическом чате;
неизвестные dynamic tools, MCP и запросы approval блокируются. Эти инструменты
читают доступные страницы и не вызывают executor записи. Найденная страница
может стать источником `pages.updateDraft.v1` только после серверного чтения
и сохранения exact snapshot текущего run; подготовка, подтверждение, apply
и rollback остаются в Data Lane. Контракт —
[самостоятельный поиск страниц](14-data-config-pipeline.md#1410-самостоятельный-поиск-и-чтение-страниц).

Для одного структурного изменения Content зарегистрирован
`pages.updateStructureDraft.v1` с действиями `page.insertContentBlock`,
`page.moveContentBlock`, `page.removeContentBlock`. Отдельный intent и executor
используют существующий Data Lane, operation/rollback hashes и exact snapshot
с catalog binding. Цель и якорь берутся из сохранённых чтений того же run.
Исполнение доступно из обычного чата после подтверждения; workflow allowlist
этим расширением не меняется. Публичный preview показывает позиции и полный
вставляемый/удаляемый текст; визуальный предпросмотр конкретной версии остаётся
отдельным этапом. Контракт —
[структура Content](14-data-config-pipeline.md#1411-структурное-редактирование-content).

Playwright smoke
проверяет preview, но не является универсальным browser executor. Возможности
внешнего агента разработки в IDE не являются возможностями установленного чата.
Browser tools, session/guard, candidate mode и восстанавливаемое исполнение
нужно подключать как отдельную проверяемую реализацию.

## 11.8. Создать сервис и продолжить исходную задачу

Явный запрос пользователя на разработку может создать связанную задачу:
описать контракт → реализовать в разрешённых границах → проверить → принять
изменение → установить точную версию → подключить capability → продолжить
исходный сценарий. Новый сервис получает описание и инструкцию по
[общему контракту элементов](../01-architecture/07-declarative-first.md#75-проверяемое-описание-и-инструкция-у-владельца).

Отсутствие сервиса само по себе не разрешает агенту менять код проекта.
Создание реализации не выдаёт ей runtime authority и не означает установку
в работающем приложении. После подключения сервер заново читает страницу и
переподготавливает операцию, если исходная версия изменилась за время разработки.

Для связанного процесса используются Code Lane и
[Mixed Change](16-mixed-change-pipeline.md): исходный запрос, engineering-result
и применение данных имеют собственные устойчивые результаты. Код, регистрация,
миграция и запись CMS не объявляются одной DB transaction. Ошибка подключения
сервиса не должна оставлять исходную задачу в состоянии «выполнено».

Текущий code worker имеет защищённые paths, включая `packages/`, `services/`
и `src/plugins/`; он не может сам снять эти ограничения. Полная разработка
нового подключаемого сервиса потребует ограниченного engineering workflow и
явно разрешённых extension points. Самостоятельная правка agent policy или
выдача себе разрешений не является частью такого workflow.
