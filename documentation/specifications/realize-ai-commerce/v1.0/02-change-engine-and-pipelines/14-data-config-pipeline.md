# 14. Data, schema и configuration pipeline

- **Статус:** target specification

## 14.1. Data/Config Lane

Executor получает versioned intent с resource type, selectors, action и
validated parameters. Сервер:

1. разрешает selectors внутри installation;
2. проверяет access, field/path policy и limits;
3. строит dry-run, before-snapshot и impact summary;
4. фиксирует exact target IDs, versions и hashes;
5. получает требуемое approval;
6. повторно проверяет optimistic locks;
7. выполняет mutation через Payload Local API/domain service с hooks/access;
8. сохраняет after-state, audit и outbox;
9. предоставляет exact compensating rollback, если он поддерживается.

Dry-run без исполняемого apply не считается завершённой capability.

## 14.2. Schema Lane

Создание/удаление поля или типа данных является schema change, а не обычным
Payload CRUD. Оно требует code/migration artifact, анализа существующих данных,
backfill/drop policy, совместимости предыдущего release и restore proof.
 destructive data loss относится минимум к R3 и может быть operator-only.

## 14.3. Installation configuration

Skills, prompts, rules, roles и другие AI settings изменяются как versioned
drafts. Side effect для runtime возникает только при активации проверенного
`AIConfigRelease`. История версий и использованные run hashes сохраняются.

Draft validation проверяет schema, уникальность stable keys и references между
agent profiles, workflows, prompts, rules, skills и capability/check bindings.
Configuration compiler отдельно проверяет bindings и их сужения по текущему
system registry. Release manifest строится детерминированно; runtime никогда не
компилирует effective context из mutable draft.

Первый текущий configuration slice уже сохраняет aggregate draft/release и
durable replay через Payload API. Runtime side effect по-прежнему отсутствует:
activate/rollback и run binding остаются отдельным следующим gate.

## 14.4. Первый текущий adapter

`catalog.assignCategory.v1` — пример profile-specific descriptor. Он не
является шаблоном закрытого списка операций: новые adapters подключаются к тем
же policy/state/audit contracts.

## 14.5. Создание черновика CMS-страницы

Текущий adapter `pages.createDraft.v1` создаёт одну запись `pages` через тот
же Data Lane. Обычная контентная страница, например «О компании» с демо-текстом,
не требует изменения исходников. Модель остаётся в `analysis-readonly` и
предлагает операцию; запись выполняет Payload после отдельных действий
администратора. Исполнитель кода и очередь `CODE_CHANGE` в этой операции
не участвуют. Валидное предложение Data Lane нельзя преобразовать в план
изменения кода.

Intent содержит только `version: "1.0"`, `kind: "pages.createDraft.v1"`,
`title`, `slug`, `sections: [{heading?, body}]` и необязательный `description`.
Модель передаёт обычный текст. Поля Payload, Lexical JSON, HTML, SQL,
relationships и `_status` не принимаются. Ограничения: заголовок страницы и
каждой секции — 1–160 символов, `slug` — 1–100 строчных латинских букв/цифр
с одиночными дефисами, 1–12 секций с `body` до 4 000 символов, весь текст
секций вместе с заголовками — до 16 000 символов; `description` — до 320.
Служебные адреса проверяет host mapper, занятые адреса — Payload, включая
черновики. Существующая страница не перезаписывается.

Host-адаптер `src/collections/Pages/mapAIPageDraft.mapper.ts` преобразует текст
в существующие поля `Pages`: заголовок `lowImpact` hero, полноширинные колонки
блоков `Content` с обычными Lexical text nodes и SEO metadata. Модель не
выбирает типы блоков, ссылки или произвольные свойства схемы. Executor задаёт
`_status: "draft"` и вызывает Payload Local API с `draft: true`, исходным
`req`, `overrideAccess: false` и штатными hooks.

Последовательность в админке:

1. «Подготовить изменение данных» сохраняет dry-run с полным текстом,
   адресом, проверкой прав и отсутствия страницы; записи `pages` ещё нет.
2. «Подтвердить создание» связывает решение с точной версией и
   `operationHash`. Hash включает intent, hash серверного `createData`,
   версию mapper и условие отсутствия `slug`.
3. «Создать черновик» повторно проверяет права, адрес и точное содержимое
   рецепта. Запись страницы, смена состояния операции и audit выполняются
   в одной транзакции.
4. Результат содержит идентификатор и ссылку «Открыть черновик». Страница
   остаётся неопубликованной; эта capability не предоставляет публикацию.
5. Откат требует отдельного подтверждения актуального `rollbackHash`.
   Стратегия `delete-created-draft` удаляет только страницу, созданную этой
   операцией, если её содержание и версия не изменились и она никогда
   не публиковалась. Изменение, autosave, публикация, удаление или утрата
   доступа блокируют автоматическое удаление.

До создания `rollbackHash` связан с рецептом. После apply он заменяется
привязкой к `operationHash`, ID страницы, `updatedAt` и fingerprint фактического
документа. Исходный hash нельзя использовать для подтверждения удаления
созданной страницы. Закрытые `createData` и `appliedSnapshot` в публичный DTO
не выдаются.

Создание и откат удерживают PostgreSQL transaction advisory lock `page-drafts`.
Тот же lock подключён в `Pages.beforeOperation` для `create`, `update`,
`delete` и `restoreVersion`, включая autosave. Он берётся до чтения документа
внутри Payload operation: запись draft-версии не может пройти между проверкой
fingerprint и удалением. Самодельные записи в БД вне Payload не входят
в поддерживаемый контракт. Если host-адаптер страницы отключён, откат ранее
созданной операции блокируется: наличие исторического snapshot не заменяет
подключённый контракт записи и общей блокировки Pages.

Существующие intent, preview и hashes `catalog.assignCategory.v1` сохраняются.
Новый registry descriptor имеет action `page.createDraft`, чтение
`payload.pages` и запись `payload.pages.draft`; workflow adapter проверяет
точное совпадение kind с разрешённым binding и создаёт только dry-run.
Добавление descriptor совместимо с system version `1.0.0`: прежние releases,
включая ограниченные `maximumRelease: "1.0.0"`, продолжают компилироваться.
Они не получают page binding автоматически. Новые compiled snapshots
фиксируют актуальный system manifest hash; исторические snapshots не меняются.

Публичные поля описаны в [API-контракте](../03-runtime-delivery-and-security/22-api-and-streaming-contracts.md#операции-данных-и-черновик-страницы),
порядок обновления схемы — в [руководстве по миграциям](../../../../delivery/03-migrations-and-rollback.md).


## 14.6. Редактирование текста существующей страницы

`pages.updateDraft.v1` использует тот же Data Lane: модель предлагает адресные
замены текста, администратор проверяет полный diff, подтверждает его и отдельно
сохраняет черновик. Операция работает с последней доступной версией страницы,
включая черновик поверх опубликованной страницы. Публикация не выполняется:
основная опубликованная запись и её содержимое сохраняются.

В обычном чате администратор выбирает одну страницу через каталог с поиском и
серверными страницами по 20 записей. Browser сохраняет только идентичность и
fingerprint. При отправке сообщения сервер заново проверяет права управления
данными и access Pages, читает снимок, сверяет fingerprint и сохраняет полный
ограниченный контекст в закрытом `turnContext` запуска. В публичном сообщении
остаётся только идентичность страницы. Провайдер получает снимок как
недоверенные данные текущего turn, отдельно от developer instructions.
Повторное использование thread связано с fingerprint; отсутствие выбора
запрещает использовать снимок из предыдущего ответа. Точный повтор уже
принятого запроса возвращает исходный run, сохраняя первоначальный контекст.

Host `src/collections/Pages/pageDraftText.adapter.ts` определяет допустимые
текстовые поля: `title`, `meta.title`, `meta.description`, Lexical text leaves
hero и блоков Content, CTA и Banner. ID блоков/колонок, форматирование,
ссылки, media, формы, relationships, порядок и типы блоков не меняются.
Изменение структуры, slug и произвольные поля Payload отсутствуют в контракте.
`path` — серверный JSON Pointer из конкретной проекции; он не предоставляет
произвольного доступа к JSON. Сдвиг индекса после перестановки блока меняет
fingerprint и делает исходное предложение недействительным.

Intent содержит `version: "1.0"`, `kind: "pages.updateDraft.v1"`, `pageID`,
`expectedUpdatedAt`, `expectedFingerprint` и `changes: [{path, before, after}]`.
`before` копируется буквально, с пробелами; повторные/неизвестные пути и
неизменившиеся значения отклоняются. Допускаются 1–32 замены, до 32 КиБ
совокупного before/after текста; максимум одного текстового листа — 4 000
символов, title/SEO title — 160, SEO description — 320. Контекст ограничен
128 полями и 64 КиБ UTF-8. Избыточный контекст отклоняется целиком, без
незаметного обрезания. Новый текст не принимает HTML или управляющие символы.
Существующий текст остаётся данными, даже если похож на инструкции или HTML.

Подготовка из assistant response сверяет pageID, revision, fingerprint и
исходные значения с сохранённым снимком именно его run и текущей страницей.
`operationHash` связывает intent, точный before/after и версию host-адаптера.
Fingerprint включает полный latest документ depth 0, идентичность последней
версии, состояние основной строки, последнюю публикацию и версию адаптера.
Idempotency replay проверяет владельца, диалог, исходный ответ и точный intent;
запрос для audit берётся из того же run, даже при параллельных сообщениях.

Применение и откат удерживают общий `page-drafts` transaction lock, используемый
также обычным редактором, autosave и восстановлением версий. После повторной
проверки снимка сервис передаёт только затронутые верхние поля в Payload
`update` с `draft: true`, `_status: "draft"`, `overrideAccess: false`,
`overrideLock: false` и исходным `req`. Поля, не перечисленные в diff,
не должны измениться даже из-за host mapper; сервис проверяет это до и после
записи. Несоответствие откатывает всю транзакцию вместе с состоянием операции
и audit.

Rollback требует отдельного подтверждения актуального `rollbackHash`,
привязанного к точной сохранённой версии. Любое последующее изменение,
autosave, восстановление, публикация, удаление или потеря прав блокирует
автоматический откат. Восстанавливаются исходные значения изменённых полей,
без удаления страницы. Исходный явный `null` сохраняется; отсутствующее
optional текстовое поле очищается через `null`, поскольку Payload не очищает
значение при omission. Опубликованная версия остаётся прежней. Собственная очистка старых version
records по `maxPerDoc` допускает исчезновение прежней записи публикации только
при неизменной основной строке; новая публикация не считается очисткой.

Registry содержит отдельную capability `pages.updateDraft.v1` с action
`page.updateDraft` и записью только `payload.pages.draft`. Существующие releases
не получают этот binding автоматически. Workflow может подготовить dry-run
по явно переданному typed intent с актуальным fingerprint; выбор страницы из
composer в workflow не переносится и отклоняется сервером. Получение CMS
контекста внутри произвольного workflow остаётся отдельным расширением.

## 14.7. Архитектура сервисов страниц для агентов

**Статус: проект архитектуры, 12 сентября 2026 года.** Текущая реализация
создания и изменения текста описана в 14.5–14.6. Приведённые ниже расширения
контекста, структуры, предпросмотра и публикации ещё не реализованы.
Первый предметный объект — CMS-страница; расширение на другие коллекции
не входит в этот этап.

### 14.7.1. Принцип и существующие владельцы

Агент формулирует намерение и использует разрешённые инструменты. Серверные
сервисы знают устройство страницы, проверяют результат и выполняют бизнес-действия.
Администратор принимает решения о записи и публикации через админку.
Такой сервис не зависит от модели, формулировки сообщения или размещения чата.

Сервисы ниже — прикладные модули в существующем приложении. Для них не нужны
отдельные процессы, базы данных, брокер, новый registry или универсальный CRUD.
Переиспользуется существующее разделение:

| Владелец | Ответственность |
| --- | --- |
| `packages/ai-contracts` | Versioned intent и явные DTO контекста, результата проверки, плана и результата операции |
| `packages/change-engine` | Capability descriptors, ограничения, hashes и общие правила управляемого изменения |
| `packages/payload-ai-plugin` | Прикладные операции страниц, авторизация, Payload repositories, DataOperation, audit и transport adapters |
| `src/collections/Pages`, `src/blocks`, `src/fields` | Фактическая схема страницы, разрешённая проекция блоков, преобразование данных и отображение |
| `services/ai-control-plane`, `packages/codex-adapter` | Доставка ограниченного контекста модели и связь с провайдером; без прямой записи в Pages |

`PageDraftCreation` и `PageDraftUpdate` остаются исходной реализацией операций.
`createTypedDataOperationPlan`, `dataOperationDecisions`, `dataOperationExecution`
и `dataOperationRollback` сохраняют единственный жизненный цикл изменений.
Декомпозиция выполняется по новым обязанностям при внедрении, без предварительного
переноса всех файлов и создания пустого каркаса.

### 14.7.2. Шесть обязанностей сервисов

| Обязанность | Что получает и возвращает | Граница |
| --- | --- | --- |
| Чтение и контекст | Поиск страниц, краткое дерево блоков, выбранные поля, текущая draft/published revision, ссылки на разрешённые зависимости | Только чтение с правами пользователя; большой документ читается частями одной ревизии |
| Каталог возможностей страницы | Поддерживаемые типы блоков, свойства, ограничения, допустимые действия, существующие шаблоны при их наличии | Проекция фактической host-схемы и реализованных adapters; не весь Payload config |
| Подготовка и изменение черновика | Типизированное намерение → точные изменения, draft candidate, diff и стратегия восстановления; после допуска Data Lane — запись | Не выдаёт approval самому себе; не меняет опубликованную версию |
| Проверка страницы | Candidate и версия правил → ошибки, предупреждения, область проверки и доказательства | Детерминированные обязательные проверки отделены от рекомендаций модели |
| Предпросмотр версии | Ссылка на конкретный candidate/revision → авторизованный preview и сведения о показанном содержимом | Использует существующий renderer; не публикует и не подменяет выбранную версию текущим draft |
| Публикация и восстановление публикации | Проверенная версия, подтверждение, ожидаемая текущая публикация → результат операции | Отдельные права и план; текущий draft rollback не используется для отмены публикации |

Каталог связывает разрешённую схему, реально доступный renderer и поддерживаемые
команды. Само присутствие блока в `Pages.layout` не разрешает агенту создавать
или редактировать его. Host явно описывает поддержанные действия; противоречие
каталога и schema/adapter блокирует подготовку. Новые типы блоков и изменение
схемы остаются отдельной задачей разработки.

### 14.7.3. Контракты и полномочия потребителей

Названия контрактов в таблице обозначают целевую ответственность, а не уже
добавленные TypeScript exports или API endpoints. Конкретные versioned DTO
вводятся перед соответствующей реализацией в `packages/ai-contracts`.

| Контракт | Минимально необходимое содержание |
| --- | --- |
| Контекст страницы | Идентичность и статус страницы, непрозрачная ссылка на ревизию, schema/adapter version, bounded outline со stable block IDs, доступные действия и поля |
| Каталог блоков | Тип и версия описания, допустимые свойства и команды, required fields, limits, способы выбора relationships; сведения только о поддержанных блоках |
| Подготовленное изменение | Существующий DataOperation envelope, точные изменения и revision bindings, validation issues, затронутые зависимости, operation hash, срок действия и rollback policy |
| Результат проверки | Стабильный check ID и версия, severity, code, адресуемая цель и сообщение; что проверено и что не проверено |
| Ссылка на предпросмотр | Идентичность candidate/версии, content/dependency hashes, версия renderer/adapter, срок действия и серверная привязка к доступу пользователя |
| Результат публикации | Ссылка на операцию, точная опубликованная версия, прежняя публикация для проверки восстановления и состояние обновления витрины |

Полные Payload documents, служебные snapshots и credentials остаются на сервере.
Идентификатор, hash или preview URL сами по себе не предоставляют доступ.
Права проверяются для каждого чтения, подготовки и записи. Для агента доступ
ограничен одновременно правами текущего пользователя, настройками интеграции,
серверным набором возможностей и разрешениями выбранного профиля. Исторический
snapshot профиля не отменяет последующий отзыв доступа.

Чтение разрешённых сведений о странице отделяется от права редактирования.
Каталог показывает вычисленные разрешённые действия и причины недоступности,
а write-сервис всё равно проверяет их повторно. Текущее требование `canManageData`
для текстового контекста из 14.6 сохраняется до отдельного внедрения этого разделения.

Контекст большой страницы возвращает обзор, затем выбранные блоки и поля с
серверной пагинацией и лимитами объёма. Каждая часть связана с общей ревизией;
данные разных версий нельзя склеивать. После изменения страницы клиент должен
перечитать контекст. Существующий v1-контракт 128 полей / 64 КиБ не расширяется
молчаливым обрезанием или сменой значения fingerprint.

Agent tool — тонкий адаптер: проверяет arguments, разрешает actor/run context,
вызывает сервис и возвращает bounded DTO. Инструменты чтения дают контекст,
инструменты предложения сохраняют план. Подтверждение, применение, публикация
и восстановление доступны управляющим действиям админки. Фраза в чате
и вызов инструмента моделью не заменяют подтверждение администратора.

Чат, workflow и интерфейс подготовки изменений используют те же сервисы.
Подключение tools к провайдеру и чтение контекста из workflow — отдельные
расширения существующих adapters, а не обещание уже работающего MCP/API.
Provenance фиксирует пользователя, run/источник, capability/config versions и
исходную ревизию. Сейчас planner требует conversation/sourceMessage; для
подготовки плана обычным интерфейсом потребуется явный вариант источника в том
же контракте аудита. Обычное ручное сохранение Payload сохраняет свой UX;
общие инварианты Pages и блокировки действуют независимо от наличия AI-плана.

### 14.7.4. От намерения к черновику

Базовый сценарий: выбрать страницу или цель создания → получить допустимый
контекст и каталог → подготовить изменение → проверить diff → подтвердить →
сохранить черновик → открыть предпросмотр сохранённой версии.
Предпросмотр candidate до записи допустим только с явной идентичностью
candidate и теми же гарантиями отображения; скрытого сохранения draft нет.

Первый вариант использует существующие `pages.createDraft.v1` и
`pages.updateDraft.v1`. Следующие структурные команды добавляются по одной:
добавить поддержанный блок, изменить разрешённые свойства, переместить блок,
удалить блок, выбрать существующий разрешённый media/form reference.
Структурные изменения адресуют stable block IDs и исходную ревизию, а host
преобразует их в фактическую схему. Произвольный JSON patch, Lexical JSON,
HTML и исполняемый код не становятся входом агента.

Подготовка не меняет CMS-документ. Она может сохранить DataOperation и его
закрытые snapshots, затем возвращает полный адресуемый diff, последствия и
результаты проверок. Изменённое предложение получает новый план и требует
нового подтверждения. На первом этапе не выполняются автоматический merge
или перенос устаревшего плана на новую версию.

Обязательная проверка перед записью включает access, существование и
уникальность целей, ограничения host-схемы, совместимость поддержанных блоков,
сохранность нетронутых данных и доступность выбранных relationships.
Проверки URL, ссылок, SEO и готовности к публикации вводятся с явными check IDs,
уровнями серьёзности и доказуемой областью покрытия. Оценка текста моделью
остаётся рекомендацией. Она не доказывает доступность ссылок, отсутствие
ошибок отображения или прохождение проверки доступности интерфейса.

Применение сохраняет общую Payload transaction, Pages lock и повторную
проверку текущих данных, прав и editor lock. Для новых видов операций
расширяются существующие discriminated DTO и registry. Старые v1 intents,
hashes, approvals и исторические планы не переинтерпретируются.

### 14.7.5. Предпросмотр, которому можно доверять при публикации

Текущий `src/utilities/preview/findPreviewDocumentBySlug.service.ts` повторно
проверяет доступ и читает latest draft по slug. Он подходит для текущего
предпросмотра редактора, но не доказывает просмотр конкретной подтверждаемой
версии. Текстовые карточки DataOperation также не являются визуальным preview.

Для публикации нужен manifest: точная версия страницы или неизменяемый candidate,
hash содержимого, schema/adapter/renderer version и перечень влияющих зависимостей.
Media, формы, общие элементы оформления и динамические блоки могут измениться
при неизменном тексте Pages; одного page fingerprint недостаточно.

Manifest указывает, какие зависимости зафиксированы и как проверяется их
неизменность, а какие данные отображаются динамически. Нельзя объявлять
динамический контент воспроизводимым по снимку страницы. Первый сценарий
публикации ограничивается поддержанным набором статических блоков; непокрытые
зависимости являются явным препятствием до внедрения соответствующей политики.

Preview использует существующее отображение страницы и блоков. Resolver получает
авторизованную ссылку на выбранный снимок; raw содержимое и секреты не передаются
в URL. Неавторизованный доступ, истечение срока, смена renderer или недоступная
версия возвращают отказ, без fallback на latest draft. При очистке Payload
versions подтверждение также утрачивает основание: срок и хранение preview
должны согласовываться с доступностью исходных snapshots.

Доказательства просмотра и проверок связываются с этим manifest. Проверка
desktop/mobile, ошибок отображения и зависимостей относится к конкретному
снимку; смена содержимого или значимой зависимости требует новой проверки.
Сохранение черновика и открытие обычной preview-ссылки сами по себе не означают
готовность к публикации.

### 14.7.6. Публикация конкретной версии

Публикация — самостоятельная DataOperation со своим разрешением и подтверждением.
Она связывает выбранный draft, проверенный preview manifest, версии обязательных
проверок и ожидаемую текущую опубликованную версию. Успешное создание или
редактирование draft не предоставляет право публикации.

Перед записью сервер под общей блокировкой Pages повторно проверяет права,
актуальность draft, действительность подтверждения, результаты проверок и
состояние зависимостей. Изменившаяся версия или зависимость блокирует исходный
план. Для изменяемых зависимостей одного повторного чтения недостаточно:
реализация должна обеспечить согласованный снимок/фиксацию или совместимый
порядок блокировок у их владельцев. До этого такой вид зависимости не входит
в гарантии поддержанного сценария публикации.

Запись Pages, переход DataOperation и audit/event фиксируются атомарно через
Payload. Обновление кэша и проверка витрины происходят за границей DB transaction;
их нельзя объявлять частью атомарной записи. Существующий audit/outbox owner
используется для расширения доставки событий, а повторяемый обработчик и
состояние обновления витрины должны быть реализованы явно. Сбой revalidation
не запускает повторную публикацию и не маскируется сообщением «всё готово».

Восстановление прошлой публикации является новой подтверждаемой операцией,
проверяющей текущую публичную версию. Она не удаляет страницу и не затирает
более новый draft автоматически. Откат черновика из 14.6 не приобретает
побочного действия над опубликованной страницей.

### 14.7.7. Последовательность внедрения и критерии

| Шаг | Результат, который можно проверить |
| --- | --- |
| 1. Контекст и каталог | Агент получает понятное описание страницы и доступных действий из host-контракта; большие страницы читаются частями одной ревизии; UI и сервер используют одинаковые ограничения |
| 2. Подготовка существующих операций | Создание и изменение текста используют согласованные проверки и результаты в прежнем Data Lane; повтор, конфликт версии и отзыв доступа не обходят подтверждение |
| 3. Preview и публикация простого типа страницы | Одна страница из поддержанных статических блоков проходит весь цикл; просмотренный, подтверждённый и опубликованный снимки совпадают; проверены конфликт, повтор и восстановление |
| 4. Расширение структуры | По одной добавляются команды блоков и relationships, с diff и проверками каждой зависимости; используются уже проверенные preview/publication contracts |

Первый implementation slice — чтение и каталог поверх текущих host adapters,
без новых записывающих возможностей. На нём проверяются отличие просмотра от
редактирования, фильтрация закрытых данных, отказ при смене ревизии между
частями контекста, соответствие каталога фактической реализации и передача
одинакового контракта в админку и агентский runtime. Сразу сохраняются точки
привязки будущего preview к ревизии; публикация этим шагом не включается.

Настройки доступных действий, моделей и профилей остаются в существующей
админке. Новый descriptor не выдаёт разрешения прежним выпускам автоматически.
Дальнейшая универсализация выполняется после полного проверенного цикла Pages;
новые коллекции и общая платформа сервисов заранее не вводятся.

## 14.8. Блоки, виджеты и гибридное редактирование

**Статус: дополнение к проекту архитектуры, 13 сентября 2026 года.**
Термины, описания и инструкции задаёт
[общий контракт элементов](../01-architecture/07-declarative-first.md#74-элементы-проекта-и-их-связи),
а варианты исполнения — [Change Engine](11-change-engine.md#116-выбор-способа-исполнения).
Эти расширения не включают browser-write в текущем runtime.

Первый каталог страницы должен представлять definition/version блока,
ID его размещения, поддержанные slots/свойства и связи с общими данными.
Форма и карусель могут иметь роль виджета; отдельное хранилище всех виджетов
не вводится ради терминологии. Структурные команды работают со stable IDs,
сохраняют незатронутые размещения и используют общий snapshot страницы.

На существующем FormBlock различаются три действия:

- изменить локальное вступление или положение формы в выбранной странице;
- заменить ссылку этого размещения на другую доступную форму;
- изменить саму общую форму, влияющую на другие размещения.

Первое и второе являются действиями над страницей с разным разрешённым scope.
Третье принадлежит владельцу forms и требует отдельной capability и анализа
зависимостей; оно не скрывается внутри редактирования страницы. В первом
Pages-сценарии общая форма остаётся только читаемой зависимостью.

Пример задачи «перемести форму выше и измени текст перед ней»: получить дерево
страницы и guide FormBlock → выбрать существующее размещение → подготовить
точные изменения локального текста и порядка → проверить → подтвердить →
применить разрешённым способом → сверить сохранённый draft и preview.
Общая форма и опубликованная страница сохраняются. Если подходящего сервиса
нет, browser candidate может подготовить тот же результат по правилам 11.7.

Работа через браузер не означает, что agent самостоятельно подтверждает план:
решение сохраняет пользователь, а executor выполняет делегированное действие
в его границах. Preview/publication сохраняют требования 14.7.5–14.7.6 вне
зависимости от того, как подготовлен черновик.

Минимальное развитие состоит из каталога Pages/Content/FormBlock и актуальных
guides, браузерного чтения/проверки и изолированной подготовки структурного
изменения. Запись в рабочую страницу подключается после server guard и
доказуемой сверки результата. Затем повторяющийся browser-сценарий может быть
реализован специализированным сервисом по запросу пользователя, сохраняя
описание бизнес-действия и общие проверки.
