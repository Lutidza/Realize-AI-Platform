# 1. Итоговое архитектурное решение

## 1.1. Что именно создаётся

Создаётся коммерческая e-commerce CMS-платформа на базе Payload CMS 3, предназначенная прежде всего для небольших и средних интернет-магазинов — клиентов маркетингового агентства.

Платформа включает:

- полноценную CMS и административную панель;
- каталог, категории, товары, страницы, медиа, формы, корзину, оформление заказа и другие подготовленные модули;
- реестр переиспользуемых блоков, виджетов и плагинов;
- собственный рабочий слой AI-агентов из `.ai/**` и адаптерный слой `.codex/**`;
- встроенный AI-чат в административной панели Payload;
- безопасные инструменты чтения и изменения данных;
- безопасный контур изменения кода;
- Change Engine с историей, статусами, подтверждениями и аудитом;
- автоматическую сборку, тестирование, preview и публикацию;
- версионирование и откат;
- центральное лицензирование;
- подписочную модель;
- учёт фактических AI-расходов и наценки;
- операторскую панель агентства.

## 1.2. Главный принцип

> Ни одно сообщение пользователя не должно напрямую изменять код, базу данных или production.

Чат создаёт намерение. Намерение преобразуется в формализованный Change Request. Только Change Engine имеет право переводить запрос по разрешённым состояниям, вызывать инструменты, запускать проверки и инициировать деплой.

## 1.3. Модель изоляции первой версии

В первой версии **не используется Payload Multi-Tenant Plugin для клиентских данных**.

Каждый клиент получает:

- отдельный экземпляр приложения;
- отдельную базу PostgreSQL;
- отдельные секреты;
- отдельное файловое хранилище или изолированный bucket/prefix;
- отдельный Git-репозиторий либо строго изолированную ветку/репозиторий конфигурации;
- отдельную историю изменений и деплоев;
- отдельный installation identity и лицензию.

Клиентские экземпляры не знают друг о друге и не имеют сетевого доступа к базам других клиентов.

## 1.4. Центральные сервисы

Централизованными остаются только сервисы агентства:

- License Service;
- Subscription and Billing Service;
- Usage Metering;
- AI Orchestrator;
- изолированный пул Codex workers;
- Build and Release Service;
- приватный OCI registry;
- операторская консоль агентства;
- release manifest/update service;
- observability stack.

Центральный контур хранит метаданные установок, лицензий, задач, usage и релизов, но не становится общей CMS-базой клиентского контента.

## 1.5. Почему это сильнее полной локальной установки AI у клиента

Постоянный OpenAI API key нельзя помещать:

- в браузер;
- в Docker-образ, который получает клиент;
- в переменные окружения на инфраструктуре, которую полностью контролирует клиент;
- в Payload Admin;
- в Git-репозиторий проекта.

Если клиент получает контейнер вместе с постоянным ключом, ключ технически можно извлечь. Поэтому вызовы Codex должны выполняться на инфраструктуре агентства или через контролируемый AI Execution Service. Клиентский сайт получает только короткоживущие capability tokens для конкретной операции.

## 1.6. Бизнес-модель

Платформа продаётся как собственный сервис агентства:

- базовая ежемесячная подписка;
- включённый пакет AI-кредитов или денежный лимит;
- metered overage за дополнительные AI-операции;
- наценка на фактические API-расходы;
- дополнительные платные модули;
- сопровождение, дизайн и разработка сложных изменений;
- платные release channels, SLA и резервное копирование.

Важно: клиенту продаётся доступ к продукту и AI-функциям, а не OpenAI account, API key или «перепродажа аккаунта». Внутренний ledger может считать токены, но коммерческая единица должна называться «AI usage», «AI credits» или «AI operations».
