# 32. Последовательность развития платформы

- **Статус:** согласованный backlog; выполненные задачи отмечены отдельно с областью проверки.
- **Дата приоритизации:** 4 октября 2026 года.
- **Область:** инженерное качество и версии всей платформы, AI-слои, стоимость,
  модели, движок, обновления клиентских проектов и промышленный выпуск.

Этот документ владеет порядком и зависимостями задач. Предметные контракты
находятся в связанных главах; активные инструкции работы агентов — в `.ai/`
и `.codex/`. Изменение roadmap само по себе не меняет их поведение или полномочия.
Перед каждой задачей сверяется фактический код: имеющиеся compiler,
draft/release/activation, runtime, capabilities и delivery foundation
развиваются у текущих владельцев без повторной реализации.

## 32.1. Зависимости и результаты

минимального контракта версий и локальной проверки совместимости; PLAT-03 —
в области доверенного локального system release и привязки исполнения.

PLAT-05 — структурных проверок и первого принятого поведенческого baseline.

## 32.2. Критерии задач

### PLAT-01. Согласование рабочего агентского слоя

Устранить противоречия rule/check/workflow, устаревшие ссылки и карты структуры.
Закрепить одного владельца требования, компактный обязательный вход и загрузку
профильных инструкций по задаче. Уточнить условия согласования, приёмки и Git
delivery с учётом уже предоставленных полномочий. Роли задают ответственность;
отдельный worker подключается по применимому процессу и реальной необходимости.

Приёмка: затронутые документы согласованы; ссылки/метаданные проверены;
для требования понятны условие применения и evidence. Проверены сценарии
диалога, read-only анализа, простой правки, контрактного изменения, недоступного
MCP и конфликта инструкций. Фактическая загрузка подтверждается для заявленных
CLI/IDE/runtime запусков; наличие файла не считается доказательством загрузки.

**Выполнено 4 октября 2026 года:** согласованы вход, общие правила, checks,
workflow/state map, роли и адаптеры; устранены пять отсутствующих источников
и две несогласованные registry/check связи. Структурно проверены 191 документ
активного слоя и все 36 зарегистрированных правил, ссылки/якоря и metadata.
В новом Codex CLI 0.160.0 подтверждены получение `AGENTS.md` до tool calls,
чтение выбранных источников и ответы по семи контрольным сценариям. Это smoke
проверка инструкций без выполнения гипотетических mutations. В текущей IDE
через настоящий S1 runtime получены полные тексты обновлённых `AGENTS.md` и
main-delivery по hash; запрос со старым hash отклонён с `CONFLICT`.
Автоматический новый старт других IDE не проверялся. Публикация рабочего слоя
в продуктовый effective snapshot относится к PLAT-03, постоянные CI/evals — к PLAT-05.

### PLAT-02. Версионирование всей платформы

Реализовать минимальный контракт
[выпусков и совместимости](../01-architecture/40-platform-versioning-and-updates.md):
ядро, пакеты, профили, API/DTO, схема, AI-слои, проверки, модели и routing policy.
Определить владельцев изменений, поддерживаемые сочетания, extension points,
release manifest, происхождение сборки и правила прекращения поддержки.
Включить контракт двух Git-назначений и исходных CI-полномочий по GIT-01/GIT-02;
основу pipeline развивать в GIT-04 с профильными gates по мере готовности.

Приёмка: exact manifest разрешается в конкретные артефакты; несовместимые
комбинации отклоняются; версии и hashes сохраняются в evidence; release можно
сопоставить с исходным commit и установленным клиентским состоянием. Формат
доставки ядра выбирается по отдельному ADR перед реализацией обновлений.

**Выполнено 4 октября 2026 года в минимальном scope:** strict DTO, source inventory
16 компонентов, manifest с core commit/OCI digest/workflow provenance, ordered
migration hash, exact compatibility и read-only CLI evidence. Контракт разделяет
Git ядра и клиента, неявные полномочия отклоняются. В существующие release
producers добавлены inventory и hashes; release candidate без установленной
основы явно хранит `platformBase: unresolved`. Model Garden/Router/pricing
указаны как unavailable, release support — development.
Локальная приёмка и ограничения описаны в
[current runbook](../../../../delivery/04-platform-versioning.md).
GIT-01/GIT-02 покрыты контрактом и текущим Actions publisher; центральное
хранилище Git credentials и подключение customer adapter ещё не завершены.
GitHub/GHCR/VPS execution, долговечный registry, signature trust и автоматическое
наблюдение/обновление клиентского состояния принимаются в последующих задачах.

### PLAT-03. Системный и админский AI-слои

Развить существующий compiler/publisher по
[контракту AI-слоёв](../01-architecture/10-ai-codex-layer-integration.md).
Связать run, Change Request, workflow и исполнение с exact system/overlay
release, применимыми инструкциями, capabilities/checks и входным контекстом.
Проверять protected resources сервером, включая `.ai`, `.codex`, `AGENTS.md`
и чувствительные ресурсы; разрешённая работа владельца над системой отделена
от возможностей клиентского runtime.

Приёмка: Admin не изменяет системное ядро и не расширяет свои полномочия;
локальные файлы не подменяют доверенную policy; несовместимый overlay не
активируется; activate/rollback/retry сохраняют историю и изоляцию; snapshot
действительно используется каждым заявленным consumer, включая executor.

**Выполнено 4 октября 2026 года в локальном runtime scope:** детерминированный
artifact `realize-system-1.0.0`, запрет перезаписи опубликованного ID и проверка
source drift в CI. Chat/workflow используют exact system reference и проверенный
overlay; CR/job сохраняют private context, связанный с исходным запросом, plan
approval и подписанным допуском executor. Проверены capability/check ceilings,
protected paths и отказ исполнения legacy snapshot без подстановки latest.
Product Codex adapter отключает загрузку локальных AGENTS и project config;
это подтверждено на CLI 0.160.0 без вызова модели.

Локально прошли 241 тест в 18 файлах и TypeScript. В отдельной PostgreSQL
проверена полная цепочка из 28 миграций, сохранение данных и запрет удаления
непустых execution snapshots. Новая additive migration применена локально после
проверенного private backup. Контракт и ограничения —
[AI-слои, §10.11](../01-architecture/10-ai-codex-layer-integration.md#1011-опубликованный-system-ai-release-и-исполнение).
Общий runtime rule и происхождение mode-specific builders опубликованы явно;
автоматической загрузки всего `.ai/.codex`, publisher доменных инструкций
Мастерской и production tenant isolation этот срез не вводит. Evals — PLAT-05,
физическое отделение закрытого AI-сервиса — PLAT-10 до внешнего пилота.

### PLAT-04. Учёт расходов до оптимизации моделей

Добавить [usage/cost ledger](../04-commercial-and-operations/25-subscriptions-and-ai-billing.md)
и [аналитику](../04-commercial-and-operations/28-observability.md) до внедрения
автоматического роутера. Разделить расходы разработки, evals и клиентских
запусков, стоимость provider, инфраструктуры и коммерческие начисления.
Собирать все attempts, cache usage, retries, время tools/build/preview и
pricing provenance. Ввести reservations, лимиты и reconciliation.

Приёмка: дубли событий не удваивают запись; реальные повторные попытки учтены;
unknown/estimated/reconciled различаются; параллельные запуски согласуют бюджет;
доступны срезы installation/project/agent/workflow/model/version и стоимость
успешной задачи. Данные клиента и секреты не попадают в cost telemetry.

**Реализованный срез, 5 октября 2026 года:** durable PostgreSQL ledger и
immutable pricing, exact nanos/currencies, admission/reservations, partial/unknown
usage и owner reconciliation. Реальные producers: chat/workflow, executor/reviewer,
checks и запуск preview. Стоимость успешного исполнения привязана к проверенному
preview; история расходов сохраняется независимо от SSE.

В Admin разделены `/admin/ai/usage` установки и `/admin/ai/usage/platform` владельца.
Server-owned scope, отдельные DTO и owner allowlist защищают себестоимость;
клиентский admin управляет своим бюджетом без доступа к provider pricing.
Источники будущих Garden/Router — те же contracts и ledger; их версии пока null.
Новые native/HTTP/browser проверки подключены к CI без платных model calls.

Охват и ограничения — [§25.7](../04-commercial-and-operations/25-subscriptions-and-ai-billing.md#257-реализованный-локальный-контур-plat-04)
и [§28.5](../04-commercial-and-operations/28-observability.md#285-административная-аналитика-plat-04).
Автоматический сбор внешних IDE расходов, внутренние provider retries/child costs,
полная стоимость инфраструктуры и коммерческие списания ещё не реализованы.
Центральная изоляция установок относится к PLAT-10; accounting ports разработки/evals
не означают подключения всех их producers. Producer evals добавлен в PLAT-05.

### PLAT-05. Проверяемое качество и baseline

Автоматизировать структурные проверки инструкций и контрактов; добавить
ограниченный набор реальных сценариев поведения агентов по
[стратегии проверок](../04-commercial-and-operations/29-testing-strategy.md).
Фиксировать версии входов, фактические действия, изменения, результат,
задержку и расход. Сравнивать варианты на одинаковых сценариях и критериях.

Приёмка: обязательные нарушения блокируют выпуск; качественный review дополняет
детерминированные проверки; есть позитивные и негативные сценарии полномочий,
источников и восстановления. CI проверяет структуру при каждом затронутом
изменении; дорогие сценарии запускаются по риску и перед соответствующим
выпуском. Набор моделей/сред, пороги и стоимость evals явно ограничены.

**Реализованный срез, 5 октября 2026 года:** структурный CI checker проверяет
185 активных документов и 1281 ссылку; версионированные evaluation DTO,
детерминированный grader и comparator принадлежат существующим пакетам.
Owner runner использует продуктовый adapter и общий ledger. Release и release
candidate требуют полный baseline с review, актуальными hashes и возрастом
не более семи дней; обычный CI не запускает платные обращения к модели.

Принят реальный baseline: 3 сценария × 2 повтора, 6/6 обязательных проверок,
`gpt-6.1-sol`, Codex CLI `0.160.0`, Linux, system release `1.1.0`.
Качественный review выполнен агентом и привязан к точному отчёту; отдельная
человеческая приёмка этим не заявляется. Проверены разрешённая правка,
попытка расширения полномочий через overlay и восстановление чтения.
96 контрактных тестов и 11 native PostgreSQL тестов подтвердили в том числе
изоляцию расходов evals от клиентской аналитики и отказ некорректного gate.

Принятый набор израсходовал 229 220 токенов за 105,6 секунды. Вместе с первой
остановленной по лимиту попыткой сохранены все 9 обращений и 350 695 токенов;
денежная стоимость без тарифа неизвестна. Evidence и границы охвата —
[§29.9](../04-commercial-and-operations/29-testing-strategy.md#299-принятый-baseline-5-октября-2026-года).
Полные IDE/skills, browser и delivery сценарии, произвольные модели и OS-аудит
всех промежуточных действий этим конечным набором не покрыты. Garden/Router
используют эти contracts и ledger в следующих этапах.

### PLAT-06. Model Garden

Реализовать [каталог](../01-architecture/41-model-garden-and-router.md) поверх
существующих integration/provider owners: обнаружение, доступность,
capabilities, тарифные снимки, результаты evals и жизненный цикл допуска.
Начать с текущего production provider V1; каталог не вводит произвольные
внешние endpoints или дополнительные credentials в клиентский слой.

Приёмка: refresh и отзыв модели имеют историю; неподтверждённые свойства
не считаются поддерживаемыми; допуск связан с контрактными проверками и evals;
Admin видит только доступные в своих пределах варианты и их ограничения.

### PLAT-07. Model Router

Реализовать выбор модели для этапа по риску, требуемому качеству, инструментам,
задержке и бюджету. Начальная policy — явные версионируемые правила, bounded
fallback и контролируемый ручной выбор. Решение сохраняется вместе с run.

Приёмка: объяснима причина выбора; несовместимая модель исключена до вызова;
нет скрытой смены provider/условий обработки данных; расходы всех attempts
учтены; fallback не повторяет side effects. Новая policy допускается по
качеству и полной стоимости результата, с возможностью возврата совместимой версии.

### PLAT-08. Возможности движка и профилей

Завершать типизированные сквозные сценарии: content/data/config вне catalog,
schema field с миграцией, page/design/frontend, project module/plugin.
Развивать первый e-commerce profile поверх универсального ядра. Каждый
сценарий проходит policy, preview, требуемое подтверждение, применение,
проверки и восстановление своего класса.

Приёмка: для каждого заявленного сценария есть настоящий пользовательский
путь и доказательство side effect/rollback; mock-only и dry-run-only не
завершают задачу. Работу можно вести параллельно Garden/Router после её
зависимостей на текущей проверенной модели; это не снимает будущую интеграцию
с общими metering и routing contracts.

### PLAT-09. Обновления клиентских проектов

Реализовать планировщик совместимости и upgrade из опубликованного upstream
с сохранением локальных расширений и явным разрешением конфликтов по
[контракту обновлений](../01-architecture/40-platform-versioning-and-updates.md).
Использовать существующие isolated execution, migration, preview и release owners.
Клиентское Git-подключение, CI и upstream update раскрыты в GIT-03/GIT-05/GIT-06.

Приёмка: чистая установка и обновление между двумя выпусками; сохранение
контента/настроек/доработок; конфликт изменённого ядра; несовместимый overlay;
сбой миграции, повтор команды и восстановление проверены. Обновление не
перезаписывает локальные файлы молча и не применяет непросмотренный upstream diff.

### PLAT-10. Центральная production-граница AI

Довести существующие control/execution services до запуска на инфраструктуре
владельца: identity установки и администратора, изоляция, короткие допуски,
durable jobs, наблюдаемость, отказоустойчивость и версионированный site API.
Закрытое системное ядро не входит в клиентскую поставку.

Приёмка: клиентский root-доступ не даёт изменения policy сервиса;
cross-installation и injection tests пройдены; потеря соединения, рестарт,
replay и отзыв допуска проверены; сайт продолжает работать при недоступном AI.
Эта граница обязательна **до первого внешнего клиентского пилота**.

### PLAT-11. Коммерческий и production-контур

Реализовать license/subscription ceilings поверх готового metering и связать
`PRODUCTION_AUTHORIZATION` с trusted exact-digest controller, существующим
Release Candidate и миграциями. Проверить release channels, quotas, grace,
rollout и восстановление приложения/данных.
Разделить platform/client production credentials и допуски по GIT-04/GIT-05;
публикация платформы не даёт разрешения на deploy клиентского сайта.

Приёмка: коммерческие полномочия не заменяют security; списания идемпотентны;
новое назначение и candidate требуют применимого разрешения; неудачная
доставка имеет durable результат и проверенный recovery; сохраняется
доступность самостоятельного сайта при сбое центрального сервиса.

### PLAT-12. Первая поставка и пилот

Пройти [DoD](34-definition-of-done.md), upgrade/recovery и security acceptance
для заявленного выпуска. Начать контролируемое подключение внешних установок,
затем расширить пилот до 5–10 сайтов по
[Phase 6](../05-implementation-roadmap/06-phase-6-hardening-pilot.md).

Приёмка: есть evidence качества, стоимости, изоляции, доступности и обновления
на точном наборе версий; определены поддержка, диагностика, бюджеты и критерии
остановки rollout. Незавершённая внешняя проверка остаётся явным ограничением,
а не записывается как passed.

## 32.3. Ближайший пакет и рубежи

PLAT-01, минимальный контракт PLAT-02, локальный PLAT-03, описанный срез
PLAT-04 и первый срез PLAT-05 — структурные проверки и принятый поведенческий
baseline с учётом расходов — реализованы. Ближайший этап — **PLAT-06: Model
Garden**, затем **PLAT-07: Model Router**; обе подсистемы ещё предстоит
реализовать. Исторический baseline не заменяет проверку актуальных hashes,
полноты review и срока evidence перед release/RC.
Полная центральная production-инфраструктура не требуется для этого
внутреннего этапа; контракт будущей границы фиксируется уже в PLAT-02/PLAT-03.

Подготовительный срез 5 октября: уточнён этот порядок, составлена
[карта существующих компонентов и критерии учёта](../01-architecture/41-model-garden-and-router.md#419-карта-компонентов-перед-plat-06)
для Garden/Router. Три документальные задачи выполнены через настоящий сервис;
[замеры и последовательность оптимизации](../04-commercial-and-operations/29-testing-strategy.md#2910-три-пилотные-задачи-и-план-оптимизации)
сохранены отдельно от release baseline. Следующая небольшая реализация PLAT-06 —
контракт записи `candidate` и mapper discovery; план оптимизации начинается
с полноты измерений и состава контекста, затем сравнивает модели в Garden.

До первой внешней установки обязательны системная изоляция, совместимость,
учёт и ограничения расходов, восстановление и критерии заявленного pilot scope.
До первого распространяемого выпуска выполняется upgrade drill между двумя
кандидатами. Эти рубежи не переносятся на период после передачи коробки клиенту.

[Phases 0–6](../05-implementation-roadmap/INDEX.md) сохраняют оценку зрелости
возможностей и завершённые результаты. Этот backlog задаёт следующий порядок
работ, а не обнуляет имеющуюся реализацию.

## 32.4. Git-интеграции и CI/CD

GIT-01–GIT-06 — декомпозиция работ PLAT-02, PLAT-09 и PLAT-11, а не отдельный
конкурирующий roadmap. GIT-01/GIT-02/GIT-04 имеют статус `in_progress`:
в PLAT-02 приняты DTO/policy и manifest текущего Actions publisher; их полная
продуктовая интеграция и внешняя приёмка ещё не завершены. GIT-03/GIT-05/GIT-06
имеют статус `planned`. Зависимости GIT задают
порядок внутри этой области; зависимости PLAT сохраняются для полной приёмки
соответствующих возможностей. Начальный CI использует существующие проверки;
новые gates из PLAT-05–PLAT-07 подключаются после их реализации.
GIT-04/GIT-05 завершаются проверенными candidates/preview и контрактами
production-доставки; реальный production controller принимается в PLAT-11.
Таким образом, проверка upstream update не ждёт завершения production rollout.

| ID     | Результат                                                      | Зависит от GIT | Связанные задачи |
| ------ | -------------------------------------------------------------- | -------------- | ---------------- |
| GIT-01 | Контракт владельцев, назначений, identities и разрешений       | —              | PLAT-02          |
| GIT-02 | Системная Git-интеграция владельца платформы                   | GIT-01         | PLAT-02          |
| GIT-03 | Git-интеграция клиентской установки/проекта                    | GIT-01         | PLAT-09          |
| GIT-04 | CI/CD ядра, доверенные проверки и выпуски платформы            | GIT-02         | PLAT-02, PLAT-11 |
| GIT-05 | CI/CD клиента, preview и проверяемое происхождение результатов | GIT-03, GIT-04 | PLAT-09, PLAT-11 |
| GIT-06 | Обновление клиента из проверенного upstream release            | GIT-04, GIT-05 | PLAT-09          |

### GIT-01. Владельцы и контракты

Закрепить [два Git-назначения](../01-architecture/40-platform-versioning-and-updates.md):
системное подключение платформы и клиентское подключение проекта. Определить
identity/revision, refs/actions, protected resources, источники credentials
и связь core release с project commit. Общий adapter не объединяет полномочия.

Приёмка: разрешённые чтение/запись/PR/publish/deploy описаны для каждого actor;
подмена repository ID, назначения или revision отклоняется до записи;
клиентский Admin не меняет системное подключение.

### GIT-02. Системная интеграция

Разместить управление основным Git в control plane владельца, отдельно от
клиентских настроек и поставки. Развить текущий adapter: права на разрешённые
репозитории/refs, ротация и отзыв credentials, проверка назначения и audit.

Приёмка: реальное scoped чтение и запись проверены в выделенном тестовом
репозитории; клиентские identity/credentials не дают системного доступа;
отзыв или изменение подключения останавливает подготовленную запись.

### GIT-03. Клиентская интеграция

Связать подключение с installation/project и его администраторами. Поддержать
проверку доступа, scoped branch/commit/push/PR, смену/отзыв подключения,
подписанные webhooks и дедупликацию. Развивать существующий Source Promotion.

Приёмка: end-to-end запись и PR в разрешённом клиентском репозитории;
cross-installation selector, stale target, повтор webhook и отозванный доступ
не создают посторонней записи; секрет не возвращается в DTO/logs/prompt.

### GIT-04. Pipeline платформы

Развить [CI/CD](../04-commercial-and-operations/26-ci-cd-pipeline.md) основного
репозитория: обязательные checks/review, изоляция PR, exact-commit build,
SBOM/provenance/signature, manifest и публикация immutable releases.
Доставка центрального сервиса отделена от публикации клиентской основы.

Приёмка: фактические branch/environment protections проверены;
недоверенный PR не получает write/deploy credentials; изменённый artifact,
неразрешённый issuer или чужой workflow не принимаются как доверенный выпуск.
Candidate совместим с контрактом PLAT-11; попытка production-доставки без
требуемой авторизации отклоняется. Реальный rollout проверяется в PLAT-11.

### GIT-05. Pipeline клиентского проекта

Дать версионируемый контракт CI и шаблоны для site/profile checks, isolated
preview, compatibility/migration evidence и approval-bound delivery. Клиент
добавляет свои проверки; обязательный check pack проверяется доверенным
verifier независимо от изменяемого клиентского workflow.

Приёмка: успешный PR проходит preview и формирует exact candidate;
поддельный зелёный статус, изменённый check pack, другой source commit или
artifact отклоняются; credentials/cache/runner не пересекают клиентские границы.
Для PLAT-11 передаются exact candidate и evidence; реальный production rollout
не является зависимостью завершения клиентского CI/preview.

### GIT-06. Upstream update

Связать выбранный manifest ядра с базой конкретного клиента, построить diff
и план обновления, подготовить отдельный PR/candidate. Проверить локальные
расширения, конфликты, schema/overlay compatibility и восстановление до rollout.

Приёмка: реальное обновление между двумя выпусками сохраняет клиентские данные
и доработки; конфликт или неизвестная база блокирует автоматическое применение;
release платформы не развёртывает клиентские сайты без их применимого допуска.
