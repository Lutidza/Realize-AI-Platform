# 40. Версионирование платформы и обновления клиентских проектов

- **Статус:** target specification; наличие документа не означает реализацию.
- **Область:** вся платформа, системный AI-слой и клиентские инсталляции.
- **Порядок реализации:** [задачи PLAT-02, PLAT-09–PLAT-12](../06-execution-governance/32-immediate-implementation-order.md).

Минимальный контракт PLAT-02 реализован отдельно от целевой системы обновлений:
[текущее устройство manifest и совместимости](../../../../delivery/04-platform-versioning.md).
Он связывает исходники, версии, OCI digest и Git provenance, проверяет exact
состояние установки и сохраняет evidence. Публикация system AI bundle,
долговечный release registry, фактический upgrade и production trust gates
не считаются реализованными этим контрактом.

## 40.1. Владельцы и границы поставки

Владелец платформы выпускает основное ядро, системный AI-слой, доверенные
адаптеры, политики, capability/check registries и стандартные профили.
Клиент управляет своим сайтом, проектным кодом, данными и installation overlay.
Изменение клиентом файлов своей установки не изменяет авторитетный системный
AI-слой сервиса владельца.

Production AI исполняется на инфраструктуре владельца по
[ADR-0003](../../../../architecture/decisions/ADR-0003-central-ai-execution.md).
Коробочная установка обслуживает сайт самостоятельно и обращается к этому
сервису через аутентифицированный контракт. Исходники закрытого системного ядра
и постоянные credentials исполнителей не входят в клиентский дистрибутив.
Контейнеризация и векторное представление инструкций не являются этой границей.
Development adapter допустим локально в пределах отдельного режима разработки.

Правила разработки из `.ai/`, процедуры `.codex/` и `AGENTS.md` принадлежат
владельцу платформы. Из них для продуктового runtime отбираются применимые
требования через явный publisher/compiler. Файлы клиентского проекта являются
проектным контекстом и не заменяют доверенную policy сервиса.

## 40.2. Единицы версионирования

| Единица                | Что фиксируется                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Выпуск платформы       | Версия, exact source commit, immutable artifact digest, происхождение и подпись                                         |
| Пакеты ядра и профили  | Версии пакетов, зависимости, допустимые сочетания и поддерживаемые точки расширения                                     |
| API, DTO и события     | Версия контракта, правила совместимости и период поддержки                                                              |
| Схема данных           | Упорядоченные миграции, исходная/целевая схема, требования к backup и восстановлению                                    |
| Системный AI-слой      | Версия и хеш инструкций, compiler, policy и обязательных capabilities/checks                                            |
| Админский AI-слой      | Immutable release и hash, версия схемы и ссылка на совместимый системный выпуск                                         |
| Модели и маршрутизация | Версии каталога, policy роутера, provider adapter и снимка тарифов                                                      |
| Проверки качества      | Версии сценариев, fixtures, критериев и результаты на точной комбинации компонентов                                     |
| Git и CI/CD            | Назначение и revision подключения, repository ID, source commit, версии workflow/check pack и происхождение результатов |
| Клиентский проект      | Установленный выпуск ядра, профиль, project commit, локальные расширения и история обновлений                           |

SemVer применяется к публикуемым контрактам и пакетам с явно определённой
совместимостью. Номер версии не доказывает совместимость схемы БД, модели или
клиентской конфигурации: для них обязательны отдельные проверки. Хеш подтверждает
целостность содержимого; доверие к выпуску задаётся подписью и авторизованным
источником. Mutable tag и ветка не являются идентификаторами поставки.

## 40.3. Manifest выпуска и совместимость

Manifest связывает перечисленные версии, происхождение сборки, migration plan,
поддерживаемые версии клиентского протокола и ссылки на acceptance evidence.
Release channels указывают на immutable выпуски; переключение канала аудитируется.
Установка хранит применённый manifest и подтверждённое состояние обновления.

Перед активацией проверяются как минимум:

- ядро ↔ плагины/профиль/расширения;
- site plugin ↔ центральный API и capabilities;
- system release ↔ installation overlay и compiler;
- schema ↔ приложение и допустимый rollback;
- модель/adapter ↔ инструменты, формат ответа и policy роутера.

Manifest задаёт конкретные поддерживаемые диапазоны и переходы. Нельзя
предполагать совместимость всех minor-версий или бессрочную поддержку клиента.
До исключения версии публикуются срок поддержки, миграционный путь и причина.
Несовместимая комбинация получает явный отказ до активации. Обновление не
переписывает snapshots уже запущенных процессов; текущий запрет доступа или
отзыв credentials применяется независимо от исторического snapshot.

## 40.4. Основной репозиторий и локальные доработки

Upstream-выпуск основного ядра связан с exact commit и manifest. В клиентском
проекте сохраняется происхождение установленной основы и локальных изменений.
Основной поддерживаемый путь доработок — проектные модули, темы, профили и
документированные extension points.

Клиент может менять доступный ему код сайта. Если он изменил поставляемые
файлы ядра, система обнаруживает расхождение и показывает конфликт или
необходимость отдельной адаптации. Такие правки не перезаписываются молча и
не повышают доверие к локальным инструкциям. Неизвестная исходная версия или
незавершённые локальные изменения блокируют автоматическое применение.

Обновление не сводится к `git pull` или замене всей клиентской рабочей копии.
Механизм определяет upstream delta относительно установленной основы,
отделяет локальные изменения и готовит проверяемый candidate. Когда требуется
слияние исходников, оно выполняется в изолированной ветке/рабочей копии с
проверкой конфликтов; для пакетной поставки проверяется новый lock/manifest.
Выбор физического формата поставки закрепляется отдельным ADR до реализации.

## 40.5. Процесс обновления

1. Проверить доверенный выпуск, установленную основу, права и совместимость.
2. Построить план: версии, diff, конфликты, миграции, ожидаемый простой,
   проверки и способ восстановления; получить требуемое разрешение.
3. Подготовить candidate в изоляции, сохранив данные, media, secrets, настройки
   и локальные расширения; миграции проверить на отдельной копии данных.
4. Выполнить контрактные, профильные, браузерные и security checks по области,
   получить preview и acceptance evidence.
5. Выпустить immutable artifact и применить его через существующий
   [production delivery](../05-implementation-roadmap/04-phase-4-production-delivery.md)
   по разрешению, привязанному к точному candidate.
6. Проверить health, записать фактические версии и результат; при сбое выполнить
   предусмотренное восстановление и сохранить диагностику.

Повтор команды не применяет миграцию или side effect второй раз. Состояние
операции сохраняется до необратимого действия; после таймаута сначала
устанавливается фактический результат. Одновременные обновления одной установки
согласуются через version/CAS и единственного владельца операции.

Возврат image не равен откату БД. Совместимый application rollback, forward fix
и восстановление backup являются разными действиями. Для восстановления данных
нужны отдельные основание, разрешение и проверенный план сохранения записей,
появившихся после backup. Необратимая миграция явно отмечается до применения.

## 40.6. Приёмка

- чистая установка и upgrade между двумя поддерживаемыми выпусками проверены;
- совместимое локальное расширение и содержимое сайта сохранены;
- конфликт локальной правки, неподдерживаемая версия и неверная подпись
  останавливают применение с объяснимой причиной;
- повтор, конкуренция, таймаут и сбой миграции имеют проверенное восстановление;
- несовместимый overlay не активируется, старые runs сохраняют происхождение;
- код/настройки клиента не меняют защищённую policy центрального AI-сервиса;
- известны установленные версии, стоимость и результат каждой операции обновления.

Первое подключение внешнего клиента требует подтверждённой центральной границы
AI. До первого распространяемого выпуска проверяется хотя бы один реальный
upgrade между двумя кандидатами с локальными доработками и восстановлением.

## 40.7. Git платформы и Git клиентского проекта

Интеграции разделены по владельцам и полномочиям. Общий Git/GitHub adapter
допустим как механизм; подключения, credentials и разрешения остаются раздельными.
Выбор репозитория не выводится из текста задачи или произвольного remote URL.

| Назначение              | Владелец и настройки                                                                | Результат                                                              |
| ----------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Git платформы           | Владелец платформы, системный control plane; настройки недоступны клиентскому Admin | Проверенные выпуски ядра, системного AI, профилей и CI-контрактов      |
| Git клиентского проекта | Уполномоченный администратор своей установки/проекта                                | Версии сайта, локальные доработки, изменения AI и кандидаты обновлений |

Системное подключение хранится на инфраструктуре владельца и не поставляется
с коробкой. Клиентские credentials не дают доступ к основному репозиторию,
закрытому AI-ядру или публикации доверенных выпусков. Клиентский root может
изменить свой сайт и локальные workflows; авторитетная policy центрального
сервиса и его проверка происхождения выпуска остаются за границей установки.
Для SaaS действует то же разделение установок и проектов.

Контракт подключения включает назначение, владельца, provider, стабильный
repository ID, допустимые refs/actions, credential reference и revision.
Перед записью executor повторно проверяет identity, текущие права, revision,
точный target и ожидаемый source/remote commit. Переименование, перенос или
переподключение репозитория требуют повторного разрешения назначения; отзыв
credentials и прав действует сразу. Проверка соединения сама по себе не
разрешает commit, push, merge или deploy.

Run, Change Request, Source Promotion и release evidence различают
`platform release / core source commit` и `customer repository / project commit`.
В manifest также фиксируются версии CI/check pack и проверенный источник
результатов. Единственного поля «текущий HEAD» для двух областей недостаточно.
Webhook принимается после проверки подписи, назначения и installation identity;
повтор события дедуплицируется, актуальные сведения сверяются с provider.

Выпуск ядра не обновляет клиентские сайты автоматически. Для выбранного
клиента проверенный upstream release создаёт отдельный update plan и PR либо
эквивалентный просматриваемый candidate для выбранного формата поставки.
Он проходит клиентский CI, compatibility/migration checks, preview и применимое
подтверждение перед rollout. Чистая установка использует тот же release manifest.
Права публикации платформы и права развёртывания клиента не взаимозаменяемы.

Pipeline и доверие к его результатам определены в
[CI/CD](../04-commercial-and-operations/26-ci-cd-pipeline.md), последовательность
работ — в [GIT-01–GIT-06](../06-execution-governance/32-immediate-implementation-order.md).
Локальный Git-воркер разработки из `.ai/.codex` обслуживает рабочую копию
разработчика; его текущая конфигурация не заменяет этот продуктовый контракт.
