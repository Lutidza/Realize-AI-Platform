# 7. Declarative-first

- **Статус:** target specification

## 7.1. Принцип

Повторяемая функция сайта сначала выражается декларативно: profile, module,
content type, block schema, component binding, theme token, integration
descriptor, capability adapter и check pack. Проектный код используется там,
где декларативной модели недостаточно.

Declarative-first не означает no-code и не запрещает агенту писать код. Он
уменьшает blast radius, упрощает preview, migration, policy и обновления ядра.

## 7.2. Владельцы

- Core registry определяет допустимые типы modules, capabilities и checks.
- Project profile выбирает и параметризует их для класса сайтов.
- Installation configuration активирует разрешённый набор для конкретного
  клиента.
- Custom code остаётся versioned source artifact и проходит Code Lane.

## 7.3. Правило выбора lane

1. Контент и существующая конфигурация — Data/Config Lane.
2. Изменение schema — Schema Lane с migration plan.
3. Сборка из зарегистрированных компонентов — Declarative UI Lane.
4. Новый компонент, plugin или нестандартная логика — Code Lane.
5. Смешанная задача — один parent Change Request с атомарно связанными
   subplans и общим acceptance.

Нельзя маскировать schema/code изменение как простую config mutation ради
снижения risk или обхода проверок.

## 7.4. Элементы проекта и их связи

**Статус разделов 7.4–7.8: проект архитектуры, 13 сентября 2026 года.**
Это развитие существующих schema/registrations и capability registry.
Автоматический каталог описаний и подключение инструкций из него ещё не реализованы.
Первый проверяемый пример — Pages, Content и FormBlock; массовое переустройство
остальных частей проекта этим решением не требуется.

| Понятие | Ответственность |
| --- | --- |
| Плагин | Поставляемое расширение с точкой подключения, зависимостями и условиями совместимости; может предоставлять несколько модулей |
| Модуль | Самостоятельная предметная функция: данные, публичные контракты, сервисы, интерфейс и доступные действия; может быть встроенным или поставляться плагином |
| Сервис | Прикладная операция модуля с явными входом, результатом и инвариантами |
| Возможность агента | Зарегистрированное разрешённое действие с контрактом входа, исполнителем, ограничениями и проверками; не каждый метод сервиса становится инструментом |
| Определение блока | Тип размещаемой части страницы: schema, допустимые свойства/slots, renderer и поддержанные команды |
| Экземпляр блока | Конкретное размещение с постоянным ID, родителем, порядком и локальными настройками |
| Виджет | Функциональная роль блока или компонента: форма, карусель, подборка и другие элементы с поведением или источником данных |
| Компонент | Реализация представления и поведения с props, состояниями, slots и привязками к общим UI tokens |
| Утилита | Чистая вспомогательная функция по проектному правилу структуры; сетевые обращения и запись относятся к сервисам/адаптерам |

Плагин здесь — расширение Realize, а не автоматически подключаемый Codex plugin.
Модуль не обязан быть отдельным npm-пакетом или процессом. Виджет не требует
отдельной универсальной коллекции: его настройки могут принадлежать размещению
или существующему связанному документу. Не каждый React-компонент является
редактируемым блоком CMS.

Это граф, а не обязательная цепочка вложенных каталогов. Основные связи:
`provides`, `contains`, `rendersWith`, `references`, `queries`, `dependsOn`,
`exposesCapability`. Один компонент может отображать несколько определений;
виджет может занимать разрешённый slot блока или иметь собственное размещение.
Вложенность разрешается host-схемой; произвольное дерево JSON не принимается.

Нужно различать три идентичности: определение и его версия, конкретное размещение
в странице и связанный общий документ. Копирование блока создаёт независимое
размещение; ссылка на общую форму сохраняет общую зависимость. Изменение
определения влияет на использующие его экземпляры, локального свойства — на
одно размещение, общего документа — на всех его потребителей.

### Статическая и текущая информация

Из регистрации и исходников строится статическое описание: definitions,
exports, схемы, renderers, зависимости и capability references. Сервисы данных
добавляют доступные пользователю экземпляры, версии и связи конкретной страницы.
Текущие данные не копируются в manifest исходников.

Динамический запрос — самостоятельная связь, а не неизменяемый список результатов.
Неполный индекс обратных связей должен показывать неполное покрытие; он не
доказывает, что общий объект больше нигде не используется. Просмотр зависимостей
сохраняет access; закрытые страницы не раскрываются через названия или ссылки.

## 7.5. Проверяемое описание и инструкция у владельца

У самостоятельного публичного элемента предусматриваются три согласованные части:

1. **Машинное описание** — небольшой typed manifest у владельца реализации.
2. **Инструкция** — краткое руководство по использованию и развитию элемента.
3. **Производный каталог** — результат сборки описаний из фактических источников.

Схемы полей, defaults, validation и сигнатуры не переписываются вручную в manifest.
Он ссылается на их реальные owners; compiler формирует разрешённую проекцию.
Человек описывает смысл, условия использования и последствия, которые нельзя
надёжно вывести из типов.

| Содержание описания | Для чего нужно агенту |
| --- | --- |
| Stable ID, вид/роли и владелец | Найти нужный элемент и отличить его от похожих |
| Версии публичного контракта и реализации | Понимать совместимость с текущим проектом |
| Ссылки на schema, public exports, renderer | Работать с фактическим API и доступными настройками |
| Capability/check references с версиями | Узнать реализованные действия и проверяемые условия |
| Зависимости, способы размещения и связи | Оценить влияние изменения на другие объекты |
| Usage/development guide references | Получить инструкции под текущую задачу |
| Lifecycle и migration/replacement references | Корректно обновить или заменить устаревший элемент |

Конкретная сериализуемая схема manifest вводится перед первым implementation
slice. Строковые ссылки не становятся shell-командами или произвольно
загружаемыми executable. Пути исходников и guides разрешаются только внутри
допустимых owners выбранного выпуска.

Инструкция отвечает на вопросы: для чего использовать элемент; как создать
экземпляр и изменить существующий; что меняется локально и совместно; какие
действия поддержаны; какие входы/результаты ожидаются; какие ограничения и
проверки обязательны; как развивать контракт без поломки существующих данных.
Сценарии использования и разработки могут быть разделами одного существующего
README/руководства. Отдельный файл оправдан самостоятельной ответственностью.

Каждой утилите доступны собственный типизированный контракт и пояснение рядом
с реализацией, а также инструкция её владельца. Отдельный AGENTS.md для каждой
функции не требуется: дублирующиеся правила быстро расходятся и перегружают
контекст. Самостоятельный сложный публичный helper может иметь собственный
guide, если его использование этого требует.

`AGENTS.md`, `.ai` и `.codex` сохраняют назначение инструкций разработки.
Product usage guide не переопределяет эти правила и не выдаёт полномочий
встроенному агенту. Runtime не предполагает, что провайдер сам найдёт все
вложенные инструкции: нужные fragments явно доставляет Context Pack compiler.

## 7.6. Обнаружение и понимание возможностей

Производный каталог дополняет существующий server-owned capability registry
сведениями об элементах и их связях. Он не является второй базой разрешений.
Метод, описанный в guide, доступен для исполнения только при наличии
зарегистрированной capability, допустимого способа исполнения и текущих прав.

Агент последовательно получает: результаты поиска → описание выбранного
элемента → связанные версии и нужные fragments инструкции → контекст экземпляра.
Используется ограниченная загрузка по задаче, а не полный каталог в каждом prompt.
Сам факт похожего названия не является основанием выбора: проверяются schema,
назначение, совместимость и влияние зависимостей.

В одном каталоге различаются: описанный элемент, установленная реализация,
пройденные проверки конкретной версии и разрешённое сейчас действие.
Отсутствующий executor или неподдержанная версия показываются явно.
Admin UI и агент получают согласованные проекции этих же сведений. Профили,
разрешения и локальные инструкции настраиваются в существующей админке;
installation overlay не регистрирует новый исполняемый код.

Run фиксирует точные версии и hashes выбранных описаний, guides и capabilities
по [правилам Context Pack](10-ai-codex-layer-integration.md#102-компиляция-context-pack).
Прочитанный текст страницы, сторонний README или незарегистрированный plugin
guide остаются недоверенным содержимым. Проверенный guide из установленного
выпуска тоже не может менять identity, границы записи или правила подтверждения.

## 7.7. Актуальность описаний

Производный каталог собирается из фактических registrations, public exports,
host schemas и manifests. Generated output не редактируется вручную.
Проверки сборки должны выявлять:

- повтор stable ID, отсутствующую ссылку или несовместимую версию;
- расхождение заявленной схемы, renderer и поддержанных операций;
- объявленный capability/check, не разрешающийся в существующем registry;
- отсутствующий guide или несоответствие проверяемых примеров текущему контракту;
- несовместимое обновление определения без стратегии для существующих экземпляров.

Изменение публичного контракта требует проверки затронутой инструкции и примеров.
Если смысл инструкции остаётся верным, review фиксирует это без искусственной
правки текста. Хеш подтверждает происхождение, но не смысловую правильность:
полностью автоматическое поддержание документации не обещается.

Проверяются затронутые контракты и сценарии; изменение renderer требует уместных
браузерных доказательств. Проверка всех функций проекта при каждой правке не
является условием этой архитектуры. В каталоге хранится привязка доказательств
к проверенной версии; прежний результат не переносится на новый код автоматически.

Удаление или отключение плагина сначала проверяет зависимые модули и размещения.
Данные страниц не удаляются из-за исчезновения renderer. Совместимость,
deprecated/replacement policy и миграция проходят управляемый процесс изменения.

## 7.8. Первый пример и критерий результата

Первый срез уже подключает host manifests Pages/Content/FormBlock, производный
каталог и ограниченный outline выбранной страницы к чату. Фактические границы
реализации и оставшиеся шаги описаны в
[14.9](../02-change-engine-and-pipelines/14-data-config-pipeline.md#149-каталог-и-структура-pages-первый-реализованный-срез).
Остальные механизмы разделов 7.4–7.7 остаются целевой архитектурой.

Первый набор — Pages, Content и FormBlock: он покрывает документ, локальный
блок, функциональный виджет и общую форму. По его описанию агент должен уметь:
найти подходящий элемент, прочитать существующую страницу, отличить изменение
размещения от изменения общей формы и выбрать разрешённый способ действия.

Для этого достаточно описать существующих владельцев и связать их с реальными
контрактами. Новые пакеты, универсальная Widget collection и паспорта всех
исходников заранее не создаются. Следующий элемент добавляется, когда проверено
повторное использование этого же контракта.

Выбор сервиса, браузера и разработки недостающего действия описан в
[Change Engine](../02-change-engine-and-pipelines/11-change-engine.md#116-выбор-способа-исполнения).
Применение к страницам — в
[Data Lane](../02-change-engine-and-pipelines/14-data-config-pipeline.md#148-блоки-виджеты-и-гибридное-редактирование).
