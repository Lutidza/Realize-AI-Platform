# 7. Declarative-first

- **Статус:** target specification
- **Уточнение от 2026-11-16:** правила идентичности, владения, версий и формы
  ссылок в §7.5.1–7.5.2 согласованы; полная schema и универсальный registry ещё
  не внедрены. Проверка пяти существующих элементов связана с §7.5.2.
- **Согласовано 2026-11-17:** начальные owner registrations P/T, отдельные
  package/source bindings и граница нейтрального resolver заданы в §7.5.3.
  Первый read-only compiled срез реализован: два owners, один package binding
  и пять разрешённых mappings. Это не полный registry опубликованных descriptors
  и не подключение к runtime startup/HTTP; границы и проверки — в §7.5.3.
- **Следующий срез согласован 2026-11-17:** самостоятельные draft layout
  definitions и exact release pins по §7.5.4. Ограниченный source/preview срез
  реализован; подтверждены адресные tests, typecheck, ESLint и ограниченная
  browser matrix. Это не публикация или production activation.

## 7.1. Принцип

Повторяемая функция сайта сначала выражается декларативно: profile, module,
content type, block schema, component binding, theme token, integration
descriptor, capability adapter и check pack. Проектный код используется там,
где декларативной модели недостаточно.

Declarative-first не означает no-code и не запрещает агенту писать код. Он
уменьшает blast radius, упрощает preview, migration, policy и обновления ядра.

## 7.2. Владельцы

- Core registry определяет допустимые типы modules, capabilities и checks.
- Project profile выбирает и параметризует их для класса сайтов.
- Installation configuration активирует разрешённый набор для конкретного
  клиента.
- Custom code остаётся versioned source artifact и проходит Code Lane.

## 7.3. Правило выбора lane

1. Контент и существующая конфигурация — Data/Config Lane.
2. Изменение schema — Schema Lane с migration plan.
3. Сборка из зарегистрированных компонентов — Declarative UI Lane.
4. Новый компонент, plugin или нестандартная логика — Code Lane.
5. Смешанная задача — один parent Change Request с атомарно связанными
   subplans и общим acceptance.

Нельзя маскировать schema/code изменение как простую config mutation ради
снижения risk или обхода проверок.

## 7.4. Элементы проекта и их связи

**Статус разделов 7.4–7.8: проект архитектуры, 13 сентября 2026 года.**
Это развитие существующих schema/registrations и capability registry.
Автоматический каталог описаний и подключение инструкций из него ещё не реализованы.
Первый проверяемый пример — Pages, Content и FormBlock; массовое переустройство
остальных частей проекта этим решением не требуется.

| Понятие            | Ответственность                                                                                                                                           |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Плагин             | Поставляемое расширение с точкой подключения, зависимостями и условиями совместимости; может предоставлять несколько модулей                              |
| Модуль             | Самостоятельная предметная функция: данные, публичные контракты, сервисы, интерфейс и доступные действия; может быть встроенным или поставляться плагином |
| Сервис             | Прикладная операция модуля с явными входом, результатом и инвариантами                                                                                    |
| Возможность агента | Зарегистрированное разрешённое действие с контрактом входа, исполнителем, ограничениями и проверками; не каждый метод сервиса становится инструментом     |
| Определение блока  | Тип размещаемой части страницы: schema, допустимые свойства/slots, renderer и поддержанные команды                                                        |
| Экземпляр блока    | Конкретное размещение с постоянным ID, родителем, порядком и локальными настройками                                                                       |
| Виджет             | Функциональная роль блока или компонента: форма, карусель, подборка и другие элементы с поведением или источником данных                                  |
| Компонент          | Реализация представления и поведения с props, состояниями, slots и привязками к общим UI tokens                                                           |
| Утилита            | Чистая вспомогательная функция по проектному правилу структуры; сетевые обращения и запись относятся к сервисам/адаптерам                                 |

Плагин здесь — расширение Realize, а не автоматически подключаемый Codex plugin.
Модуль не обязан быть отдельным npm-пакетом или процессом. Виджет не требует
отдельной универсальной коллекции: его настройки могут принадлежать размещению
или существующему связанному документу. Не каждый React-компонент является
редактируемым блоком CMS.

Это граф, а не обязательная цепочка вложенных каталогов. Основные связи:
`provides`, `contains`, `rendersWith`, `references`, `queries`, `dependsOn`,
`exposesCapability`. Один компонент может отображать несколько определений;
виджет может занимать разрешённый slot блока или иметь собственное размещение.
Вложенность разрешается host-схемой; произвольное дерево JSON не принимается.

Нужно различать три идентичности: определение и его версия, конкретное размещение
в странице и связанный общий документ. Копирование блока создаёт независимое
размещение; ссылка на общую форму сохраняет общую зависимость. Изменение
определения влияет на использующие его экземпляры, локального свойства — на
одно размещение, общего документа — на всех его потребителей.

### Статическая и текущая информация

Из регистрации и исходников строится статическое описание: definitions,
exports, схемы, renderers, зависимости и capability references. Сервисы данных
добавляют доступные пользователю экземпляры, версии и связи конкретной страницы.
Текущие данные не копируются в manifest исходников.

Динамический запрос — самостоятельная связь, а не неизменяемый список результатов.
Неполный индекс обратных связей должен показывать неполное покрытие; он не
доказывает, что общий объект больше нигде не используется. Просмотр зависимостей
сохраняет access; закрытые страницы не раскрываются через названия или ссылки.

## 7.5. Проверяемое описание и инструкция у владельца

У самостоятельного публичного элемента предусматриваются три согласованные части:

1. **Машинное описание** — небольшой typed manifest у владельца реализации.
2. **Инструкция** — краткое руководство по использованию и развитию элемента.
3. **Производный каталог** — результат сборки описаний из фактических источников.

Схемы полей, defaults, validation и сигнатуры не переписываются вручную в manifest.
Он ссылается на их реальные owners; compiler формирует разрешённую проекцию.
Человек описывает смысл, условия использования и последствия, которые нельзя
надёжно вывести из типов.

| Содержание описания                          | Для чего нужно агенту                               |
| -------------------------------------------- | --------------------------------------------------- |
| Stable ID, вид/роли и владелец               | Найти нужный элемент и отличить его от похожих      |
| Версии публичного контракта и реализации     | Понимать совместимость с текущим проектом           |
| Ссылки на schema, public exports, renderer   | Работать с фактическим API и доступными настройками |
| Capability/check references с версиями       | Узнать реализованные действия и проверяемые условия |
| Зависимости, способы размещения и связи      | Оценить влияние изменения на другие объекты         |
| Usage/development guide references           | Получить инструкции под текущую задачу              |
| Lifecycle и migration/replacement references | Корректно обновить или заменить устаревший элемент  |

Конкретная сериализуемая схема manifest вводится перед первым implementation
slice. Строковые ссылки не становятся shell-командами или произвольно
загружаемыми executable. Пути исходников и guides разрешаются только внутри
допустимых owners выбранного выпуска.

Инструкция отвечает на вопросы: для чего использовать элемент; как создать
экземпляр и изменить существующий; что меняется локально и совместно; какие
действия поддержаны; какие входы/результаты ожидаются; какие ограничения и
проверки обязательны; как развивать контракт без поломки существующих данных.
Сценарии использования и разработки могут быть разделами одного существующего
README/руководства. Отдельный файл оправдан самостоятельной ответственностью.

Каждой утилите доступны собственный типизированный контракт и пояснение рядом
с реализацией, а также инструкция её владельца. Отдельный AGENTS.md для каждой
функции не требуется: дублирующиеся правила быстро расходятся и перегружают
контекст. Самостоятельный сложный публичный helper может иметь собственный
guide, если его использование этого требует.

`AGENTS.md`, `.ai` и `.codex` сохраняют назначение инструкций разработки.
Product usage guide не переопределяет эти правила и не выдаёт полномочий
встроенному агенту. Runtime не предполагает, что провайдер сам найдёт все
вложенные инструкции: нужные fragments явно доставляет Context Pack compiler.

### 7.5.1. Идентичность, владелец и версии

**Согласовано 16 ноября 2026 года.** Этот раздел задаёт общие правила описания
публичных элементов. Он не объявляет реализованными универсальную schema,
resolver или новый порядок установки ядра. Ограниченный owner resolver
реализован последующим срезом §7.5.3. Формы ссылок заданы в §7.5.2;
полная schema описания требует отдельного контрактного шага. Существующие
manifests и wire contracts сохраняются.

Постоянная идентичность элемента — пара `namespace + id`. Namespace задаёт
контролируемое пространство идентификаторов; для стандартных элементов
платформы используется `realize`, для собственных элементов организаций и
проектов — их устойчивые пространства. Namespace и ID назначаются явно,
не выводятся из текущего пути, имени React-функции или npm-пакета.

Версия и `kind` не входят в постоянную идентичность. Kind определяет способ
интерпретации и профиль проверки; он не разрешает создать второй элемент с
тем же `namespace + id`. Отображаемое название, путь и поставляющий пакет могут
меняться без смены ID. Опубликованный ID не переиспользуется для другого
элемента; восстановление того же элемента и переустановка прежнего выпуска
разрешены. Удалённый неопубликованный черновик не обязан навсегда резервировать имя.
Определение, его размещение и связанный общий документ сохраняют разные ID
по §7.4. Новые ID рекомендуется задавать читаемыми именами в нижнем регистре;
действующие ID, включая `blocks.formBlock`, не нормализуются молча.

Локальная native identity не обязана быть глобальной. У template и palette
Control Panel совпадает native ID, а `default` у макета локален шаблону.
Адаптер явно сопоставляет исходную ссылку с её областью действия и глобальную
identity; исходные templateId/paletteId/layoutId, версии и selections сохраняются.
Назначенный глобальный ID не пересчитывается автоматически из текущего kind,
владельца или имени пакета. Самостоятельные элементы получают свои identities;
внутренние slots и настройки могут оставаться локальными ключами контракта.

У элемента один логический владелец контракта: модуль, пакет либо проект.
Владелец отвечает за публичный контракт, документацию, совместимость и миграции.
Пакет может быть владельцем примитива, если несёт эту ответственность; отдельный
модуль ради заполнения поля не создаётся. Для самого пакета ответственность
может принадлежать проекту или функциональному модулю. Сопровождающая команда
и права конкретного пользователя не подменяют архитектурное владение.

`owner` хранит ссылку на identity владельца без повторения его kind и без версии
поставки. Resolver проверяет фактический kind и допустимость владельца по
профилю поля; неизвестный owner и недопустимый kind вызывают явный отказ.
Автоматической подстановки проекта нет. Связь palette/layout с template не
делает template их логическим владельцем: эта связь и owner различаются.
Корневой project owner подтверждается доверенной конфигурацией host и завершает
цепочку; рекурсивный descriptor для каждого следующего владельца не требуется.
Контакты сопровождающей команды разрешаются по owner и не копируются в каждый
элемент. Их изменение не требует перевыпуска всех принадлежащих элементов.

Поставка реализации описывается отдельно: package/source, точный выпуск,
публичный export и подтверждённое происхождение артефакта. Эти сведения и digest
связывает механизм поставки. Указание owner или namespace в manifest само по
себе не предоставляет права регистрации или публикации; host проверяет
доверенную регистрацию. Перенос реализации между пакетами сохраняет ID и
может сохранять владельца. Передача ответственности фиксируется отдельно,
без изменения прежних опубликованных версий и их owner bindings.

| Значение                    | Назначение                                                                       |
| --------------------------- | -------------------------------------------------------------------------------- |
| `schemaVersion`             | Формат общего описания                                                           |
| `version`                   | Неизменяемая опубликованная версия определения элемента                          |
| Версия публичного контракта | Самостоятельный API, props или schema, если у них отдельный жизненный цикл       |
| Версия реализации           | Выпуск поставляющего пакета или исходного артефакта                              |
| Версия/снимок руководства   | Конкретная редакция guide                                                        |
| `descriptorHash`            | Вычисленное точное содержимое описания; не версия совместимости и не digest кода |

Отдельная версия API вводится при самостоятельной ответственности контракта,
а не автоматически для каждого компонента. Дополнительный ручной счётчик
`descriptorRevision` не требуется. Для новых определений применяется SemVer:
PATCH — совместимые исправления и уточнения, MINOR — совместимые расширения,
MAJOR — несовместимые изменения. Для `0.y.z` стабильность не предполагается,
совместимость подтверждается явно. Правила и неизменяемость опубликованных
версий основаны на [SemVer 2.0.0](https://semver.org/).

Неизменяемость начинается с принятой публикации. Рабочий черновик допускает
редактирование без новой SemVer на каждое сохранение; его preview связывается
с конкретным снимком/hash. Строка версии в исходном manifest не доказывает
публикацию. Draft и опубликованная версия различаются явно. Descriptor остаётся
кратким, подробные объяснения и примеры принадлежат самостоятельным guides.

Изменение полей опубликованного определения, включая description, owner или
guide reference, требует новой версии определения. Совместимое уточнение
выпускается как PATCH. Исправление реализации при неизменном определении
требует нового выпуска реализации. Изменение отдельного руководства создаёт
его новую версию или неизменяемый снимок и не обязано менять версию API.
Если при этом изменяется guide reference внутри определения, оно также
получает новую версию. Удаление обязательного slot или несовместимое изменение
данных требует несовместимой версии и стратегии перехода.

`namespace + id + version` закрепляет опубликованное определение. Для исполнения,
предпросмотра и Context Pack отдельно фиксируются точные release/source bindings
и hashes разрешённых schema/guide ресурсов. Из версии определения нельзя
вывести digest реализации. Диапазоны допустимы в требованиях совместимости;
сохранённое назначение и контекст исполнения используют точные разрешённые
версии. Compiler должен выявлять разные описания одной identity/version,
изменение фактической публичной схемы под прежней версией контракта и конфликт
регистрации namespace. Несколько представлений связываются с одним контрактом
явно; порядок регистрации не выбирает реализацию молча.

Пользовательский самостоятельный компонент или fork получает новую идентичность
и явную ссылку на исходное определение. Presentation override остаётся отдельным
совместимым представлением с binding к контракту. Ни fork, ни override не
присваивают идентичность исходного компонента.

Общий каталог подключает существующие источники через адаптеры. Они сохраняют
исходные ID, версии, hashes, назначения и receipts: `pages`, `blocks.content`,
`blocks.formBlock` с версиями `1.0`/`1.1` и template
`realizeai-control-panel@0.1.0` не переписываются под новый формат. Версия `1.1`
не преобразуется автоматически в `1.1.0`; регистр ID не меняется. Формат и
правила сравнения определяет зарегистрированный профиль соответствующего
контракта, а не универсальная догадка по строке версии. Legacy `realize`
сохраняет собственную идентичность и не становится alias нового renderer.

### 7.5.2. Формы ссылок и проверка разрешения

**Согласовано 16 ноября 2026 года с уточнениями после проверки модели.** Это
сериализуемые формы контракта. Runtime validation identity/owner reference
реализована в ограниченном §7.5.3; VersionedElementRef и полная модель
опубликованных descriptors ещё не являются готовым общим API:

```ts
type ElementIdentity = {
  readonly namespace: string;
  readonly id: string;
};

type ElementOwnerRef = {
  readonly identity: ElementIdentity;
};

type VersionedElementRef = {
  readonly identity: ElementIdentity;
  readonly version: string;
};
```

Объекты строгие: дополнительные поля не принимаются. Identity сравнивается
как точная пара полей с сохранением регистра; внутренний ключ использует
однозначную tuple/JSON-сериализацию. Склейка через точку недопустима:
`["realize.ui", "button"]` и `["realize", "ui.button"]` различаются.

Начальные пределы размера — namespace 63, id 256, version 128 символов. Это
продуктовые bounds, а не обещание соответствия DNS или другому стандарту.
Проверяются непустота, допустимые token characters, отсутствие управляющих и
невидимых символов и краевых пробелов; некорректный ввод отклоняется, а не
исправляется через trim/lowercase. Полная грамматика задаётся в schema/profile
до реализации; строковый TypeScript-тип не заменяет runtime validation.
Проверенные типы Namespace/ElementId/DefinitionVersion создаются через validators,
чтобы путь файла или другая строка не подставлялись вместо ссылки случайно.

OwnerRef не фиксирует версию поставки владельца. Допустимые owner kinds
проверяются resolver независимо от содержимого ссылки и против выбранного
snapshot. Самоссылающийся package owner не используется ради заполнения поля.
Для первого среза достаточно явной доверенной host-регистрации; универсальный
сервис выдачи namespace или отдельная БД владельцев не являются условием.

Версионируемая ссылка содержит точную native version целевого определения.
Её формат проверяет зарегистрированный профиль; versionScheme/profileRef
не копируются в каждую ссылку. Каждый потребитель также проверяет ожидаемый
kind/profile и требуемый контракт: существование ссылки ещё не означает
совместимость с областью или операцией. Отсутствующая identity/version, неверный
профиль или несовместимый контракт дают диагностируемый отказ без выбора latest,
поиска одноимённого элемента другого kind либо молчаливого fallback.
Диапазоны зависимостей описываются отдельно как требования совместимости,
которые compiler разрешает в точные pins.

Descriptor hash, release/source bindings, результаты проверок, readiness и
текущие права принадлежат производным слоям. Перед исполнением фиксируются
точные версии и resource hashes; простая VersionedElementRef их не заменяет.
Registry compiler выявляет drift manifest/schema/renderer/capability references
и сообщает конкретную причину, путь и затронутые зависимости. Admin, редактор
и агенты получают подходящие проекции общего каталога; весь каталог и тексты
guides не копируются в каждый client bundle или prompt.

[отчёт от 16 ноября 2026 года](../../../../reports/2026-11-16-element-identity-model-check.md).
Отчёт различает существующие native данные, контрольные новые mappings и ещё
не реализованные регистрации владельцев и публикации определений макетов.

### 7.5.3. Первые регистрации владельцев и нейтральный resolver

**Согласовано 17 ноября 2026 года.** Первый срез вводит две явные регистрации
владельцев для пяти проверенных элементов из отчёта §7.5.2. Это развитие
общего контракта, не отдельная модель владения UI или ИИ. Первый read-only
compiled срез реализован и проверен; он не является полным registry
опубликованных descriptors или подтверждением runtime installation.

| Обозначение | Identity                                               | Kind      | Title                   | Владелец                                         |
| ----------- | ------------------------------------------------------ | --------- | ----------------------- | ------------------------------------------------ |
| P           | `realize` / `project.realize-ai-platform`              | `project` | Realize — AI Platform   | Нет owner; явный доверенный terminal host anchor |
| T           | `realize` / `package.template-realizeai-control-panel` | `package` | RealizeAI Control Panel | `{ identity: P }`                                |

P регистрируется host явно как корневой проект и завершает цепочку. Это не
автоматический fallback для неизвестных owners и не скрытое утверждение прав
на namespace. T является самостоятельной package identity, не template ID и
не npm packageName. OwnerRef содержит только identity, без копирования kind
или версии владельца. Resolver проверяет фактический kind зарегистрированного
владельца и политику цепочки; самоссылка package и неразрешённый owner вызывают
диагностируемый отказ.

**Owner registration и опубликованный descriptor — разные представления одной
identity.** `OwnerRegistration` фиксирует достаточные для разрешения владения
identity/kind/title и owner-происхождение. Она не является опубликованным
определением и не получает выдуманную SemVer ради заполнения version. Если
позже у проекта или пакета публикуется descriptor, он использует ту же identity,
проверяемый kind и собственную опубликованную версию; новая identity для этого
не создаётся. Формат полного descriptor остаётся отдельным контрактным шагом.

Изменяемый состав owner registrations фиксируется детерминированным
**snapshot hash конфигурации**. Hash не заменяет версию API resolver, не является
SemVer определения и не выдаётся за digest поставленного кода. Контекст
проверки может ссылаться на конкретный snapshot. Действующие published
определения и старые owner bindings не переписываются этим config-срезом.

**Связь с поставкой вынесена отдельно.** Package binding связывает T с точными
npm packageName/version и необходимыми публичными exports. Для первого пакета
это `./manifest`, `./admin`, `./settings`, `./registry`. Ожидаемая точная версия
пакета берётся из dependency host `package.json`, фактические name/version/exports
— из доверенно импортированного `package.json` шаблона через отдельный public
export `./package.json`. Версия пакета не выводится из template.version как
общее правило; совпадение `0.1.0` в первом срезе не связывает их жизненные циклы.
Source bindings связывают существующие native элементы и их владельцев. Owner registration не
подменяется `package.json`; запись пути или имени пакета не подтверждает
установку, доверие к артефакту, readiness либо право исполнения. Права actor,
ACL, применимость инструкций и namespace admission сохраняют существующих
владельцев и не выдаются через registry.

Пять начальных element-owner bindings задаются явно:

| `pages`                                         | P     | Definition/guide `pages@1.1` без преобразования в `1.1.0`; collection slug `pages`                                                                             |
| `realizeai-control-panel`                       | T     | Template ID/version `realizeai-control-panel@0.1.0`                                                                                                            |
| `realizeai-control-panel.palette`               | T     | Palette ID/version `realizeai-control-panel@0.1.0` в scope template                                                                                            |
| `realizeai-control-panel.layout-default`        | T     | Local layoutId `default` и точный template scope; на первом owner-срезе собственной версии не было, draft definition `0.1.0` введена последующим §7.5.4        |

Пакет реализации `@realize/template-realizeai-control-panel@0.1.0` связан с T

публикует descriptor макета задним числом. Существующие selections, IDs,

фиктивные module/project записи для наполнения графа не создаются.

**Реализованные границы первого среза:**

- нейтральный `@realize/element-registry@0.1.0` владеет общими типами,
  validation, построением snapshot и разрешением owner цепочек; контракт не
  помещается в `ai-contracts` или Template SDK, поскольку применяется ко всем
  видам элементов;
- package-owned server-safe export `@realize/template-realizeai-control-panel/registry`

- построение snapshot выполняет проверяемое копирование и глубокое freezing;
  hash детерминирован по содержимому и не зависит от порядка регистрации.

Публичный `@realize/element-registry` entry предоставляет browser-safe schemas,
типы и identity key. Server entry `/server` экспортирует `createOwnerRegistry`

подключён к Payload/Extension Manager startup или runtime admission**:

выбранными export targets. Он **не покрывает пять element-owner mappings,
исходники реализации, артефакт установки или ACL**. Наблюдавшийся hash первого

Он не становится версией опубликованного определения.

Не реализованы полная schema опубликованного descriptor, общий versioned
resolver и module-owner profile. Новый HTTP/Admin API, коллекция БД, installer,
UI-каталог всех элементов и подключение новых инструкций агентам в этот срез
не входят. Предыдущий отчёт от 16 ноября остаётся исторической проверкой

### 7.5.4. Самостоятельные определения макетов и pins выпуска

**Согласовано 17 ноября 2026 года; реализован ограниченный source/preview
срез двух draft definitions `0.1.0`.** Решение развивает implemented owner-срез
§7.5.3, не меняя его идентичности, проверки или границы snapshot hash. Это не
публикация определений, runtime activation или полный редактор; объём
подтверждённых проверок перечислен ниже.

У двух макетов сохраняются независимые глобальные identities в namespace
`realize`: `realizeai-control-panel.layout-default` и
`realizeai-control-panel.layout-without-topbar`. Первыми самостоятельными
**draft definition versions** назначаются `0.1.0` для каждого. Это новые
декларативные определения с явным draft-статусом, не приписывание собственной
версии старому native макету задним числом. Native aliases `default` и
`without-topbar` сохраняются; template/package release `0.1.0` не является
правилом вычисления definition version. Публикация и immutable publication gate
остаются отдельным последующим действием.

Строгий специализированный layout profile принадлежит Template SDK. Он
проверяет сериализуемые metadata макета: identity, версию, owner reference,
название/описание, template identity, target/screen, profile ID/version, области
и вложенные slots, owner-bound guide reference. Draft здесь обозначает состояние
исходного среза до публикации; отдельного approval/status поля и publication
сервиса первый profile не вводит. Это не общий published
ElementDescriptor всех видов элементов. Pure parsing отделён от Node hashing:
SDK subpath `/layouts/server` выполняет синхронную серверную компиляцию/hash;
React/CSS и произвольное чтение файлов в metadata parser не допускаются.
Новых внешних dependencies этот срез не требует.

Package-owned public export `@realize/template-realizeai-control-panel/layouts`
предоставляет server-safe metadata и исходные release alias pins без React/CSS.
**Один авторский источник** определяет local IDs, labels, самостоятельные
identities/версии и метаданные. Settings enum/labels и host mappings производятся
из него; ручные копии этих сведений в schema, renderer и host не создаются.
React-реализации подключаются отдельным compiled mapping с точным покрытием:
каждое объявленное определение имеет одну реализацию, а отсутствующие, лишние
или конфликтующие entries отклоняются. Публичные IDs/labels frozen, ссылки и
descriptors нормализуются validators перед сверкой compiled binding. Host owner
mappings выводятся из metadata с одним элементом на global identity, не
дублируя его при нескольких aliases/versions. JSON не выполняется как import кода.

**Область и slot различаются.** `rail`, `topbar`, `sidebar`, `panel-content`,
`footer` — области каркаса. `brand` — вложенный slot rail, а не шестая корневая
область; его существующая геометрия сохраняется также без topbar. Пустые
поддерживаемые области не исчезают. В `without-topbar` topbar отсутствует по
контракту макета. Отсутствие области не разрешает renderer молча выбросить
переданный context/контент: поддержка должна быть выражена контрактом, а
неподдерживаемый вход — явным отказом. Автоматический перенос или скрытая
потеря функционального содержимого не являются fallback.

Описание slot указывает структурную точку передачи содержимого; оно **не
доказывает совместимость произвольного компонента или готовность редактора**.
Component profile и проверка допуска компонентов остаются отдельным срезом.
Публичные presentation props renderer этим шагом не изменяются.

Реализация использует один устойчивый `ControlPanelFrame` и узел содержимого
при смене макета. Переключение CSS-варианта/metadata не должно заменять React component
type обёртки и перемонтировать доменный controller/форму. Совместимая смена
layout/mode сохраняет состояние содержимого; обязательны отдельные проверки
реального mount/state, а не только одинакового HTML.

Геометрия, адаптивность и размещение областей — фактическая часть layout
контракта. Metadata должны соответствовать CSS и runtime. Контрактное изменение
геометрии/областей требует версии определения и соответствующего выпуска
реализации, а не правки CSS под прежним published описанием. Пока определение
draft, его изменения связываются с новым snapshot/hash; draft-версия в исходниках
не подтверждает публикацию и не запускает immutable gate автоматически.

**Каталог точного выпуска** связывает native alias внутри конкретного template
release с точным pin `global identity + definition version`. Разрешение не
выбирает latest и не подменяет отсутствующий pin одноимённым макетом. Host
компилирует отдельный layout catalog hash по metadata и release mappings;
owner snapshot hash из §7.5.3 для этого не используется. Layout catalog hash
покрывает template identity/version, default alias, exact alias pins и metadata
определений. Он не покрывает bytes renderer/CSS/guides или артефакт установки.
Pure parser проверяет строгую форму DTO, граф ссылок и формат hash, но не
выполняет криптографическую проверку его значения. Серверный builder
`createTemplateLayoutCatalog` пересчитывает SHA-256 и сверяет переданный либо
ожидаемый hash; browser consumer должен получать доверенный build/server
snapshot. Формально допустимый hash сам по себе не подтверждает происхождение. Старые manifestHash, appearance catalogHash,
assignments и receipts не переписываются ради layout-каталога.

При наследовании key `settings.layoutId` отсутствует (`undefined` при чтении
отсутствующего свойства); явный alias сохраняется как выбор пользователя,
а default разрешается из выбранного выпуска.
`null` по-прежнему невалиден и не означает наследование. Ни отсутствие, ни
промежуточный effective выбор не материализуются автоматически в persisted
`default`/`null`.

Guide reference привязан к владельцу T и реальному package `README.md`, разделу
`макеты-и-самостоятельные-версии`. Для него не выдумываются Document ID,
публикация, SemVer инструкции или новый AI tool. Разрешение инструкции не
выдаёт actor полномочий и не делает текст системной инструкцией агента.

### 7.5.5. Exact layout binding назначения и reader-before-writer

**Согласовано 2026-11-18; первый reader-only этап реализован и проверен в source.
Второй source-срез описан ниже; durable запись binding остаётся выключенной.**
Назначение шаблона получает опциональную привязку точного определения макета.
Она отделена от пользовательского намерения в `settings.layoutId`:

```ts
layout?: {
  schemaVersion: "1.0";
  localId: string;
  reference: LayoutVersionedRef;
  catalogHash: string;
};
```

`ExtensionAssignment.layout` — server-derived часть назначения, не входной
параметр выбора пользователя. `localId` — alias внутри точного template release;
`reference` — global identity и точная самостоятельная версия определения;
`catalogHash` — hash layout-каталога этого выпуска из §7.5.4, а не owner snapshot
hash и не appearance catalog hash. Строгий сериализуемый контракт принадлежит
Template SDK; Extension Manager использует его в общих assignment/DTO/codec
границах, не создавая второй schema того же binding.

При наличии binding явный `settings.layoutId` обязан совпадать с `layout.localId`.
Отсутствие key настройки (`undefined` при чтении отсутствующего свойства)
сохраняет наследование default выбранного выпуска. Pure resolver второго среза фиксирует
разрешённый effective pin в `layout`, сохраняя
отсутствующее поле настройки отсутствующим. `null` не означает наследование и
невалиден. Старое назначение без binding остаётся явно legacy: его частные
settings не переосмысливаются новым reader, defaults не добавляются, отсутствующий
binding не выводится по текущему каталогу и не дописывается в историю.
Settings ограничены JSON-контрактом: явно записанный `layoutId: undefined`
невалиден. Отсутствующий `layout` тоже должен быть опущен; собственные поля
`layout: undefined` и `layout: null` отклоняются.

**Граница первого этапа.** Реализованы строгие readers общих типов,
DTO, store/plan/receipt codec для опционального binding. Чтение проверяет форму,
неизвестные поля, exact version/hash format и согласованность явного alias.
Оно не доказывает наличие pin в доверенном каталоге, корректность значения hash,
совместимость target/profile, установку renderer, readiness или ACL. На первом
этапе resolver/prepare формировал прежнее назначение без `layout`, без
обогащения записей по новому каталогу. Appearance catalog hash, legacy plan/state
hashes и успешные replay receipts этим этапом не менялись и не пересчитывались.
Assign/recover/apply commands не
принимают binding извне; optional поле расширяет readers, а не command input.

Итоговый единый source-прогон первого reader-only этапа: **10 suites / 259 tests passed** — 31 новый
reader test и 228 regression tests. Полный typecheck с новым тестовым файлом,
адресные ESLint/Prettier и headers 8/8 прошли. Golden fixtures подтверждают прежние
legacy hashes и неизменную wire JSON форму, отсутствие добавленного binding
в resolver/prepare и сохранность успешного replay. Для host catalog первого
этапа проверен фиксированный baseline
`31e93e60a3671440d6618e483593bd7faf5b3205ef8e3c28688b3cda5776636d`;
это fixture-проверка compiled registration, не подтверждение установки в runtime.
HTTP API, SQL migrations и поведение renderer этим этапом не менялись;
реальный PostgreSQL и runtime pin validation им не проверяются.

**Второй source-срез реализован и проверен в исходниках 2026-11-18.
Durable запись остаётся выключенной.**
Доверенная compiled registration расширяется опциональным полем:

```ts
layouts?: {
  templateIdentity: unknown;
  catalog: unknown;
};
```

`templateIdentity` — ожидаемая global identity шаблона, явно заданная host
mapping. Общий compiler не вычисляет её из native ID. Он строго проверяет
catalog через SDK server contract, сверяет identity и точную template version
с registration/manifest, а target/screen макетов — с объявленной поддержкой
выпуска. Невалидная заявленная registration отклоняется. Нормализованный
`layoutCatalog?: TemplateLayoutCatalog` появляется в compiled entry и DTO;
отсутствующее поле legacy entry остаётся отсутствующим. Новое поле DTO требует
совместимого client reader, даже если durable writer пока выключен.

В hash projection существующего appearance catalog добавляется только для
layout-aware entry поле `layoutCatalogHash`. Оно связывает план с exact release
catalog без второй независимой схемы подтверждения. Hash projection legacy
entries и их manifestHash не меняется; hash общего каталога после добавления
layout metadata меняется. Все pending plans с прежним общим hash становятся
stale, в том числе планы legacy templates. Сохранённые assignments/history и
receipts не переписываются; успешный apply replay возвращает прежний receipt.

Для layout-aware entry pure `resolveExtensionAssignment` всегда формирует
server-derived `assignment.layout` после нормализации settings и разрешения
alias/default; отсутствие `settings.layoutId` сохраняется. Пользователь не
передаёт binding через новые поля command input. Legacy entry без layout
registration сохраняет прежнюю форму назначения. Неизвестный alias, неполная
registration или несовместимый exact pin не заменяются legacy/default.
Recover не обогащает прежнее назначение автоматически: отсутствующий либо
устаревший binding у previous layout-aware назначения приводит к отказу.
Inventory comparator также сверяет manifest/settings и полную layout фиксацию;
отсутствующий/неверный pin отмечается как `invalid_assignment`, выбранное
назначение и фактически активное оформление остаются разными состояниями.

**Durable gate.** Trusted policy pure operations
`layoutAssignmentWrites?: "disabled" | "enabled"` по умолчанию `"disabled"`;
это не пользовательский HTTP/body параметр. Все четыре durable вызова
appearance/Admin Shell prepare/apply передают `"disabled"` явно.
`"enabled"` используется только pure fixtures, результаты
которых не сохраняются. Общий validator перед возвратом не-replay результата
проверяет полный appearance/admin-shell store: targets, pending plans,
receipts и вложенные назначения. Если в нём присутствует binding, при
выключенной policy операция отказывает с `LAYOUT_BINDING_WRITES_DISABLED`.
Guard применяется также к apply; он защищает все возвращаемые assignments,
а не только новое desired assignment. Layout-aware prepare поэтому не
сохраняет новый plan/prepare receipt и не обходит запрет старой формой без binding.
Shell apply дополнительно проверяет consumed plan до его удаления: его apply
receipt уже не содержит assignment. Наличие binding в bootstrap другого target
тоже не разрешает сохранить его вместе с новой legacy операцией.

В pure operation успешный apply replay возвращается до нового write guard и
свежих catalog/layout/readiness/TTL checks. Прежняя проверка TTL prepare replay сохраняется;
она не превращается в бессрочный replay. Actor/scope границы не ослабляются.
В реальном appearance service сохраняется известная граница: catalog и
bootstrap строятся до lookup receipt в repository. Поэтому replay при
невалидной host-конфигурации каталога не гарантирован; новый write gate эту
границу не расширяет и не помещён в сборку каталога.
Pure SDK parser/codec остаётся reader без lookup и без write policy. SQL schema,
данные БД, HTTP command fields, renderer и activation этим срезом не меняются.
Результаты pure prepare fixtures не подтверждают реальные записи или installation.

Итоговый единый source-прогон второго среза: **13 suites / 310 tests passed**,
включая 29 проверок нового suite и 281 regression tests. Полный typecheck,
адресный ESLint и headers 23/23 прошли. Проверены строгая registration и hash,
default/version drift, exact binding pure prepare/preview DTO, старые replay/
legacy golden fixtures, закрытый writer, bootstrap другого target и inventory
comparator. HTTP fixtures используют настоящий service с изолированным
repository; это не PostgreSQL acceptance и не browser-приёмка exact-pin renderer.

## 7.6. Обнаружение и понимание возможностей

Производный каталог дополняет существующий server-owned capability registry
сведениями об элементах и их связях. Он не является второй базой разрешений.
Метод, описанный в guide, доступен для исполнения только при наличии
зарегистрированной capability, допустимого способа исполнения и текущих прав.

Агент последовательно получает: результаты поиска → описание выбранного
элемента → связанные версии и нужные fragments инструкции → контекст экземпляра.
Используется ограниченная загрузка по задаче, а не полный каталог в каждом prompt.
Сам факт похожего названия не является основанием выбора: проверяются schema,
назначение, совместимость и влияние зависимостей.

В одном каталоге различаются: описанный элемент, установленная реализация,
пройденные проверки конкретной версии и разрешённое сейчас действие.
Отсутствующий executor или неподдержанная версия показываются явно.
Admin UI и агент получают согласованные проекции этих же сведений. Профили,
разрешения и локальные инструкции настраиваются в существующей админке;
installation overlay не регистрирует новый исполняемый код.

Run фиксирует точные версии и hashes выбранных описаний, guides и capabilities
по [правилам Context Pack](10-ai-codex-layer-integration.md#102-компиляция-context-pack).
Прочитанный текст страницы, сторонний README или незарегистрированный plugin
guide остаются недоверенным содержимым. Проверенный guide из установленного
выпуска тоже не может менять identity, границы записи или правила подтверждения.

## 7.7. Актуальность описаний

Производный каталог собирается из фактических registrations, public exports,
host schemas и manifests. Generated output не редактируется вручную.
Проверки сборки должны выявлять:

- повтор stable ID, отсутствующую ссылку или несовместимую версию;
- расхождение заявленной схемы, renderer и поддержанных операций;
- объявленный capability/check, не разрешающийся в существующем registry;
- отсутствующий guide или несоответствие проверяемых примеров текущему контракту;
- несовместимое обновление определения без стратегии для существующих экземпляров.

Изменение публичного контракта требует проверки затронутой инструкции и примеров.
Если смысл инструкции остаётся верным, review фиксирует это без искусственной
правки текста. Хеш подтверждает происхождение, но не смысловую правильность:
полностью автоматическое поддержание документации не обещается.

Проверяются затронутые контракты и сценарии; изменение renderer требует уместных
браузерных доказательств. Проверка всех функций проекта при каждой правке не
является условием этой архитектуры. В каталоге хранится привязка доказательств
к проверенной версии; прежний результат не переносится на новый код автоматически.

Удаление или отключение плагина сначала проверяет зависимые модули и размещения.
Данные страниц не удаляются из-за исчезновения renderer. Совместимость,
deprecated/replacement policy и миграция проходят управляемый процесс изменения.

## 7.8. Первый пример и критерий результата

Первый срез уже подключает host manifests Pages/Content/FormBlock, производный
каталог и ограниченный outline выбранной страницы к чату. Фактические границы
реализации и оставшиеся шаги описаны в
[14.9](../02-change-engine-and-pipelines/14-data-config-pipeline.md#149-каталог-и-структура-pages-первый-реализованный-срез).
Остальные механизмы разделов 7.4–7.7 остаются целевой архитектурой.

Первый набор — Pages, Content и FormBlock: он покрывает документ, локальный
блок, функциональный виджет и общую форму. По его описанию агент должен уметь:
найти подходящий элемент, прочитать существующую страницу, отличить изменение
размещения от изменения общей формы и выбрать разрешённый способ действия.

Для этого достаточно описать существующих владельцев и связать их с реальными
контрактами. Новые пакеты, универсальная Widget collection и паспорта всех
исходников заранее не создаются. Следующий элемент добавляется, когда проверено
повторное использование этого же контракта.

Выбор сервиса, браузера и разработки недостающего действия описан в
[Change Engine](../02-change-engine-and-pipelines/11-change-engine.md#116-выбор-способа-исполнения).
Применение к страницам — в
[Data Lane](../02-change-engine-and-pipelines/14-data-config-pipeline.md#148-блоки-виджеты-и-гибридное-редактирование).
