# Медиатека Realize: обработка изображений, загрузка и использование в блоках

Статус: **библиотека, профили и native обработка подключены**,
версия 0.5, 2026-09-15. Исходники, версии рецептов, Jobs и варианты проверены
на отдельной PostgreSQL и через рабочие формы админки. Новая панель проверена
на узких экранах; у штатной шапки Payload зафиксировано отдельное переполнение.
Разделы ниже различают текущую реализацию и целевую архитектуру использования.
Сопутствующий документ: [референсы и требования к экранам](media-management-references.md).

## 1. Результат для пользователя

Администратор загружает файлы, быстро находит нужное изображение и управляет
размерами и качеством через админку. Один исходник используется на разных
страницах с подходящими размерами и кадрированием. Изменение настроек не портит
оригиналы и не меняет опубликованные страницы без управляемого применения.

Медиатека должна оставаться частью Payload Admin и общего визуального языка
Realize. Сценарии должны одинаково работать из раздела «Медиа», поля выбора
изображения на странице и разрешённых сервисных вызовов агента.

Рабочая граница первой версии: полноценная обработка **изображений**; для видео
и документов — загрузка, поиск, метаданные и хранение. Перекодирование видео,
стриминг, распознавание содержимого и редактор изображений уровня Photoshop
выделяются в последующие задачи. Этот scope уточняется при обсуждении.

### 2.1. Первый рабочий срез библиотеки

Основной адрес — `/admin/collections/media`. Тонкий клиентский
[MediaListView](../../src/components/admin/media/MediaListView.component.tsx)
добавляет сетку карточек и переключение на штатную таблицу через публичные
`Table`/`BeforeListTable` slots компонента `DefaultListView`.
Это документированная точка расширения
[Payload List View](https://payloadcms.com/docs/custom-components/list-view).

Записи читает native серверный ListView с текущим `req` и
`overrideAccess: false`. Поиск по `filename`/`alt`, фильтры по полям (включая
`mimeType`), сортировка, пагинация, права и массовые действия остаются у Payload.
Начальная страница содержит 12 записей; доступны 24 и 48. Сохранённые preferences
пользователя имеют приоритет над начальными значениями. Размер страницы интерфейса
не является новым жёстким ограничением REST API.

Карточка показывает имя, альтернативный текст и фактические метаданные; ведёт
в native editor. Preview использует публичный `Thumbnail`, а выбор нескольких
записей — штатный `SelectionProvider`. Числовые ID не преобразуются в строки
при выборе. Небольшой mapper внутри admin owner передаёт карточке только нужные
поля и не создаёт нового публичного API/DTO.

Создание файла и массовая загрузка используют формы Payload, включая обязательный
`alt`, ошибки каждого файла и сохранение. В upload-полях страниц действует
исходный `DefaultListView`: собственная сетка не подменяет `ListDrawer`.
Новый сервис чтения, upload endpoint, схема, миграция и обработчик Sharp для этого
среза не требуются. Существующая политика хранения и обработки исходника сохранена;
неизменяемый master в этом первом срезе не подключался. Его последующее
подключение описано в текущем контракте ниже.

Макет `/admin/collections/media/reference` остаётся отдельным демонстрационным
материалом для последующих разделов. Его папки, профили и состояния обработки
не выдаются за данные рабочей библиотеки.

Проверены TypeScript, адресные ESLint/шапки/форматирование и восемь тестов
mapper. Браузер подтвердил поиск по имени и alt, MIME-фильтр, сортировку,
пагинацию, перенос массового выбора между видами, native single/bulk upload
с реальным сохранением и обязательным alt, а также исходный selector в Pages.
Светлая/тёмная темы проверены на 1440, 390 и 320 px. Временные QA файлы и записи
удалены; исходные Media, Pages и версии сохранены.
Материалы проверки находятся в
[задаче рабочего среза](../../.ai-workspace/tasks/2026-09-14-media-library-integration/TASK.md).

Планирование прошло через настоящий workflow `frontend.reference-to-layout`
в админской беседе 24; после локальной проверки контрактов агент получил
дополнение и оформил конкретный handoff. Исходники интегрировал и проверил
инженер в рабочем checkout. Workflow не объявлялся исполнителем кода или
браузерной приёмки; Code Lane в этом срезе не запускался.

## 3. Модель: файл, профиль, вариант, использование

### 3.1. Текущий контракт обработки (2026-09-15)

Владелец обработки — `src/collections/Media`, формы и версии профилей — native
Payload. Коллекции `media-profiles`, `media-originals`, `media-processing-sets`
и `media-variants` дополняют существующую `media`, сохраняя её ID и публичные URL.
Новая загрузка JPEG/PNG/WebP сохраняет точные байты в приватном хранилище вне
`public`. Для существующего `Media.url` создаётся отдельная техническая WebP-копия
до 2400 px, quality 85, без увеличения, EXIF/GPS и ICC. Это совместимая копия
для отображения, а не матрица вариантов профиля; повторный Next optimizer для
неё отключён. Профиль задаёт отдельные размеры и параметры форматов.

Global Sharp из Payload исключается: иначе native upload повторно кодирует
WebP. Crop/замена файла в существующей записи запрещены; прежние focal-поля,
файлы и ссылки сохраняются. Для legacy-записи обработка использует копию
сохранённого файла с явным происхождением `legacy-copy`: исходные байты до
старой обработки восстановить нельзя. Другие типы файлов сохраняют native upload
и не получают обещания обработки этим сервисом.

Задание получает ID набора; набор хранит источник, hash и полный рецепт с ID
native версии профиля. Правка профиля не запускает обработку старых материалов.
Намерение и native Payload job создаются одной транзакцией. Уникальные ключи,
проверка hash и готовности полного набора обеспечивают повтор без замены старых
URL. Частичные варианты закрыты native read-Where access; исходник доступен
только администратору. `MEDIA_PRIVATE_STORAGE_DIR` задаёт постоянный корень
хранилища; локальное значение — `.data/media`.

Один процесс `media:worker` запускается существующим dev supervisor независимо
от AI worker. Он исполняет native `jobs.run`, удерживает блокировку очереди в БД,
дожидается активной задачи при остановке и адресно восстанавливает прерванные
задания после получения блокировки. В production запускается тот же worker.
В карточке Media показываются версия профиля, состояние, варианты и повтор
ошибочного набора. Применение вариантов к опубликованным страницам — отдельный
этап; изменение профиля не переключает их содержимое.

Рабочие адреса: `/admin/collections/media-profiles` и карточка записи в
`/admin/collections/media`. Профиль выбирается в native single/bulk upload.
Ширины `small`/`medium`/`large`, WebP/JPEG quality и PNG compression редактируются
native формой. Стартовые профили — «Фото товара», «Баннер», «Логотип».
Текущая геометрия пропорциональная, без увеличения и crop; логотип использует
PNG без потерь. Прозрачный исходник с JPEG выдаёт ошибку, не теряя оригинал.

Смена выбранного профиля с сохранением файла ставит новый набор в очередь.
Правка самого профиля не меняет старые наборы: для применения новой версии
администратор нажимает «Создать варианты по текущему профилю» в карточке Media.
Нативная версия и рецепт фиксируются в момент команды. Панель показывает пять
наборов на страницу, готовые файлы, исходник, статус и повтор. Пока набор занят,
его статус обновляется автоматически; после native Save данные перечитываются.
Штатные retries ограничены, ручных повторов одного набора — до трёх. Массовое
назначение профиля существующим записям пока запрещено; native bulk upload
новых файлов и массовые правки alt/подписи сохранены.

Набор и job создаются в одной PostgreSQL транзакции под блокировкой Media.
Технические записи нельзя изменять REST/GraphQL вызовом; HTTP запуск native Jobs
закрыт, исполнение принадлежит одному worker. Удаление занятого Media отклоняется;
файлы удаляются только после native проверки блокировки редактора. Автоматической
очистки orphan-файлов после process crash пока нет; они закрыты native access.
Резервное копирование и ограничения rollback описаны в
[runbook миграций](../delivery/03-migrations-and-rollback.md).

Проверка активной конфигурации в disposable PostgreSQL включает 20 миграций,
точные исходники трёх форматов, закрытые orphan/partial файлы, две native версии,
атомарность intent+job, реальный retry, native lock 423 без удаления файлов,
отказ bulk смены профиля до записи и штатное удаление всей собственной цепочки.
Рабочая БД обновлена после private backup, restore и upgrade клона; прежние
Media/Pages/versions и остальные строки сохранены.

Браузер подтвердил native single/bulk upload с профилем, обязательный alt,
постоянный worker без ручного `jobs.run`, hashes/ACL, сохранение метаданных,
новую версию профиля, старые URL и повтор прежнего рецепта. Панель укладывается
в 1440/390/320 px в светлой и тёмной темах. Полная страница админки имеет
переполнение 15/6/32 px соответственно: native tooltip, account и breadcrumbs;
новая панель его не создаёт. Полная native шапка не объявляется исправленной.
Все QA файлы, профили и учётки удалены. Итог —
[приёмка обработки](../../.ai-workspace/tasks/2026-09-15-media-processing-profiles/logs/media-processing-acceptance-final.json).
TypeScript, scoped ESLint/шапки и адресные тесты пройдены. Docker/Compose
проверены статически; образ в этой среде не собирался, Docker CLI отсутствует.

| Понятие                  | Пример                                | Что в нём хранится                                                                    |
| ------------------------ | ------------------------------------- | ------------------------------------------------------------------------------------- |
| Исходник                 | Фотография товара                     | Файл, его контрольная сумма, фактический формат и размеры; исходные байты сохраняются |
| Профиль обработки        | «Фото товара», «Баннер», «Логотип»    | Разрешённые размеры, форматы, качество, правила кадрирования и ограничения            |
| Размер внутри профиля    | `small`, `medium`, `large`            | Конкретные размеры и способ вписывания; название само по себе не задаёт геометрию     |
| Вариант                  | WebP 1024 px по версии профиля 3      | Готовый файл, его URL, размеры, вес, версия рецепта, состояние обработки              |
| Использование в контенте | Изображение в блоке страницы доставки | Ссылка на исходник/набор вариантов, профиль, локальные alt/подпись/кадрирование       |

**Размер и назначение — разные оси.** `small` обозначает размер, а «Фото товара»
определяет правила: товар целиком на карточке и баннер с заполнением области
могут требовать разных вариантов одного изображения.

Изменение alt, подписи или кадрирования в одном блоке не должно менять остальные
использования изображения. Значения медиатеки служат значениями по умолчанию;
локальное значение блока имеет приоритет. Декоративность задаётся в конкретном
использовании, а не навсегда для всего файла.

## 4. Настройки изображений

### 4.1. Стартовая сетка размеров

Это начальные значения для измерений на реальных изображениях проекта, а не
универсальный стандарт качества.

| Размер      | Максимальная ширина | Обычное применение                                    |
| ----------- | ------------------: | ----------------------------------------------------- |
| `thumbnail` |              320 px | Списки и превью медиатеки                             |
| `small`     |              640 px | Небольшие карточки и мобильный контент                |
| `medium`    |             1024 px | Изображение в тексте, крупная карточка                |
| `large`     |             1600 px | Большой блок страницы                                 |
| `xlarge`    |             2400 px | Широкий баннер и экраны с высокой плотностью пикселей |

По умолчанию сохраняются пропорции, высота вычисляется из исходника и увеличение
маленького изображения запрещено. Фиксированная высота/соотношение сторон
добавляется только там, где этого требует профиль. Наличие пяти размеров не
означает обязательное создание всех пяти для каждого файла.

### 4.2. Редактор профиля в админке

- Название, стабильный идентификатор, описание назначения, состояние и версия.
- Применимые типы изображений и набор именованных размеров.
- Ширина, высота либо соотношение сторон; `inside`/`contain`/`cover` с понятными
  подписями и наглядными примерами; фон для прозрачности при необходимости.
- Политика фокусной точки, кадрирования и увеличения исходника.
- Выходные форматы и отдельные параметры каждого кодека.
- Максимальный вес как **целевой бюджет**, минимально допустимое качество и
  поведение, если уложиться в бюджет невозможно.
- Сводка числа будущих вариантов и ожидаемой области применения изменений.

Не показывать три неясных регулятора «сжатие», «качество» и «оптимизация»,
которые управляют одним параметром. Для JPEG/WebP/AVIF — качество и, в расширенных
настройках, вычислительные параметры кодека. Для PNG — уровень сжатия без потерь;
уменьшение палитры отдельно обозначается как потенциальная потеря качества.
Значения quality разных кодеков не равнозначны. Основание для конкретных
параметров — [Sharp output options](https://sharp.pixelplumbing.com/api-output/).

### 4.3. Начальные профили

| Профиль            | Геометрия                                                    | Начальная политика форматов/качества                                                   |
| ------------------ | ------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| Фотография/контент | Пропорционально, без увеличения                              | WebP около 80; JPEG fallback около 82; AVIF около 50 после измерения времени обработки |
| Фото товара        | Полный предмет, `contain`, нейтральный фон либо прозрачность | WebP; PNG/lossless для значимых прозрачных областей; не обрезать товар автоматически   |
| Баннер             | `cover`, заданное соотношение, фокусная точка                | WebP/JPEG; отдельный мобильный кадр только при необходимости                           |
| Логотип/графика    | Пропорционально, без обрезания и потери прозрачности         | PNG либо WebP lossless; не применять профиль фотографии                                |

Эти числа — предложения для стартовой настройки. Приёмка включает фотографии,
мелкий текст, градиенты, прозрачность и логотипы. Не обещать одинаковый вес и
качество для разных изображений. Режим «быстрее обработка / меньше файл» должен
объяснять влияние на время генерации, а не маскироваться под визуальное качество.

### 4.4. Обработка особых случаев

- Ориентация EXIF применяется к производным изображениям; цвет приводится к
  согласованному sRGB. GPS и лишние EXIF не выдаются в публичных вариантах.
- Прозрачность сохраняется, пока выбранный формат её поддерживает. Замена фона
  показывается до применения.
- Маленькое изображение не увеличивается молча: используется допустимый меньший
  размер с объяснением в карточке.
- JPEG/PNG и статические WebP/AVIF — кандидаты V1; фактическую поддержку входного
  AVIF проверить на выбранной сборке Sharp. GIF/animated WebP нельзя молча
  превращать в первый кадр. Их трансформации — отдельная capability с лимитом кадров.
- SVG допускается только после отдельной проверки и очистки активного содержимого;
  до её реализации — явный отказ либо заранее доверенные проектные файлы.
  Неподдерживаемые HEIC/RAW получают понятное сообщение, а не сломанный preview.

## 5. Архитектура и запрет дублирования

### 5.1. Развилка, которую нельзя скрывать в интерфейсе

В установленном Payload `imageSizes` — статический массив; его имена участвуют
в построении `sizes.<name>` полей схемы. Вызовов для разрешения произвольного
рецепта из БД на каждый upload в публичном контракте не найдено. Генерация файла
происходит раньше `beforeValidate`/`beforeChange`; изменение общего config в
`beforeOperation` не считается допустимым решением из-за гонок между запросами.

| Вариант                                                   | Когда подходит                                                                          | Цена решения                                                                           |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Полностью штатные `imageSizes`                            | Набор рецептов задаёт разработчик, изменения проходят выпуск конфигурации               | Минимальный собственный код; произвольная немедленная настройка из админки отсутствует |
| Штатная загрузка + управляемые профили и фоновые варианты | Пользователь меняет размеры/качество в админке без правки кода и перезапуска приложения | Нужен небольшой собственный владелец рецептов, очереди, результатов и их выбора        |

**Для этапа 0 выбран второй вариант**, поскольку задача требует удобного
управления настройками. Изолированная инженерная проверка фиксирует публичные
точки интеграции на установленном Payload до разработки расширенного интерфейса.

Payload остаётся владельцем upload CRUD, прав, файловой интеграции, форм,
папок и очереди. Sharp выполняет собственно преобразования. Наш модуль владеет
тем, чего нет в статических размерах: версиями рецептов из админки, планом
регенерации, закреплением результата и разрешением варианта для использования.

Не генерировать одну и ту же матрицу размеров одновременно через `imageSizes`,
свой обработчик и Next optimizer. В Payload 3.88 общий `config.sharp` вызывает
повторное кодирование WebP даже без `imageSizes`/`resizeOptions`. Поэтому
изолированная конфигурация этапа 0 не передаёт Sharp в Payload: сервис обработки
импортирует его напрямую, а штатный upload сохраняет готовые файлы. Общий config
не меняется на запросе. Для подключения этого решения в рабочем приложении
нужен адресный аудит всех native resize/crop consumers; действующий
`src/payload.config.ts` на этапе 0 сохраняется. Техническая миниатюра также
может быть именованным вариантом того же сервиса. Собственные crop/focal инструменты не создавать, если штатный
компонент можно подключить с сохранением неразрушающего контракта.

Штатный crop может переписать основной файл до `beforeValidate`/`beforeChange`.
Неизменяемый master защищается сервером **до обработки файла**, включая прямые
API-вызовы. Crop хранится в рецепте/использовании и применяется к производному
файлу; скрытая кнопка не заменяет эту защиту. Публичная интеграция native crop
компонента должна доказать этот контракт на этапе 0.

### 5.2. Владельцы и данные

- Расширять активную [Media collection](../../src/collections/Media.ts), а не
  регистрировать вместо неё старый `RealizeCore` и не менять существующие ID.
- Профили — типизированная Payload collection с версиями рецепта; общие лимиты
  и политика обработки — Global. В админке нужны нормальные поля, не JSON-редактор.
- Варианты — отдельные записи с индексами и ссылкой на исходник/рецепт/набор.
  Не хранить бесконечную историю производных файлов в одном растущем array Media.
- Загрузка производных файлов проходит через upload-enabled collection и штатный
  storage adapter; отсутствие повторного кодирования подтверждается hash байтов,
  а не только отсутствием `imageSizes` у collection.
- Задания используют [Payload Jobs](https://payloadcms.com/docs/jobs-queue/overview),
  с отдельной media queue. Не заводить ещё одну систему очередей и не использовать
  Codex execution worker для обычного преобразования изображений.
- Публичный DTO выбора содержит только необходимые URL/размеры/формат/alt;
  закрытые storage keys, исходные EXIF и внутренние job logs не выдаются.
- Одна область media services рядом с активным владельцем; выделение workspace
  package выполнять при доказанном повторном использовании, а не ради названия.

Полезные функции старого планировщика разрешается перенести после проверки,
с адресными тестами и актуальными контрактами. Старые ссылки на отсутствующую
`documentation/media/media-technical-reference.md` не делать новым источником истины.

### 5.3. Жизненный цикл

1. Проверить права, размер файла, сигнатуру формата и размеры декодированного
   изображения. Сохранить исходник и вычислить hash байтов.
2. Зафиксировать неизменяемую версию рецепта и план вариантов. Возвратить в UI
   состояние «Загружено, обрабатывается» без ожидания всех тяжёлых преобразований.
3. Поставить ограниченные задания в media queue. Повтор не должен создавать
   вторую копию того же результата.
4. Сохранить файлы по новым адресам; проверить их фактические dimensions, MIME,
   filesize и доступность. Не публиковать URL ещё не записанного объекта.
5. В одной DB-транзакции отметить набор готовым и переключить ссылку на него
   для разрешённого scope. Сбой не удаляет предыдущий рабочий набор.
6. Удалять недопривязанные временные файлы отдельным контролируемым cleanup.

Сохранение намерения обработки и постановка Payload job должны быть надёжно
связаны: одна DB-транзакция с передачей `req` там, где это поддерживает Jobs,
либо восстановление сохранённых намерений, оставшихся без задания. Перезапуск
не оставляет файл навсегда в состоянии «Обрабатывается». Новая система очередей
для этого не создаётся.

Генерируются назначенные профили и необходимые размеры. Произвольный URL с
параметрами width/quality не запускает неограниченную обработку на публичном
запросе; frontend выбирает из уже готовых допустимых вариантов.

Ключ результата включает hash исходных байтов, нормализованный рецепт, его версию,
параметры кадрирования и версию обработки/кодеков. Имя файла содержит версию/hash:
изменение качества не должно перезаписывать старый URL с теми же dimensions.
DB-транзакция не откатывает S3 или файловую систему; это учитывается в порядке
записи и сборке осиротевших файлов.

Базовые лимиты для проверки: до 25 MiB и 40 MP на исходное изображение, до 16
вариантов по одному плану, один тяжёлый job одновременно. Это стартовые потолки,
которые уточняются замерами памяти/CPU; администратор не может превысить жёсткие
ресурсные пределы установки. Нужны bounded retries, backoff, отмена оставшейся
партии и видимое состояние «Ожидает / Обрабатывается / Готово / Ошибка».

Локальный media runner запускается штатно вместе с проектом; в production его
запуск и health входят в эксплуатационный контракт. Кнопки в админке управляют
очередью и повтором, а состояние отсутствующего runner явно видно пользователю.

## 6. Применение новых настроек и регенерация

Настройки проходят состояния **Черновик → Пробная обработка → Активная версия**.
Перед активацией показываются реальный пример, размеры, вес, число вариантов и
сравнение с прежним рецептом. Preview качества использует тот же обработчик,
что и итоговые варианты, на ограниченной выборке с очисткой временных результатов.

Для применения предлагаются отдельные действия:

- Только новые загрузки.
- Выбранные файлы или папка с предварительным подсчётом.
- Все подходящие существующие файлы — отдельная массовая задача с подтверждением.

Обновление профиля не запускает незаметно обработку всей библиотеки. Задание
содержит snapshot версии профиля и границы выборки; очередная правка профиля
не меняет уже выполняемый job. «Повторить ошибки» не повторяет успешные результаты.

Сгенерировать новый вариант и переключить опубликованные использования — разные
действия. Старые варианты сохраняются, пока на них ссылается текущая публикация,
сохранённая версия страницы или разрешённый rollback. Срок хранения и очистка
учитывают также CDN cache TTL. Замена исходных байтов использованного файла
создаёт новый исходник/ревизию и показывает область замены; не перезаписывает
файл по прежнему публичному адресу.

Опубликованное использование закрепляет `sourceRevision` и `variantSetID`,
а также итоговые alt/подпись, включая применённые значения по умолчанию.
Его resolver не обращается к текущему `Media.activeSet` или последнему профилю.
Так обновление метаданных медиатеки не меняет содержание точной публикации.

## 7. Интерфейс медиатеки и загрузки

Первой поставкой интерфейса становится отдельный интерактивный макет:
**Библиотека / Добавление / Детали / Профили / Обработка / Выбор для блока /
Источники**. Карта экранов и приёмка определены в
[требованиях к вёрстке](media-management-references.md#3-карта-интерактивного-макета).
Данные и будущие результаты обработки в нём демонстрационные; штатные list,
upload, bulk upload и поля Media сохраняются. Подразделы ниже задают целевую
рабочую медиатеку, а не перечень уже подключённых функций макета.

### 7.1. Раздел «Медиа»

Верхний уровень: **Библиотека / Обработка / Настройки**. По умолчанию открывается
библиотека; технические параметры не вытесняют основной сценарий выбора файла.

На широком экране: слева папки и сохранённые фильтры, в центре результаты,
справа открываемая панель выбранного файла. Панель не обязательна постоянно.
На узком экране папки и детали открываются последовательно, без трёх узких колонок.

Toolbar: поиск, фильтры, переключение «Сетка / Список», сортировка, загрузка.
Фильтры: тип, папка, профиль, размеры/ориентация, дата, автор, состояние обработки,
наличие alt. «Используется / Не используется» доступно лишь после реализации
полного механизма ссылок, а не по приблизительной эвристике.

Сетка содержит соразмерные миниатюры, короткое название, формат/размер и состояние.
Список удобен для массовой работы: название, размеры, вес, тип, обновление,
использование, обработка. Hover не является единственным способом открыть меню.
Массовые действия появляются при выборе; выбранное число и границы выбора по
страницам видны явно. «Все результаты фильтра» отличается от текущей страницы.

Фильтры/сортировка/страница сохраняются в URL либо штатных query presets. Сервер
выполняет фильтрацию и пагинацию; весь массив Media не загружается в браузер.
Папки использовать штатные Payload: это логическая организация, не обещание
перемещения файлов по путям на диске или в object storage.

### 7.2. Загрузка

Одна область drag-and-drop, кнопка выбора файлов и штатная массовая загрузка.
Поле MediaBlock открывает тот же выборщик с контекстом требуемого типа/размеров.

Для каждого файла видны thumbnail, имя, размер, progress и причина отказа.
Разделять «Файл передан» и «Варианты готовы». До обработки доступны общая папка/
профиль и групповые метаданные с возможностью индивидуального исправления.
Дубликат по hash предлагает использовать существующий файл или сохранить копию;
разные файлы с одинаковым именем не объединяются.

Ошибки одного файла не отменяют остальные. Предусмотреть отмену ожидающей загрузки,
повтор конкретного отказа и понятный итог партии. Восстановление передачи после
перезагрузки вкладки не обещать как штатное: если оно понадобится, выделить
resumable upload протокол и согласовать storage adapter отдельно.

### 7.3. Панель файла

Вкладки **Сведения / Варианты / Использование / История**. Сведения: preview,
имя, фактический формат/размеры/вес, alt, подпись, папка, теги, источник.
Варианты: профиль/версия, размеры, кодек, вес, состояние, сравнение до/после.
Использование: тип документа, название, поле/блок, draft/published и ссылка на
редактор. История: замена исходника, смена рецепта, обработка и actor.

В быстрые действия входят «Выбрать», «Редактировать сведения», «Скачать» и меню.
«Удалить» и массовая регенерация не конкурируют с основным действием. Список
зависимостей проверяется сервером повторно непосредственно перед удалением.

### 7.4. Визуальный и доступный интерфейс

Оформление — [UI-kit Realize](../architecture/ui-kit.md): существующие `--ui-*`,
типографика, плотность, радиусы и состояния. Payload components сохраняют форму,
validation, upload и фокус; свои панели используют общие примитивы Realize.
Не применять глобальные CSS overrides к внутренним классам Payload.

Нужны светлая/тёмная темы, клавиатура, заметный focus, восстановление фокуса после
закрытия drawer, доступные названия кнопок, объявления progress/errors и
поддержка reduced motion. Кадрирование должно иметь доступную альтернативу
перетаскиванию. Не переносить ограничения доступности внешних референсов.

## 8. MediaBlock, frontend и агенты

MediaBlock получает выбор изображения и **профиля использования**, геометрию
контейнера, локальные alt/подпись и при необходимости локальную crop/focal
настройку. На форме видны нехватка разрешения, обработка и готовность нужных
вариантов. Выбор «small» вручную не заменяет автоматическую адаптацию к экрану.

Общий Media renderer выбирает готовые варианты с корректными `srcset`/`sizes`,
сохраняет aspect ratio и не вызывает layout shift. DPR учитывается выбором ширины
из набора, а не безусловным умножением числа вариантов. Приоритет загрузки
назначается месту изображения на странице; все изображения не становятся LCP.

Для подготовленных вариантов используется одна стратегия доставки: собственный
loader, выбирающий готовые URL, либо `<picture>` в существующем Media owner.
Не отправлять уже сжатый вариант повторно на lossy оптимизацию Next по умолчанию.
Возможность native `<Image>` loader/sizes основана на
[Next Image](https://nextjs.org/docs/app/api-reference/components/image); выбор
способа реализации и его проверка входят в первую техническую итерацию.

Preview страницы использует **только Payload Live Preview и общий frontend
renderer**. Сравнение качества отдельного изображения не является вторым
предпросмотром страницы.

Действующая политика публикации агента пока блокирует Media. Для её расширения
нужны проверка доступности исходника/набора, полный manifest ссылок, права,
готовность нужных размеров и закрепление версии набора в публикации. Изменение
кадрирования, источника или значимого recipe после подготовки делает план
устаревшим; незавершённая обработка не обходится ссылкой на случайный оригинал.

Предлагаемые сервисные capabilities: поиск/чтение Media, чтение профилей,
подготовка изменения блока, план регенерации, просмотр статуса. Запись и массовые
действия выполняются с действующими правами и подтверждением по риску. В описание
MediaBlock для агента входят поддержанные действия, форматы, поля, ограничения,
версии и примеры. Manifest и инструкции проверяются на соответствие schema;
параллельную вручную поддерживаемую схему агенту не создавать.

## 9. Хранение, зависимости и защита

Сегодня `public/media` означает прямую публичную выдачу Next: ограничить Payload
read недостаточно для защиты файла по такому адресу. В целевой модели исходники
с закрытыми метаданными доступны администраторам, публичные варианты — по
принятой политике публикации. **Не обещать закрытость оригиналов, пока прямой
доступ к их storage проверенно не закрыт.**

В первой инженерной итерации согласовать схему приватного master storage и
публичных вариантов через штатные upload collections/adapters, без обходных
публичных копий оригиналов. Для production — устойчивое хранилище вне ephemeral
файловой системы: persistent volume либо официальный
[Payload storage adapter](https://payloadcms.com/docs/upload/storage-adapters).
Секреты подключения не входят в обычную форму рецепта или DTO.

Доступы раздельные: просмотр, загрузка, редактирование метаданных, управление
профилями, массовая регенерация, замена и удаление. Проверки выполняются на API
и в jobs, не только скрытием кнопок. Импорт по URL отключён до согласования
allowlist и SSRF-защиты; MIME из браузера не является доказательством формата.

Учёт использования покрывает известные upload/relationship поля, вложенные
блоки, rich text, черновики и сохраняемые версии публикаций. Его расширяют
явные адаптеры владельцев контента. Индекс ссылок — производная проекция;
источником истины остаются документы Payload. Если полнота неизвестна, нельзя
показывать «Не используется» и автоматически удалять файл.

Массовое удаление показывает число файлов и зависимости, требует подтверждения
и повторной серверной проверки. Используемые или закреплённые версии блокируют
удаление. Нужны срок хранения, восстановление после ошибки и согласованные
backup/restore для БД и файлов; резервная копия одной БД не сохраняет изображения.

Публикация новой ссылки и удаление файла должны иметь общий механизм защиты
от гонок: согласованный lock/guard либо состояние удаления, запрещающее новые
ссылки до его завершения. Проверка использования и фактическое удаление не
могут быть двумя независимыми действиями без такой защиты.

## 10. Совместимость с обновлениями Payload

Абсолютную совместимость с любым будущим релизом гарантировать нельзя.
Цель — ограничить зависимость публичными API и обнаруживать несовместимость до
обновления рабочей установки.

- Использовать collection/global configs, документированные hooks, Local API,
  Jobs, storage adapters и публичные exports компонентов. Native Upload расширять
  через `admin.components.edit.Upload`, по возможности обёрткой над `<Upload>`;
  [официальные custom components](https://payloadcms.com/docs/custom-components/overview).
- Не копировать исходники Payload, не импортировать `/dist/**`, не патчить
  `node_modules`, не переписывать внутренние providers и CSS-селекторы.
- Зависимости интеграции изолировать в адаптерах; правила профилей, hash и выбор
  варианта проверять отдельно от React и Payload.
- Зафиксировать проверенные версии Payload и связанных пакетов единым обновлением
  lockfile. Peer range отражает проверенную совместимость; установка новой версии
  сама по себе не означает её поддержку.
- Две проверки CI: текущая поддержанная версия и конкретный кандидат обновления.
  Выполнить генераторы, проверку migration diff, contracts и адресные browser flows.
- На staging обновлять копию БД **и** представительную выборку файлов; проверять
  существующие ID/URL, crop/focal, повторную загрузку, jobs/retry, удаление, выбор
  MediaBlock и Live Preview. Миграции и import map генерируются, не редактируются вручную.
- Сбой расширенной панели не должен уничтожать данные. Возврат к штатной форме
  допустим для базовых действий, но не обходит запреты замены/удаления и не выдаёт
  неподдержанную обработку за успешную.

### 11.1. Границы исполняемого прототипа этапа 0

Подтверждено на Payload 3.88.0 с настоящими файлами и отдельной PostgreSQL-базой:

- Один JPEG 2400×1600 с EXIF orientation → две версии рецепта, по три варианта
  в каждой: WebP 320/640 px и JPEG 640 px. После ориентации высоты равны
  480/960 px. Изменение качества создаёт новые URL; старые файлы и исходные
  байты, включая EXIF оригинала, сохраняются.
- Штатный multipart upload, редактирование alt, закрытое чтение исходника
  (`403` без авторизации) и публичная выдача готовых файлов. Прямые попытки
  crop, замены файла и разрешения перезаписи отклоняются до обработки.
- Intent и Payload job откатываются одной транзакцией. Искусственный сбой
  после записи файлов допускает реальный Jobs retry без новых документов/URL;
  повтор уже завершённой очереди не создаёт варианты заново.
- Настоящий `EditUpload` смонтирован в DOM-проверке: числовые crop/focal
  возвращаются через `onSave`, отмена ничего не сохраняет, повторного upload
  нет. Это проверка контракта компонента, а не визуальная приёмка нового UI.
- Браузер проверил две версии в шести сценариях desktop/узкий экран/DPR 2:
  выбираются готовые WebP 320/640 px точного набора, по одному запросу изображения,
  с совпадающим hash; `/_next/image`, горизонтального переполнения и ошибок
  страницы нет. Основной renderer проекта пока не переключён на этот DTO.

Измерение одного локального прогона всего proof, включая создание синтетического
исходника, авторизацию, HTTP-обработчики и Jobs: 2,31 с wall time, 2,57 с CPU user,
0,10 с CPU system; пиковый RSS процесса около 478 MiB. Подготовка тестовой схемы
и браузер в этот wall time не входят. RSS учитывает загрузку библиотек процесса;
это не расход одной картинки и не лимит production worker. Высокочастотный
синтетический рисунок проверяет доставку/контрольные суммы; по нему не выбирается
качество фотографий. Производственный concurrency/RSS budget остаётся предметом
отдельного измерения этапа 2.

Ядро находится рядом с владельцем Media:
[контракт рецепта](../../src/collections/Media/MediaProcessing.types.ts),
[проверка рецепта](../../src/collections/Media/validateMediaRecipe.validator.ts),
[обработка](../../src/collections/Media/processMediaVariants.service.ts),
[защита исходника](../../src/collections/Media/protectMediaOriginal.hook.ts) и
[DTO готового изображения](../../src/collections/Media/mapReadyMediaPicture.mapper.ts).
Подключение upload/Jobs проверяется отдельной тестовой конфигурацией, без импорта
рабочего Payload config. На этапе 0 они не подключались к действующей медиатеке;
срез раздела 3.1 затем подключил этот сервис через active config и native Jobs.

Проверяемая область рецепта: JPEG/PNG/WebP на входе, JPEG/WebP с заданным quality
и PNG без потерь на выходе; именованная ширина, пропорциональное уменьшение без
увеличения, нормализация ориентации/sRGB, удаление EXIF. Рецепт и исходные байты
фиксируются до первого асинхронного шага. Ключ набора включает hash исходника,
канонический рецепт с версией и версии обработчика/кодеков. Порядок перечисления
размеров не меняет результат; изменение качества создаёт новый адрес.

Лимиты прототипа: 25 MiB/40 MP исходника, 16 вариантов, ширина до 8192 px,
64 MiB суммарных выходных буферов. Это ограничения проверки, не окончательные
настройки продукта. Обработка вариантов последовательная. Анимация, SVG,
AVIF, crop, upscale и прозрачный исходник → JPEG отклоняются явно; неизвестные
параметры рецепта не игнорируются.

Проверка native хранения использует отдельную одноразовую PostgreSQL-базу и
каталог вне `public/`. Schema push выключен; схема создаётся генератором
миграций Payload. Сгенерированный модуль находится внутри игнорируемого
`.ai-workspace/tasks/media-architecture-prototype/tmp/`, чтобы разрешать зависимости
из `node_modules` проекта без собственного loader. База и файлы принадлежат только тесту и удаляются после него;
рабочая схема, документы и существующие изображения не изменяются.

На момент этапа 0 редактор профилей и постоянный runner оставались будущими
задачами; теперь они подключены по разделу 3.1. Облачный storage,
кадрирование в обработчике, перенос имеющихся файлов и закрепление Media
в публикациях Pages ещё не реализованы. Самостоятельная проверка
crop/focal UI означает проверку публичного компонента, а не поставку готового
редактора неразрушающего кадрирования.

Повторяемые проверки используют установленный runtime проекта:

```bash
npm run test:int -- tests/int/mediaProcessing.int.spec.ts tests/int/mediaPicture.int.spec.ts tests/int/mediaDisposableDatabase.int.spec.ts
npm exec -- vitest run --config tests/int/support/mediaArchitecture/mediaNativeEditor.fixture.config.ts
MEDIA_ARCHITECTURE_PROOF=1 npm run test:int -- tests/int/mediaArchitectureNative.int.spec.ts
```

Последняя команда явно включает создание отдельной локальной БД. Адрес локального
кластера берётся из `DATABASE_URI`/`DATABASE_URL` штатного окружения или отдельного
`MEDIA_ARCHITECTURE_SOURCE_DATABASE_URI`; секреты в команду не подставляются.
Имеющаяся рабочая база используется только для определения адреса кластера.
Нужны права создать свою одноразовую базу и удалить её. Обычный suite пропускает
native proof без флага; отдельная проверка защит create/drop включается через
`REALIZE_MEDIA_DATABASE_TESTS=1` для `mediaDisposableDatabase.int.spec.ts`.

### 11.2. Проверенный макет: референсы и интерактивная вёрстка

Согласована компактная композиция: навигация слева, библиотека в центре,
открываемые детали справа; на мобильном — последовательные экраны. Подборка
Sanity и Cloudinary задаёт организацию действий, а действующий
[UI-kit](../architecture/ui-kit.md) — тему, цвет, типографику и элементы Realize.
Просмотрены исходные desktop-кадры native Media list/create и каталога агентского
слоя, а также официальные кадры библиотеки Sanity и добавления Cloudinary.
Это исходное сравнение, не приёмка нового макета; границы доказательств указаны
в [карте отличий](media-management-references.md#4-карта-отличий-и-владельцы).

Владелец компонентов макета — `src/components/admin/media/reference/`.
Host зарегистрировал отдельное collection view у
[Media](../../src/collections/Media.ts): `/admin/collections/media/reference`.
В штатном списке Media перед таблицей доступна ссылка «Посмотреть макеты».
Семь разделов показывают библиотеку, добавление, детали, профили, обработку,
выбор для блока и источники. Root интегрировал 15 файлов, подготовленных
штатным coding worker, добавил семь URL существующих изображений и исправил
callbacks/refs, плотность и размещение в оболочке Payload.
Рабочие `/admin/collections/media` и `/admin/collections/media/create`, native
выбор файлов и связи страниц не заменяются. В макете нет записи в Media,
загрузки на сервер, регистрации папок, активации профилей или запуска Jobs.

В активном installation release версии 4 доступны профиль
`frontend.interface-designer` («Дизайнер интерфейсов») и процесс
`frontend.reference-to-layout` («Референсы → план вёрстки»); существующий demo
интернет-магазина сохранён. Процесс содержит три `agent_turn`: исследование,
композиция, итоговый план, затем `finish`. Вход — бриф, экраны, источники,
допустимые пути и критерии приёмки. Финальный план сохраняет точные публичные
URL визуальных материалов или явный props-контракт их передачи, согласованные
выводы и только действительно изменяемые файлы. Все 15 записей demo
магазина сохранены по content hash. Системный слой и полномочия не изменялись.

Встроенный агент выполнил исследование, композицию и итоговый план; исправленный
ответ прошёл preflight с 15 точными файлами. Change Request 4 / job 2 завершился
`validation_failed`: обязательная проверка секретов обнаружила искусственный
маркер в существующем тесте исходного Git `HEAD`. Остальные четыре обязательные
проверки не запускались, native acceptance не выполнялся. Этот статус сохранён.
Root просмотрел созданные файлы, зафиксировал их hashes и перенёс результат
в рабочую копию как локальную интеграцию. Synthetic fixture исправлен без
изменения runtime значения и assertions; правила scanner не менялись.

Админский агент читает контекст и использует `web_search`, включённый для
запуска; workflow не принимает attachments и не имеет browser/imagegen.
Исполнимый результат этого процесса — самодостаточный план с точными путями.
Вёрстка передаётся отдельно в Code Lane: worker работает от Git `HEAD` и не
получает автоматически незакоммиченные изменения; protected owners не обходятся.
Host-интегратор подключает представление в разрешённом scope, а основной агент
проводит browser review доступными ему инструментами. Отчёт должен разделять
фактическую работу этих исполнителей и возможный fallback.

Набор обязательных проверок Code Lane — зарегистрированные `secrets`, `lint`,
`typecheck`, `test:int` и `build`. Адресные проверки компонентов и финальный
browser review дополняют этот набор; они не заменяют обязательные проверки
worker. Произвольные команды или сокращённые аналоги в план не добавляются.

После локальной интеграции прошли TypeScript, scoped ESLint без предупреждений,
проверка шапок 21 исходника, штатная проверка секретов рабочей копии и 22 теста
изменённого workflow fixture. Полный suite и build в этом срезе не подтверждены;
эти результаты не изменяют исторический статус Code Lane.

Браузер подтвердил семь разделов, поиск/фильтры/пагинацию, детали и возврат
фокуса, локальные файлы и выбор для блока; светлую/тёмную темы на ширинах
320/390/1024/1440 px без горизонтального overflow. Диагностика собственного
локального файла подтвердила освобождение object URL: создан один адрес,
освобождён один, после ухода из макета активных не осталось. Модальный выбор
размещён порталом в `document.body` с собственной обёрткой `UiTheme`.
Финальная проверка подтвердила размещение над плавающей кнопкой AI,
Cancel/Escape/Confirm и возврат фокуса. Временные QA-аккаунты, preferences и
браузеры очищены. Снимки и
состояние проверок собраны в [приёмке экранов](media-management-references.md#5-приёмка-текущего-среза).

Подробная процедура живёт в
[frontend workflow](../../.ai/workflows/frontend/next-react/guardrail/WORKFLOW.md#reference-to-frontend).
Эта спецификация фиксирует продуктовый результат и границы макета, не вводит
новые инструменты, права или второй порядок выполнения.

## 12. Критерии приёмки

Для текущего этапа 1 применяются
[критерии интерактивного макета](media-management-references.md#5-приёмка-текущего-среза):
семь согласованных разделов, честные примеры, локальные взаимодействия,
сохранённые native действия и browser evidence. Следующие пункты относятся
к рабочей интеграции этапов 2–5; успешный макет не означает их выполнения.

1. В админке создать профиль и изменить размеры/quality без редактирования кода;
   увидеть черновую и действующую версии и scope применения.
2. Загрузить смешанную партию: корректные фото, прозрачную графику, маленькое
   изображение, дубликат, повреждённый и превышающий лимиты файл. Ошибки локальны.
3. Подтвердить сохранение hash оригинала, ожидаемые dimensions, цвет/ориентацию,
   прозрачность и отсутствие GPS в публичном результате.
4. Обработать один исходник разными профилями параллельно: рецепты не смешиваются,
   нет лишних вариантов, потерянного состояния или повторной публикации результата.
5. Прервать job после записи файла и до переключения набора; безопасно повторить,
   сохранив прежний рабочий набор и возможность cleanup.
6. Изменить профиль при работающем job: старое задание заканчивает свою версию,
   новое использует новую; массовая обработка требует явного действия.
7. Найти файл и выбрать его из MediaBlock, настроить локальную подпись/alt/кадр,
   не изменив другое использование того же исходника.
8. На frontend проверить реально выбранный файл по сети, его размеры/формат,
   отсутствие повторной lossy обработки и стабильность геометрии страницы.
9. Пройти draft → Payload Live Preview → подтверждение → публикация MediaBlock;
   изменение зависимости после подготовки закрывает устаревший план.
10. Попытаться удалить используемый файл, его закреплённый вариант и файл без
    полного учёта ссылок: сервер сохраняет целостность опубликованного контента.
11. Проверить роли, прямые file URLs и восстановление БД вместе с файлами.
12. Пройти те же ключевые сценарии после обновления Payload на staging.

Для масштаба подготовить benchmark библиотеки 10 000/100 000 записей: серверная
пагинация, отсутствие полной загрузки списка, ограниченные preview-запросы.
Целевой p95 поиска/фильтра — до 500 ms на согласованном стенде; окончательный SLO
фиксируется вместе с его ресурсами и индексами. Это критерий будущего измерения,
а не заявление о текущей производительности.
