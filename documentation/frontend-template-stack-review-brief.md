# Realize — краткий бриф для выбора стека интерфейсов и шаблонов

**Дата:** 19 октября 2026 года. **Статус:** предложение для независимой оценки.
Стек ниже ещё не утверждён; его нужно критически проверить и при необходимости заменить.

## Проект

**Realize — AI Platform** — модульная ИИ-платформа для создания и развития сайтов
и рабочей среды компании. Целевой продукт объединяет CMS, контент, клиентов,
задачи, документы, бизнес-модули и ИИ-агентов. Люди и агенты работают с общими
данными; агенты также смогут создавать компоненты и расширять код платформы.

Текущая реализация включает CMS, интернет-магазин, Admin, Task Manager и
ИИ-инструменты. У каждой установки своё приложение и база данных. Сейчас
используются Next.js, React, TypeScript, Payload CMS и PostgreSQL. Это контекст
интеграции: новый стек интерфейсов следует выбирать по целевым требованиям.

## Цели интерфейсов и шаблонов

- Единая архитектура для публичного сайта и Admin: реактивность, доступность,
  адаптивность, локализация и предсказуемая производительность сложных экранов.
- Самодостаточные версионируемые пакеты шаблонов: единые правила установки,
  совместимости, обновления, предпросмотра, переключения и отката.
- Одно назначение шаблона на весь Admin и отдельное назначение на весь сайт.
  Набор экранов зависит от модулей и прав; новые экраны подключаются через общий
  контракт. Старая тема внутри новой оболочки не считается полноценным переключением.
- Строгие границы: токены → примитивы → компоненты → композиции → шаблон.
  Данные, права и бизнес-действия предоставляет приложение. Переключение
  оформления должно сохранять незавершённые формы и состояние работы.
- В дальнейшем — сборка страниц, оболочек и рабочих экранов через браузер:
  размещение компонентов, параметры, адаптивные настройки и привязки данных.
  Код, визуальный редактор и ИИ должны использовать общий каталог компонентов.

Первый стандартный шаблон **Realize-AI One** начинается с качественной оболочки:
header, sidebar, контентная область, footer, общие элементы, вход, регистрация
и управление оформлением. Полный визуальный конструктор — последующий этап,
но совместимые с ним контракты нужны с самого начала.

## Предлагаемый стек

| Слой                | Предложение и назначение                                                                                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Приложение          | **TypeScript strict + React + Next.js**: маршруты, серверный рендеринг, интерактивный Admin и редактор. UI и шаблоны отделены от Next.js и CMS адаптерами.                           |
| Компоненты          | **React Aria Components + собственный Realize UI**: доступное поведение примитивов, сложных коллекций, форм и диалогов; собственный дизайн и публичный контракт.                     |
| Стили               | **DTCG-токены → CSS variables + CSS Modules**, cascade layers и container queries. Общие семантические токены, светлая/тёмная тема, плотность и адаптивность.                        |
| Данные и состояние  | **TanStack Query** для клиентской работы с серверными данными; **Zustand** для сложного локального состояния. Один владелец каждого состояния, без дублирования хранилища редактора. |
| Формы и схемы       | **React Hook Form + Zod**. Версионируемый JSON-документ Realize описывает композицию; схемы проверяют параметры, вложенность и допустимые привязки.                                  |
| Браузерный редактор | **Puck как кандидат**, подключённый через адаптер. Каталог компонентов и формат хранения принадлежат Realize; преобразование документов должно сохранять данные и поведение.         |

Компонент получает стабильный ID, версию, свойства, допустимые вложенные области,
варианты оформления и доступные действия. Предпросмотр и опубликованный интерфейс
используют общий каталог и контракты с адаптерами серверного и клиентского рендеринга.
Настройка композиции и темы доступна без пересборки; новый исполняемый компонент
проходит сборку, проверки и выпуск. Публикация предусматривает черновик,
валидацию, предпросмотр, историю и откат. Авторизация проверяется сервером.

Основные первичные источники для проверки предложения:
[Next.js](https://nextjs.org/docs/app/getting-started/server-and-client-components),
[React Aria](https://react-aria.adobe.com/),
[DTCG](https://www.designtokens.org/tr/2025.10/format/),
[TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview),
[Zustand](https://github.com/pmndrs/zustand),
[React Hook Form](https://github.com/react-hook-form/react-hook-form),
[Zod](https://zod.dev/json-schema),
[Puck и RSC](https://puckeditor.com/docs/integrating-puck/server-components).

## Вопрос для независимой оценки

**Что в этом решении не так, какие ограничения проявятся при развитии платформы
и какой стек лучше выбрать под описанные требования?**

Оцени предложение независимо от текущего кода и референсов:

1. Где есть лишняя сложность, несовместимость или зависимость от конкретной
   библиотеки? Достаточны ли выбранные решения для сложного Admin и браузерного
   конструктора, включая SSR, реактивность, диалоги, iframe и сохранение состояния?
2. Сравни ключевые альтернативы: Next.js / TanStack Start / Vue-Nuxt / SvelteKit;
   React Aria / Base UI / Radix; CSS Modules / Tailwind / Panda / vanilla-extract;
   Puck / Craft.js / GrapesJS. Учитывай редакции продуктов, лицензии и стоимость
   разработки. Обоснуй замену там, где она даёт практическое преимущество.
3. Какие контракты компонентов, тем, данных и документов нужно заложить сейчас,
   чтобы позднее добавить визуальную сборку и создание компонентов через ИИ?
4. Предложи один итоговый согласованный стек, его компромиссы и небольшой
   проверочный прототип. Раздели обязательную основу и инструменты следующих этапов.

Проверь актуальные стабильные версии и совместимость по официальным источникам.
Сначала оцени целевое решение, затем отдельно — сложность перехода с текущего стека.
