# Шаблон: Worker Assignment Manifest (`TEMPLATE-WORKER-ASSIGNMENT-MANIFEST`)

```yaml
template_id: TEMPLATE-WORKER-ASSIGNMENT-MANIFEST
template_type: ai-runtime-manifest-template
owner_layer: .ai/templates/worker-assignment/
runtime_owner: .ai/workflows/core/worker-assignment/WORKFLOW.md
runtime_sources:
  - .ai/checks/worker-runtime/CHECK-WORKER-ASSIGNMENT-SCOPE.md
  - .ai/rules/worker-runtime/RULE-WORKER-ASSIGNMENT-MANIFEST.md
  - .ai/workflows/core/worker-assignment/WORKFLOW.md
```

## Общий шаблон поручения

Для нативного делегирования достаточно заполнить эти строки и отправить их
исполнителю. Укажи права в пределах поручения пользователя и возможностей
выбранной среды. [Правило назначения](../../rules/worker-runtime/RULE-WORKER-ASSIGNMENT-MANIFEST.md#назначение-и-полномочия)

```text
Цель — <что нужно сделать и в каких границах>.
Исполнитель — <роль и почему она подходит>.
Владелец области — <кто отвечает за затронутую часть проекта>.
Источники — <обязательные инструкции и материалы>.
Разрешённые действия — <что можно читать и какие операции создания, изменения или удаления разрешены на каких путях>.
Проверки — <что проверить и по каким критериям принять работу>.
Результат — <что передать, в какой форме и кому>.
При препятствии — <при каком условии и кому сообщить, чего недостаёт>.
```

## Решение оркестратора

Перед выдачей проверь, что источники доступны, а выданных прав достаточно
для порученной работы. Если запрошена только подготовка, верни заполненное
поручение для просмотра. При выборе адаптера Realize проверь допуск конкретного
исполнителя перед передачей. [Готовность к запуску](../../rules/worker-runtime/RULE-WORKER-ASSIGNMENT-MANIFEST.md#готовность-к-запуску)

## Приёмка результата

Исполнитель передаёт результат указанному получателю, приводит выполненные
проверки, их подтверждения и существенные ограничения. При правке перечисляет
изменённые пути. Оркестратор сверяет результат с границами поручения и
критериями приёмки. [Общий порядок делегирования](../../workflows/core/worker-assignment/WORKFLOW.md#общий-порядок-делегирования)

Если план статического аудита предусматривает независимое ревью, аудитор
передаёт отчёт и карту покрытия. Ревьюер сверяет их с закреплёнными
источниками и передаёт заключение оркестратору для принятия решения.
[Порядок независимого ревью](../../workflows/core/worker-assignment/WORKFLOW.md#независимое-ревью-статического-аудита)

## Пример для CLI Assignment

Этот пример применяется при выборе CLI Assignment в режиме `static-read-only`.

### Сообщение исполнителю

Для CLI скопируй YAML-блок в манифест выбранного назначения. Заполни значения
в угловых скобках и укажи фактическую ревизию.

```yaml
id: "<assignment-id>"
revision: 1
baseCommit: "<base-commit>"
assignedBy: "<assigning-agent>"
returnsTo: "<result-recipient>"
mission: "<проверяемая цель>"
ownerLayer: "<слой проекта, отвечающий за предмет работы>"
role: "<role-path>"
roleReason: "<почему эта роль отвечает за поручение>"
mode: static-read-only
requiredSources:
  - "<role-path>"
reviewScope:
  paths:
    - "<review-file-path>"
permissions:
  read: [requiredSources, reviewScope]
  writePaths: []
  tools: [repo_read_file]
  output: reply-to-orchestrator
checks:
  - "<что проверить и по какому критерию>"
expectedOutput:
  - "<какой результат и какие доказательства вернуть>"
stopCondition: "<при каком препятствии вернуть поручение и что сообщить>"
```

В `baseCommit` укажи полный SHA исходного коммита из 40 шестнадцатеричных
символов нижнего регистра. В `requiredSources` включи файл выбранной роли
и остальные обязательные источники. В `reviewScope.paths` перечисли от 1 до
64 файлов от корня репозитория. Пути в обоих списках должны быть уникальными
и не пересекаться. Обработчик `repo_read_file` разрешает чтение файлов из обоих списков.

### Привязка и допуск

В файле привязки укажи те же `id`, `revision` и `baseCommit`. Поле
`manifestPath` указывает на заполненный манифест, `manifestSha256` закрепляет
его YAML, а `files` содержит путь и SHA-256 каждого файла из обоих списков.
Для манифеста в Markdown хешируется содержимое YAML-блока.

Для предпросмотра передай файл привязки в `prepare --lock`. Даже полный пакет
до привязки получает `blocked`. Если поручена привязка, используй `bind`
с тем же файлом. При повторном открытии сверь `contextId`, `assignmentId`,
`revision`, `lockSha256`, состав пакета и права. Успешный `bind` подтверждает
готовность локального контекста. Перед порученным запуском проверь допуск
выбранного исполнителя для этой попытки. [Команды CLI](../../workflows/core/worker-assignment/WORKFLOW.md#подготовка-и-привязка-через-cli-assignment) · [Допуск через адаптер Realize](../../rules/worker-runtime/RULE-WORKER-ASSIGNMENT-MANIFEST.md#допуск-через-адаптер-realize)
