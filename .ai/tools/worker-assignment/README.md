# Подготовка назначения исполнителю

Команды запускаются из корня проекта. Вместо `<путь-к-привязке>` укажи путь
к файлу привязки нужного назначения относительно корня проекта.

```text
npm run --silent ai:assignment -- prepare --lock <путь-к-привязке> [--bundle]
```

Команда читает указанный файл привязки и находит манифест назначения по его полю `manifestPath`.
Область ревью в `reviewScope.paths` задаётся списком от 1 до 64 уникальных путей
от корня проекта. В форме `reviewScope` с полями `route`, `directory` и `files`
область включает маршрут и файлы указанного каталога.
Манифест использует одну из этих форм. Обязательные источники `requiredSources`
и файлы ревью образуют непересекающиеся списки. Файл привязки закрепляет SHA-256 каждого файла.
В JSON выводятся роль и причина выбора, права, критерии приёмки, пути, SHA-256,
размеры проверенных файлов и причины статуса. `--bundle` дополнительно выводит
полные тексты проверенных обязательных источников. Оба режима работают в памяти.

`packageComplete` означает, что содержимое всего пакета совпало с привязкой.
Для `ready` нужны также подтверждения доставки и эффективных прав одного контекста
исполнителя по [правилу готовности](../../rules/worker-runtime/RULE-WORKER-ASSIGNMENT-MANIFEST.md#готовность-к-запуску).
Команда `prepare` проверяет исходные файлы в памяти. Даже полный пакет
получает `blocked` до привязки адаптера. Код выхода 2 означает `blocked`,
1 — ошибку команды, 0 — успех.

В привязке фиксируются идентичность назначения, исходный коммит, SHA-256 YAML
и каждого входного файла. Для Markdown хешируется содержимое YAML-блока без
ограждений, включая завершающий перевод строки. Для отдельного YAML —
весь файл. При изменении содержимого сверяй новую ревизию и её привязку;
команда сама хеши не обновляет. Первый срез поддерживает целые источники
и режим `static-read-only`.

## Очередь IDE

Bootstrap MCP и отдельный локальный оркестратор используют один
`REALIZE_IDE_ASSIGNMENT_QUEUE` и один checkout. Владелец задаёт абсолютный
путь к каталогу 0700 вне репозитория. Для независимости от IDE оркестратор
можно запустить до появления задания. Сервер возвращает `runId` сразу после
сохранения заявки в SQLite.

```sh
npm run --silent ai:assignment:ide -- wait-claim
```

Команда ожидает ближайшее поручение, резервирует его на 30 минут, связывает
проверенный пакет с контекстом и возвращает `runId`, `assignmentId`,
`revision`, `contextId`, параметры привязки и частный `token` попытки.
`claim` выполняет ту же операцию без ожидания. Оркестратор передаёт исполнителю
только сведения о назначении и доступ к его read-only контексту. Отчёт и
статус `completed` либо `blocked` публикуются через
`npm run --silent ai:assignment:ide -- finish` с JSON на stdin
(`runId`, `token`, `status`, `report`). Постоянное хранилище и токен
остаются у оркестратора. Если срок истёк, следующий claim получает новую
попытку; старый токен теряет возможность завершать run. Повторная публикация
того же результата той же попытки идемпотентна. Процесс разрешает вызов
исполнителя отдельному оркестратору; собственную модель или внешний API
команда сама не выбирает. См. [MCP](../../../documentation/specifications/internal-mcp.md).

### Постоянный оркестратор

Для автоматической выдачи запустите `npm run ai:assignment:serve` в отдельном
процессе. Он использует тот же `REALIZE_IDE_ASSIGNMENT_QUEUE`; для исполнителя
укажите `REALIZE_IDE_CODEX_HOME` с авторизованным `auth.json` и включите
`codex` в PATH. После claim процесс открывает привязку, сверяет SHA-256 и
материализует обязательные тексты и полные файлы области через закреплённый
reader. При превышении бюджета входа 384 КиБ оркестратор возвращает blocker.
Внешний Codex получает материалы через stdin. Его cwd и профиль временные,
доступ к credential передан только клиенту; инструменты отключены. Профиль
filesystem ограничен системным минимумом и пустым рабочим каталогом,
sandbox-сеть выключена. После ответа, ошибки или 10 минут выполняется
cleanup. Полный ответ сохраняется в очереди; журнал службы содержит ID запуска
и статус. При остановке процесса незавершённая аренда возвращается в выдачу
после истечения срока.

Для текстового задания IDE вызывает `task_submit` с `task` и `idempotencyKey`. Служба готовит снимок указанных файлов и применимых инструкций перед запуском. Для тематического аудита оркестратор вызывает штатный agent-search по предмету поручения, затем ищет ссылки на найденных кандидатов. При достижении лимита строк или байтов оркестратор перечисляет совпавшие файлы штатным поиском. Он передаёт группу на проверку, исключает уже перечисленные пути из следующей страницы и делит группы пополам через `--within`, сохраняя профиль и его исключения. Одиночный файл с избытком совпадений передаётся исполнителю по закреплённым диапазонам. Итоговая квитанция различает покрытие файлов поиска и фактически завершённых проверок. Под одним runId создаются назначения на отдельные группы файлов и диапазоны строк; полученные отчёты и пропуски передаются на итоговое обобщение. Недоступные источники указываются в покрытии, при отсутствии пригодного пакета возвращается `blocked`. Обсуждение в очередь не отправляется.

## Привязка и повторное открытие

```text
npm run --silent ai:assignment -- bind --lock <путь-к-привязке>
```

Первый вызов создаёт отдельный `contextId`, атомарно сохраняет поручение,
тексты и права в личном файле `runtime/contexts/<contextId>.json` (0600, вне Git)
и заново читает его. Для повторного открытия укажи полученный `contextId` и тот же путь к привязке.

```text
npm run --silent ai:assignment -- bind --lock <путь-к-привязке> --context <contextId>
```

Если заданный контекст недоступен, команда возвращает `blocked`.

Допуск относится к сочетанию `contextId`, `assignmentId`, `revision` и
`lockSha256`. Для каждого доставленного текста отчёт содержит путь, SHA-256
и число байтов UTF-8, вычисленные при чтении. Инструмент `repo_read_file` читает
только файлы из разрешённого списка назначения и проверяет SHA-256 при каждом вызове.
Запись и другие инструменты закрыты.
Неполный текст даёт `context_not_delivered`, расхождение прав — `access_mismatch`,
чужой контекст или ревизия — `context_mismatch`. При отказе обработчик
недоступен, а `effectiveAccess` в отчёте равен `null`.

Будущий исполнитель получает `initialInput` и `callTool` из успешного
повторного открытия в сервисе `bindAssignment`. Только этот интерфейс
обеспечивает проверенные права. Команда CLI выводит отчёт и завершает работу
до запуска исполнителя. Для удаления или переноса рабочей копии учитывай,
что контексты хранятся локально.

## Проверка передачи без модели

`deliverAssignmentContext` повторно открывает указанный контекст. Оркестратор задаёт
выбранного исполнителя и новую попытку. Сервис проверяет V1-подтверждение по
метаданным назначения и наблюдениям адаптера. При допуске транспорт принимает
`initialInput` с проверкой той же привязки непосредственно при передаче. Запросы чтения проходят через `callTool`
из этой привязки. По успешным ответам сервис возвращает путь, SHA-256 и
фактический диапазон строк. Событие с чужим `threadId` или `turnId` даёт
`blocked`. Финальное сообщение своего хода получает статус `received`;
решение о приёмке остаётся за оркестратором после независимого ревью.

Транспорт в тестах работает в памяти. Он записывает первый запрос, запрашивает
чтения и передаёт заранее заданные события. Проверка из корня проекта:

```bash
node --import=tsx/esm --test .ai/tools/worker-assignment/test/deliverAssignmentContext.test.ts
```

## Проверка реального транспорта до передачи назначения

```text
npm run --silent ai:assignment -- preflight --lock <путь-к-привязке> --context <contextId>
```

Команда повторно открывает указанную привязку и создаёт пустую временную
сессию в локальном Codex App Server с изолированным профилем и каталогом.
Временный MCP-сервер читает через обработчик этого же контекста. Команда
сверяет полный ответ `mcpServerStatus/list` для сессии, включая точные пути
в схеме единственного `repo_read_file`. Через `mcpServer/tool/call` она
запрашивает первую строку каждого разрешённого файла, проверяет путь и SHA-256,
а также отказ для другого пути и незарегистрированного инструмента записи.
Вывод содержит только результаты проверки и пути. Процессы и временный профиль
закрываются при завершении.

В отчёте `preflight` поле `cliVersion` содержит версию, которую сообщила открытая
сессия, в том числе при отказе во время проверки каталога. Если версия недоступна,
значение равно `null`. Решение о передаче `initialInput` зависит от фактически
подтверждённых прав этой сессии. Для назначения в режиме `static-read-only`
разрешён один прямой `repo_read_file`. Его `path.enum` должен точно совпадать
с путями обязательных источников и файлов ревью выбранного назначения. Запись, вложенные и отложенные маршруты
выходят за пределы назначения.

Каталог `mcpServerStatus/list` охватывает MCP. После успешных проб текущий
`preflight` возвращает `mcp.status: verified`, `blocked`, причину
`native_tools_unverified` и код выхода 2. Расхождение каталога даёт
`transport_access_mismatch`. Команда завершается до `turn/start`.
При открытии другой сессии проверка выполняется заново.

## Проверка допуска V1 без исполнителя

Для назначения в режиме `static-read-only` общий валидатор принимает подтверждение адаптера, проверенный отчёт `bind`, выбор оркестратора и доступ к наблюдениям текущей попытки. В отчёте Codex поле `evidence` появляется после успешной привязки локального контекста. Для API `inspectApiAuditAdmission` работает с уже подготовленным запросом и зарегистрированной политикой инструментов провайдера. Проверка выполняется внутри Realize. [Формат и значения статусов](../../../documentation/architecture/assignment-adapter/adapter-access-evidence-v1.md)

Чтобы воспроизвести `ready` и `blocked` в памяти, выполни из корня проекта

```bash
node --import=tsx/esm --test --test-isolation=none .ai/tools/worker-assignment/test/{assessAdapterAdmission,apiAuditAdmission,preflightAssignment,deliverAssignmentContext}.test.ts
```

Проверки используют реальный ограниченный обработчик файлов для запроса API и тестовый транспорт для Codex. Они покрывают неполный каталог MCP, лишние маршруты, подмену назначения и потерю привязки, включая промежуток между допуском и передачей.

## Рабочий адаптер OpenAI Chat Completions

Команда принимает путь к привязке выбранного назначения, `contextId` успешного `bind` и модель. Она локально проверяет тело запроса и права обработчика по тем же правилам, что и отправка. В примерах ниже укажите один и тот же lock-файл и контекст. Первая команда выбирает зарегистрированный снимок модели, вторая — алиас вне этого профиля.

```text
npm run --silent ai:assignment -- preflight-api --lock <путь-к-привязке> --context <contextId> --model gpt-5.4-mini-2026-03-17
npm run --silent ai:assignment -- preflight-api --lock <путь-к-привязке> --context <contextId> --model gpt-5.4-mini
```

При полном пакете и подтверждённых правах первая команда возвращает `ready` и применённую политику в `providerPolicy`. Вторая возвращает `blocked / access_unverified` и `providerPolicy: null`. Ключ API для этих локальных проверок не нужен. [Источник политики](../../../documentation/architecture/assignment-adapter/openai-chat-completions.md#источник-и-границы-политики) · [Проверка запроса](../../../documentation/architecture/assignment-adapter/openai-chat-completions.md#проверка-запроса)

## Одно чтение на имитаторе

Проверка создаёт временное назначение с одним файлом или с файлами из разных каталогов. В каждом успешном обмене имитатор принимает два запроса одной попытки и возвращает ответы в памяти. Для разрешённого чтения тест сверяет полученные байты и квитанцию с выбранным файлом. Для соседнего пути он проверяет ответ `FORBIDDEN` без текста файла. Изменение файла после чтения или подмена `tool_call_id` блокирует отправку продолжения. [Порядок обмена](../../../documentation/architecture/assignment-adapter/single-read.md#порядок-обмена)

```bash
node --import=tsx/esm --test --test-isolation=none .ai/tools/worker-assignment/test/singleReadExchange.test.ts
```

## Контрольные точки на PostgreSQL

Для проверки двух последовательных чтений и восстановления после остановки процесса выполни из корня проекта

```bash
npm run check:assignment:postgres -- checkpoint
```

Потребуются непривилегированный пользователь, доступ на запись в `/tmp`, `pg_config` в `PATH` и серверные программы PostgreSQL в каталоге `pg_config --bindir` (`initdb`, `pg_ctl`, `createdb`). Команда создаёт временный кластер в закрытом каталоге, запускает его на отдельном Unix-сокете с отключённым TCP, включает `fsync` и `synchronous_commit`, создаёт БД `realize_assignment_test`. Участники работают с временной копией закреплённых файлов. Все ответы даёт имитатор, внешний вызов модели заблокирован. По завершении команда останавливает кластер и удаляет его временный каталог. [Среда запуска](test/checkpoints/runIsolatedPostgres.mjs)

Успешный прогон завершается с кодом 0 и показывает пять пройденных сценариев. Сверяются журнал отправок, неизменяемые ревизии, квитанции, содержимое пакета для ревью, остановка через `SIGKILL` и выдача lease двум конкурирующим процессам. [Состав хранилища и результаты](../../../documentation/specifications/task-management/execution/checkpoint-storage.md)

## Публикация в досье и выдача ревью

Для сквозной проверки от полученного отчёта до выдачи работы независимому ревьюеру выполни из корня проекта

```bash
npm run check:assignment:postgres -- publication
```

Команда использует тот же временный кластер PostgreSQL и разворачивает в нём схему Foundation и хранилища контрольных точек, досье и очереди ревью. Сценарий создаёт задачу с двумя назначениями и подтверждает чтения имитатором. После аварийного завершения процесса получатель забирает работу из очереди, читает отчёт и карту из досье и сверяет хеши обеих версий. Вызов модели заблокирован, рабочая админка в прогоне не участвует. [Среда запуска](#контрольные-точки-на-postgresql) · [Контракт и результаты](../../../documentation/specifications/task-management/execution/audit-report-publication.md)

## Устройство и проверка

В `src/` находятся обработчик команды, чтение определения, проверка области,
сборка пакета, оценка готовности и типы результата. Сервис получает
путь к привязке от вызывающего кода. Тесты из `test/` используют отдельные
временные каталоги.

```bash
npm run typecheck:worker-assignment
node --import=tsx/esm --test --test-isolation=none .ai/tools/worker-assignment/test/*.test.ts
```

Штатная команда `npm run typecheck` включает проверку этого инструмента.

## Заключение ревьюера и приёмка

Команда `npm run check:assignment:postgres -- conclusion` поднимает временную PostgreSQL для проверки независимых чтений, публикации заключения в досье, передачи оркестратору, приёмки и адресной доработки. Имитатор проходит от реальных версий исходников до сохранённого решения. [Контракт](../../../documentation/specifications/task-management/execution/review-conclusion.md)

## Доработка и повторная приёмка

`npm run check:assignment:postgres -- rework` поднимает временную PostgreSQL, создаёт адресованные поручения, проводит следующий аудит или уточнение, доставляет его на повторное ревью и проверяет окончательное решение. Команда печатает версии отчёта и заключения. Проверку исходной публикации и первого решения можно воспроизвести отдельно командами `npm run check:assignment:postgres -- publication` и `npm run check:assignment:postgres -- conclusion`. [Контракт цикла](../../../documentation/specifications/task-management/execution/review-rework.md)

Для полного прогона всех четырёх этапов выполните `npm run ai:assignment:audit-cycle`. Он последовательно проверяет контрольные точки, публикацию отчёта, первое заключение и цикл доработки на отдельных временных кластерах.
