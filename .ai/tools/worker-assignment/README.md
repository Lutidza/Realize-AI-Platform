# Подготовка назначения исполнителю

Для статического аудита формы «Создать статью» выполни из корня проекта:

```bash
npm run --silent ai:assignment -- prepare
```

Команда читает [образец назначения](../../templates/worker-assignment/TEMPLATE-WORKER-ASSIGNMENT-MANIFEST.md)
и [привязку к его ревизии](article-audit.lock.json).
В JSON выводятся роль и причина выбора, права, критерии приёмки, пути, SHA-256,
размеры проверенных файлов и причины статуса. `--bundle` дополнительно выводит
полные тексты проверенных обязательных источников. Оба режима работают в памяти.

`packageComplete` означает, что содержимое всего пакета совпало с привязкой.
Для `ready` нужны также подтверждения доставки и эффективных прав одного контекста
исполнителя по [правилу готовности](../../rules/worker-runtime/RULE-WORKER-ASSIGNMENT-MANIFEST.md#готовность-к-запуску).
Команда `prepare` проверяет исходные файлы в памяти. Даже полный пакет
получает `blocked` до привязки адаптера. Код выхода 2 означает `blocked`,
1 — ошибку команды, 0 — успех.

Для другого назначения этого же формата передай `--lock <путь от корня>`.
В привязке фиксируются идентичность назначения, исходный коммит, SHA-256 YAML
и каждого входного файла. Для Markdown хешируется содержимое YAML-блока без
ограждений, включая завершающий перевод строки. Для отдельного YAML —
весь файл. При изменении содержимого сверяй новую ревизию и её привязку;
команда сама хеши не обновляет. Первый срез поддерживает целые источники
и режим `static-read-only`.

## Привязка и повторное открытие

```bash
npm run --silent ai:assignment -- bind
npm run --silent ai:assignment -- bind --context <contextId>
```

Первый вызов создаёт отдельный `contextId`, атомарно сохраняет поручение,
тексты и права в личном файле `runtime/contexts/<contextId>.json` (0600, вне Git)
и заново читает его. Второй вызов открывает этот же контекст, в том числе из
другого процесса. Для собственной привязки указывай тот же `--lock` в обоих вызовах.
Если заданный контекст недоступен, команда возвращает `blocked`.

Допуск относится к сочетанию `contextId`, `assignmentId`, `revision` и
`lockSha256`. Для каждого доставленного текста отчёт содержит путь, SHA-256
и число байтов UTF-8, вычисленные при чтении. Для примера формы это шесть
текстов. Единственный инструмент `repo_read_file` читает 18 точных путей
с проверкой SHA-256 при каждом вызове. Запись и другие инструменты закрыты.
Неполный текст даёт `context_not_delivered`, расхождение прав — `access_mismatch`,
чужой контекст или ревизия — `context_mismatch`. При отказе обработчик
недоступен, а `effectiveAccess` в отчёте равен `null`.

Будущий исполнитель получает `initialInput` и `callTool` из успешного
повторного открытия в сервисе `bindAssignment`. Только этот интерфейс
обеспечивает проверенные права. Команда CLI выводит отчёт и завершает работу
до запуска исполнителя. Для удаления или переноса рабочей копии учитывай,
что контексты хранятся локально.

## Проверка передачи без модели

`deliverAssignmentContext` повторно открывает указанный контекст. Оркестратор задаёт
выбранного исполнителя и новую попытку. Сервис проверяет V1-подтверждение по
метаданным назначения и наблюдениям адаптера. При допуске транспорт принимает
`initialInput` с проверкой той же привязки непосредственно при передаче. Запросы чтения проходят через `callTool`
из этой привязки. По успешным ответам сервис возвращает путь, SHA-256 и
фактический диапазон строк. Событие с чужим `threadId` или `turnId` даёт
`blocked`. Финальное сообщение своего хода получает статус `received`;
решение о приёмке остаётся за оркестратором после независимого ревью.

Транспорт в тестах работает в памяти. Он записывает первый запрос, запрашивает
чтения и передаёт заранее заданные события. Проверка из корня проекта:

```bash
node --import=tsx/esm --test .ai/tools/worker-assignment/test/deliverAssignmentContext.test.ts
```

## Проверка реального транспорта до передачи назначения

```bash
npm run --silent ai:assignment -- preflight --context <contextId>
```

Команда повторно открывает указанную привязку и создаёт пустую временную
сессию в локальном Codex App Server с изолированным профилем и каталогом.
Временный MCP-сервер читает через обработчик этого же контекста. Команда
сверяет полный ответ `mcpServerStatus/list` для сессии, включая точные пути
в схеме единственного `repo_read_file`. Через `mcpServer/tool/call` она
запрашивает первую строку каждого разрешённого файла, проверяет путь и SHA-256,
а также отказ для другого пути и незарегистрированного инструмента записи.
Вывод содержит только результаты проверки и пути. Процессы и временный профиль
закрываются при завершении.

В отчёте `preflight` поле `cliVersion` содержит версию, которую сообщила открытая
сессия, в том числе при отказе во время проверки каталога. Если версия недоступна,
значение равно `null`. Решение о передаче `initialInput` зависит от фактически
подтверждённых прав этой сессии. Для аудита формы разрешён один прямой
`repo_read_file` на 18 закреплённых путей. Запись, вложенные и отложенные маршруты
выходят за пределы назначения.

Каталог `mcpServerStatus/list` охватывает MCP. После успешных проб текущий
`preflight` возвращает `mcp.status: verified`, `blocked`, причину
`native_tools_unverified` и код выхода 2. Расхождение каталога даёт
`transport_access_mismatch`. Команда завершается до `turn/start`.
При открытии другой сессии проверка выполняется заново.

## Проверка допуска V1 без исполнителя

Для аудита формы общий валидатор принимает подтверждение адаптера, проверенный отчёт `bind`, выбор оркестратора и доступ к наблюдениям текущей попытки. В отчёте Codex поле `evidence` появляется после успешной привязки локального контекста. Для API `inspectApiAuditAdmission` работает с уже подготовленным запросом и зарегистрированной политикой инструментов провайдера. Проверка выполняется внутри Realize. [Формат и значения статусов](../../../documentation/architecture/assignment-adapter/article-audit-evidence.md)

Чтобы воспроизвести `ready` и `blocked` в памяти, выполни из корня проекта

```bash
node --import=tsx/esm --test --test-isolation=none .ai/tools/worker-assignment/test/{assessAdapterAdmission,apiAuditAdmission,preflightAssignment,deliverAssignmentContext}.test.ts
```

Проверки используют реальный ограниченный обработчик файлов для запроса API и тестовый транспорт для Codex. Они покрывают неполный каталог MCP, лишние маршруты, подмену назначения и потерю привязки, включая промежуток между допуском и передачей.

## Рабочий адаптер OpenAI Chat Completions

Команда принимает `contextId` успешного `bind` и выбранную модель. Она использует тот же код подготовки HTTP-запроса, что и отправка. Для воспроизведения обоих решений на одном контексте выполни

```bash
npm run --silent ai:assignment -- preflight-api --context <contextId> --model gpt-5.4-mini-2026-03-17
npm run --silent ai:assignment -- preflight-api --context <contextId> --model gpt-5.4-mini
```

При полном пакете первая команда возвращает `ready` и ревизию применённой политики в `providerPolicy`. Вторая возвращает `blocked / access_unverified` и `providerPolicy: null`. Ключ и связь с моделью для этих команд не нужны. [Источник политики и граница допуска](../../../documentation/architecture/assignment-adapter/openai-chat-completions.md)

## Одно чтение на имитаторе

Проверка использует привязку аудита «Создать статью» на временной копии файлов. Имитатор принимает два допущенных запроса одной попытки и возвращает заданные сообщения в памяти. Для разрешённого чтения тест сверяет полученные байты с файлом, для соседнего пути — с кодом `FORBIDDEN`. Изменение файла после чтения и подмена `tool_call_id` останавливают отправку второго запроса. [Контракт обмена](../../../documentation/architecture/assignment-adapter/single-read.md)

```bash
node --import=tsx/esm --test --test-isolation=none .ai/tools/worker-assignment/test/singleReadExchange.test.ts
```

## Контрольные точки на PostgreSQL

Для проверки двух последовательных чтений и восстановления после остановки процесса выполни из корня проекта

```bash
npm run ai:assignment:checkpoint-pilot
```

Потребуются непривилегированный пользователь, доступ на запись в `/tmp`, `pg_config` в `PATH` и серверные программы PostgreSQL в каталоге `pg_config --bindir` (`initdb`, `pg_ctl`, `createdb`). Команда создаёт временный кластер в закрытом каталоге, запускает его на отдельном Unix-сокете с отключённым TCP, включает `fsync` и `synchronous_commit`, создаёт БД `realize_checkpoint_pilot`. Участники работают с временной копией закреплённых файлов. Все ответы даёт имитатор, внешний вызов модели заблокирован. По завершении команда останавливает кластер и удаляет его временный каталог. [Среда запуска](test/checkpoints/runIsolatedPostgres.mjs)

Успешный прогон завершается с кодом 0 и показывает пять пройденных сценариев. Сверяются журнал отправок, неизменяемые ревизии, квитанции, содержимое пакета для ревью, остановка через `SIGKILL` и выдача lease двум конкурирующим процессам. [Состав хранилища и результаты](../../../documentation/specifications/task-management/execution/article-audit-storage-pilot.md)

## Публикация в досье и выдача ревью

Для сквозной проверки от полученного отчёта до выдачи работы независимому ревьюеру выполни из корня проекта

```bash
npm run ai:assignment:publication-pilot
```

Команда использует тот же временный кластер PostgreSQL и разворачивает в нём схему Foundation и закрытые хранилища пилота. Сценарий создаёт задачу с двумя назначениями и подтверждает чтения имитатором. После аварийного завершения процесса получатель забирает работу из очереди, читает отчёт и карту из досье и сверяет хеши обеих версий. Вызов модели заблокирован, рабочая админка в прогоне не участвует. [Среда запуска](#контрольные-точки-на-postgresql) · [Контракт и результаты](../../../documentation/specifications/task-management/execution/article-audit-publication.md)

## Устройство и проверка

В `src/` находятся обработчик команды, чтение определения, проверка области,
сборка пакета, оценка готовности и типы результата. Опубликованный путь
`article-audit.lock.json` используется CLI для примера формы. Сервис получает
путь к привязке от вызывающего кода. Тесты из `test/` используют отдельные
временные каталоги.

```bash
npm run typecheck:worker-assignment
node --import=tsx/esm --test --test-isolation=none .ai/tools/worker-assignment/test/*.test.ts
```

Штатная команда `npm run typecheck` включает проверку этого инструмента.

## Заключение ревьюера и приёмка

Команда `npm run ai:assignment:conclusion-pilot` поднимает временную PostgreSQL для проверки независимых чтений, публикации заключения в досье, передачи оркестратору, приёмки и адресной доработки. Имитатор проходит от реальных версий исходников до сохранённого решения. [Контракт](../../../documentation/specifications/task-management/execution/article-audit-conclusion.md)

## Доработка и повторная приёмка

`npm run ai:assignment:rework-pilot` поднимает временную PostgreSQL, создаёт адресованные поручения, проводит следующий аудит или уточнение, доставляет его на повторное ревью и проверяет окончательное решение. Команда печатает версии отчёта и заключения. Проверку исходной публикации и первого решения можно воспроизвести отдельно командами `npm run ai:assignment:publication-pilot` и `npm run ai:assignment:conclusion-pilot`. [Контракт цикла](../../../documentation/specifications/task-management/execution/article-audit-rework.md)

Для полного прогона всех четырёх этапов выполните `npm run ai:assignment:audit-cycle`. Он последовательно проверяет контрольные точки, публикацию отчёта, первое заключение и цикл доработки на отдельных временных кластерах.

Для ручной проверки результата в браузере предусмотрено [досье на постоянной тестовой PostgreSQL](../../../documentation/specifications/task-management/execution/article-audit-dossier-preview.md).
