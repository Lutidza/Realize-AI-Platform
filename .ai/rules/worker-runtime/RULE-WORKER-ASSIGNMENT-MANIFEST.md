## Назначение и полномочия

При делегировании оркестратор указывает цель, роль исполнителя и причину её
выбора, владельца затронутой области, обязательные источники, ожидаемый
результат и его получателя. Он определяет границы работы, разрешённые операции,
критерии проверки и условия, при которых исполнитель должен сообщить о препятствии.

Для работы с репозиторием оркестратор указывает область чтения. Если поручена
правка, он указывает пути и разрешённые операции создания, изменения и удаления.
При параллельной записи оркестратор распределяет файлы между исполнителями
или согласует порядок правок. Права ограничены поручением пользователя
и возможностями выбранной среды.

Для нативного делегирования достаточно сообщения с этими сведениями. Формат
манифеста и способ передачи задаёт выбранный инструмент. Для внешнего процесса
сохрани его handle и проверь завершение по [workflow сессии](../../workflows/core/worker-session/WORKFLOW.md).
Для Git-доставки действует [контракт Git-воркера](../git/RULE-GIT-DELIVERY.md#исполнитель-и-разрешение).

## Готовность к запуску

До выдачи оркестратор проверяет, что у исполнителя есть нужные источники
и что поручение выполнимо в пределах разрешённых операций. Если поручена
только подготовка, оркестратор возвращает подготовленное назначение для просмотра.

### Допуск через адаптер Realize

При передаче через адаптер Realize оркестратор проверяет полноту пакета и
фактические права одной попытки по [контракту допуска](../../../documentation/architecture/assignment-adapter/contract.md).

1. Для выбранной ревизии назначения сверяет пути, SHA-256 и требуемый объём
   текстов в подготовленном контексте. Ранее доставленный тому же исполнителю
   текст можно зачесть при совпадении версии и покрытия.
2. Сверяет выбранного исполнителя, все доступные способы вызова инструментов,
   пути и операции. Адаптер технически ограничивает доступ областью назначения.
   При передаче проверяется привязка к той же сессии или подготовленному запросу.

Оркестратор выставляет `ready`, когда оба условия выполнены и привязка
действительна. Иначе он указывает `blocked` и конкретную причину. После её
устранения повторяет проверку. Факт передачи исполнителю фиксируется при запуске.

Для локальной IDE-очереди профиль `scoped-write` получает отдельное разрешение
владельца на точные файлы. Приёмка сверяет фактическую область и полный diff
по [контракту Code Lane для IDE](../../tools/worker-assignment/README.md#назначение-правки).

### Привязка в CLI Assignment

При выборе CLI Assignment оркестратор заполняет [манифест режима `static-read-only`](../../templates/worker-assignment/TEMPLATE-WORKER-ASSIGNMENT-MANIFEST.md)
и передаёт `--lock`. Привязка закрепляет идентификатор и ревизию назначения,
исходный коммит, SHA-256 текста YAML и SHA-256 каждого выбранного файла
с учётом незакоммиченных изменений. Для манифеста в Markdown хешируется
содержимое YAML-блока.

`prepare` сверяет пакет. До привязки даже полный пакет получает `blocked`.
`bind` сохраняет поручение и тексты обязательных источников в локальном
контексте. При повторном открытии адаптер сверяет `contextId`, `assignmentId`,
`revision`, `lockSha256`, а также пути, SHA-256 и размеры текстов.
Обработчик разрешает только `repo_read_file` для закреплённых файлов,
проверяет SHA-256 при чтении и отклоняет запись. Несовпадение версий,
неполная доставка или расхождение прав дают `blocked`. Успешная привязка
подтверждает готовность локального контекста. Допуск конкретного исполнителя
проверяется перед передачей. [Команды и статусы CLI](../../tools/worker-assignment/README.md)

## Исполнение и приёмка

Исполнитель возвращает указанному получателю результат, выполненные проверки,
доказательства и ограничения. При правке перечисляет изменённые пути.
При работе только на чтение может предложить изменение. Если для продолжения
нужна запись, сообщает назначившему агенту путь и операцию. Правку можно
выполнить после получения назначения с соответствующими правами.

Оркестратор сверяет результат с областью поручения и критериями приёмки.
Проверки выбираются по задаче. [Правило передачи результата](RULE-WORKER-HANDOFF-CONTRACT.md)

### Статический аудит кода

Если поручен статический аудит кода, исполнитель указывает для каждого
замечания применимое правило, место в коде и наблюдаемое последствие.
Выявленное нарушение может быть результатом успешно выполненного аудита.
Если план предусматривает независимое ревью, аудитор передаёт отчёт и карту
покрытия, ревьюер проверяет выводы и передаёт заключение оркестратору для
приёмки. [Порядок независимого ревью](../../workflows/core/worker-assignment/WORKFLOW.md#независимое-ревью-статического-аудита)
