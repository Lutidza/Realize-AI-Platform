## Область применения

Создание и рефакторинг собственных исходников приложения, пакетов, сервисов
и инструментов. До реализации определи существующего владельца поведения,
границы модуля, контракт и зависимости. Выполняй законченную реализацию для
целевого окружения по общим правилам разработки.

## Ответственность файла

- Одна основная реализация компонента, класса, самостоятельной операции или
  хука — один файл. Компонент и функциональный модуль могут состоять из группы файлов.
- Локальные обработчики и закрытые вспомогательные функции одной операции
  допустимы рядом. Самостоятельный контракт, причина изменения или повторное
  использование требуют выделения владельца; одинаковую логику не копируй.
- Число строк, включая ориентир 300, — повод проверить связность, а не лимит
  и не основание для отдельного согласования. Не дроби связный код и не
  сжимай содержание ради размера; это относится также к тестам и документации.

| Роль                            | Ответственность                                                                                                       |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Контроллер, обработчик маршрута | Чтение запроса, вызов прикладной операции, формирование ответа; без бизнес-решений и SQL                              |
| Сервис, прикладная операция     | Одно бизнес-действие и его координация через контракты зависимостей; без представления и деталей транспорта/хранилища |
| Репозиторий                     | Запросы, запись и транзакции хранилища; без управления интерфейсом и прикладным сценарием                             |
| Адаптер                         | Работа с внешним протоколом, SDK или инфраструктурой за контрактом модуля                                             |
| Валидатор                       | Проверка входа и инвариантов; без управления прикладным сценарием                                                     |
| Маппер                          | Явное преобразование данных; без запросов и записи                                                                    |
| Утилита                         | Чистая вспомогательная операция без запросов, состояния, секретов и побочных эффектов                                 |
| Конфигурация                    | Описание и сборка настроек; без реализации прикладного поведения                                                      |

Роль выбирается по содержимому. Перенос смешанной логики из контроллера целиком
в сервис не устраняет нарушение. Не создавай ненужные слои и сборники несвязанных
`helpers`, `utils` или `common`.

## Компоненты и хуки

- Представление содержит JSX, отображение props, условия отображения и вызов
  переданных обработчиков. Запросы, бизнес-решения, состояние и эффекты
  размещаются в соответствующих сервисах, операциях и хуках.
- Основной компонент связывает поведение с представлением. При отсутствии
  отдельного поведения достаточно файла компонента; дополнительный контейнер
  создаётся только для самостоятельной ответственности.
- Один React- или Payload-хук — один файл без JSX. React-хуки объявляются
  на уровне модуля; динамические фабрики React-хуков не создаются.
  Для конфигурируемого Payload-хука допустима фабрика одного хука.
- `primitives` содержит базовые элементы без бизнес-правил конкретной
  функциональности; `components` — составные элементы интерфейса.

## Типы

Используй подходящие сгенерированные типы Payload, типы его API и вывод типов
TypeScript. Не создавай ручные копии документов Payload или лишние объявления
ради повторения уже известного типа.

Собственные типы, интерфейсы и контракты props/аргументов/результатов размещай
в `.types.ts` у владельца. Связанные типы одного контракта могут находиться
вместе; общий склад типов проекта не создаётся. Файл типов не содержит
исполняемой логики: значения `as const` и runtime enum относятся к
`.constants.ts`, классы ошибок — к `.error.ts`. `.model` обозначает поведение,
а не копию документа Payload.

За публичной границей формируй явный DTO по
[правилу DTO](backend/RULE-DTO-CONTRACTS-NO-RAW-PAYLOAD.md).
Переиспользование типов внутри владельца не разрешает выдачу исходных
документов Payload и закрытых полей потребителю.

## Каталоги

Группируй код сначала по функциональности, затем по нужным ролям; `client` и
`server` выделяй по границе исполнения. Каждый уровень обозначает владельца
или границу. Не создавай пустой каркас и повторения вроде `components/components`.
Маленький компонент хранит свои файлы рядом; отдельные `hooks` и `types`
внутри каждого компонента не обязательны.

Пример размещения при наличии соответствующих обязанностей:

```text
connection-form/
├── ConnectionForm.component.tsx
├── ConnectionForm.view.tsx
├── ConnectionForm.types.ts
├── useConnectionForm.hook.ts
└── formatConnectionStatus.util.ts
```

Общее поведение частей одной функциональности остаётся у неё. Для независимых
функциональностей используй существующий общий модуль или пакет с явным
контрактом; новый `shared` не создаётся только ради переноса файла.
Имена и публичные точки входа задаёт [правило именования](RULE-CODE-NAMING.md).

## Переносимость и импорты

Переносимый модуль получает настройки и зависимости через явные контракты
и подключается к другому проекту Payload без импорта внутренностей host-проекта.
Между пакетами используй публичные exports; внутри пакета — локальные пути
или его настроенные внутренние импорты, поддерживаемые сборкой и исполнением.

`@/` допустим внутри приложения, где он настроен. Переносимый пакет не зависит
от alias `@/` и внутренних путей `src/**` приложения; `../` и `../../`
допустимы внутри границ пакета.
Не добавляй alias, loader или framework только ради замены рабочего локального
импорта. Клиентский код не зависит от серверной реализации и секретов.

## Рефакторинг и проверка

В согласованном модуле устраняй обнаруженное смешение обязанностей, дублирование,
неправильное размещение, [именование](RULE-CODE-NAMING.md) и
[комментарии](RULE-CODE-COMMENT-DISCIPLINE.md) в той же задаче. Проверяй модуль
целиком, а не только изменённые строки. Прямых потребителей обновляй настолько,
насколько требуется для корректности изменения; независимый долг фиксируй отдельно.

Границы разрешённого исправления и работа со старыми путями задаются
[правилом очистки](../scope-control/RULE-STALE-ARTIFACT-CLEANUP-AFTER-REFACTOR.md).
Явные ограничения пользователя сохраняются. Остаток, который они не позволяют
исправить, указывается в результате и не выдаётся за полное соответствие.

Сохраняй внешнее поведение и публичные контракты, если их изменение не входит
в задачу. Проверяй фактические зависимости, данные и поведение затронутых
частей; отдельный отчёт на каждый файл и автоматический полный набор тестов
ради декомпозиции не требуются.
