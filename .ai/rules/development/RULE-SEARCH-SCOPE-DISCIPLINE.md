## Область и способ работы

Перед поиском файлов, владельца, повторно используемого решения или evidence
определи цель, ожидаемый тип источника, явные пути и способ ограничения выдачи.
Предпочитай `rg` и `rg --files`. CLI `agent-search` применяет готовые профили;
его использование не обязательно, если прямой поиск сохраняет те же границы.

Основной агент и worker могут искать напрямую. Отдельный search-worker нужен
только для полезной независимой подзадачи по правилу координации. Direct/native
поиск не требует SQLite session, monitor, bootstrap или peer edges. При
делегировании передай адресату краткие findings с путями и строками через
реальные средства выбранной среды; managed metadata применяется только в
явно выбранном managed external режиме.

## Качество и стоимость поиска

- Выполняй поиск детерминированно через `rg`/CLI, без LLM-вызова для каждого
  запроса. Отдельная модель полезна только для самостоятельной задачи анализа
  найденного материала; её выбор регулируется правилом координации и выбором
  модели worker-а. Не создавай постоянный индекс или фонового агента ради
  обычного поиска по рабочему дереву.
- Выбирай минимально достаточную выдачу: имена файлов (`paths`), файлы с
  совпадениями (`files`) либо короткие фрагменты с координатами (`matches`).
  Если нужный файл уже известен, переходи к нему сразу. Не повторяй полный
  поиск ради получения другой формы уже найденных данных.
- Для идентификаторов и точного текста предпочитай литеральный поиск;
  regexp включай явно. После широкого результата сужай область и запрос,
  прежде чем увеличивать бюджет.
- Для определения известного TS/JS имени используй CLI `--intent=definitions`
  или MCP `repo_search intent=definitions` в ожидаемом owner. Для usages —
  `references`, для module/binding/alias — `imports`; `imports '*'` перечисляет
  зависимости известного файла. Не выполняй все операции автоматически.
  `text` остаётся маршрутом для comments/config/других языков и вычисляемых связей.
- Для перехода от import известного TS/JS файла к исходному объявлению используй
  CLI `--intent=imports --resolve-imports --from=<file>` либо MCP
  `intent=imports, resolveImports=true, path=<file>`. Передавай конкретный binding;
  точное имя приоритетнее substring другого module specifier в этом файле.
  Разрешённая область должна включать targets; metadata не расширяет доступ.
  Target/chain имеют точность static_imports, не полноценное symbol binding.
  Не запускай разрешение для обычного поиска текста или уже известного файла.
- Проверяй resolution reason и coverage: цикл, неоднозначность, закрытый путь
  и неподдерживаемая конфигурация не означают отсутствия объявления. При бюджете
  уточняй binding/owner или читай известный target; не повторяй широкий `*`.
  MCP cursor продолжает страницу проверенного snapshot и повторно проверяет
  содержимое; он не возобновляет оборванный scan. CLI continuation отсутствует.
- `references` — синтаксические употребления, не доказанное связывание символов.
  Проверяй локальные aliases/imports и контекст объявления перед изменениями;
  одноимённые identifiers из разных scopes могут попадать вместе. Module specifier
  не даёт разрешения читать файл вне исходной политики.
- Проверяй navigation coverage: unsupported требует подходящего text поиска;
  skipped/syntax-errors означают неполное покрытие даже без pagination truncation.
  Prefiltered — прочитанные файлы без возможного совпадения, не разобранный AST.
  Для известного проблемного файла используй text/read; не повторяй тот же scan.
- Для сужения готового профиля используй `--within`: он сохраняет исключения
  и выбирает только разрешённые файлы/каталоги. `--path` по-прежнему расширяет
  область и требует причины.
- Ограничивай количество результатов, UTF-8 байты выдачи и время процесса.
  CLI прекращает чтение и завершает `rg` при превышении бюджета; усечение
  памяти или вывода после полного накопления результатов недостаточно.
- Явно различай полный результат, неполную выдачу по лимиту, отсутствие
  совпадений и ошибку. Ограниченный результат не доказывает отсутствие других
  совпадений. Байтовый бюджет ограничивает контекст, но не является точным
  счётчиком токенов модели.

## Ограничения

- Обычный поиск исключает зависимости, `.next`, `dist`, `build`, `coverage`,
  бинарные файлы, изображения, архивы, SQLite/JSONL и generated
  `.ai/tools/agent-runtime/runtime/**`. Не читай секреты и production dumps.
- Обычные кодовые профили исключают `src/RealizeCore/**`,
  `src/app/_realize/**`, `src/app/(reference)/**`; обычные документы —
  `documentation/reports/**` и `documentation/temp/**`. Историю и референсы
  выбирай адресно по текущей задаче через `reference`/`special` с причиной.
- Lock-файлы нужны только для dependency/package audit, установки или
  обновления. Нужный lock-файл выбирай явным путём с причиной.
- `--path` расширяет поиск только существующим путём внутри репозитория.
  Абсолютные пути, `..` и symlink, разрешающийся вне корня, запрещены.
  Расширение профиля через `--path` требует причины. CLI является trusted
  developer tool, а не границей доступа MCP к произвольно меняемому filesystem.
- `--within` принимает существующий файл/каталог внутри уже выбранных корней
  профиля и разрешённых `--path`. Повторные значения объединяются; каждый путь
  после разрешения symlink обязан оставаться в выбранной области. Общий предок,
  соседняя область, исключённый или отсутствующий путь отклоняются. Новая
  причина для самого сужения не нужна; обязательные причины профиля и точное
  разрешение на lock-файл сохраняются.
- Сужение сохраняет ignore-контекст исходных корней. `--within` и glob не
  возвращают игнорируемые кандидаты. Фильтры путей/расширений/glob применяются
  до чтения содержимого; перечисление и поиск разделяют общий бюджет и отмену.
- Glob поиска и проверки исключений должны учитывать скрытые каталоги:
  `**/*.md` находит разрешённые `.ai/**/*.md` и `.codex/**/*.md`, а вложенный
  скрытый каталог не позволяет обойти исключение.
- Пользовательский glob имеет одинаковую семантику в `paths`, `files` и
  `matches`, в том числе вместе с `--ext`; её описывает README CLI. Ограничения
  результата и времени действуют на весь запрос, а не на отдельный пакет файлов.
- Для `reference`/`special` нужны конкретные `--path`, а не весь корень.
  Не включай целиком `.ai-workspace/tasks` ради одного task artifact.
- Отсутствующий путь встроенного профиля допускается пропустить с явным
  предупреждением; отсутствие всех его путей является ошибкой. Неверный
  явно переданный `--path`/`--within` не пропускается молча. Вложенные и повторные области
  не должны дублировать выдачу.
- Ограничь вывод и уточняй широкий запрос. Совпадение не даёт разрешения
  менять найденный файл, расширять задачу или считать отчёт source of truth.

## Диагностика поиска

- Контракт, владельцы и покрытие метрик описаны в
  [архитектуре поиска](../../../documentation/architecture/repository-search.md).
  Диагностика CLI и managed MCP собирается автоматически, без LLM или sub-agent.
  Для измеряемого поиска предпочитай agent-search с теми же профилями и бюджетами;
  прямой rg остаётся допустимым, но в эту историю не попадает.
- Не сохраняй query, path, glob, snippet, cursor, credentials и произвольные
  ошибки в telemetry. Неизмеренные bytes/tokens обозначай `null`, не оценивай
  затраты модели по размеру ответа.
- CLI автоматически пишет bounded буфер в собственном ignored `runtime/`.
  Control plane доставляет его в общее хранилище без участия модели и пользователя.
  `--metrics-file` в `logs` задачи — дополнительный экспорт для отладки; новый
  файл не заменяется. Поиск не зависит от успеха записи или доступности БД/сети.
- Managed MCP пишет через bounded очередь; отсутствие события не доказывает
  отсутствие вызова. Автоматическая доставка CLI сохраняет отдельное происхождение
  локально предоставленных замеров, не подтверждённого сервером runtime evidence.
- Для изменений измерений проверяй ограничения хранения/доступа и отсутствие
  дополнительных проходов поиска. Unicode-проверки включают приоритетные EN/RU,
  грузинский, арабский, CJK, emoji, combining marks, регистр, BOM и CRLF.
- Настройки диагностики принадлежат существующему feature: bounded policy,
  revision/CAS и подтверждённое применение. Очистку проверяй с preview,
  idempotency и защитой от возвращения старых событий. Ручное удаление рабочих
  замеров не является проверкой: используй изолированную БД. Heartbeat и
  автообслуживание действуют без новых поисков; отказ сборщика не меняет поиск.

## Приёмка изменений инструмента

При изменении поискового движка, CLI/MCP контракта, доставки или управления
диагностикой выполни `npm run check:search` по
[описанию приёмки](../../../documentation/architecture/repository-search.md#полная-приёмка).
Full command сначала сверяет текущую установленную сборку и подтверждение
реальных consumers, включая внешний ChatGPT. Missing evidence — incomplete,
не passed. `check:search:isolated` предназначен для fixtures/CI и возвращает
только isolated_passed. Затем команда проверяет адаптеры, PostgreSQL и Admin UI; пустой набор,
skip/todo, ошибка и повторно успешный browser test не означают приёмку.
Если prerequisite недоступен, явно сообщи непроверенный контур; не выдавай
частичный прогон за готовность к поставке. Обычный поиск по проекту и правка
только документации не требуют полного запуска.

Используй созданные runner-ом fixture databases, процессы и материалы задачи.
Full preflight использует только read-only события рабочей БД; fixture процессы
не наследуют её credentials. Не отключай guards и не очищай историю
пользователя ради проверки. Корпуса запускай без параллельной тяжёлой нагрузки;
сравнивай первый и повторные прогоны раздельно, проверяй budgets чтения/ответа
и независимые цели. Не выводи стоимость модели из длительности или bytes.

Если источник отсутствует или нужный доступ выходит за разрешённый scope,
назови конкретное ограничение и продолжай независимую работу. Повторный
approval для уже разрешённого поиска не требуется.
