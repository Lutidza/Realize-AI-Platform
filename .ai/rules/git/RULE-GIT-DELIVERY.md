## Исполнитель и разрешение

Все команды Git рабочего слоя выполняет программный обработчик через
разрешённый адаптер. Development `inspect` использует отдельный программный
адаптер без модели; `commit`, `push`, `manage` (включая чтение), `fetch`, `pull`
и `merge` — отдельного Git-воркера. Основной агент передаёт typed-команду и
оценивает подтверждённый результат; самостоятельно Git не запускает.
IDE-обработчик, продуктовые execution/preview/SourcePromotion и серверные
repository reads используют общий `@realize/git-runtime` по
[ADR-0016](../../../documentation/architecture/decisions/ADR-0016-development-git-delivery-handler.md).
ReleaseCandidate, приёмка и развёртывание сохраняют собственные полномочия.

### Общий программный контракт

- Запуск Git, лимиты, фильтрация окружения и lock lease принадлежат
  `packages/git-runtime`; адаптеры не создают параллельные shell/process owners.
- Изменяющие фазы удерживают общую блокировку канонического `git-common-dir`.
  Lease выдаёт и проверяет программный owner; модель не получает её и не
  назначает root, argv, профиль исполнения или credentials. Build, review и
  копирование БД выполняются вне Git-блокировки.
- Разрешения проверяет вход: IDE — область пользователя и checks; платформа —
  CR/job, approval и evidence; GPT/MCP — principal, grants и allowlist tools.
  Общий исполнитель не переносит полномочия между этими входами.
- Commit/push разработчика сохраняют настроенные hooks и подпись. Служебный
  commit preview использует контролируемый service profile по продуктовому
  контракту; это не разрешает отключить hooks в IDE.
- Проверки изменений и установленная приёмка относятся к своим source/build
  bindings. Новый код общего executor сам по себе не активирует runtime и не
  подтверждает прежние installed receipts на новой версии.

### Вызов development Git-адаптера

Вход `git:worker -- inspect` сохраняет имя CLI и выполняет
`validateGitWorkerContext` → `deliverGitWorkerCommand` → `runDelivery` →
`@realize/git-runtime` без Codex App Server,
модели, prompt/profile и `REALIZE_GIT_CODEX_HOME`. Программный адаптер проверяет
typed-команду, корень установленного инструмента, разрешённое действие, scope
и `verification.inputPaths`; ограниченная сводка и fingerprint сохраняют прежний
контракт evidence. Разрешены только локальные чтения: без staging, изменения
индекса, hooks, БД, сети и журнала доставки. Прямой Git и произвольный вызов
shared executor основным агентом не разрешены.

Для остальных действий воркер не наследует историю диалога. Модель выбирается по настройке и указанию
пользователя; текущий выбор — `gpt-5.6-luna` с уровнем рассуждения `low`.
Недоступность модели, обработчика или
доверенного контекста блокирует вызов; замена моделью основного агента или
ручными Git-командами не допускается. Идентификаторы моделей не угадываются.

`inspect` и читающие операции `manage` требуют разрешённого анализа репозитория.
Изменяющие операции `manage`, `fetch`, `pull`, commit, push, merge и их область
должны быть разрешены пользователем; завершение правки этого разрешения не
даёт. Повторное согласование уже разрешённого действия не требуется.
Полный состав включается только при явно разрешённом полном снимке изменений.
Это относится к включению всего накопленного состава, в том числе правок
других задач. Ответ пользователя «включить всё» на описанный состав является
достаточным разрешением; повторный вопрос не нужен. Позднее возникшие изменения
и новые действия не добавляются к этому снимку автоматически.

Для явно разрешённого полного add/commit вызывающая среда может назначить
`scope: { mode: "all", includePartialIndex: true }`: текущая рабочая версия
всех разрешённых файлов заменяет их частично подготовленные версии в индексе.
Снимок до/после проверок должен включать индекс и рабочие данные. Без этого
явного поля частичный индекс блокирует обычный commit; для `mode: "paths"`
поле недопустимо. Модель не назначает его; новые правки требуют отдельного снимка.

Для подключённых ограниченных модельных воркеров модель получает только инструкцию
[commit](../../../.codex/prompts/workflows/delivery/git/commit.md),
[push](../../../.codex/prompts/workflows/delivery/git/push.md),
[manage](../../../.codex/prompts/workflows/delivery/git/manage.md),
[fetch](../../../.codex/prompts/workflows/delivery/git/fetch.md),
[pull](../../../.codex/prompts/workflows/delivery/git/pull.md) или
[merge](../../../.codex/prompts/workflows/delivery/git/merge.md) и команду.
Полные AGENTS, правила, workflow и навыки ей не передаются.
Основной агент применяет Git-маршрут до запуска; механизм запуска и обработчик
обеспечивают фиксированную рабочую копию, инструменты разрешённого действия
и подтверждённый результат. При доработке этого маршрута синхронизируй инструкцию
и программные ограничения. Исключение не распространяется на разработку или расширение полномочий.

Для записи вызывающая среда связывает контекст с явным запросом пользователя:
область, назначение, результаты проверок и авторство для commit передаются
отдельно от Git-воркера.
Файл контекста — средство передачи, а не доказательство согласия пользователя.
Неполный контекст блокирует запуск; модель не дополняет и не расширяет его.

Не создавай управляемое досье только ради Git-операции. Выбор короткого
операционного контекста или существующей задачи определяется
[правилом материалов](../scope-control/RULE-TASK-WORKSPACE-ARTIFACTS.md#выбор-рабочего-контекста).
Это сохраняет разрешённый адаптер, обязательные проверки и журнал восстановления;
`taskId` и каталог служебных файлов сами по себе не требуют TASK/манифеста.

## Подключение и границы

### Серверный порт чтения MCP

По [ADR-0017](../../../documentation/architecture/decisions/ADR-0017-internal-mcp-and-server-management.md)
платформа и GPT/MCP используют deterministic machine read ports существующего
`.ai/tools/git-delivery/src/read` через общий executor:
серверный MCP вызывает только HEAD/status/diff и проверку Git metadata
для диагностики без LLM на каждый RPC. Внутренний helper HEAD/branch не создаёт
дополнительных прав и не проверяет content snapshot или чистоту рабочей копии.
Доверенная composition задаёт repository root, principal, scope, deadline и лимиты;
политика путей применяется до чтения содержимого. Порт не выполняет запись,
staging, сетевые операции и произвольные команды. Обычные Git-операции
development-агента используют собственный адаптер: программный `inspect`
или модельного воркера остальных действий. Использовать MCP machine port
для обхода этого маршрута запрещено.

### Маршрут доставки

- Удалённый репозиторий и выбранный HTTPS/SSH берутся из БД интеграций через
  общего серверного владельца. Локальная рабочая копия — из среды запуска.
  Секреты получает только программный исполнитель, без передачи модели,
  записи в URL, исходники, диагностику или отчёт.
- HTTPS использует токен, SSH — настроенный ключ или `ssh-agent`. Подлинность
  сервера проверяется; интерактивная авторизация и автоматическая смена
  транспорта, назначения или учётных данных запрещены.
- Для `inspect` и commit с явным автором БД не нужна. Если автор не передан,
  загрузчик читает его из включённой интеграции до запуска модели, без получения
  токена. Внешняя сеть и проверка подключения для локального commit не нужны.
  Успешное чтение удалённого репозитория не доказывает право push или управления
  репозиторием через GitHub API. Права каждой внешней операции проверяются
  при её выполнении; роль Admin приложения не задаёт права GitHub. Отдельный
  полный сетевой preflight нужен при настройке или диагностике соединения.
- Сохраняй чужие изменения и индекс. Случайные материалы, секреты и результаты
  сборки не включаются. Push покрывает весь публикуемый набор коммитов и явную
  ветку; `defaultBranch` не даёт права переключать её или публиковать в неё.
- Этот маршрут не выполняет force push, stash/reset/rebase, PR, generic local
  merge, deploy или попутное исправление кода. Pull допускает только
  фиксированный fast-forward через `--ff-only --no-edit`. Остальные действия
  требуют отдельной задачи и соответствующей реализации.
- `merge` создаёт GitHub commit только из отдельно разрешённого и проверенного
  candidate tree с двумя закреплёнными parents. Контракт `approved-tree` не
  выбирает стратегию слияния и не разрешает конфликты; локальная актуализация
  выполняется отдельно через `pull`.
- Исправление прерванного commit допускается только через явно разрешённое
  восстановление прежнего requestId с актуальными проверками. Обработчик
  доказывает принадлежность индекса и сохраняет принятый снимок до staging;
  назначение, автора, сообщение и состав обязательных проверок не подменяют. Это не разрешает
  изменение содержимого после подготовки дерева или возможного запуска hooks.
- После неизвестного исхода push сначала сверяй назначение. Новая запись
  требует разрешённого восстановления прежней операции и следующего номера
  попытки в доверенном контексте. Его сохранение до push исключает повторную
  отправку тем же заданием. Журнал не сбрасывай, requestId и назначение не подменяй.

### Управление и синхронизация

`manage` выполняет ровно одну операцию из доверенного контекста: чтение remote,
worktrees, веток, log или адресного diff; смену URL remote, repair worktrees,
создание или переключение ветки. Модель получает только `git_manage({})`.
URL меняется со сверкой прежнего значения, в пределах GitHub-владельца и
выбранного транспорта. Создание и переключение ветки требуют чистой рабочей
копии; новая ветка создаётся от ожидаемого HEAD. Repair получает только точные
пути из явного списка, покрывающего весь затрагиваемый набор существующих
зарегистрированных внешних worktrees. Неполный список блокируется до repair; пользовательские данные
сохраняются, каталоги не переносятся.
GitHub rename, CAS интеграции и filesystem move принадлежат отдельным владельцам;
локальный `remote-set-url` их не выполняет.

`fetch` и `pull` получают подключение у того же серверного владельца, что push.
Контекст закрепляет текущие ветку/HEAD и удалённый commit. Fetch читает одну ветку
в служебную ссылку ветки без tags, prune и submodules. Pull после fetch допускает
только fast-forward к этому commit при чистом состоянии и полной истории.
Изменившиеся локальный источник, удалённая ветка или ревизия подключения
блокируют продолжение. Автоматического stash, rebase или разрешения конфликтов нет.

`merge` получает GitHub API credential у общего владельца интеграций. Контекст
закрепляет repository ID/slug/revision, target/source refs и OID, target tree,
candidate tree, точные `approvedChangedPaths` и descriptors `candidate.files`.
Канонический `candidateSourceRoot` ограничен task-каталогом
`<repositoryRoot>/.ai-workspace/tasks/<taskId>/tmp/**`. Полные recursive tree manifests
должны быть без truncation; за пределами разрешённых конечных путей сохраняются
type, mode и object SHA. Проверки вызывающей среды привязаны к fingerprint
refs/tree, candidateSourceRoot и файловых metadata; текст задания или наличие дерева не заменяют
проверку содержимого и сохранения принятой работы.

До любого POST обработчик читает только approved bytes с `O_NOFOLLOW`,
проверяет Git blob SHA, mode, пути и секреты. Полный target leaf set с accepted
overlays должен вычислять назначенный candidate tree OID. Immutable blob POST
и tree POST с `base_tree: target.treeOid` сверяются по assigned SHA, затем
полный manifest candidate повторно проверяется. Model не получает raw blobs.
Проверяющий исполнитель использует отдельный dependency/build cache вне
approved paths; проверка не расширяет публикуемый состав.

Journal до первого POST закрепляет два ordered parents, identity, message,
UTC date и expected commit. Pending object сохраняется до каждого upload;
unknown object сначала сверяется GET. Подтверждённый object не создаётся повторно,
его отсутствие блокирует запись; могут продолжаться только ещё не начатые uploads.
Перед обновлением target ref сверяются обе refs, PATCH использует `force: false`,
после него проверяется target ref. GitHub обеспечивает fast-forward guard;
endpoint не принимает expected old OID, поэтому это не unconditional CAS.
Merge не меняет локальные refs, рабочие файлы или индекс. Неопределённый исход
сначала сверяется; новый requestId не разрешает слепую запись.

Изменяющие операции используют общий Git lock и атомарный журнал до побочного
эффекта. Повтор сохраняет исходный контекст и сверяет фактическое состояние;
неизвестный исход или расхождение не разрешают новую запись. Параметры операций,
лимиты и реализованные границы описаны в README обработчика, критерии — в
[management check](../../checks/git/CHECK-GIT-MANAGEMENT-SCOPE.md) и
[sync check](../../checks/git/CHECK-GIT-SYNC-READINESS.md) и
[merge check](../../checks/git/CHECK-GIT-APPROVED-TREE-MERGE.md).

## Достаточность проверок

Используй фактические результаты для проверенного содержимого, конфигурации и
зависимостей. Изменение значимых входов отменяет их применимость. Состав файлов
сам по себе не доказывает выполнение тестов; отсутствие результата не означает
успех. При необходимости выбирай проверки по затронутому поведению:

- документы и инструкции — содержание, ссылки, формат и метаданные;
- код — относящиеся к изменению lint, типы и тесты;
- схема — профильные проверки миграций; интерфейс — нужное браузерное evidence.

Команды берутся из актуального проекта. Полный набор тестов и сборка не
запускаются автоматически ради Git. Обязательные hooks и CI сохраняются.
Для автоматического сохранения результатов используй явный план
[`git:verify`](../../tools/git-delivery/README.md#сохранение-и-повторное-использование-проверок).
IDE и platform execution/preview используют общий `@realize/verification-runtime`;
не создавай отдельный runner или формат доказательства для нового входа.
Git fingerprint/OID proofs и product approvals остаются у своих адаптеров.
Вызывающая среда выбирает checks и их inputs; широкий/полный запуск требует
конкретного `reason`, а известную широкую npm-команду нельзя объявить targeted.
Инструмент исполняет только выбранные проверки с missing, failed или stale
результатом либо с `reuse: "never"`. Успешный local receipt повторно используется при совпадении полного
ключа проверки, включая файловые входы, command/runtime, environment и сведения
об установленных зависимостях. Изменённый или неизвестный вход отменяет reuse.

Для внешнего состояния БД, browser или установленного runtime применяй
`reuse: "never"`; local filesystem receipt не доказывает его неизменность.
Секреты и значения environment не сохраняются в receipts. Нельзя создавать
`passed` из текста старого лога, подменять recipe либо переносить результат
текущего checkout на другой commit без точной сохранённой привязки.

`REALIZE_GIT_VERIFICATION_PLAN` явно включает подготовку evidence перед
`git:worker commit|push`. Authorization, scope, identity, target и requiredChecks
остаются в отдельном контексте; они проверяются до запуска команд или модели.
Снимки Git для привязки receipts проходят через программный адаптер `inspect`.
Проверки используют отдельную verification-блокировку, общий Git lock во время тестов не удерживается.
Low-level Git-обработчик сам не запускает тесты и проверяет материализованное
evidence под своей блокировкой. Для push автоматический маршрут использует
подтверждённые proofs точных OID; недостающий proof не заменяется тестированием
нынешнего checkout. Без плана сохраняется ручной контекст проверок.
Selected check с `reuse: "never"` допускает для commit только текущий запуск
и блокирует автоматический push; сохранённый proof не переносит внешнее состояние.
Порядок, восстановление после сбоя и отчёт задаёт связанный workflow;
проверки ниже — критерии конкретного действия, а не дополнительный аудит.
