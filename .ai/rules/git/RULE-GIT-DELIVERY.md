## Исполнитель и разрешение

Все команды Git рабочего слоя, включая чтение состояния, выполняет отдельный
Git-воркер через программный обработчик. Основной агент передаёт задание и
оценивает подтверждённый отчёт; самостоятельно Git не запускает. Продуктовые
SourcePromotion, ReleaseCandidate и их полномочия этим правилом не меняются.

Воркер не наследует историю диалога. Модель выбирается по настройке и указанию
пользователя; текущий выбор — Spark. Недоступность модели, обработчика или
доверенного контекста блокирует вызов; замена моделью основного агента или
ручными Git-командами не допускается. Идентификаторы моделей не угадываются.

`inspect` требует разрешённого анализа репозитория. Commit, push и их область
должны быть разрешены пользователем; завершение правки этого разрешения не
даёт. Повторное согласование уже разрешённого действия не требуется.
Полный состав включается только при явно разрешённом полном снимке изменений.

## Подключение и границы

- Удалённый репозиторий и выбранный HTTPS/SSH берутся из БД интеграций через
  общего серверного владельца. Локальная рабочая копия — из среды запуска.
  Секреты получает только программный исполнитель, без передачи модели,
  записи в URL, исходники, диагностику или отчёт.
- HTTPS использует токен, SSH — настроенный ключ или `ssh-agent`. Подлинность
  сервера проверяется; интерактивная авторизация и автоматическая смена
  транспорта, назначения или учётных данных запрещены.
- Для `inspect` и локального commit БД, сеть и проверка подключения не нужны.
  Успешное чтение удалённого репозитория не доказывает право push. Отдельный
  полный сетевой preflight нужен при настройке или диагностике соединения.
- Сохраняй чужие изменения и индекс. Случайные материалы, секреты и результаты
  сборки не включаются. Push покрывает весь публикуемый набор коммитов и явную
  ветку; `defaultBranch` не даёт права переключать её или публиковать в неё.
- Этот маршрут не выполняет force push, stash/reset/rebase, PR, merge, deploy
  или попутное исправление кода. Такие действия требуют отдельной задачи.

## Достаточность проверок

Используй фактические результаты для проверенного содержимого, конфигурации и
зависимостей. Изменение значимых входов отменяет их применимость. Состав файлов
сам по себе не доказывает выполнение тестов; отсутствие результата не означает
успех. При необходимости выбирай проверки по затронутому поведению:

- документы и инструкции — содержание, ссылки, формат и метаданные;
- код — относящиеся к изменению lint, типы и тесты;
- схема — профильные проверки миграций; интерфейс — нужное браузерное evidence.

Команды берутся из актуального проекта. Полный набор тестов и сборка не
запускаются автоматически ради Git. Обязательные hooks и CI сохраняются.
Порядок, восстановление после сбоя и отчёт задаёт связанный workflow;
проверки ниже — критерии конкретного действия, а не дополнительный аудит.
