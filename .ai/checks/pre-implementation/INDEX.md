# Проверки перед изменением

```yaml
artifact_id: ai-checks-pre-implementation
artifact_type: ai-checks-index
owner_layer: .ai/checks/pre-implementation/
```

Каталог хранит общие checks подготовки. Профильные проверки остаются у своих
владельцев, например в `checks/development/frontend` и `backend`.
Порядком задачи владеет [main-delivery](../../workflows/core/main-delivery/WORKFLOW.md).

1. Определи тип шага: `dialog_only`, `read_only` или `work_task`.
2. Для проектной работы выбери общие и профильные правила через
   [реестр](../../registry/rules/INDEX.md), учитывая фактические действия.
3. До правки установи источник, владельца, область и достаточные проверки.
4. Выполни только применимые checks. Их критерии не заменяют правило
   и не расширяют полномочия; структурное соответствие не доказывает семантику.
5. Продолжай после устранения препятствий для выбранного действия.
   Уже разрешённые действия повторно не согласуются.

Для оптимизации, performance-инцидента, бюджета или изменения критичного
горячего пути применяй [check области замера](CHECK-PERFORMANCE-MEASUREMENT-SCOPE.md)
по соответствующему правилу. Обычные изменения без ожидаемого влияния на
производительность не требуют benchmark.

Для диалога не нужен рабочий gate. Read-only анализ применяет правила чтения
и доступа, пропуская checks изменения, записи, generated outputs и delivery.
`not_required` означает неприменимость, а не пройденную проверку.

Отдельный отчёт на каждый check не нужен: подготовка входит в план/TASK,
результаты и существенные ограничения — в общий итог. Невыполненное обязательное
условие обозначай явно; оно останавливает зависимое действие, а не всю работу.
