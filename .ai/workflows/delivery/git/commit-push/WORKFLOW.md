## Маршрут

Серверный MCP status/diff использует отдельный ограниченный read port по
Git-правилу и ADR-0017. Этот workflow по-прежнему описывает development
Git-воркера; machine port не заменяет его inspect и не предоставляет delivery.

Прочитай [правило Git](../../../../rules/git/RULE-GIT-DELIVERY.md).
Используй `inspect`, `commit`, `push` или `commit_push`; подключай только
проверки выбранного действия. Передача задания и текущая доступность вызова —
в [навыке Codex](../../../../../.codex/skills/git-commit-push/SKILL.md).
Развёрнутый ADR нужен при доработке обработчика, а не для каждой операции.

## Порядок выполнения

1. Основной агент передаёт действие и необязательное сообщение коммита.
   Механизм запуска добавляет доверенные область, рабочую копию, разрешение и
   доступные результаты проверок. Он запускает воркера без истории диалога.
2. Воркер вызывает обработчик. Тот проверяет контекст, получает блокировку
   репозитория и читает состояние; для `inspect` возвращает сводку и завершает
   работу без staging, тестов и записи состояния доставки.
3. Для commit обработчик определяет состав и проверяет применимость переданных
   результатов проверок. Недостающие проверки выполняет проверяющий исполнитель
   и передаёт подтверждённые результаты через механизм запуска. До первой записи обработчик сохраняет исходное
   состояние. После staging выполняет pre-commit check и сохраняет подготовленное
   дерево; затем создаёт commit и записывает его хеш.
4. Для push обработчик получает подключение, проверяет публикуемые коммиты и
   назначение по pre-push check, сохраняет состояние перед отправкой и выполняет
   push. При `commit_push` проверка настроек подключения по возможности предшествует
   commit; `push` не создаёт commit и не повторяет тесты без нового основания.
5. Обработчик устанавливает результат, обновляет запись операции и освобождает
   блокировку. Воркер передаёт краткий отчёт основному агенту; тот проверяет
   соответствие заданию и сообщает результат пользователю.

## Сбой и результат

После сбоя сохраняй выполненную часть. Повтор с тем же идентификатором сверяет
запись и фактическое состояние, не создаёт второй commit и не захватывает новые
правки. Обрыв после отправки означает неопределённый результат до проверки
назначения. Неоднозначность, конфликт и ошибка авторизации блокируют автоматическую
повторную запись. После разбора и разрешённого восстановления вызывающая среда
задаёт следующую `recovery.attempt` в прежнем контексте; порядок и пределы —
в README обработчика. Номер сохраняется до push и используется один раз.

Отчёт содержит статус, commit, ветку, результат push, фактические проверки и
причину остановки. Успех требует подтверждения; созданный commit при неудачном
push — частичный результат. Сырые журналы и полный diff не передаются по умолчанию.

Native-воркер использует механизм завершения своей среды. Если уже назначенная
внешняя сессия требует запись результата или завершение процесса, выполни её
контракт. Дополнительные monitor, SQLite, assignment-файл и постоянный отчёт
специально ради Git не создаются.

Для разрешённого исправления до подготовки дерева commit вызывающая среда
обновляет результаты проверок и назначает recovery прежней операции по
[README обработчика](../../../../../.ai/tools/git-delivery/README.md#восстановление-локального-commit).
Обработчик проверяет старый индекс, сохраняет новое поколение до staging и
продолжает обычные проверки. Модель получает ту же команду commit без новых
инструментов и самостоятельного выбора попытки.

## Подключённый запуск

`inspect`, `commit` и `push` доступны через вход из Git-навыка: новая ephemeral-сессия
Codex App Server и настроенная модель. Механизм запуска
загружает только конфигурацию и краткую инструкцию из `.codex`, согласно
исключению Git-правила. Основной агент не составляет пересказ документов.
Рабочую копию определяет механизм запуска по размещению инструмента; команда
модели не принимает пути или полномочия. Контекст чтения существует в памяти.

Обычный `inspect` получает только чтение. Для адресного снимка перед проверками
вызывающая среда задаёт те же scope и inputPaths, что нужны будущему commit.
Одинаковые fingerprint до и после фактических проверок позволяют привязать
их результаты; старые результаты без такой привязки не объявляются подходящими.

Для `commit` среда передаёт отдельный контекст уже разрешённой записи. Явное
авторство сохраняется; при его отсутствии загрузчик получает имя/email из
настроенной интеграции. Это не добавляет разрешений или результатов проверок. До модели
проверяются рабочая копия, действие, авторство и полнота проверок; актуальность
снимка проверяет обработчик. С заданным сообщением доступен только `git_commit`;
без сообщения — сначала `git_inspect` в той же области, затем `git_commit`.
Воркер составляет сообщение по сводке путей и статусов, без выдуманных деталей.

Для `push` среда передаёт назначение, исходный и ожидаемый удалённый хеш,
точный набор отправляемых коммитов и применимые результаты проверок. Воркер
вызывает единственный `git_push` без аргументов. Обработчик читает подключение
из БД, сверяет его ревизию и фактическую удалённую ветку; `pre-push` guard
проверяет её версию непосредственно перед отправкой и вызывает настроенный hook.
Push не меняет индекс и не запускает тесты. Без назначенного восстановления
повтор неизвестного результата только устанавливает исход: подтверждённый хеш
означает успех, иначе запись блокируется. Разрешённая новая попытка сохраняет
исходное назначение, проверяет прежнюю удалённую версию и расходует номер до записи.

Отчёт возвращает эффективную команду. Для повтора сохраняй её сообщение,
контекст и requestId; другой текст не является повтором прежней операции.
При утрате сообщения или неоднозначном результате сначала разбери сохранённое
состояние. Не создавай новый requestId для обхода конфликта.

Управление сессией и её закрытие встроены в запуск; внешняя сессия `codex exec`
и её отдельная регистрация не требуются. Реализованная доступность остальных
действий указана в Git-навыке, а подробности — в README обработчика.
